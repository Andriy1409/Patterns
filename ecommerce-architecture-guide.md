## Навіщо взагалі патерни у великому магазині

Маленький магазин на 50 товарів можна написати "в лоб" — прямими if-else, без жодного патерну, і це буде нормально. Патерни починають окупатись саме на **масштабі**: коли одночасно потрібно —

- додавати нові типи товарів/категорій, не ламаючи старі;
- підключати нові способи оплати й доставки без переписування замовлення;
- давати адмінці й клієнту різні "вигляди" на одні й ті самі дані;
- масштабувати каталог до сотень тисяч товарів без вибуху пам'яті чи часу відповіді;
- давати десяткам розробників паралельно змінювати різні частини системи, не заважаючи одне одному.

**Головне правило:** патерн застосовується не тому, що "GoF так каже", а тому, що в конкретному місці системи є **реальна вісь змінюваності** (щось, що буде змінюватись/розширюватись найближчим часом). Якщо такої осі немає — патерн лише додає зайвий шар абстракції. Нижче для кожної підсистеми магазину явно вказано, **яка саме вісь змінюваності** виправдовує патерн.

## Архітектура на високому рівні

Перш ніж розкладати патерни по підсистемах, важливо зафіксувати межі трьох великих блоків:

```
┌─────────────────────┐     ┌─────────────────────┐
│   Клієнтська панель   │     │      Адмінка         │
│  (каталог, кошик,    │     │ (товари, категорії,  │
│   замовлення, відгуки)│     │  замовлення, звіти)  │
└──────────┬────────────┘     └───────────┬──────────┘
           │                              │
           │      Тонкі, різні API        │
           ▼                              ▼
┌─────────────────────────────────────────────────────┐
│                  Спільне доменне ядро                │
│  Каталог │ Ціноутворення │ Замовлення │ Коментарі    │
│  Склад   │ Сповіщення    │ Інтеграції │ Звітність    │
└─────────────────────────────────────────────────────┘
```

Клієнт і адмінка **ніколи не повинні напряму дертись у доменне ядро** — кожна панель дивиться на ядро через власний тонкий шар (детальніше — у розділі про Facade). Це головна архітектурна межа: усі патерни нижче живуть **всередині доменного ядра**, а панелі лише споживають вже спрощений API.

## Каталог: категорії та товари

### Проблема
Категорії утворюють дерево довільної глибини (Електроніка → Телефони → Смартфони → Android). Водночас товари всередині категорії мають десятки опціональних полів (варіанти кольору/розміру, галерея, SEO-метадані, знижки, наявність), і адмін часто створює новий товар "на основі" вже наявного.

### Composite — для дерева категорій
**Вісь змінюваності:** глибина дерева невідома наперед і буде рости (нові підкатегорії з'являються постійно, без зміни коду).

Категорія і товар у категорії трактуються через один спільний інтерфейс "вузол каталогу" — і категорія, і товар вміють відповісти на запити "яка твоя ціна" (сума/значення), "скільки товарів всередині", "чи є в наявності". Завдяки цьому:
- побудова хлібних крихт, підрахунок кількості товарів у категорії з підкатегоріями, пошук — все працює рекурсивно й однаково, незалежно від глибини дерева;
- додавання нового рівня вкладеності (підкатегорія підкатегорії) **не потребує зміни жодного існуючого коду** — просто ще один вузол дерева.

**Правильне використання:** чітко розділяй "операції над деревом" (Composite) від "операцій над конкретним товаром" (звичайна бізнес-логіка товару). Composite відповідає лише за структуру й агрегацію, а не за ціноутворення чи валідацію — це окремі шари (див. нижче).

### Builder — для створення товару
**Вісь змінюваності:** кількість опціональних полів товару росте з часом (сьогодні додали "відео-огляд", завтра — "3D-модель").

Замість конструктора з 20 параметрами (або ще гірше — публічних сеттерів, які дозволяють залишити товар у "напівготовому" стані) — покроковий будівельник, який гарантує, що товар або повністю валідний, або взагалі не створюється. Особливо критично в адмінці: форма створення товару природньо мапиться на кроки білдера (основна інформація → варіанти → медіа → SEO → публікація).

**Правильне використання:** білдер валідує на кожному кроці, а не лише в кінці — це дає адміну миттєвий фідбек, що саме не так, а не одну загальну помилку після заповнення всієї форми.

### Prototype — для клонування товару
**Вісь змінюваності:** адмін часто створює товар, "схожий на" вже наявний (той самий бренд, ті самі характеристики, інша модель).

Товар вміє клонувати сам себе — глибока копія всіх полів, окрім тих, що мають лишатись унікальними (SKU, дата створення, залишок на складі). Це економить адміну хвилини на кожен новий товар у великому каталозі, де таких товарів — тисячі.

**Правильне використання:** чітко визнач, які поля копіюються, а які **обнуляються** при клонуванні (залишок складу, статистика продажів, дата публікації) — це найчастіша помилка: скопіювати те, що мало бути унікальним.

### Factory Method / Abstract Factory — для різних типів товарів
**Вісь змінюваності:** магазин продає принципово різні типи товарів (фізичний товар з доставкою, цифровий товар без доставки, підписка з періодичним списанням) — кожен потребує своєї логіки створення й валідації.

Замість `if (type == "digital") ... else if (type == "physical") ...` в одному місці — окрема фабрика на кожен тип товару, яка знає, які поля обов'язкові саме для цього типу (цифровому не треба вага/розміри, підписці — треба період списання).

**Правильне використання:** застосовуй тільки якщо типів товарів справді кілька і вони справді відрізняються бізнес-логікою (не просто інша іконка) — інакше це over-engineering для одного типу "товар".

## Ціноутворення та знижки

### Проблема
Ціна товару рідко буває статичним числом у великому магазині: знижки за категорією, промокоди, оптові знижки, сезонні акції, персональні знижки для VIP-клієнтів — і все це може діяти **одночасно**.

### Strategy — для взаємозамінних правил ціноутворення
**Вісь змінюваності:** правила розрахунку ціни/знижки з'являються й змінюються часто (маркетинг постійно вигадує нові акції), а обирає конкретне правило контекст (тип клієнта, категорія, дата).

Кожен спосіб розрахунку знижки — окремий, повністю ізольований клас, який можна протестувати незалежно від інших. Додавання нової акції — нова стратегія, **без зміни коду існуючих акцій**.

### Decorator — для накладання кількох знижок одночасно
**Вісь змінюваності:** знижки не взаємовиключні — клієнт може одночасно мати знижку за категорією, промокод і кешбек-бали.

Кожна знижка "обгортає" базову ціну і додає свою модифікацію, не знаючи про інші знижки. Порядок обгортання визначає порядок застосування (що важливо: відсоткова знижка до чи після фіксованої — це різний результат, і це має бути свідомим бізнес-рішенням, а не випадковістю коду).

**Правильне використання:** ціноутворення — це саме та підсистема, де Strategy і Decorator природньо працюють **разом**: Strategy обирає, ЯКІ знижки застосовні цьому клієнту/товару, Decorator визначає, **у якому порядку** їх накласти одна на одну. Найчастіша помилка — розмазати обчислення фінальної ціни по UI-шару (адмінка/клієнт рахують по-різному) замість одного спільного місця в доменному ядрі.

## Кошик та оформлення замовлення

### Проблема
Замовлення проходить через чітку послідовність станів, і в кожному стані дозволені лише певні дії (не можна відправити неоплачене замовлення, не можна скасувати вже доставлене). Водночас адміну потрібна можливість відкатити помилкову дію.

### State — для життєвого циклу замовлення
**Вісь змінюваності:** статуси замовлення й правила переходів між ними — це саме те, що бізнес регулярно уточнює (додали статус "очікує підтвердження оплати", розділили "скасовано клієнтом" і "скасовано системою").

Кожен статус — окремий клас, який точно знає, які дії дозволені саме з нього і в який статус можна перейти далі. Це прибирає з коду величезні `switch(order.Status)` розкидані по всій системі, і, що важливіше, **робить недопустимі переходи технічно неможливими**, а не просто "не рекомендованими".

**Правильне використання:** не тримай паралельно і enum-статус, і State-об'єкт — обирай щось одне (детальніше в антипатернах файлу State). У великому магазині статусів зазвичай 6-10 — це саме той розмір, де ручні `if`-перевірки вже стають джерелом багів (забули перевірити один перехід), а State робить їх неможливими на рівні компіляції.

### Command + Memento — для скасування дій в адмінці
**Вісь змінюваності:** адмін робить масові операції (зміна ціни для 500 товарів, зміна статусу групи замовлень) і йому потрібна можливість відкату, якщо щось пішло не так.

Кожна адмінська дія — окремий об'єкт-команда, яка перед виконанням зберігає знімок попереднього стану (Memento). Це дає безкоштовний Undo для будь-якої дії адмінки без написання окремої "зворотної" логіки для кожної операції вручну.

**Правильне використання:** застосовуй саме там, де ціна помилки висока (масові зміни цін, видалення категорій) — не варто огортати кожен дрібний CRUD-виклик у Command, це виправдано лише для дій, які реально потребують історії/відкату.

### Adapter — для платіжних і доставочних систем при оформленні
Детально розглянуто нижче, в розділі "Інтеграції" — сама точка входу цих адаптерів саме тут, у процесі checkout.

## Коментарі та відгуки

### Проблема
Коментарі формують дерево (відповідь на відповідь), кожен новий коментар має пройти модерацію за кількома незалежними критеріями, і кілька різних частин системи мають дізнатись про новий коментар (модератор, аналітика, лічильник рейтингу товару).

### Composite — для дерева відповідей
**Вісь змінюваності:** глибина обговорення не обмежена — відповідь на відповідь на відповідь.

Той самий принцип, що й для категорій: "коментар" і "гілка коментарів" мають спільний інтерфейс, тому підрахунок кількості відповідей, згортання гілки, підрахунок середньої оцінки — рекурсивні операції, які працюють однаково на будь-якій глибині.

### Chain of Responsibility — для конвеєра модерації
**Вісь змінюваності:** критерії модерації регулярно розширюються (додали фільтр на спам-посилання, потім на ненормативну лексику, потім на дублікати).

Кожен коментар проходить через ланцюжок незалежних перевірок (спам → лайка → дублікат → авто-схвалення чи ручна черга), і кожна перевірка нічого не знає про інші. Додавання нового правила модерації — новий елемент ланцюжка, без зміни існуючих.

**Правильне використання:** порядок ланцюжка має значення (дешеві швидкі перевірки — спочатку, дорогі — в кінці), і має бути явний термінальний обробник (що робити, якщо жодна перевірка не спрацювала — а не тихе "нічого не сталось").

### Observer — для сповіщення про новий коментар
**Вісь змінюваності:** кількість "зацікавлених сторін" у новому коментарі росте (спочатку тільки модератор, потім додали аналітику, потім — перерахунок рейтингу товару, потім — email автору товару).

Публікація коментаря лише "оповіщає", що подія відбулась — сама не знає і не повинна знати, скільки і яких підписників на неї відреагують. Це та ж вісь змінюваності, що й у розділі "Сповіщення" нижче — по суті одна й та сама механіка, що переносить один і той самий Observer через кілька доменних областей магазину.

## Сповіщення

### Проблема
Одна подія (зміна статусу замовлення, товар знову в наявності, впала ціна на товар у списку бажань, новий коментар) має спричинити кілька незалежних реакцій: email, SMS, push, оновлення лічильника в адмінці, запис в аналітику.

### Observer — центральний патерн цього розділу
**Вісь змінюваності:** канали сповіщень і їхня кількість змінюються найчастіше з усієї системи (сьогодні лише email, за півроку — ще й push-нотифікації, за рік — Telegram-бот).

Джерело події (замовлення, товар, коментар) взагалі не знає про існування email-сервісу, SMS-шлюзу чи аналітики — воно лише "сповіщає, що щось відбулось". Хто і як на це реагує — питання підписників, а не джерела події.

**Правильне використання (критично на масштабі):**
- один підписник, що впав з помилкою, **не повинен** зупиняти сповіщення решти підписників (кожен виклик підписника — в ізольованому блоці обробки помилок);
- на масштабі "великого магазину" сповіщення майже завжди мають бути **асинхронними** (через чергу повідомлень), а не синхронним викликом всередині того самого запиту — інакше повільний email-провайдер сповільнює саме оформлення замовлення;
- обов'язково передбач відписку (typical "lapsed listener" — короткоживучий підписник, що забув відписатись і роками накопичується в пам'яті).

## Інтеграції: платежі, доставка, склад

### Проблема
Магазин працює з кількома платіжними шлюзами, кількома службами доставки, іноді — з зовнішньою ERP/складською системою. Кожна зовнішня система має власний, несумісний з іншими API.

### Adapter — для кожної зовнішньої інтеграції
**Вісь змінюваності:** зовнішні провайдери (платежі, доставка) змінюються і додаються регулярно, а їхні API повністю поза контролем магазину.

Доменне ядро працює з єдиним внутрішнім інтерфейсом "спосіб оплати" / "служба доставки", а кожен конкретний провайдер (Stripe, LiqPay, Нова Пошта, Укрпошта) — окремий адаптер, що перекладає внутрішній інтерфейс у специфічний виклик цього провайдера.

**Правильне використання:** ядро замовлення **ніколи** не повинно знати назву конкретного провайдера — лише абстрактний "спосіб оплати"/"служба доставки". Найчастіша помилка на цьому масштабі — просочування деталей конкретного провайдера (наприклад, специфічний код помилки Stripe) у доменну логіку замовлення, через що заміна провайдера перетворюється на переписування половини системи оформлення замовлення.

### Bridge — якщо доставка/склад мають дві незалежні осі варіативності
**Вісь змінюваності:** якщо одночасно варіюються і "тип служби доставки" (кур'єр/відділення/поштомат), і "конкретний перевізник" (Нова Пошта/Укрпошта/DHL) — і ці дві осі комбінуються незалежно (кожен перевізник підтримує кілька типів доставки).

Без Bridge це призводить до "вибуху класів" (NovaPoshtaCourier, NovaPoshtaBranch, UkrPoshtaCourier, UkrPoshtaBranch...) — Bridge розділяє "тип доставки" (абстракція) від "перевізника" (реалізація), і вони комбінуються на льоту.

**Правильне використання:** застосовуй Bridge, лише коли справді є **дві незалежні** осі варіативності одночасно — якщо вісь одна (просто різні перевізники), достатньо звичайного Adapter, Bridge буде зайвим ускладненням.

## Звітність та експорт в адмінці

### Проблема
Адмінці потрібні звіти (продажі, залишки, найпопулярніші товари), а також експорт каталогу/замовлень у різні формати (PDF, Excel, CSV) для бухгалтерії чи маркетингу.

### Template Method — для звітів зі спільною структурою
**Вісь змінюваності:** типи звітів різні (продажі, склад, клієнти), але загальна структура генерації однакова (отримати дані → застосувати фільтри → відформатувати → додати шапку/підвал → експортувати).

Спільний скелет генерації звіту фіксується один раз, а кожен конкретний тип звіту перевизначає лише ті кроки, які справді відрізняються (яким чином отримати дані, як саме форматувати). Це прибирає дублювання "шапки/підвалу/фільтрів", яке інакше копіюється в кожен новий звіт.

### Visitor — для кількох незалежних операцій над деревом каталогу
**Вісь змінюваності:** потрібно кілька повністю різних операцій над тим самим деревом категорій/товарів (експорт в XML, експорт в JSON, підрахунок сумарної вартості складу, валідація перед публікацією) — і додавання нової операції не повинно чіпати класи категорій/товарів.

Кожна операція — окремий "відвідувач", який обходить дерево каталогу і виконує свою логіку для кожного типу вузла, не змінюючи сам клас категорії чи товару.

**Правильне використання:** Visitor виправданий, лише якщо структура дерева (типи вузлів) відносно стабільна, а от кількість операцій над нею — росте. Якщо навпаки, типи вузлів каталогу змінюються часто, а операцій мало — Visitor стане тягарем (кожен новий тип вузла вимагає правок у всіх візиторах).

## Продуктивність при великому масштабі

### Проблема
При сотнях тисяч товарів наївна реалізація (кожен товар — важкий об'єкт з дублюванням спільних даних) починає впиратись у пам'ять і швидкість.

### Flyweight — для спільних характеристик товару
**Вісь змінюваності: тут не змінюваність, а обсяг** — коли товарів дуже багато і значна частина їхніх даних повторюється між тисячами екземплярів (бренд, розмірна сітка, матеріал, категорія-довідник).

Спільна, незмінна частина даних (бренд, довідник розмірів, шаблон характеристик) зберігається один раз і переюзується всіма товарами, які на неї посилаються — замість дублювання цих даних у кожному товарі окремо.

**Правильне використання:** застосовуй лише коли пам'ять справді є вузьким місцем (виміряй перед тим, як ускладнювати код) — передчасна оптимізація тут типова помилка. Спільна (intrinsic) частина обов'язково має бути незмінною — інакше зміна "спільного" бренду в одному товарі випадково зачепить усі інші товари цього бренду.

### Proxy — для дорогих операцій каталогу
**Вісь змінюваності:** деякі операції над каталогом дорогі (побудова повного дерева категорій із підрахунком товарів, складні фільтри), а результат можна кешувати.

Проксі-об'єкт стоїть перед реальним важким сервісом і повертає кешований результат, якщо він ще актуальний, звертаючись до реального сервісу лише за потреби. Так само проксі використовується для перевірки прав доступу перед тим, як дозволити дорогу/чутливу операцію в адмінці (protection proxy).

## Як патерни комбінуються між собою

У реальному великому магазині патерни майже завжди працюють **групами**, а не поодинці. Кілька наскрізних зв'язок, які легко пропустити:

- **Composite + Visitor** — дерево категорій (Composite) обходиться операцією експорту/підрахунку (Visitor) — це одна пара, що зустрічається одночасно і в каталозі, і в деревах коментарів.
- **Strategy + Decorator** — обчислення фінальної ціни: Strategy обирає застосовні знижки, Decorator накладає їх у правильному порядку.
- **Command + Memento** — будь-яка "скасовувана" дія адмінки: Command інкапсулює саму дію, Memento зберігає стан для відкату.
- **Observer** пронизує щонайменше три різні підсистеми одночасно (коментарі, замовлення, склад/сповіщення про наявність) — варто зробити це **одним спільним механізмом сповіщень** у ядрі, а не трьома окремими реалізаціями.
- **State + Command** — дія адмінки "змінити статус замовлення" — це Command, який делегує саму зміну поточному State-об'єкту замовлення (State сам вирішує, чи дозволений цей перехід).

## Типові помилки при впровадженні

1. **Патерн заради патерну.** Якщо конкретна вісь змінюваності відсутня (наприклад, у магазині завжди буде рівно один спосіб оплати) — не варто ставити Strategy "про всяк випадок". Зайва абстракція ускладнює читання коду без жодної реальної користі.
2. **Просочування деталей провайдера в ядро.** Найдорожча помилка інтеграцій — коли специфічний код помилки чи формат відповіді конкретного платіжного шлюзу "протікає" в доменну логіку замовлення. Заміна провайдера тоді ламає половину системи, хоча саме для цього й існує Adapter.
3. **Синхронні сповіщення в критичному шляху.** Якщо Observer викликає email-провайдер синхронно всередині запиту "оформити замовлення" — повільний зовнішній сервіс сповільнює клієнта. На масштабі сповіщення мають йти через чергу.
4. **Дублювання логіки ціноутворення в адмінці й на клієнті.** Ціна має рахуватись **в одному місці** доменного ядра (Strategy + Decorator), а не окремо для відображення в адмінці і окремо для checkout — інакше рано чи пізно вони розійдуться в значеннях.
5. **State разом зі старим enum-статусом "про всяк випадок".** Якщо вже впровадили State — прибери паралельний enum-статус повністю, інакше два джерела істини рано чи пізно розійдуться.
6. **Composite без обмежень на вкладеність.** Дерево категорій/коментарів технічно необмежене, але без розумного ліміту глибини (і захисту від циклічного посилання категорії самої на себе) це джерело нескінченної рекурсії.

## Рекомендований порядок впровадження

Не варто впроваджувати все одразу. Практичний порядок для нового великого магазину:

1. **Composite** для дерева категорій — це фундамент, на якому будується весь каталог.
2. **Builder** для створення товару — одразу дає адмінці правильну, поетапну форму створення.
3. **State** для статусів замовлення — критично важливо зафіксувати правильно з самого початку, оскільки статуси проникають у весь код замовлення.
4. **Strategy** для ціноутворення/знижок — маркетинг завжди вимагатиме нових акцій, і краще одразу мати місце для них.
5. **Observer** для сповіщень — впроваджується один раз як спільний механізм, а не окремо для кожної підсистеми.
6. **Adapter** для першої платіжної й доставочної інтеграції — навіть якщо провайдер поки один, межа "ядро / зовнішній API" повинна існувати з першого дня.
7. Решта (**Decorator**, **Command+Memento**, **Chain of Responsibility**, **Visitor**, **Flyweight**, **Bridge**, **Proxy**) — додаються вже тоді, коли конкретна вісь змінюваності (масові акції, потреба в undo, ріст обсягу модерації, ріст обсягу каталогу) реально проявляється на практиці, а не наперед "про всяк випадок".
