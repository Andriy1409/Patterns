## Firewall (Міжмережевий екран)

**Firewall** — це мережевий пристрій (апаратний або програмний), який контролює трафік, що проходить між двома мережами (зазвичай — між "довіреною" внутрішньою мережею та "недовіреним" зовнішнім світом, тобто інтернетом), фільтруючи його на основі набору правил.

Головна робота firewall — приймати рішення **"пропустити" (Allow/Permit)** чи **"заблокувати" (Deny/Drop)** для кожного пакета або з'єднання, яке намагається пройти через нього.

### 🛡️ Аналогія з реального життя

Уявіть охоронця на прохідній великого офісного центру:

- У охоронця є список — хто має право заходити (аналог IP-адрес/мереж), а хто ні.
- Охоронець перевіряє не лише "чи ви є в списку", а й **на який поверх/у яку кімнату** вам дозволено зайти (аналог портів і протоколів — наприклад, "дозволено на 3-й поверх (порт 443), але заборонено в серверну (порт 22)").
- Якщо відвідувача немає в жодному правилі списку — за замовчуванням він **не проходить** (це і є "implicit deny all" — неявна заборона за замовчуванням).
- Охоронець перевіряє список **згори донизу** і зупиняється на першому правилі, що підходить — тому порядок правил у списку критично важливий.

Це практично точна модель того, як працює firewall.

### Типи firewall

| Тип | Рівень OSI | Що інспектує | Переваги | Недоліки |
|---|---|---|---|---|
| **Packet-filtering (stateless)** | L3/L4 (мережевий/транспортний) | Заголовки кожного пакета окремо: source/destination IP, порт, протокол | Дуже швидкий, простий, мінімальні витрати ресурсів | Не розуміє контексту з'єднання; не бачить, що пакет — це відповідь на вже дозволений запит; легко обійти підробкою заголовків |
| **Stateful inspection** | L3/L4 | Те саме + **стан з'єднання** (таблиця активних сесій: TCP handshake, номери послідовностей) | Розуміє, що пакет — частина вже дозволеної сесії (напр. відповідь на TCP SYN); сучасний базовий стандарт; значно безпечніший | Складніший, споживає пам'ять на таблицю станів, вразливий до атак виснаження цієї таблиці (SYN flood) |
| **Application-layer / Proxy firewall** | L7 (прикладний) | Вміст пакета на рівні застосунку: наприклад, розрізняє HTTP GET від POST, перевіряє URL, заголовки, вміст файлів | Найглибша видимість; може блокувати конкретні дії всередині дозволеного протоколу | Повільніший (глибший аналіз), може вимагати окремого проксі на кожен протокол |
| **NGFW (Next-Generation Firewall)** | L3–L7 | Все вищезгадане + IPS/IDS (запобігання вторгненням), Deep Packet Inspection, розпізнавання конкретних застосунків (напр. "це Skype-трафік", а не просто "порт 443"), інтеграція з репутаційними базами (URL/IP reputation) | Максимальна функціональність в одному пристрої; поєднує L3-L7 контроль | Найдорожчий, найскладніший у налаштуванні, потенційно найбільша затримка обробки |

**Ключова відмінність для співбесіди:** stateless firewall перевіряє кожен пакет "у вакуумі" (немає пам'яті про попередні пакети), тоді як stateful firewall веде **таблицю з'єднань (connection/state table)** і дозволяє, наприклад, вхідний пакет автоматично, якщо він є відповіддю на раніше дозволений вихідний запит — навіть без окремого явного правила на "вхід".

### Правила (Rules) та порядок обробки

Firewall-правила обробляються **послідовно, згори донизу**, і застосовується принцип **"перший збіг виграє" (first match wins)** — щойно пакет підпадає під якесь правило, обробка зупиняється і застосовується дія цього правила; правила нижче вже не перевіряються для цього пакета.

Наприкінці списку завжди неявно існує правило **"deny all"** — усе, що не було явно дозволено жодним правилом вище, автоматично блокується.

**Чому порядок правил критично важливий:** якщо широке (загальне) правило "allow" розташоване вище за вузьке (специфічне) правило "deny", специфічна заборона ніколи не спрацює — трафік буде дозволено ще на широкому правилі раніше.

#### Приклад помилки в порядку правил

```
Правило 1: ALLOW  from 10.0.0.0/8      to any            port any
Правило 2: DENY   from 10.0.5.13       to any            port 22   (SSH)
Правило 3: DENY   from any             to any            (implicit)
```

Пакет від хоста `10.0.5.13` на порт 22 (SSH):

```
Пакет: src=10.0.5.13, dst=any, port=22
        │
        ▼
  Правило 1: 10.0.0.0/8 містить 10.0.5.13? ТАК → ЗБІГ!
        │
        ▼
  Рішення: ALLOW  ❌ (правило 2 навіть не перевіряється!)
```

Адміністратор хотів заблокувати SSH саме з хоста `10.0.5.13`, але через те, що широке правило 1 стоїть вище, воно "перехоплює" пакет першим, і Правило 2 ніколи не спрацьовує. **Правильне рішення:** специфічні (вузькі) правила завжди повинні стояти вище за загальні (широкі):

```
Правило 1: DENY   from 10.0.5.13       to any            port 22   (SSH)   ✅ спочатку виняток
Правило 2: ALLOW  from 10.0.0.0/8      to any            port any         ✅ потім загальне правило
Правило 3: DENY   from any             to any            (implicit)
```

Це один з найпоширеніших багів у реальних конфігураціях firewall/ACL — і улюблене питання на технічних співбесідах.

## ACL (Access Control List)

**ACL (Access Control List)** — це список правил, який використовують маршрутизатори (routers) і комутатори (switches) для дозволу чи заборони трафіку, що проходить через конкретний мережевий інтерфейс. Концептуально ACL дуже схожий на набір firewall-правил, але зазвичай простіший, обробляється апаратно (швидше) і застосовується безпосередньо **на інтерфейсі** пристрою L3 (маршрутизатора) або керованого комутатора.

ACL — це, по суті, "дешевший" і швидший фільтр, вбудований у мережеве обладнання, тоді як спеціалізований firewall зазвичай пропонує глибшу інспекцію (stateful, L7).

### Standard ACL vs Extended ACL

| Характеристика | Standard ACL | Extended ACL |
|---|---|---|
| Фільтрація за | Лише **source IP-адресою** | Source IP, **destination IP**, порт, протокол (TCP/UDP/ICMP) |
| Гранулярність | Груба (coarse) | Точна (fine-grained) |
| Номери (Cisco) | 1–99, 1300–1999 | 100–199, 2000–2699 |
| Типове застосування | Розміщується **якомога ближче до джерела призначення** (близько до destination), бо не можна вказати куди саме йде трафік | Розміщується **якомога ближче до джерела трафіку** (source), бо можна одразу відсіяти небажане ще на вході |
| Приклад використання | "Заблокувати весь трафік з мережі 192.168.5.0/24" | "Заблокувати лише HTTP (порт 80) з хоста 192.168.5.10 до сервера 10.0.0.5" |

### Приклад синтаксису (Cisco-style)

**Standard ACL** — блокує весь трафік з конкретної підмережі, незалежно від призначення чи порту:

```
access-list 10 deny  192.168.5.0 0.0.0.255
access-list 10 permit any
```

**Extended ACL** — блокує лише конкретний протокол/порт між конкретними хостами:

```
access-list 110 deny  tcp host 192.168.5.10 host 10.0.0.5 eq 80
access-list 110 permit ip any any
```

Тут `eq 80` означає "порт дорівнює 80 (HTTP)" — це саме та гранулярність, якої стандартний ACL забезпечити не може.

### Inbound vs Outbound на інтерфейсі

ACL застосовується на конкретному інтерфейсі в конкретному напрямку:

- **Inbound (вхідний)** — ACL перевіряє пакети, які **заходять** у маршрутизатор через цей інтерфейс, ще **до** прийняття рішення про маршрутизацію. Це ефективніше, якщо пакет треба відкинути одразу (не витрачаємо ресурси на маршрутизацію того, що все одно буде відкинуто).
- **Outbound (вихідний)** — ACL перевіряє пакети **після** того, як маршрутизатор вже вирішив, через який інтерфейс їх відправити, безпосередньо перед виходом.

```
                    ┌─────────────────────────┐
   Вхідний пакет ──▶│ ACL (inbound)  → Routing │──▶ ACL (outbound) ──▶ Вихідний пакет
                    │  таблиця                 │
                    └─────────────────────────┘
```

**Практичне правило:** один ACL можна прив'язати до інтерфейсу лише один раз на напрямок (тобто максимум один inbound ACL і один outbound ACL на інтерфейс на кожен протокол).

## NAT (Network Address Translation)

**NAT (Network Address Translation)** — це технологія, яка транслює (переписує) IP-адреси в заголовках пакетів під час проходження через маршрутизатор чи firewall. Історично NAT з'явився для вирішення проблеми **вичерпання публічних адрес IPv4**: замість того, щоб кожному пристрою в приватній мережі виділяти окрему публічну IP-адресу, багато пристроїв з приватними адресами можуть "спільно користуватись" однією публічною адресою при виході в інтернет.

### 📬 Аналогія з реального життя

Уявіть офісну будівлю з однією загальною поштовою адресою у міському довіднику (наприклад, "вул. Хрещатик, 1"). Всередині будівлі працюють сотні співробітників, кожен за своїм окремим столом (внутрішня, "приватна" адреса). Зовнішній світ бачить лише одну адресу будівлі. Коли лист приходить на адресу будівлі, **пошта (mailroom)** дивиться, кому саме він адресований (за іменем отримувача чи номером кабінету), і розносить його правильному співробітнику. NAT-пристрій виконує роль такої пошти: зовні видно лише одну публічну IP-адресу, а всередині — маршрутизатор (mailroom) знає, який саме внутрішній пристрій відповідає за кожне конкретне з'єднання.

### Типи NAT

| Тип | Механізм | Типове застосування |
|---|---|---|
| **Static NAT** | Фіксоване відображення **1:1** — конкретна приватна IP завжди транслюється в ту саму конкретну публічну IP | Публікація внутрішнього сервера назовні (напр. веб-сервер 10.0.0.5 завжди доступний як 203.0.113.5) |
| **Dynamic NAT** | Пул публічних IP-адрес динамічно призначається приватним адресам за принципом "перший вільний" | Коли є декілька публічних IP, але їх менше, ніж внутрішніх хостів, і потрібне пряме (без портів) відображення |
| **PAT / NAT Overload** | **Багато-до-одного**: усі внутрішні хости діляться **однією** публічною IP, а розрізняються за **номером порту** | Найпоширеніший сценарій — домашній роутер, офісний шлюз в інтернет |

**PAT (Port Address Translation)**, також відомий як **NAT overload**, — найпоширеніший вид NAT у щоденному використанні. Він дозволяє тисячам внутрішніх пристроїв виходити в інтернет через **одну єдину публічну IP-адресу**, розрізняючи їхні сесії за допомогою **номерів портів**.

### Як PAT відстежує трансляції: NAT-таблиця

Маршрутизатор веде таблицю відповідностей **(внутрішня IP:порт) ↔ (публічна IP:порт)**:

```
                         ІНТЕРНЕТ (зовнішня мережа)
                                  │
                                  │ Публічна IP: 203.0.113.10
                    ┌─────────────▼─────────────┐
                    │      NAT-пристрій          │
                    │   (PAT / NAT Overload)     │
                    │                            │
                    │   NAT-таблиця:             │
                    │  ┌───────────────┬────────────────────┐
                    │  │ Внутрішній     │ Публічний          │
                    │  │ 192.168.1.10:5000 │ 203.0.113.10:40001 │
                    │  │ 192.168.1.11:5001 │ 203.0.113.10:40002 │
                    │  │ 192.168.1.10:5002 │ 203.0.113.10:40003 │
                    │  └───────────────┴────────────────────┘
                    └─────────────┬─────────────┘
                                  │  Приватна мережа
              ┌───────────────────┼───────────────────┐
              │                   │                   │
       192.168.1.10        192.168.1.11         192.168.1.12
       (Хост A)             (Хост B)             (Хост C)
```

Коли Хост A (`192.168.1.10:5000`) надсилає пакет в інтернет, NAT-пристрій:
1. Замінює source-адресу пакета на `203.0.113.10:40001` (публічна IP + новий, унікальний порт).
2. Записує це відображення в NAT-таблицю.
3. Коли повертається відповідь на `203.0.113.10:40001`, NAT дивиться в таблицю і **зворотно транслює** її назад у `192.168.1.10:5000`, після чого надсилає пакет правильному внутрішньому хосту.

Без цієї таблиці зовнішній сервер, що відповідає, взагалі не знав би, кому з десятків внутрішніх хостів адресована відповідь — адже зовні всі вони "виглядають" як одна публічна адреса.

### Побічні ефекти NAT, важливі для моніторингу й діагностики

- **Ускладнює end-to-end моніторинг і traceroute**: із зовнішньої точки зору видно лише публічну IP-адресу NAT-пристрою, а не реальну внутрішню адресу джерела. Якщо кілька внутрішніх хостів виходять через одну публічну IP, зовнішній спостерігач (наприклад, лог сервера чи traceroute) бачить лише "хтось за 203.0.113.10", а не конкретний внутрішній хост.
- **Ускладнює протоколи, що передають IP-адреси у своєму payload** (а не лише в заголовках) — класична проблема **"NAT traversal"**. Історичний приклад: **FTP у активному режимі (active mode)**, де клієнт передає серверу свою IP-адресу і порт **у тілі команди** (`PORT` command) для зворотного з'єднання даних; NAT-пристрій, який не "розуміє" протокол FTP, не підмінить цю адресу всередині payload, і зовнішній сервер спробує з'єднатися з приватною (недосяжною ззовні) адресою. Аналогічні проблеми історично виникали в деяких VoIP-протоколах (SIP), де IP-адреса передається у SDP-повідомленні. Рішення — ALG (Application Layer Gateway) на NAT-пристрої або пасивний режим (passive mode) у FTP.

## VPN (Virtual Private Network)

**VPN (Virtual Private Network)** створює **зашифрований, автентифікований тунель** через недовірену мережу (як правило — публічний інтернет), так що трафік всередині тунелю виглядає так, ніби він проходить через приватну, захищену мережу, хоча фізично рухається через загальнодоступну інфраструктуру.

### 🔒 Аналогія з реального життя

Уявіть бронований, повністю запечатаний кур'єрський фургон, який їде звичайними публічними вулицями міста. Вміст вантажу всередині фургона (дані) неможливо побачити чи підмінити нікому із зовнішніх спостерігачів на маршруті — фургон їде тими самими дорогами, що й усі інші, але вміст надійно захищений протягом усієї подорожі. VPN робить те саме з мережевим трафіком: пакети фізично проходять через звичайний, недовірений інтернет, але їхній вміст зашифрований і захищений від перегляду чи модифікації.

### Site-to-Site VPN vs Remote-Access VPN

| Характеристика | Site-to-Site VPN | Remote-Access VPN |
|---|---|---|
| Що з'єднує | Дві мережі/офіси **постійно** (маршрутизатор-маршрутизатор) | Окремий віддалений користувач ↔ корпоративна мережа |
| Типова технологія | IPsec між шлюзами (gateway-to-gateway) | VPN-клієнт (напр. IPsec client, SSL VPN client) на пристрої користувача |
| Тривалість з'єднання | Постійне (always-on) з'єднання між офісами | Встановлюється сесійно, коли користувач підключається |
| Приклад | З'єднання головного офісу і філії в іншому місті | Співробітник підключається з дому чи готелю до корпоративної мережі |

### IPsec (Internet Protocol Security)

**IPsec** — набір протоколів для захисту IP-трафіку на мережевому рівні (L3). Складається з двох основних протоколів:

- **AH (Authentication Header)** — забезпечує **автентифікацію та цілісність** даних (гарантує, що пакет не був підмінений і дійсно надісланий заявленим відправником), **але не шифрує** сам вміст (немає конфіденційності).
- **ESP (Encapsulating Security Payload)** — забезпечує **і шифрування (конфіденційність), і автентифікацію/цілісність**. Саме ESP використовується в переважній більшості реальних VPN-впроваджень, оскільки AH сам по собі не приховує дані.

Два режими роботи IPsec:

- **Transport mode** — шифрується/автентифікується лише **payload** (корисне навантаження) вихідного IP-пакета, а оригінальний IP-заголовок залишається відкритим. Використовується для захисту з'єднання **між двома кінцевими хостами** напряму (host-to-host).
- **Tunnel mode** — **весь оригінальний IP-пакет** (разом із заголовком) шифрується та інкапсулюється в новий IP-пакет з новим заголовком. Використовується у **site-to-site VPN** між шлюзами — саме тому зовнішній спостерігач бачить лише адреси шлюзів, а не реальних внутрішніх хостів джерела/призначення.

### SSL/TLS VPN як альтернатива

**SSL VPN** (іноді TLS VPN) — простіша альтернатива IPsec, що працює **поверх стандартного HTTPS-порту (TCP 443)**. Оскільки порт 443 майже завжди відкритий на будь-якому корпоративному чи публічному firewall (це стандартний веб-трафік), SSL VPN значно легше "проходить" через обмежувальні мережеві політики, ніж IPsec, який традиційно потребує окремих протоколів (ESP, IKE на UDP 500/4500), що часто явно блокуються суворими firewall-політиками.

| Характеристика | IPsec VPN | SSL/TLS VPN |
|---|---|---|
| Складність налаштування | Вища (потребує узгодження параметрів шифрування, IKE-фаз, іноді сертифікатів на обох сторонах) | Нижча (часто достатньо браузера чи легкого клієнта) |
| Порт / сумісність з firewall | Потребує UDP 500 (IKE), UDP 4500 (NAT-T), протокол ESP (50) — може блокуватись суворими firewall | Працює через TCP 443 (HTTPS) — практично завжди дозволено |
| Рівень роботи | Мережевий рівень (L3) — увесь IP-трафік проходить через тунель | Зазвичай рівень застосунку (L7), хоча "SSL VPN full tunnel" може працювати як L3 |
| Типове застосування | Site-to-site з'єднання між офісами, постійні корпоративні тунелі | Remote-access для окремих користувачів, особливо з ненадійних/публічних мереж (готелі, кафе) |

## Практичні приклади на C#

Важливе застереження: firewall, NAT і VPN зазвичай реалізуються на спеціалізованому мережевому обладнанні або в операційній системі (iptables/nftables, Windows Firewall, апаратні маршрутизатори), а не пишуться "з нуля" на C#. Проте інструменти мережевого моніторингу та управління (як продукти SolarWinds) **написані на C#/.NET** і активно взаємодіють із цими концепціями: перевіряють доступність портів, аналізують правила, симулюють поведінку мереж для тестування. Нижче — три ілюстративні приклади, що демонструють саме цю логіку.

### Приклад 1: `FirewallRuleEngine` — симуляція stateless-фільтрації пакетів

Цей приклад демонструє основний принцип "перший збіг виграє" та важливість порядку правил.

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

namespace NetworkSecurityDemo;

public enum RuleAction
{
    Allow,
    Deny
}

/// <summary>
/// Просте правило firewall: якщо всі поля збігаються (або поле = "*" — wildcard),
/// застосовується вказана дія (Allow/Deny).
/// </summary>
public sealed class FirewallRule
{
    public string Name { get; init; } = string.Empty;
    public string SourceIp { get; init; } = "*";
    public string DestinationIp { get; init; } = "*";
    public int? Port { get; init; }          // null = будь-який порт
    public string Protocol { get; init; } = "*"; // TCP / UDP / *
    public RuleAction Action { get; init; }

    public bool Matches(Packet packet)
    {
        bool sourceMatches = SourceIp == "*" || SourceIp == packet.SourceIp;
        bool destMatches = DestinationIp == "*" || DestinationIp == packet.DestinationIp;
        bool portMatches = Port is null || Port == packet.Port;
        bool protocolMatches = Protocol == "*" ||
            string.Equals(Protocol, packet.Protocol, StringComparison.OrdinalIgnoreCase);

        return sourceMatches && destMatches && portMatches && protocolMatches;
    }
}

public sealed record Packet(string SourceIp, string DestinationIp, int Port, string Protocol);

public sealed record EvaluationResult(RuleAction Action, string MatchedRuleName);

/// <summary>
/// Обробляє список правил у порядку "згори донизу", застосовуючи
/// принцип first-match-wins. Якщо жодне правило не збіглось —
/// спрацьовує неявне правило "deny all".
/// </summary>
public sealed class FirewallRuleEngine
{
    private readonly List<FirewallRule> _rules;

    public FirewallRuleEngine(IEnumerable<FirewallRule> rules)
    {
        _rules = rules.ToList(); // порядок у списку зберігається — це критично!
    }

    public EvaluationResult Evaluate(Packet packet)
    {
        foreach (var rule in _rules)
        {
            if (rule.Matches(packet))
            {
                return new EvaluationResult(rule.Action, rule.Name);
            }
        }

        // Неявне правило: якщо нічого не збіглось — блокуємо (implicit deny all)
        return new EvaluationResult(RuleAction.Deny, "IMPLICIT-DENY-ALL");
    }
}

public static class Program
{
    public static void Main()
    {
        // Навмисно демонструємо "неправильний" порядок правил (баг),
        // а потім "правильний" — щоб показати, чому порядок важливий.

        Console.WriteLine("=== СЦЕНАРІЙ 1: Неправильний порядок правил (баг) ===\n");

        var buggyRules = new List<FirewallRule>
        {
            new() { Name = "ALLOW-ALL-INTERNAL", SourceIp = "10.0.0.0/8".Split('/')[0],
                    Action = RuleAction.Allow }, // спрощено: трактуємо як точну адресу для демо
            new() { Name = "DENY-SSH-FROM-BAD-HOST", SourceIp = "10.0.5.13",
                    Port = 22, Protocol = "TCP", Action = RuleAction.Deny },
        };

        var buggyEngine = new FirewallRuleEngine(buggyRules);
        var testPacket = new Packet("10.0.5.13", "10.0.0.1", 22, "TCP");

        var buggyResult = buggyEngine.Evaluate(testPacket);
        Console.WriteLine($"Пакет: {testPacket}");
        Console.WriteLine($"Результат: {buggyResult.Action} (правило: {buggyResult.MatchedRuleName})");
        Console.WriteLine("❌ Помилка: правило ALLOW-ALL-INTERNAL стоїть вище і 'перехоплює' пакет,");
        Console.WriteLine("   тому DENY-SSH-FROM-BAD-HOST ніколи не спрацьовує!\n");

        Console.WriteLine("=== СЦЕНАРІЙ 2: Правильний порядок правил (fix) ===\n");

        var fixedRules = new List<FirewallRule>
        {
            new() { Name = "DENY-SSH-FROM-BAD-HOST", SourceIp = "10.0.5.13",
                    Port = 22, Protocol = "TCP", Action = RuleAction.Deny }, // специфічне — першим!
            new() { Name = "ALLOW-ALL-INTERNAL", SourceIp = "10.0.5.13",
                    Action = RuleAction.Allow },
        };

        var fixedEngine = new FirewallRuleEngine(fixedRules);
        var fixedResult = fixedEngine.Evaluate(testPacket);
        Console.WriteLine($"Пакет: {testPacket}");
        Console.WriteLine($"Результат: {fixedResult.Action} (правило: {fixedResult.MatchedRuleName})");
        Console.WriteLine("✅ Тепер специфічне правило DENY стоїть вище — SSH з цього хоста коректно блокується.\n");

        Console.WriteLine("=== СЦЕНАРІЙ 3: Пакет, що не підпадає під жодне правило ===\n");

        var unknownPacket = new Packet("192.168.99.99", "10.0.0.1", 443, "TCP");
        var unknownResult = fixedEngine.Evaluate(unknownPacket);
        Console.WriteLine($"Пакет: {unknownPacket}");
        Console.WriteLine($"Результат: {unknownResult.Action} (правило: {unknownResult.MatchedRuleName})");
        Console.WriteLine("🔒 Спрацювало неявне правило 'deny all' — за замовчуванням усе заборонено.");
    }
}
```

### Приклад 2: `NatTable` — симуляція PAT/NAT Overload

Демонструє, як один публічний IP може обслуговувати багато внутрішніх хостів завдяки трансляції портів, і як зворотна трансляція повертає відповідь правильному внутрішньому хосту.

```csharp
using System;
using System.Collections.Generic;

namespace NetworkSecurityDemo;

public sealed record InternalEndpoint(string Ip, int Port);
public sealed record PublicEndpoint(string Ip, int Port);

/// <summary>
/// Спрощена симуляція NAT-таблиці для PAT (Port Address Translation / NAT Overload).
/// Одна публічна IP-адреса використовується для багатьох внутрішніх хостів,
/// розрізнення відбувається за унікальним публічним портом.
/// </summary>
public sealed class NatTable
{
    private readonly string _publicIp;
    private int _nextPublicPort = 40000;

    // Пряма таблиця: внутрішній ендпоінт -> публічний ендпоінт
    private readonly Dictionary<InternalEndpoint, PublicEndpoint> _outboundMap = new();

    // Зворотна таблиця: публічний ендпоінт -> внутрішній ендпоінт
    private readonly Dictionary<PublicEndpoint, InternalEndpoint> _inboundMap = new();

    public NatTable(string publicIp)
    {
        _publicIp = publicIp;
    }

    /// <summary>
    /// Транслює вихідний пакет: внутрішня IP:порт -> публічна IP:новий порт.
    /// Якщо трансляція для цього внутрішнього ендпоінта вже існує — перевикористовує її.
    /// </summary>
    public PublicEndpoint TranslateOutbound(InternalEndpoint source)
    {
        if (_outboundMap.TryGetValue(source, out var existing))
        {
            return existing;
        }

        var publicEndpoint = new PublicEndpoint(_publicIp, _nextPublicPort++);
        _outboundMap[source] = publicEndpoint;
        _inboundMap[publicEndpoint] = source;
        return publicEndpoint;
    }

    /// <summary>
    /// Зворотна трансляція: коли приходить відповідь на публічну IP:порт,
    /// знаходимо, якому внутрішньому хосту вона насправді призначена.
    /// </summary>
    public bool TryTranslateInbound(PublicEndpoint destination, out InternalEndpoint internalHost)
    {
        return _inboundMap.TryGetValue(destination, out internalHost!);
    }
}

public static class NatDemo
{
    public static void Main()
    {
        var nat = new NatTable("203.0.113.10");

        var hostA = new InternalEndpoint("192.168.1.10", 5000);
        var hostB = new InternalEndpoint("192.168.1.11", 5001);
        var hostAAgain = new InternalEndpoint("192.168.1.10", 5002); // той самий хост, інша сесія

        Console.WriteLine("=== Вихідні (outbound) пакети: трансляція в публічну адресу ===\n");

        var publicA = nat.TranslateOutbound(hostA);
        Console.WriteLine($"{hostA.Ip}:{hostA.Port,-6} --> {publicA.Ip}:{publicA.Port}");

        var publicB = nat.TranslateOutbound(hostB);
        Console.WriteLine($"{hostB.Ip}:{hostB.Port,-6} --> {publicB.Ip}:{publicB.Port}");

        var publicAAgain = nat.TranslateOutbound(hostAAgain);
        Console.WriteLine($"{hostAAgain.Ip}:{hostAAgain.Port,-6} --> {publicAAgain.Ip}:{publicAAgain.Port}");

        Console.WriteLine("\n=== Вхідні (inbound) пакети-відповіді: зворотна трансляція ===\n");

        // Відповідь приходить на publicB — перевіримо, що NAT правильно
        // маршрутизує її назад саме до hostB, а не до hostA.
        if (nat.TryTranslateInbound(publicB, out var resolvedHost))
        {
            Console.WriteLine($"Відповідь на {publicB.Ip}:{publicB.Port} --> направлено до {resolvedHost.Ip}:{resolvedHost.Port}");
            Console.WriteLine(resolvedHost == hostB ? "✅ Коректно: відповідь дійшла саме до Хоста B" : "❌ ПОМИЛКА трансляції!");
        }

        // Спроба трансляції невідомого публічного порту (немає в таблиці)
        var unknownPublic = new PublicEndpoint("203.0.113.10", 59999);
        bool found = nat.TryTranslateInbound(unknownPublic, out _);
        Console.WriteLine($"\nВідповідь на {unknownPublic.Ip}:{unknownPublic.Port} --> {(found ? "знайдено" : "НЕ знайдено в NAT-таблиці (пакет буде відкинуто)")} ❌");
    }
}
```

**Очікуваний консольний вивід:**

```
=== Вихідні (outbound) пакети: трансляція в публічну адресу ===

192.168.1.10:5000  --> 203.0.113.10:40000
192.168.1.11:5001  --> 203.0.113.10:40001
192.168.1.10:5002  --> 203.0.113.10:40002

=== Вхідні (inbound) пакети-відповіді: зворотна трансляція ===

Відповідь на 203.0.113.10:40001 --> направлено до 192.168.1.11:5001
✅ Коректно: відповідь дійшла саме до Хоста B

Відповідь на 203.0.113.10:59999 --> НЕ знайдено в NAT-таблиці (пакет буде відкинуто) ❌
```

### Приклад 3: Перевірка доступності портів через firewall (погляд інструменту моніторингу)

Цей приклад ілюструє реалістичний сценарій: сервер моніторингу (наприклад, SolarWinds Orion) повинен перевірити, чи доступні критичні порти на віддаленому пристрої, перш ніж почати опитування (polling). Це базова перевірка здоров'я з'єднання (health check), яку реально виконують подібні продукти.

```csharp
using System;
using System.Net.Sockets;
using System.Threading.Tasks;

namespace NetworkSecurityDemo;

public sealed record PortCheckResult(string Host, int Port, string ServiceName, bool IsReachable, string Details);

/// <summary>
/// Спрощений "port checker" — перевіряє TCP-доступність конкретних портів
/// на віддаленому хості з коротким таймаутом. Використовується інструментами
/// моніторингу для діагностики: чи не блокує firewall/ACL/NAT потрібний трафік
/// ще до того, як звинувачувати саме моніторингове ПЗ.
/// </summary>
public sealed class FirewallPortValidator
{
    private readonly TimeSpan _connectTimeout;

    public FirewallPortValidator(TimeSpan? connectTimeout = null)
    {
        _connectTimeout = connectTimeout ?? TimeSpan.FromSeconds(2);
    }

    public async Task<PortCheckResult> CheckPortAsync(string host, int port, string serviceName)
    {
        using var client = new TcpClient();

        try
        {
            var connectTask = client.ConnectAsync(host, port);
            var timeoutTask = Task.Delay(_connectTimeout);

            var completedTask = await Task.WhenAny(connectTask, timeoutTask);

            if (completedTask == timeoutTask)
            {
                return new PortCheckResult(host, port, serviceName, false,
                    $"Таймаут ({_connectTimeout.TotalSeconds}с) — ймовірно заблоковано firewall/ACL");
            }

            // Переконуємось, що саме connectTask завершився без винятку
            await connectTask;
            return new PortCheckResult(host, port, serviceName, true, "З'єднання встановлено успішно");
        }
        catch (SocketException ex)
        {
            return new PortCheckResult(host, port, serviceName, false, $"Відхилено: {ex.SocketErrorCode}");
        }
    }
}

public static class PortCheckDemo
{
    public static async Task Main()
    {
        var validator = new FirewallPortValidator(TimeSpan.FromSeconds(2));

        // Типові порти, критичні для мережевого моніторингу
        var checks = new (string Host, int Port, string Service)[]
        {
            ("device-01.corp.local", 161, "SNMP"),
            ("device-01.corp.local", 22, "SSH"),
            ("device-01.corp.local", 514, "Syslog (UDP, ілюстративно через TCP-порт для демо)"),
            ("device-01.corp.local", 135, "WMI (RPC endpoint mapper)"),
        };

        Console.WriteLine("=== Перевірка доступності моніторингових портів через мережу ===\n");

        foreach (var (hostName, port, service) in checks)
        {
            var result = await validator.CheckPortAsync(hostName, port, service);
            var icon = result.IsReachable ? "✅" : "❌";
            Console.WriteLine($"{icon} {result.Host}:{result.Port,-5} [{service,-30}] -> {(result.IsReachable ? "ДОСТУПНО" : "НЕДОСТУПНО")} ({result.Details})");
        }

        Console.WriteLine("\nВисновок: якщо порт локально відкритий на пристрої, але недоступний звідси —");
        Console.WriteLine("перевірте firewall/ACL на маршруті та правила NAT/port-forwarding, а не сам сервіс моніторингу.");
    }
}
```

**Приклад консольного виводу (у реальному середовищі, де 161 та 22 відкриті, а 514 і 135 заблоковано firewall):**

```

✅ device-01.corp.local:161   [SNMP                          ] -> ДОСТУПНО (З'єднання встановлено успішно)
✅ device-01.corp.local:22    [SSH                           ] -> ДОСТУПНО (З'єднання встановлено успішно)
❌ device-01.corp.local:514   [Syslog (UDP, ілюстративно через TCP-порт для демо)] -> НЕДОСТУПНО (Таймаут (2с) — ймовірно заблоковано firewall/ACL)
❌ device-01.corp.local:135   [WMI (RPC endpoint mapper)     ] -> НЕДОСТУПНО (Таймаут (2с) — ймовірно заблоковано firewall/ACL)

Висновок: якщо порт локально відкритий на пристрої, але недоступний звідси —
перевірте firewall/ACL на маршруті та правила NAT/port-forwarding, а не сам сервіс моніторингу.
```

> **Примітка:** SNMP (161) та Syslog (514) реально працюють через **UDP**, а не TCP — `TcpClient` тут використано лише для ілюстрації логіки перевірки доступності; для UDP-портів на практиці використовують інші техніки (напр. надсилання SNMP GET-запиту й очікування відповіді, або `UdpClient` з таймаутом).

## Реальний сценарій: чому це важливо для мережевого моніторингу

Для компанії, що виробляє продукти мережевого моніторингу й управління (як SolarWinds з Orion, NCM та іншими рішеннями), теми firewall/ACL/NAT/VPN — це не абстрактна теорія, а **щоденна практична реальність підтримки клієнтів**.

**Чому це критично:**

- Сервер моніторингу (poller) повинен **діставатися** до кожного пристрою в мережі через конкретні протоколи й порти: **SNMP (UDP 161 для опитування, UDP 162 для trap-повідомлень)**, **Syslog (UDP 514)**, **WMI (TCP 135 + динамічний діапазон портів для RPC)**, **ICMP** (для базового ping-моніторингу доступності).
- **Величезна частка реальних тікетів підтримки** на кшталт "моніторинг не бачить пристрій" чи "SNMP timeout" **не є проблемою самого моніторингового ПЗ** — вони спричинені тим, що десь на шляху між сервером моніторингу і пристроєм firewall або ACL блокує саме один із цих необхідних портів/протоколів. Досвідчений інженер підтримки завжди перевіряє мережевий шлях **до того**, як шукати баг у самому продукті.
- **NAT ускладнює моніторинг пристроїв за NAT-шлюзом**: якщо кілька внутрішніх пристроїв ховаються за одним NAT-шлюзом (наприклад, ціла віддалена філія виходить в інтернет через одну публічну IP), сервер моніторингу, розташований зовні, **може бачити лише публічну адресу NAT-пристрою**, а не кожен внутрішній хост окремо — якщо тільки для кожного пристрою явно не налаштовано static NAT / port-forwarding з унікальним зовнішнім портом на кожен внутрішній пристрій. Це фізичне обмеження: NAT приховує внутрішню топологію за дизайном.
- Саме тому інструменти моніторингу часто розгортаються за **архітектурою розподілених агентів/пулерів**: наприклад, **Additional Polling Engines (додаткові сервери опитування)** або **Agents** у SolarWinds, які встановлюються **безпосередньо всередині** віддаленої мережі чи сайту, підключеного через VPN. Це дозволяє обійти саме ті бар'єри firewall/NAT/VPN, які б інакше заблокували єдиний центральний сервер моніторингу від прямого доступу до пристроїв у віддаленому сегменті: локальний агент опитує пристрої **зсередини** їхньої власної мережі (де жодних firewall-обмежень немає), а потім передає вже зібрані дані центральному серверу через один консолідований, заздалегідь узгоджений канал (часто теж захищений — HTTPS чи VPN).

Розуміння цього ланцюжка — "де саме в мережі трафік моніторингу може бути заблокований і чому" — є однією з ключових практичних компетенцій для роботи в компанії, що будує мережеве програмне забезпечення.

## Поширені проблеми та діагностика

| Симптом | Ймовірна причина | Що перевірити |
|---|---|---|
| Моніторинг раптово перестав бачити пристрій | Хтось нещодавно змінив ACL/firewall правило на мережевому обладнанні (типова причина — planned/unplanned зміна конфігурації) | Історія змін конфігурації обладнання (change log), нещодавні деплойменти на маршрутизаторах/firewall |
| SNMP timeout лише для одного сайту (інші сайти працюють нормально) | Трафік до цього конкретного сайту блокується firewall/ACL на маршруті, а не проблема самого пристрою чи агента SNMP | `traceroute`/`tracert` до пристрою, порівняння ACL на маршрутизаторах саме на цьому сегменті |
| Порт відкритий локально на пристрої, але недоступний ззовні | NAT/port-forwarding не налаштовано (або налаштовано на інший внутрішній порт/хост) | Конфігурація NAT/port-forwarding на прикордонному маршрутизаторі/firewall |
| VPN-тунель піднятий (UP), але трафік через нього не йде | Тунель встановлено успішно, але ACL чи маршрутизація **всередині** тунелю блокують конкретний трафік — проблема не в самому VPN | ACL/routing-таблиці по обидва боки тунелю, а не лише статус самого VPN-з'єднання |
| Моніторинг бачить пристрій, але лише частково (напр. ping працює, SNMP — ні) | Різні протоколи можуть мати різні правила ACL/firewall — ICMP дозволено, а UDP 161 — ні | Порівняти правила окремо для кожного протоколу/порту, а не перевіряти "мережу загалом" |

**Корисні інструменти для діагностики:**

- **`Test-NetConnection`** (PowerShell) або класичний **`telnet host port`** — перевірка, чи відкритий конкретний TCP-порт з даної машини.
- **`show access-lists`** (у контексті Cisco IOS) — перегляд активних ACL на маршрутизаторі/комутаторі, включно з лічильниками збігів (hit counters), що показують, які правила реально спрацьовують.
- **`traceroute` / `tracert`** — допомагає визначити, **на якому саме хопі (hop)** трафік перестає проходити, звужуючи пошук до конкретного пристрою на шляху.
- **Перевірка NAT-таблиці / conntrack** на прикордонному пристрої — щоб побачити, чи взагалі створюється трансляція для конкретного з'єднання.

## Питання та відповіді для співбесіди

**1. Чим stateful firewall відрізняється від stateless?**
Stateless (packet-filtering) firewall перевіряє кожен пакет окремо, лише за заголовками, без пам'яті про попередні пакети. Stateful firewall веде таблицю активних з'єднань (connection table) і розуміє контекст — наприклад, що вхідний пакет є легітимною відповіддю на раніше дозволений вихідний запит, навіть без окремого явного правила для цього напрямку.

**2. Що таке ACL і чим стандартний ACL відрізняється від розширеного?**
ACL (Access Control List) — список правил permit/deny, який застосовується на інтерфейсі маршрутизатора чи комутатора. Standard ACL фільтрує лише за source IP-адресою (груба фільтрація). Extended ACL додатково враховує destination IP, порт і протокол, забезпечуючи точну (fine-grained) фільтрацію.

**3. Поясни, як працює PAT/NAT overload.**
PAT дозволяє багатьом внутрішнім хостам з приватними IP-адресами виходити в інтернет через одну публічну IP-адресу. Розрізнення сесій відбувається за номером порту: NAT-пристрій веде таблицю відповідностей (внутрішня IP:порт ↔ публічна IP:унікальний порт) і використовує цю таблицю для правильної зворотної трансляції відповідей.

**4. Чому порядок правил у firewall/ACL критично важливий?**
Правила обробляються послідовно, і застосовується принцип "перший збіг виграє" (first match wins) — щойно пакет підпадає під якесь правило, подальші правила не перевіряються. Якщо широке правило "allow" стоїть вище за вузьке "deny", специфічна заборона ніколи не спрацює, бо трафік буде дозволено раніше. Тому специфічні правила завжди повинні йти вище загальних.

**5. Чим site-to-site VPN відрізняється від remote-access VPN?**
Site-to-site VPN створює постійний тунель між двома мережами/офісами (маршрутизатор-маршрутизатор), зазвичай через IPsec. Remote-access VPN дозволяє окремому віддаленому користувачу підключатися до корпоративної мережі за допомогою VPN-клієнта, встановлюючи з'єднання сесійно.

**6. Що таке IPsec? Назви основні компоненти (AH/ESP).**
IPsec — набір протоколів для захисту IP-трафіку на мережевому рівні. AH (Authentication Header) забезпечує автентифікацію й цілісність, але не шифрує дані. ESP (Encapsulating Security Payload) забезпечує і шифрування, і автентифікацію — саме тому ESP використовується в переважній більшості реальних VPN.

**7. Чим відрізняються tunnel mode і transport mode в IPsec?**
Transport mode шифрує лише payload пакета, залишаючи оригінальний IP-заголовок відкритим — використовується для захисту з'єднання між двома кінцевими хостами напряму. Tunnel mode шифрує весь оригінальний пакет разом із заголовком і інкапсулює його в новий пакет — використовується в site-to-site VPN між шлюзами.

**8. Чому SSL VPN часто простіше проходить через фаєрволи, ніж IPsec?**
SSL VPN працює через стандартний HTTPS-порт (TCP 443), який майже завжди відкритий на будь-якому firewall, оскільки це звичайний веб-трафік. IPsec потребує окремих протоколів (ESP, IKE на UDP 500/4500), які часто явно блокуються суворими firewall-політиками, особливо в готелях, кафе чи публічних мережах.

**9. Наведи приклад, як NAT ускладнює діагностику мережі.**
Із зовнішньої точки зору видно лише публічну IP-адресу NAT-пристрою, а не реальну внутрішню адресу джерела — traceroute чи логи показуватимуть "хтось за 203.0.113.10", не вказуючи конкретний внутрішній хост. Це ускладнює end-to-end моніторинг та ідентифікацію конкретного пристрою за NAT без додаткового налаштування (наприклад, static NAT для кожного хоста).

**10. Що таке "NAT traversal" проблема? Наведи приклад.**
Це проблема, коли протокол передає IP-адреси/порти у своєму payload (тілі повідомлення), а не лише в заголовках пакета. NAT-пристрій, що не "розуміє" цей протокол, не підмінить адресу всередині payload. Класичний приклад — FTP у active mode, де клієнт передає серверу свою IP-адресу в команді PORT для зворотного з'єднання даних; якщо ця адреса приватна, зовнішній сервер не зможе з'єднатися назад.

**11. Що таке "implicit deny all" у firewall/ACL?**
Це неявне правило, яке автоматично застосовується в кінці списку правил: усе, що не було явно дозволено жодним попереднім правилом, автоматично блокується. Це принцип "безпека за замовчуванням" (secure by default, deny-by-default).

**12. Чим Next-Generation Firewall (NGFW) відрізняється від звичайного stateful firewall?**
NGFW додає до звичайної stateful-фільтрації глибшу функціональність: систему запобігання вторгненням (IPS), Deep Packet Inspection, розпізнавання конкретних застосунків на рівні L7 (наприклад, розрізняє Skype-трафік від звичайного HTTPS навіть на порту 443), а також інтеграцію з репутаційними базами URL/IP.

**13. Чому inbound і outbound ACL на одному інтерфейсі поводяться по-різному?**
Inbound ACL перевіряє пакети одразу при вході в інтерфейс, до прийняття рішення про маршрутизацію — це ефективніше для швидкого відкидання небажаного трафіку. Outbound ACL перевіряє пакети вже після рішення про маршрутизацію, безпосередньо перед виходом через інтерфейс.

**14. Як NAT впливає на роботу інструментів мережевого моніторингу?**
Якщо кілька внутрішніх пристроїв ховаються за одним NAT-шлюзом, зовнішній сервер моніторингу бачить лише публічну адресу NAT-пристрою, а не кожен внутрішній хост окремо — якщо для кожного пристрою явно не налаштовано static NAT чи port-forwarding. Це часто вирішується розгортанням локального агента/полінг-двигуна всередині віддаленої мережі, який опитує пристрої зсередини (де немає NAT-обмежень) і передає зібрані дані центральному серверу одним консолідованим каналом.

## Підсумок

### Firewall — типи

| Тип | Рівень | Ключова ознака |
|---|---|---|
| Packet-filtering | L3/L4 | Кожен пакет окремо, без контексту з'єднання |
| Stateful inspection | L3/L4 | Таблиця станів з'єднань — сучасний базовий стандарт |
| Application-layer/Proxy | L7 | Розуміє вміст протоколу застосунку |
| NGFW | L3–L7 | + IPS, DPI, розпізнавання застосунків |

### NAT — типи

| Тип | Механізм |
|---|---|
| Static NAT | 1:1 фіксоване відображення (публікація сервера назовні) |
| Dynamic NAT | Пул публічних IP, динамічний розподіл |
| PAT / NAT Overload | Багато-до-одного через розрізнення портами (найпоширеніше) |

### VPN — типи

| Тип | Застосування |
|---|---|
| Site-to-site (IPsec, tunnel mode) | Постійне з'єднання між офісами/мережами |
| Remote-access (IPsec client або SSL VPN) | Окремий віддалений користувач ↔ корпоративна мережа |
| SSL/TLS VPN | Простіший, проходить через TCP 443, зручний для обмежувальних мереж |

### Порти, критичні для мережевого моніторингу (мають бути відкриті через firewall/ACL)

| Порт | Протокол | Призначення |
|---|---|---|
| UDP 161 | SNMP | Опитування пристроїв (polling) |
| UDP 162 | SNMP Trap | Асинхронні повідомлення від пристроїв |
| UDP 514 | Syslog | Прийом лог-повідомлень |
| TCP 135 + динамічний діапазон | WMI/RPC | Моніторинг Windows-хостів |
| — | ICMP | Базова перевірка доступності (ping) |
| TCP 80 / 443 | HTTP/HTTPS | Веб-інтерфейси управління, API-запити |
| TCP 22 | SSH | Віддалений доступ до CLI мережевих пристроїв |

**Ключова думка для співбесіди:** переважна більшість реальних інцидентів "моніторинг не працює" — це не баг у моніторинговому ПЗ, а наслідок того, що десь на мережевому шляху firewall, ACL чи NAT блокує один із перелічених вище портів/протоколів. Уміння швидко локалізувати, **на якому саме сегменті мережі** відбувається блокування — це базова, але критично важлива навичка для роботи з продуктами мережевого управління.
