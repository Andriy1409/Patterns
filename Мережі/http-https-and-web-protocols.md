## 1. Що таке HTTP і як він працює

**HTTP (HyperText Transfer Protocol)** — це протокол прикладного рівня (Application Layer), який визначає, як клієнт (зазвичай браузер, але це може бути будь-яка програма — наприклад, агент моніторингу) і сервер обмінюються повідомленнями через мережу. HTTP — це **протокол запит-відповідь (request-response)**: клієнт завжди ініціює обмін, надсилаючи запит, а сервер завжди відповідає — сервер сам ніколи не "дзвонить" клієнту першим (принаймні в класичній моделі HTTP/1.1; HTTP/2 Server Push і WebSocket — окремі історії).

HTTP історично працює поверх **TCP** (надійного транспорту з гарантованою доставкою й порядком байтів — це критично, бо HTML-сторінка чи JSON-відповідь, у якій переплутані байти або яка загубила частину, просто марна). HTTP/3 змінює це, використовуючи QUIC поверх UDP (детальніше в розділі 4), але ідея "надійної доставки повідомлення" залишається — просто реалізується на іншому рівні.

### Ключові характеристики HTTP

- **Текстовий протокол (у HTTP/1.1)** — запити й відповіді можна прочитати "очима" у сирому вигляді (у HTTP/2/3 формат бінарний, але концептуальна модель — заголовки + тіло — та сама).
- **Без стану (stateless)** — сервер за замовчуванням **не пам'ятає** нічого про попередній запит того ж клієнта. Кожен HTTP-запит обробляється незалежно, ніби це перший і єдиний запит у житті сервера.
- **Модель "запит-відповідь"** — клієнт формулює намір (метод + ресурс + додаткові дані), сервер повертає результат (код стану + дані).
- **Розширюваний через заголовки (headers)** — метадані про запит/відповідь (тип вмісту, розмір, авторизація, кешування тощо) передаються окремо від "корисного навантаження" (body).

### Аналогія з реального життя

Уявіть **прилавок фастфуду**. Ви підходите і кажете: *"Один бургер, без цибулі, з собою"*. Касир обробляє саме цей запит, дає вам чек (код підтвердження) і бургер (дані). А тепер найважливіше: **касир не пам'ятає, що ви щойно тут стояли**. Якщо через хвилину ви підійдете знову і скажете просто "те саме, що і минулого разу" — касир не зрозуміє, про що йдеться, бо попередня взаємодія **не зберігається жодним чином**. Вам доведеться повторити повний запит з усіма деталями заново (або пред'явити якийсь доказ — наприклад, номерок/чек — щоб касир "згадав" контекст).

Це і є **statelessness** HTTP: кожен запит містить у собі всю інформацію, необхідну серверу для його обробки. Якщо потрібно "пам'ятати" щось між запитами (що ви залогінені, що у вас є товари в кошику) — це не властивість самого HTTP, а надбудова поверх нього: **cookies**, токени авторизації (`Authorization` header), або session ID, які клієнт сумлінно надсилає **у кожному новому запиті**, щоб сервер міг "згадати" контекст, звірившись зі своєю базою даних чи сховищем сесій.

Саме statelessness — одна з причин, чому HTTP так добре масштабується: сервер не зобов'язаний тримати в пам'яті стан мільйонів клієнтів, і будь-який із багатьох однакових серверів (за балансувальником навантаження) може обробити будь-який запит, не потребуючи "спільної пам'яті" про історію взаємодії з конкретним клієнтом.

## 2. Структура HTTP-запиту та відповіді

### 2.1 Сирий HTTP-запит

```
GET /api/devices/42 HTTP/1.1
Host: api.example-monitoring.com
User-Agent: OrionAgent/2024.1
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Connection: keep-alive

```

А ось приклад запиту з тілом (POST):

```
POST /api/devices HTTP/1.1
Host: api.example-monitoring.com
Content-Type: application/json
Content-Length: 58
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

{"name":"Router-Core-01","ip":"10.0.0.1","type":"router"}
```

Структура запиту складається з трьох частин:

1. **Стартовий рядок (Request Line):** `МЕТОД ШЛЯХ ВЕРСІЯ` — наприклад, `GET /api/devices/42 HTTP/1.1`.
2. **Заголовки (Headers):** пари `Ключ: значення`, кожна на своєму рядку, до порожнього рядка.
3. **Порожній рядок** — розділяє заголовки й тіло (обов'язковий навіть якщо тіла немає).
4. **Тіло (Body)** — необов'язкове; є в `POST`/`PUT`/`PATCH`, зазвичай відсутнє в `GET`/`DELETE`.

### 2.2 Сира HTTP-відповідь

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 87
Cache-Control: no-cache
Date: Sun, 23 Aug 2026 10:15:32 GMT
Server: nginx/1.25.3

{"id":42,"name":"Router-Core-01","ip":"10.0.0.1","status":"up","lastPolled":"2026-08-23T10:15:00Z"}
```

Структура відповіді дзеркальна:

1. **Статусний рядок (Status Line):** `ВЕРСІЯ КОД ТЕКСТ` — наприклад, `HTTP/1.1 200 OK`.
2. **Заголовки** — метадані відповіді.
3. **Порожній рядок.**
4. **Тіло** — власне дані відповіді (HTML, JSON, зображення, файл тощо).

### 2.3 HTTP-методи

| Метод | Призначення | Safe? | Idempotent? | Має тіло запиту? |
|---|---|---|---|---|
| **GET** | Отримати ресурс (Read) | ✅ Так | ✅ Так | Зазвичай ні |
| **POST** | Створити новий ресурс / виконати дію (Create) | ❌ Ні | ❌ Ні | ✅ Так |
| **PUT** | Повністю замінити ресурс (Update — повна заміна) | ❌ Ні | ✅ Так | ✅ Так |
| **PATCH** | Частково оновити ресурс (Update — часткова зміна) | ❌ Ні | ❌ Ні (в загальному випадку) | ✅ Так |
| **DELETE** | Видалити ресурс (Delete) | ❌ Ні | ✅ Так | Зазвичай ні |
| **HEAD** | Як GET, але повернути лише заголовки, без тіла | ✅ Так | ✅ Так | Ні |
| **OPTIONS** | Дізнатись, які методи/можливості підтримує ресурс (часто — CORS preflight) | ✅ Так | ✅ Так | Зазвичай ні |

**Пояснення термінів:**

- **Safe (безпечний метод)** — не змінює стан сервера (тільки читання). GET, HEAD, OPTIONS вважаються safe — їх можна викликати скільки завгодно разів без побічних ефектів (у теорії; на практиці погано спроектований сервер може порушити цю угоду, але це вважається помилкою дизайну).
- **Idempotent (ідемпотентний)** — повторний виклик з тими самими параметрами дає **той самий результат на сервері**, скільки б разів його не викликати. `PUT /users/5 {"name":"Bob"}` викликаний 1 раз чи 10 разів — стан користувача 5 однаковий. А от `POST /users {"name":"Bob"}`, викликаний 10 разів, створить (у типовому дизайні) 10 різних користувачів — це **не** ідемпотентно. `DELETE /users/5` ідемпотентний: перший виклик видаляє, кожен наступний — це вже "нема що видаляти" (типово повертає 404, але **стан сервера** — "користувача 5 не існує" — не змінюється від повторних викликів).
- **PATCH** формально не гарантує ідемпотентності, бо часто описує "різницю" чи операцію (наприклад, "збільшити лічильник на 1") — повторний виклик такої операції змінить результат щоразу. Якщо ж PATCH описує "встановити поле X у значення Y" — на практиці він може бути ідемпотентним, але це не гарантується специфікацією як для PUT.

### 2.4 Найважливіші HTTP-заголовки

| Заголовок | Напрямок | Призначення |
|---|---|---|
| **Host** | Запит | Домен, до якого звертається клієнт (обов'язковий у HTTP/1.1; дозволяє одному IP/серверу обслуговувати кілька доменів — virtual hosting) |
| **Content-Type** | Обидва | MIME-тип тіла (`application/json`, `text/html`, `multipart/form-data` тощо) |
| **Content-Length** | Обидва | Розмір тіла в байтах — потрібен, щоб отримувач знав, де тіло закінчується |
| **Authorization** | Запит | Дані для автентифікації (`Bearer <token>`, `Basic <base64>` тощо) |
| **User-Agent** | Запит | Ідентифікує клієнтське ПЗ (браузер, бот, агент моніторингу) |
| **Cache-Control** | Обидва | Директиви кешування (`no-cache`, `max-age=3600`, `no-store`) |
| **Cookie** | Запит | Клієнт надсилає раніше збережені пари ключ-значення серверу |
| **Set-Cookie** | Відповідь | Сервер просить клієнта зберегти пару ключ-значення і надсилати її в наступних запитах |
| **Accept** | Запит | Які формати відповіді клієнт готовий прийняти (`application/json`, `text/html`) |
| **Location** | Відповідь | Використовується з 3xx — куди перенаправити клієнта |
| **ETag** | Відповідь | "Відбиток" версії ресурсу для умовних запитів і кешування |

## 3. Коди стану HTTP (Status Codes)

Коди стану — це трицифрове число в статусному рядку відповіді, перша цифра якого визначає **клас**:

| Клас | Значення |
|---|---|
| **1xx** | Informational — проміжна відповідь, обробка триває |
| **2xx** | Success — запит успішно оброблено |
| **3xx** | Redirection — потрібна додаткова дія (зазвичай перехід за іншою URL) |
| **4xx** | Client Error — помилка з боку клієнта (неправильний запит, немає прав тощо) |
| **5xx** | Server Error — помилка з боку сервера (навіть якщо запит клієнта був ідеальний) |

### 3.1 Найважливіші коди для співбесіди

| Код | Назва | Пояснення |
|---|---|---|
| **200** | OK | Стандартна успішна відповідь із тілом (типово для GET) |
| **201** | Created | Ресурс успішно створено (типово для POST); часто разом із заголовком `Location`, що вказує URL нового ресурсу |
| **204** | No Content | Успіх, але тіла відповіді немає (типово для DELETE або PUT, коли повертати нічого) |
| **301** | Moved Permanently | Ресурс **назавжди** переїхав на нову URL; клієнти/пошукові системи повинні оновити посилання; метод запиту іноді змінюється на GET при редиректі (історична неоднозначність) |
| **302** | Found | Ресурс **тимчасово** перебуває за іншою URL; історично також міг змінювати метод на GET — джерело плутанини десятиліттями |
| **307** | Temporary Redirect | Те саме, що 302, але **гарантовано зберігає** оригінальний метод і тіло запиту (якщо був POST — редирект теж піде як POST) |
| **308** | Permanent Redirect | Те саме, що 301, але так само **гарантовано зберігає** метод і тіло |
| **400** | Bad Request | Сервер не може розібрати/зрозуміти запит (некоректний синтаксис, невалідний JSON тощо) |
| **401** | Unauthorized | Клієнт **не автентифікований** — сервер не знає, хто ви (відсутній/невалідний токен чи логін) |
| **403** | Forbidden | Клієнт **автентифікований**, сервер знає, хто ви, але **у вас немає прав** на цю дію/ресурс |
| **404** | Not Found | Ресурс за такою URL не існує |
| **409** | Conflict | Запит суперечить поточному стану ресурсу (наприклад, одночасне редагування, дублікат унікального ключа) |
| **429** | Too Many Requests | Перевищено ліміт запитів (rate limiting); часто разом із заголовком `Retry-After` |
| **500** | Internal Server Error | Загальна, "неопрацьована" помилка на сервері (виняток, необроблений баг) |
| **502** | Bad Gateway | Сервер, що виступає проксі/шлюзом, отримав **невалідну відповідь від upstream/backend-сервера** |
| **503** | Service Unavailable | Сервер тимчасово не може обробити запит (перевантаження, планове обслуговування) |
| **504** | Gateway Timeout | Сервер-проксі/шлюз **не дочекався відповіді** від upstream-сервера вчасно |

### 3.2 401 vs 403 — класичне питання на співбесіді

Це питання ставлять майже завжди, бо на практиці ці коди часто плутають:

- **401 Unauthorized = "Я не знаю, хто ти"** (насправді назва трохи оманлива — правильніше було б назвати "Unauthenticated"). Сервер не зміг ідентифікувати клієнта: токен відсутній, прострочений, невалідний, або логін/пароль неправильні. **Правильна дія клієнта:** автентифікуватись (залогінитись, оновити токен) і спробувати знову.
- **403 Forbidden = "Я знаю, хто ти, але тобі не можна"**. Сервер успішно ідентифікував клієнта (автентифікація пройшла), але в системі прав доступу (авторизації) для цього користувача **немає дозволу** на запитану дію чи ресурс. **Правильна дія клієнта:** повторна спроба з тим самим токеном нічого не змінить — потрібні інші, вищі права (звернутись до адміністратора).

Проста мнемоніка: **401 — "хто ти?" (автентифікація), 403 — "тобі не можна" (авторизація).** Автентифікація (authentication) — це підтвердження особи; авторизація (authorization) — це перевірка прав цієї вже підтвердженої особи.

### 3.3 502 vs 503 vs 504 — критично для моніторингу веб-застосунків

Ці три коди особливо важливі для компанії, що робить продукти моніторингу (наприклад, SolarWinds SAM), тому що вони описують **різні точки відмови** в ланцюжку "клієнт → reverse proxy/load balancer → backend-сервер":

- **502 Bad Gateway** — проміжний сервер (наприклад, nginx, що виступає reverse proxy перед вашим застосунком) **зв'язався** з backend-сервером, але отримав від нього **невалидну або зіпсовану відповідь** (або backend раптово розірвав з'єднання, або backend взагалі не слухає порт, на який намагається достукатись проксі). Часто означає, що **сам застосунок впав або не запущений** за проксі.
- **503 Service Unavailable** — сервер (або проксі) **свідомо** відповідає "я зараз не можу обробити запит" — типово через перевантаження (вичерпано пул з'єднань/потоків), планове технічне обслуговування, або спрацював circuit breaker/health check, що позначив backend як нездоровий. На відміну від 502, тут сервер **живий і відповідає**, просто відмовляється обробляти запит зараз.
- **504 Gateway Timeout** — проміжний сервер **достукався** до backend, backend **прийняв** з'єднання, але **не відповів вчасно** (перевищено таймаут очікування). Це часто вказує на повільний backend (наприклад, застряглий довгий SQL-запит, дедлок, вичерпання ресурсів), а не на його повну відсутність.

Практична різниця для діагностики: **502** → перевірити, чи взагалі запущений і слухає backend-процес; **503** → перевірити навантаження/пул з'єднань і health-check-статус; **504** → перевірити продуктивність backend (повільні запити, дедлоки, зависання) і значення таймауту на проксі.

## 4. HTTP/1.1 vs HTTP/2 vs HTTP/3 — коротко

### HTTP/1.1 (1997, RFC 2616 → RFC 7230-7235)

Текстовий протокол. Кожне TCP-з'єднання в принципі може обробляти кілька запитів послідовно завдяки **persistent connections** (`Connection: keep-alive`), уникаючи накладних витрат на нове TCP-рукостискання для кожного запиту. Є можливість **pipelining** (надсилання кількох запитів підряд без очікування відповіді на кожен), але вона практично не використовується через **Head-of-Line (HoL) Blocking на рівні HTTP**: відповіді повинні прийти **в тому самому порядку**, у якому були надіслані запити, тож один повільний запит блокує чергу відповідей позаду себе. Через це браузери традиційно відкривають **кілька паралельних TCP-з'єднань** до одного хоста (типово 6), щоб обійти це обмеження — ціною додаткових накладних витрат (нові TCP+TLS-рукостискання).

### HTTP/2 (2015, RFC 7540)

Головні нововведення:

- **Бінарний фреймінг (binary framing)** замість тексту — повідомлення розбиваються на бінарні фрейми, що ефективніше парсити та які дозволяють мультиплексування.
- **Мультиплексування потоків (multiplexing)** — кілька незалежних "потоків" (streams) запит/відповідь можуть передаватись **одночасно через одне TCP-з'єднання**, перемежовуючись фреймами. Це вирішує HoL blocking **на рівні HTTP**: повільна відповідь на потік №1 більше не блокує потік №2 в межах того самого з'єднання.
- **Стиснення заголовків (HPACK)** — заголовки часто повторюються майже незмінними між запитами (Cookie, User-Agent тощо); HPACK використовує статичні/динамічні таблиці й хаффман-кодування, суттєво зменшуючи об'єм переданих метаданих.
- **Server Push** — сервер може проактивно надіслати ресурси, які клієнт ще не запитував, але, ймовірно, скоро запросить (наприклад, CSS/JS разом з HTML) — на практиці ця можливість не набула широкого застосування і вилучена з Chrome.

Важливо: HTTP/2 усе ще працює **поверх одного TCP-з'єднання**, тож HoL blocking **на рівні TCP** (втрата одного TCP-сегмента блокує доставку **всіх** байтів по цьому з'єднанню, доки він не буде повторно переданий — незалежно від того, до якого HTTP/2-потоку належать наступні байти) **залишається проблемою**.

### HTTP/3 (2022, RFC 9114)

Головна відмінність — HTTP/3 працює **поверх QUIC** (RFC 9000), який, у свою чергу, працює **поверх UDP**, а не TCP:

- **QUIC реалізує власну надійність і мультиплексування на рівні транспорту**, а не покладається на TCP. Кожен потік у QUIC незалежний **навіть при втраті пакетів** — втрата пакета одного потоку більше не блокує інші потоки того ж з'єднання (вирішується HoL blocking **на рівні транспорту**, а не лише HTTP, як у HTTP/2).
- **Швидше встановлення з'єднання** — QUIC поєднує транспортне й TLS-рукостискання в один раунд обміну (а при повторному підключенні до вже відомого сервера — навіть 0-RTT), тоді як TCP+TLS 1.2 традиційно потребували кількох послідовних раундів (TCP handshake, потім TLS handshake).
- **Вбудоване шифрування** — QUIC шифрує практично все, включно з метаданими транспортного рівня, які в TCP передавались відкритим текстом.

### Порівняльна таблиця

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| **Транспорт** | TCP | TCP | QUIC (поверх UDP) |
| **Формат** | Текстовий | Бінарний (фрейми) | Бінарний (фрейми QUIC) |
| **Мультиплексування** | Немає (або через кілька TCP-з'єднань) | Так, у межах одного TCP-з'єднання | Так, незалежні потоки на рівні транспорту |
| **HoL Blocking** | Так (на рівні HTTP) | Вирішено на рівні HTTP, залишається на рівні TCP | Вирішено і на рівні HTTP, і на рівні транспорту |
| **Стиснення заголовків** | Немає | HPACK | QPACK (адаптація HPACK під QUIC) |
| **Встановлення з'єднання** | TCP + TLS handshake окремо | TCP + TLS handshake окремо | Об'єднане (1-RTT, або 0-RTT при повторному підключенні) |
| **Типове застосування зараз** | Досі широко (легасі-системи, прості API) | Стандарт для більшості сучасних вебсайтів | Активно зростає (Google, Cloudflare, великі CDN); підтримка браузерами вже широка |

## 5. HTTPS та TLS

### 5.1 Навіщо потрібен HTTPS

**HTTPS = HTTP, переданий через TLS-зашифроване з'єднання.** Сам HTTP не має жодного захисту: усе, що передається (включно з паролями, токенами, персональними даними), передається відкритим текстом і може бути перехоплене й прочитане (або навіть змінене) будь-ким на шляху пакета — від Wi-Fi-точки в кав'ярні до проміжного маршрутизатора провайдера.

TLS (Transport Layer Security — сучасний наступник SSL, який вважається застарілим і небезпечним) додає три властивості:

- 🔒 **Конфіденційність (confidentiality)** — дані шифруються, тож навіть якщо їх перехопили, прочитати без ключа неможливо.
- 🔒 **Цілісність (integrity)** — будь-яка зміна даних під час передачі виявляється (через MAC/AEAD-механізми), тож підмінити вміст непомітно неможливо.
- 🔒 **Автентифікація сервера (authentication)** — клієнт може бути впевнений, що спілкується саме з тим сервером, за який той себе видає (через сертифікат, підписаний довіреним центром сертифікації), а не з зловмисником, що видає себе за нього (класична атака "людина посередині", Man-in-the-Middle).

### 5.2 TLS Handshake — покроково

Мета рукостискання — узгодити спільний **симетричний сеансовий ключ**, використовуючи асиметричну криптографію лише для безпечного початкового обміну.

```
   Клієнт                                              Сервер
     |                                                    |
     |------------------ ClientHello -------------------->|
     |   (підтримувані версії TLS, набори шифрів,         |
     |    випадкове число client_random, SNI-ім'я хоста)  |
     |                                                    |
     |<--------- ServerHello + Сертифікат ----------------|
     |   (обраний набір шифрів, випадкове число           |
     |    server_random, сертифікат сервера з публічним   |
     |    ключем, підписаний CA)                          |
     |                                                    |
     |------------- Обмін ключами (Key Exchange) --------->|
     |   Клієнт перевіряє сертифікат (ланцюг довіри,       |
     |   термін дії, збіг hostname), потім за допомогою    |
     |   публічного ключа сервера (або через ECDHE)        |
     |   узгоджується спільний "premaster secret"          |
     |                                                    |
     |<====== Обидві сторони обчислюють ======>            |
     |     однаковий симетричний сеансовий ключ            |
     |     (з premaster secret + випадкові числа)          |
     |                                                    |
     |------------------ Finished ------------------------>|
     |<----------------- Finished -------------------------|
     |   (перше повідомлення, зашифроване новим            |
     |    симетричним ключем — підтвердження, що обидві    |
     |    сторони отримали однаковий ключ)                 |
     |                                                    |
     |        З'ЄДНАННЯ ЗАХИЩЕНЕ, ДАНІ ШИФРУЮТЬСЯ           |
     |           СИМЕТРИЧНИМ КЛЮЧЕМ (напр. AES)             |
```

Спрощені кроки (деталі відрізняються між TLS 1.2 і сучасним TLS 1.3, який скоротив кількість раундів обміну, але суть та сама):

1. **ClientHello** — клієнт надсилає список підтримуваних версій TLS, наборів шифрів (cipher suites), випадкове число, і, важливо, **SNI** (ім'я домену, до якого звертається — див. розділ 5.4).
2. **ServerHello + сертифікат** — сервер обирає версію протоколу й шифр із запропонованих клієнтом, надсилає своє випадкове число та **цифровий сертифікат**, що містить публічний ключ сервера.
3. **Перевірка сертифіката й обмін ключами** — клієнт перевіряє: чи підписаний сертифікат довіреним CA (ланцюг довіри), чи не прострочений, чи збігається домен у сертифікаті з тим, до якого клієнт звертається. Далі (сучасний підхід — ECDHE, Diffie-Hellman на еліптичних кривих) обидві сторони обмінюються даними, які дозволяють кожній стороні **незалежно обчислити той самий спільний секрет**, не передаючи його напряму в мережу.
4. **Обчислення сеансового ключа** — з отриманого спільного секрету (і випадкових чисел з кроків 1-2) обидві сторони незалежно виводять **однаковий симетричний ключ сесії**.
5. **Finished** — обидві сторони надсилають тестове повідомлення, зашифроване вже новим симетричним ключем, підтверджуючи, що рукостискання пройшло успішно й обидві сторони мають однаковий ключ.
6. Після цього **весь подальший обмін даними (сам HTTP-трафік) шифрується симетричним ключем** (наприклад, AES-256-GCM).

### 5.3 Чому гібридний підхід (асиметричне + симетричне шифрування)

Це питання про **"чому"** ставлять на співбесідах дуже часто:

- **Асиметрична криптографія (RSA, ECDHE)** використовує пару ключів (публічний/приватний) і не вимагає попереднього спільного секрету — саме тому вона придатна для **першого контакту** двох сторін, які раніше нічого спільного не мали. Але вона **обчислювально дорога й повільна** — застосовувати її до кожного байта великого обсягу даних (наприклад, відео чи великого JSON-відповіді) було б неприйнятно повільно і витратно за ресурсами CPU.
- **Симетрична криптографія (AES тощо)** використовує **один і той самий ключ** для шифрування й розшифрування, і працює **на порядки швидше** за асиметричну — вона чудово підходить для шифрування великих обсягів даних, але вимагає, щоб обидві сторони **вже мали** цей спільний ключ, а безпечно передати його заздалегідь через незахищений канал — саме та проблема, яку асиметрична криптографія й вирішує.

Тому TLS поєднує обидва підходи: **асиметрична криптографія використовується лише один раз на початку з'єднання**, щоб безпечно узгодити спільний симетричний ключ (без ризику, що зловмисник, який підслуховує канал, зможе його вирахувати), а весь **подальший, набагато більший за обсягом трафік** шифрується вже швидкою симетричною криптографією. Це класичний приклад **гібридної криптосистеми** — беремо найкраще з обох світів: безпеку встановлення з'єднання без попереднього спільного секрету від асиметричної частини, і швидкість масового шифрування від симетричної.

### 5.4 Сертифікати: що вони доводять

**Цифровий сертифікат (X.509)** — це, по суті, документ, що зв'язує **публічний ключ** із **доменним ім'ям (та іноді організацією)**, і цей зв'язок **засвідчений цифровим підписом довіреного Центру Сертифікації (CA — Certificate Authority)**.

- **Ланцюг довіри (chain of trust)**: сертифікат сайту зазвичай підписаний проміжним CA, чий сертифікат, у свою чергу, підписаний кореневим CA (root CA), чий сертифікат **вже попередньо довірений** операційною системою/браузером (вбудований у "довірене сховище"). Перевірка ланцюга — це перевірка кожного підпису вгору аж до кореня, якому клієнт довіряє апріорі.
- Сертифікат **не** доводить, що сайт "чесний" чи "безпечний" за змістом — він доводить лише, що **саме ця сторона** (яка володіє приватним ключем, що відповідає публічному в сертифікаті) справді контролює домен, зазначений у сертифікаті (при базовій Domain Validation).

**Що насправді означають типові помилки сертифіката** (дуже поширений реальний сценарій для продукту, що моніторить HTTPS-ендпоінти):

- **"Сертифікат прострочений" (certificate expired)** — поле `Not After` у сертифікаті вже в минулому. Сервер продовжує використовувати старий сертифікат, який CA вже не гарантує (навіть якщо технічно ключі не скомпрометовані). Браузери й HTTP-клієнти за замовчуванням відмовляються довіряти такому з'єднанню.
- **"Самопідписаний сертифікат" (self-signed)** — сертифікат підписаний не довіреним CA, а самим власником сайту (сам собі видав "довідку"). Це не обов'язково означає щось шкідливе (часто зустрічається у внутрішніх/тестових середовищах, локальних дашбордах пристроїв), але клієнт **не має способу криптографічно підтвердити**, що це справді той сервер, за якого він себе видає — довіра тут "сліпа".
- **"Невідповідність hostname" (hostname mismatch)** — домен, до якого звертається клієнт (наприклад, `app.example.com`), не збігається з доменом(ами), перерахованим(и) у полі сертифіката `Subject Alternative Name (SAN)`. Найчастіша причина на практиці — неправильно налаштований reverse proxy/load balancer, що видає "не той" сертифікат для конкретного піддомену, або сертифікат виданий тільки для `example.com`, а звертання йде на `www.example.com` (чи навпаки).

### 5.5 SNI (Server Name Indication)

Одна фізична IP-адреса нерідко обслуговує **безліч різних HTTPS-доменів** (наприклад, спільний хостинг чи CDN). Проблема: сервер повинен показати клієнту **правильний сертифікат для потрібного домену ще ДО того**, як почнеться шифрована частина з'єднання — але сам запит (з заголовком `Host`) передається лише **всередині** вже зашифрованого HTTP-трафіку, який іде **після** завершення рукостискання.

**SNI** вирішує цю проблему: клієнт додає ім'я домену **у відкритому вигляді прямо в ClientHello** (перше повідомлення рукостискання, до якого симетричне шифрування ще не застосовується). Отримавши ClientHello з SNI, сервер уже знає, **для якого саме домену** потрібно віддати сертифікат, і надсилає у відповідь саме потрібний. Без SNI кожен HTTPS-домен на спільному хостингу вимагав би окремої виділеної IP-адреси — саме SNI дозволив масштабувати HTTPS на мільйони доменів без вичерпання пулу IPv4-адрес.

## 6. REST API — основи

**REST (Representational State Transfer)** — це не протокол, а **архітектурний стиль** побудови веб-API, запропонований Роєм Філдінгом у 2000 році. REST будується поверх HTTP і спирається на кілька ключових ідей:

- **Ресурси, ідентифіковані URL** — усе, з чим працює API (пристрій, користувач, замовлення), є **ресурсом** з унікальною адресою: `/api/devices/42`, `/api/users/17/orders`.
- **Стандартні HTTP-методи відображаються на CRUD-операції:**

| HTTP-метод | CRUD-операція | Приклад |
|---|---|---|
| **GET** | Read (читання) | `GET /api/devices/42` — отримати дані про пристрій 42 |
| **POST** | Create (створення) | `POST /api/devices` — створити новий пристрій |
| **PUT / PATCH** | Update (оновлення) | `PUT /api/devices/42` — замінити дані пристрою; `PATCH /api/devices/42` — оновити лише частину полів |
| **DELETE** | Delete (видалення) | `DELETE /api/devices/42` — видалити пристрій |

- **Без стану (stateless)** — так само, як і базовий HTTP: кожен запит до REST API повинен містити всю інформацію, потрібну для його обробки (включно з даними автентифікації); сервер не зберігає "сесію" клієнта між запитами на своєму боці (у класичній REST-моделі).
- **Єдиний формат подання (representation)** — типово **JSON** (раніше нерідко й XML), який описує стан ресурсу в машинно- і людино-читабельному вигляді.
- **Клієнт-серверна архітектура** — чіткий поділ відповідальності: клієнт відповідає за UI/взаємодію з користувачем, сервер — за дані й бізнес-логіку; вони можуть розвиватись незалежно, поки контракт (структура URL, формат даних) стабільний.
- **Кешованість (cacheability)** — відповіді повинні явно позначати, чи можна їх кешувати (заголовки `Cache-Control`, `ETag`), щоб клієнти й проміжні системи могли уникати зайвих запитів.

### Актуальність для SolarWinds

SolarWinds Orion надає **SWIS (SolarWinds Information Service)** — REST-подібний (а історично також SOAP-based) API для програмного читання й керування даними моніторингу: стан пристроїв, метрики, алерти, топологія мережі тощо. Розуміння REST безпосередньо застосовне до роботи з таким API: типовий сценарій — `GET`-запит до SWIS REST endpoint для вибірки списку пристроїв зі статусом "Down", або `POST` для створення нового моніторованого вузла програмно (наприклад, з CI/CD-пайплайну автоматичного додавання нового сервера в моніторинг одразу після його розгортання).

### 6.1 REST vs SOAP

| | REST | SOAP |
|---|---|---|
| **Формат даних** | Зазвичай JSON (іноді XML) | Завжди XML (жорстка схема — WSDL) |
| **Транспорт** | Практично завжди HTTP(S) | HTTP, SMTP та інші (менш прив'язаний до HTTP) |
| **Стиль** | Архітектурний стиль, гнучкий | Формальний протокол з чіткою специфікацією |
| **Контракт** | Часто неформальний (OpenAPI/Swagger — опційно) | Обов'язковий, строго типізований (WSDL) |
| **Складність** | Легший, менше "церемоній" | Важчий, більше boilerplate (envelope, namespaces) |
| **Типове застосування** | Сучасні веб- і мобільні API, більшість хмарних сервісів | Легасі корпоративні системи, деяке мережеве обладнання, банківські/enterprise-інтеграції зі строгими вимогами до контракту та вбудованої безпеки (WS-Security) |

У сфері мережевого обладнання й enterprise-систем SOAP усе ще зустрічається (деякі старі API мережевих пристроїв, деякі OSS/BSS-системи телеком-операторів), тож розуміти обидва підходи корисно, навіть якщо REST безумовно домінує в сучасній розробці.

### Приклад 1: простий GET-запит через HttpClient

```csharp
using System;
using System.Net.Http;
using System.Threading.Tasks;

class SimpleGetExample
{
    // Один статичний HttpClient на весь час життя застосунку — 
    // рекомендована практика (уникаємо вичерпання сокетів при
    // створенні нового HttpClient на кожен запит).
    private static readonly HttpClient client = new HttpClient
    {
        Timeout = TimeSpan.FromSeconds(10)
    };

    static async Task Main()
    {
        try
        {
            HttpResponseMessage response = await client.GetAsync("https://api.github.com/repos/dotnet/runtime");

            Console.WriteLine($"Код стану: {(int)response.StatusCode} {response.ReasonPhrase}");
            Console.WriteLine("Заголовки відповіді:");
            foreach (var header in response.Headers)
            {
                Console.WriteLine($"  {header.Key}: {string.Join(", ", header.Value)}");
            }

            string body = await response.Content.ReadAsStringAsync();

            if (response.IsSuccessStatusCode) // true для будь-якого коду 2xx
            {
                Console.WriteLine("✅ Успішна відповідь.");
                Console.WriteLine($"Перші 200 символів тіла: {body.Substring(0, Math.Min(200, body.Length))}");
            }
            else if ((int)response.StatusCode >= 400 && (int)response.StatusCode < 500)
            {
                Console.WriteLine($"❌ Помилка клієнта (4xx): можливо, невірний запит або немає прав доступу.");
            }
            else if ((int)response.StatusCode >= 500)
            {
                Console.WriteLine($"❌ Помилка сервера (5xx): проблема на боці сервера, спробуйте пізніше.");
            }
        }
        catch (TaskCanceledException)
        {
            Console.WriteLine("❌ Таймаут запиту — сервер не відповів вчасно.");
        }
        catch (HttpRequestException ex)
        {
            Console.WriteLine($"❌ Помилка мережі: {ex.Message}");
        }
    }
}
```

### Приклад 3: утиліта перевірки "здоров'я" вебсайту (як у SAM)

```csharp
using System;
using System.Diagnostics;
using System.Net.Http;
using System.Threading.Tasks;

public enum HealthStatus { Up, Degraded, Down }

public record HealthCheckResult(string Url, HealthStatus Status, int? StatusCode, long ResponseTimeMs, string? ErrorMessage);

class WebsiteHealthChecker
{
    private static readonly HttpClient client = new HttpClient();

    // Порогові значення, аналогічні тим, що налаштовуються в реальному моніторингу
    private const long DegradedThresholdMs = 1000; // повільніше 1с — вважаємо "Degraded"
    private const int TimeoutMs = 5000;             // якщо взагалі не відповів за 5с — "Down"

    public static async Task<HealthCheckResult> CheckAsync(string url)
    {
        var stopwatch = Stopwatch.StartNew();
        using var cts = new System.Threading.CancellationTokenSource(TimeoutMs);

        try
        {
            HttpResponseMessage response = await client.GetAsync(url, cts.Token);
            stopwatch.Stop();

            int statusCode = (int)response.StatusCode;
            bool isSuccess = statusCode >= 200 && statusCode < 300;

            if (!isSuccess)
            {
                return new HealthCheckResult(url, HealthStatus.Down, statusCode, stopwatch.ElapsedMilliseconds,
                    $"Неуспішний код стану: {statusCode}");
            }

            HealthStatus status = stopwatch.ElapsedMilliseconds > DegradedThresholdMs
                ? HealthStatus.Degraded
                : HealthStatus.Up;

            return new HealthCheckResult(url, status, statusCode, stopwatch.ElapsedMilliseconds, null);
        }
        catch (OperationCanceledException)
        {
            stopwatch.Stop();
            return new HealthCheckResult(url, HealthStatus.Down, null, stopwatch.ElapsedMilliseconds,
                $"Таймаут: сервер не відповів за {TimeoutMs} мс");
        }
        catch (HttpRequestException ex)
        {
            stopwatch.Stop();
            return new HealthCheckResult(url, HealthStatus.Down, null, stopwatch.ElapsedMilliseconds,
                $"Помилка з'єднання: {ex.Message}");
        }
    }

    static async Task Main()
    {
        // Симуляція перевірки кількох ендпоінтів, як робив би моніторинговий агент
        string[] urlsToCheck =
        {
            "https://www.google.com",
            "https://httpstat.us/500",     // спеціальний тестовий сервіс, що навмисно повертає 500
            "https://httpstat.us/200?sleep=2000" // навмисна затримка 2с — має класифікуватись як Degraded/Down
        };

        Console.WriteLine("=== Перевірка стану вебсайтів ===\n");

        foreach (var url in urlsToCheck)
        {
            HealthCheckResult result = await CheckAsync(url);

            string icon = result.Status switch
            {
                HealthStatus.Up => "✅",
                HealthStatus.Degraded => "⚠️",
                HealthStatus.Down => "❌",
                _ => "?"
            };

            Console.WriteLine($"{icon} {result.Url}");
            Console.WriteLine($"   Статус: {result.Status}, HTTP-код: {result.StatusCode?.ToString() ?? "N/A"}, " +
                               $"Час відповіді: {result.ResponseTimeMs} мс");
            if (result.ErrorMessage != null)
                Console.WriteLine($"   Деталі: {result.ErrorMessage}");
            Console.WriteLine();
        }
    }
}
```

**Очікуваний вивід (приблизно, значення часу відповіді умовні):**


### Приклад 4: інспекція TLS-сертифіката (монітор строку дії)

```csharp
using System;
using System.Net.Http;
using System.Security.Cryptography.X509Certificates;
using System.Threading.Tasks;

class CertificateInspector
{
    public static async Task InspectCertificateAsync(string url)
    {
        X509Certificate2? capturedCert = null;

        var handler = new HttpClientHandler
        {
            // Цей callback викликається під час TLS-рукостискання для валідації сертифіката.
            // Тут ми не лише перевіряємо його (у реальному коді ВАЖЛИВО не завжди
            // повертати true — інакше зникає весь сенс перевірки сертифіката!),
            // а й "перехоплюємо" сертифікат, щоб прочитати його дані.
            ServerCertificateCustomValidationCallback = (request, cert, chain, sslPolicyErrors) =>
            {
                capturedCert = cert != null ? new X509Certificate2(cert) : null;

                // У продакшн-коді моніторингового інструменту тут варто ЛОГУВАТИ
                // sslPolicyErrors (наприклад, RemoteCertificateNameMismatch,
                // RemoteCertificateChainErrors), навіть якщо ми свідомо продовжуємо
                // з'єднання для збору діагностичної інформації.
                if (sslPolicyErrors != System.Net.Security.SslPolicyErrors.None)
                {
                    Console.WriteLine($"⚠️ Виявлено проблему з сертифікатом: {sslPolicyErrors}");
                }

                return true; // дозволяємо з'єднання продовжитись, щоб зчитати сертифікат навіть при помилках
            }
        };

        using var client = new HttpClient(handler);

        try
        {
            await client.GetAsync(url);
        }
        catch (HttpRequestException ex)
        {
            Console.WriteLine($"Запит завершився з помилкою (можливо, очікувано): {ex.Message}");
        }

        if (capturedCert == null)
        {
            Console.WriteLine("Не вдалося отримати сертифікат (можливо, з'єднання не HTTPS).");
            return;
        }

        Console.WriteLine($"=== Інформація про сертифікат для {url} ===");
        Console.WriteLine($"Subject (кому виданий):  {capturedCert.Subject}");
        Console.WriteLine($"Issuer (хто видав, CA):  {capturedCert.Issuer}");
        Console.WriteLine($"Дійсний з:               {capturedCert.NotBefore:yyyy-MM-dd}");
        Console.WriteLine($"Дійсний до:              {capturedCert.NotAfter:yyyy-MM-dd}");

        TimeSpan timeUntilExpiry = capturedCert.NotAfter - DateTime.Now;

        if (timeUntilExpiry.TotalDays < 0)
        {
            Console.WriteLine($"❌ СЕРТИФІКАТ ПРОСТРОЧЕНИЙ ({Math.Abs(timeUntilExpiry.TotalDays):F0} днів тому)!");
        }
        else if (timeUntilExpiry.TotalDays < 30)
        {
            Console.WriteLine($"⚠️ УВАГА: сертифікат спливає через {timeUntilExpiry.TotalDays:F0} днів — " +
                               "рекомендується згенерувати попереджувальний алерт.");
        }
        else
        {
            Console.WriteLine($"✅ Сертифікат дійсний ще {timeUntilExpiry.TotalDays:F0} днів.");
        }
    }

    static async Task Main()
    {
        await InspectCertificateAsync("https://www.google.com");
    }
}
```

**Очікуваний вивід (приблизно, дати умовні):**

```
=== Інформація про сертифікат для https://www.google.com ===
Subject (кому виданий):  CN=www.google.com
Issuer (хто видав, CA):  CN=WR2, O=Google Trust Services, C=US
Дійсний з:               2026-06-30
Дійсний до:              2026-09-22
✅ Сертифікат дійсний ще 30 днів.
```

> **Примітка щодо безпеки:** у прикладі 4 колбек `ServerCertificateCustomValidationCallback` навмисно завжди повертає `true`, щоб продемонструвати читання сертифіката незалежно від його валідності (саме так і повинен поводитись інструмент **діагностики**, якому потрібно побачити сертифікат, навіть якщо він прострочений чи має інші проблеми). У звичайному клієнтському коді, що просто споживає API, **так робити не можна** — це вимикає весь захист від MITM-атак. Такий підхід виправданий лише в спеціалізованих діагностичних/моніторингових утилітах, чиє єдине завдання — перевірити сам сертифікат.

## 8. Реальний сценарій: HTTP/HTTPS-моніторинг у продукті на кшталт SolarWinds SAM

**Server & Application Monitor (SAM)** та подібні продукти реалізують моніторинг веб-застосунків здебільшого через **синтетичні перевірки (synthetic monitoring)** — сам продукт періодично поводиться як "штучний клієнт", що звертається до застосунку так само, як це робив би реальний користувач, і оцінює результат.

### 8.1 Періодичні HTTP(S)-перевірки

Основний елемент — **опитувач (poller)**, що з певним інтервалом (наприклад, кожні 30-60 секунд) надсилає HTTP(S)-запит (типово GET) на налаштовану URL і фіксує:

- чи взагалі отримано відповідь (чи стався таймаут/помилка з'єднання);
- код стану HTTP;
- час відповіді (response time);
- опційно — вміст відповіді, якщо потрібно перевірити наявність конкретного рядка/шаблону в тілі (наприклад, "перевір, що на сторінці міститься слово 'Success'", щоб відрізнити коректну сторінку від, наприклад, сторінки-заглушки хостера, яка теж повертає 200).

### 8.2 Тренди часу відповіді — не лише "up/down"

Критично важливий нюанс, який відрізняє зрілий продукт моніторингу від простого "пінгера": **сайт, що повертає 200 OK, але робить це за 8 секунд замість звичних 200 мс, — це теж проблема**, навіть якщо формально він "доступний". Тому SAM-подібні системи:

- зберігають **історію часу відповіді** для побудови графіків трендів;
- дозволяють налаштувати **пороги деградації** (наприклад, "попередження, якщо час відповіді > 2с; критичний алерт, якщо > 5с"), аналогічно до логіки з прикладу 3 вище (`Up` / `Degraded` / `Down`);
- виявляють **поступову деградацію** (наприклад, час відповіді зростає з 200мс до 2с протягом тижня) — сигнал про наближення проблеми **до того**, як станеться повна відмова.

### 8.3 Алертинг на основі коду стану — диференційовано

Грамотна система моніторингу **не** трактує "будь-що, крім 200" однаково — 4xx і 5xx означають принципово різні речі:

- **5xx (помилка сервера)** — практично завжди означає **реальну проблему на боці застосунку/backend**: впала служба, вичерпані ресурси, необроблений виняток. Це майже завжди підстава для **критичного алерту** з негайним сповіщенням чергового інженера.
- **4xx (помилка клієнта)** — часто вказує на проблему **конфігурації самої перевірки** (наприклад, перевірка налаштована на URL, що вимагає автентифікації, якої монітор не надає, — 401/403; або URL застаріла й повернула 404 після редизайну сайту) — це радше сигнал переглянути налаштування самого моніторингу, ніж однозначна ознака відмови продакшн-системи. Хоча стійке 429 (rate limiting) теж вартий уваги — можливо, сам монітор занадто агресивно опитує ціль.

Тому правила алертингу зазвичай дозволяють налаштувати **різну поведінку окремо для класів кодів** (наприклад, "5xx → критичний інцидент негайно", "4xx → попередження, що вимагає перевірки конфігурації перевірки").

### 8.4 Моніторинг строку дії TLS-сертифікатів

Це одна з найцінніших "проактивних" (а не лише реактивних) можливостей: замість того, щоб дізнатись про проблему **після того**, як сайт впав через прострочений сертифікат (а браузери агресивно блокують доступ до сайтів із простроченими сертифікатами — це миттєвий, повний і дуже помітний для користувачів "outage"), система моніторингу **регулярно перевіряє дату закінчення дії сертифіката** (як у прикладі 4) і генерує **попереджувальний алерт за 30/14/7 днів до закінчення**. Це дозволяє інженерам оновити сертифікат спокійно, у плановому порядку, а не в режимі екстреного усунення інциденту о 3-й ночі.

### 8.5 Синтетичні багатокрокові транзакції (advanced)

Найпростіша перевірка — "чи повернула конкретна URL код 200" — не завжди достатня. Багато критичних несправностей проявляються тільки в **середині користувацького сценарію**, а не на головній сторінці (яка може бути статичною і завжди "живою", навіть коли решта застосунку зламана). Тому просунуті продукти моніторингу підтримують **синтетичні транзакції (synthetic/scripted transactions)** — послідовність кроків, що емулює реальний користувацький шлях:

1. `POST /login` з тестовими обліковими даними → перевірка, що повернувся код 200/302 і, наприклад, cookie сесії.
2. `GET /dashboard` з отриманою сесією → перевірка вмісту сторінки.
3. `POST /orders` з тестовими даними форми → перевірка, що замовлення успішно створено (код 201, повернутий ID).
4. (опційно) `DELETE /orders/{id}` — прибирання тестових даних після перевірки.

Якщо будь-який крок зазнає невдачі — фіксується **саме той крок**, на якому стався збій, що набагато швидше вказує на корінь проблеми, ніж просте "сайт недоступний" (наприклад: "головна сторінка працює, логін працює, але створення замовлення падає з 500" — одразу звужує зону пошуку до конкретного модуля бекенду).

## 9. Поширені проблеми та діагностика

| Симптом | Ймовірна причина | Як діагностувати |
|---|---|---|
| **502 Bad Gateway** | Проблема на upstream/backend-сервері, за яким стоїть reverse proxy чи load balancer (backend впав, не слухає порт, або розірвав з'єднання передчасно) | Перевірити, чи запущений і слухає процес backend (`netstat`/`ss` на backend-хості); перевірити логи проксі (nginx/HAProxy) на предмет "connect() failed"; перевірити стан backend-сервісу напряму, минаючи проксі |
| **503 Service Unavailable** | Сервер перевантажений (вичерпано пул потоків/з'єднань) або на плановому технічному обслуговуванні; спрацював health check і backend виключений з ротації | Перевірити метрики навантаження (CPU, кількість активних з'єднань, розмір черги запитів); перевірити статус health-check у балансувальнику; перевірити, чи не триває заплановане обслуговування |
| **504 Gateway Timeout** | Backend прийняв запит, але не відповів у межах налаштованого таймауту (повільний SQL-запит, дедлок, вичерпання ресурсів) | Профілювання повільних запитів на backend (APM-інструменти, slow query log БД); перевірка значення таймауту на проксі (можливо, воно занадто мале для важких операцій); перевірка на дедлоки/зависання потоків |
| **Сертифікат прострочений** | Ніхто не оновив сертифікат вчасно (немає автоматизації) | Перевірити дату `Not After` (як у прикладі 4); налаштувати автоматичне оновлення (наприклад, через Let's Encrypt/ACME з автопродовженням) і моніторинг строку дії з попередженням за кілька тижнів |
| **"SSL handshake failed"** | Невідповідність підтримуваних версій TLS між клієнтом і сервером (наприклад, сервер вимкнув застарілий TLS 1.0/1.1, а клієнт їх не оновлював); застарілий/невзаємно-підтримуваний cipher suite; проблема з SNI (проксі не знайшов відповідний сертифікат для запитаного імені хоста) | `openssl s_client -connect host:443 -servername host` для перегляду деталей рукостискання й обраного cipher suite; перевірка списку підтримуваних TLS-версій на сервері; перевірка конфігурації SNI на reverse proxy |
| **"Hostname mismatch"** | Сертифікат виданий для іншого домену/піддомену, ніж той, до якого звертається клієнт (наприклад, немає `www.` у SAN, або неправильний сертифікат на проксі за кількома доменами) | Переглянути поле `Subject Alternative Name` сертифіката (`openssl x509 -noout -text`); перевірити конфігурацію віртуальних хостів на reverse proxy |
| **401 замість очікуваного 200** | Токен/облікові дані прострочені, відсутні, або запит не містить заголовок `Authorization` | Перевірити термін дії токена, правильність формату заголовка (`Bearer <token>`), і чи взагалі надсилається заголовок (перевірка через DevTools/`curl -v`) |
| **403 замість очікуваного 200** | Обліковий запис автентифікований, але не має потрібної ролі/дозволу | Перевірити роль/права користувача в системі авторизації; звернутись до адміністратора системи прав доступу — повторна автентифікація тут не допоможе |
| **Повільний час відповіді, але код 200** | Backend виконує важку операцію (складний SQL-запит, зовнішній виклик), або мережева затримка/перевантаження каналу | Аналіз через APM/трасування запитів (де саме йде час — у застосунку, у БД, у мережі); порівняння з історичними трендами часу відповіді |

**Основні інструменти діагностики HTTP/HTTPS:**

- **Браузерні DevTools (вкладка Network)** — перегляд повного запиту/відповіді: заголовки, тіло, час завантаження по фазах (DNS lookup, TCP-з'єднання, TLS handshake, час до першого байта — TTFB), код стану.
- **`curl -v`** — командний рядок для відтворення точного запиту з повним виводом заголовків запиту й відповіді, кодів стану, і навіть інформації про TLS-рукостискання (`curl -v https://example.com`).
- **`openssl s_client -connect host:443 -servername host`** — низькорівнева діагностика TLS: показує весь ланцюг сертифікатів, обрану версію протоколу й cipher suite, дозволяє перевірити, чи сервер правильно налаштований для SNI-запитів конкретного домену.
- **`Test-NetConnection -ComputerName host -Port 443`** (PowerShell) — базова перевірка, чи взагалі відкритий порт 443/80, перш ніж заглиблюватись у деталі HTTP/TLS.

## 10. Питання та відповіді для співбесіди

**1. Чим відрізняється 401 від 403?**
401 (Unauthorized) означає, що сервер не зміг ідентифікувати клієнта — відсутні або невалідні дані автентифікації (проблема "хто ти?"). 403 (Forbidden) означає, що сервер уже знає, хто клієнт, але у нього недостатньо прав для цієї дії (проблема "тобі не можна"). При 401 варто повторно автентифікуватись; при 403 повторна автентифікація нічого не змінить — потрібні інші права.

**2. Чим відрізняється 502 від 503 і 504?**
502 (Bad Gateway) — проксі/шлюз отримав невалідну відповідь від backend (або backend взагалі не відповідає на з'єднання). 503 (Service Unavailable) — сервер свідомо відмовляється обробляти запит зараз (перевантажений або на обслуговуванні), хоча сам сервер живий. 504 (Gateway Timeout) — проксі достукався до backend, але той не відповів у межах таймауту (повільна операція, зависання).

**3. Поясни, як працює TLS handshake на високому рівні.**
Клієнт надсилає ClientHello (підтримувані версії/шифри, SNI). Сервер відповідає ServerHello і своїм сертифікатом з публічним ключем. Клієнт перевіряє сертифікат (ланцюг довіри, термін дії, збіг домену), потім через асиметричну криптографію (наприклад, ECDHE) обидві сторони узгоджують спільний секрет, з якого незалежно обчислюють однаковий симетричний сеансовий ключ. Обмін завершальними повідомленнями Finished, зашифрованими цим ключем, підтверджує успішність рукостискання. Далі весь трафік шифрується вже швидким симетричним алгоритмом (наприклад, AES-GCM).

**4. Навіщо потрібен SNI?**
Щоб один сервер (одна IP-адреса) міг обслуговувати кілька HTTPS-доменів з різними сертифікатами. Оскільки заголовок Host передається лише всередині вже зашифрованого HTTP-трафіку (тобто після рукостискання), сервер не знає, який сертифікат показати, доки не отримає ім'я домену. SNI вирішує це, передаючи ім'я домену у відкритому вигляді прямо в ClientHello, ще до шифрування, щоб сервер міг одразу обрати правильний сертифікат.

**5. Чим HTTP/2 краще за HTTP/1.1?**
HTTP/2 використовує бінарний фреймінг замість тексту, підтримує мультиплексування кількох запитів/відповідей через одне TCP-з'єднання (вирішуючи Head-of-Line blocking на рівні HTTP, властивий HTTP/1.1), і стискає заголовки через HPACK, зменшуючи накладні витрати на повторювані метадані. Водночас HTTP/2 усе ще вразливий до HoL blocking на рівні TCP, оскільки працює поверх одного TCP-з'єднання — цю проблему вирішує вже HTTP/3.

**6. Що таке ідемпотентність HTTP-методу, наведи приклади.**
Ідемпотентний метод — це такий, повторний виклик якого з тими самими параметрами не змінює результат порівняно з одноразовим викликом. GET, PUT, DELETE ідемпотентні: `DELETE /users/5`, викликаний 10 разів, залишає той самий стан (користувача 5 немає), як і після одного виклику. POST — не ідемпотентний: повторний виклик `POST /users` типово створює новий ресурс щоразу.

**7. Чим PUT відрізняється від PATCH?**
PUT замінює ресурс повністю — клієнт надсилає повне представлення нового стану ресурсу, і будь-які поля, не вказані в запиті, типово скидаються/зникають. PATCH застосовує часткову зміну — клієнт надсилає лише ті поля, які потрібно змінити, решта залишається без змін. PUT ідемпотентний за визначенням, PATCH — не обов'язково (залежить від семантики операції, яку він описує).

**8. Що таке REST і його основні принципи?**
REST (Representational State Transfer) — архітектурний стиль побудови API поверх HTTP, де ресурси ідентифікуються унікальними URL, а стандартні HTTP-методи відображаються на CRUD-операції (GET=Read, POST=Create, PUT/PATCH=Update, DELETE=Delete). Основні принципи: клієнт-серверна архітектура, відсутність стану на сервері (statelessness), кешованість відповідей, уніфікований інтерфейс, і типове використання JSON як формату подання даних.

**9. Чому HTTPS використовує і асиметричне, і симетричне шифрування одночасно?**
Асиметрична криптографія не потребує попередньо узгодженого спільного секрету, тому підходить для першого встановлення довіри між незнайомими сторонами, але вона обчислювально повільна. Симетрична криптографія на порядки швидша й підходить для шифрування великих обсягів даних, але вимагає, щоб обидві сторони вже мали спільний ключ. TLS використовує асиметричну криптографію лише один раз — щоб безпечно узгодити симетричний сеансовий ключ, — а весь подальший трафік шифрує вже швидким симетричним алгоритмом (наприклад, AES).

**10. Що означає помилка "сертифікат самопідписаний" або "hostname mismatch"?**
"Самопідписаний" означає, що сертифікат підписаний не довіреним центром сертифікації (CA), а самим власником сайту — клієнт не може криптографічно підтвердити автентичність сервера через ланцюг довіри. "Hostname mismatch" означає, що домен, до якого звертається клієнт, не збігається з доменом(ами), перерахованими в полі Subject Alternative Name сертифіката — часто через неправильно налаштований reverse proxy або сертифікат, виданий для іншого піддомену.

**11. Що таке statelessness у HTTP і навіщо він потрібен?**
Statelessness означає, що сервер не зберігає жодного контексту про попередні запити того самого клієнта — кожен запит обробляється незалежно й повинен містити всю потрібну інформацію самостійно (наприклад, токен автентифікації). Це критично для масштабованості: будь-який із багатьох ідентичних серверів за балансувальником навантаження може обробити будь-який запит, не потребуючи спільної пам'яті про історію взаємодії з конкретним клієнтом.

**12. Що таке HPACK/QPACK і навіщо вони потрібні?**
Це алгоритми стиснення HTTP-заголовків у HTTP/2 (HPACK) і HTTP/3 (QPACK, адаптація під особливості QUIC). Заголовки (Cookie, User-Agent, Accept тощо) часто повторюються майже незмінними в кожному запиті одного клієнта; HPACK/QPACK використовують статичні й динамічні таблиці разом із хаффман-кодуванням, щоб не передавати ці метадані повторно в повному обсязі щоразу, суттєво зменшуючи накладні витрати мережі.

**13. У чому головна відмінність HTTP/3 від HTTP/2 на рівні транспорту?**
HTTP/2 працює поверх TCP, тож попри мультиплексування на рівні HTTP, втрата одного TCP-сегмента блокує доставку всіх байтів з'єднання (Head-of-Line blocking на рівні транспорту). HTTP/3 працює поверх QUIC (яке саме працює поверх UDP), де кожен потік незалежний навіть при втраті пакетів — втрата пакета одного потоку більше не блокує інші потоки того самого з'єднання.

**14. Що таке 3xx-редиректи, і чим 301 відрізняється від 302, а 307 від 308?**
301 і 308 означають "постійний" редирект (ресурс назавжди переїхав); 302 і 307 — "тимчасовий". Історична пара 301/302 у деяких клієнтах могла непередбачувано змінювати метод запиту на GET під час редиректу; 307/308 — це "строгі" версії, що гарантовано зберігають оригінальний HTTP-метод і тіло запиту при редиректі (307 = тимчасовий + збереження методу, 308 = постійний + збереження методу).

**15. Що доводить TLS-сертифікат і що таке ланцюг довіри?**
Сертифікат зв'язує публічний ключ із конкретним доменним іменем, і цей зв'язок засвідчений цифровим підписом центру сертифікації (CA). Ланцюг довіри — послідовність підписів від сертифіката сайту через один чи кілька проміжних CA аж до кореневого CA, якому клієнт/ОС довіряє апріорі (вбудований у довірене сховище). Перевірка сертифіката — це перевірка кожного підпису в цьому ланцюжку вгору до кореня.

**16. Навіщо в системі моніторингу веб-застосунків потрібно відстежувати не лише "up/down", а й час відповіді?**
Тому що застосунок може формально повертати 200 OK, але робити це настільки повільно, що це вже неприйнятно для користувачів — деградація продуктивності часто передує повній відмові й є раннім сигналом проблеми. Відстеження трендів часу відповіді дозволяє виявити поступове погіршення (наприклад, зростання затримки протягом днів) і відреагувати проактивно, до того як станеться повний збій.

**17. Чому 4xx і 5xx варто обробляти по-різному в правилах алертингу моніторингу?**
5xx майже завжди означає реальну проблему на боці сервера/застосунку і виправдовує критичний алерт. 4xx частіше вказує на проблему в самому налаштуванні перевірки (застаріла URL, відсутня автентифікація) або на некоректний запит клієнта, а не на відмову продакшн-системи — тому зазвичай вимагає перегляду конфігурації моніторингу, а не негайного інциденту.

## 11. Підсумок

### Швидкий довідник кодів стану

| Код | Значення |
|---|---|
| 200 | OK — успіх |
| 201 | Created — ресурс створено |
| 204 | No Content — успіх без тіла відповіді |
| 301 / 308 | Постійний редирект (308 гарантовано зберігає метод) |
| 302 / 307 | Тимчасовий редирект (307 гарантовано зберігає метод) |
| 400 | Bad Request — некоректний запит |
| 401 | Unauthorized — не автентифікований |
| 403 | Forbidden — автентифікований, але немає прав |
| 404 | Not Found — ресурс не існує |
| 409 | Conflict — конфлікт зі станом ресурсу |
| 429 | Too Many Requests — перевищено ліміт запитів |
| 500 | Internal Server Error — необроблена помилка сервера |
| 502 | Bad Gateway — невалідна відповідь від backend |
| 503 | Service Unavailable — сервер тимчасово не обробляє запити |
| 504 | Gateway Timeout — backend не відповів вчасно |

### Швидкий довідник методів

| Метод | CRUD | Safe | Idempotent |
|---|---|---|---|
| GET | Read | ✅ | ✅ |
| POST | Create | ❌ | ❌ |
| PUT | Update (повна заміна) | ❌ | ✅ |
| PATCH | Update (часткова зміна) | ❌ | ❌ (зазвичай) |
| DELETE | Delete | ❌ | ✅ |
| HEAD | — (метадані GET) | ✅ | ✅ |
| OPTIONS | — (можливості ресурсу) | ✅ | ✅ |

### HTTP/1.1 vs HTTP/2 vs HTTP/3 — коротко

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| Транспорт | TCP | TCP | QUIC (UDP) |
| Мультиплексування | Немає | Так (HTTP-рівень) | Так (транспортний рівень) |
| HoL Blocking | Так | Частково вирішено | Повністю вирішено |
| Стиснення заголовків | Немає | HPACK | QPACK |

### Ключові ідеї, які варто пам'ятати

- HTTP — **stateless**, запит-відповідь, поверх TCP (або QUIC/UDP у HTTP/3).
- **401 = хто ти? (автентифікація), 403 = тобі не можна (авторизація).**
- **502 = backend не відповів валідно, 503 = сервер свідомо відмовляється, 504 = backend не встиг відповісти.**
- HTTPS = HTTP + TLS: **асиметрична криптографія для узгодження ключа, симетрична — для швидкого шифрування трафіку.**
- **SNI** дозволяє серверу обрати правильний сертифікат ще до шифрування, читаючи ім'я домену з відкритої частини ClientHello.
- REST будує API навколо **ресурсів і URL**, мапуючи HTTP-методи на CRUD, і залишається stateless за духом базового HTTP.
- Для продукту моніторингу веб-застосунків важливі не лише коди стану, а й **тренди часу відповіді**, **диференційований алертинг за класами кодів**, **проактивний моніторинг строку дії сертифікатів**, і, для зрілих рішень, **синтетичні багатокрокові транзакції**.
