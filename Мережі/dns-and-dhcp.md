## DNS (Domain Name System)

**DNS (Domain Name System)** — це розподілена ієрархічна система, яка перетворює зрозумілі людині доменні імена (наприклад, `www.example.com`) на IP-адреси (наприклад, `93.184.216.34`), які й використовуються для фактичної маршрутизації пакетів у мережі. Без DNS користувачам довелося б запам'ятовувати числові адреси кожного сервіса, яким вони хочуть скористатися.

### Аналогія 📞

Уявіть телефонну книгу (або список контактів у смартфоні). Ви пам'ятаєте ім'я людини — "Олена" — але не пам'ятаєте (і не повинні пам'ятати) її номер телефону. Коли ви натискаєте на контакт "Олена", телефон сам знаходить прив'язаний до цього імені номер і здійснює дзвінок. DNS працює за тим самим принципом:

- **Ім'я людини** → доменне ім'я (`www.example.com`)
- **Телефонна книга** → система DNS
- **Номер телефону** → IP-адреса (`93.184.216.34`)
- **Дзвінок** → фактичне TCP/IP-з'єднання

DNS — це, по суті, найбільша у світі розподілена база даних типу "ключ-значення", яка працює на порту **UDP/TCP 53**.

### Навіщо потрібен DNS

1. **Зручність для людей** — імена запам'ятати простіше, ніж набори цифр.
2. **Гнучкість інфраструктури** — сервер за доменним іменем можна перенести на іншу IP-адресу (наприклад, при міграції в інший дата-центр), і клієнтам не потрібно нічого змінювати — досить оновити DNS-запис.
3. **Балансування навантаження** — один домен може вказувати на декілька IP-адрес (round-robin DNS) або через CDN спрямовувати користувачів на географічно найближчий сервер.
4. **Гнучкість сервісів на одному хості** — кілька доменних імен (і навіть кілька сайтів) можуть співіснувати на одній IP-адресі завдяки virtual hosting.

## Ієрархія DNS

DNS побудований як **перевернуте дерево** (ієрархічна структура імен), де кожен рівень делегує повноваження наступному.

```
                              . (корінь, root)
                              |
        ┌─────────────────────┼─────────────────────┐
        |                     |                      |
      .com                  .org                    .ua
        |                     |                      |
   ┌────┴─────┐          ┌────┴────┐            ┌─────┴─────┐
example.com  google.com  wikipedia.org        example.ua   gov.ua
   |
   ├── www.example.com        (субдомен)
   ├── mail.example.com       (субдомен)
   └── ftp.example.com        (субдомен)
```

Повне доменне ім'я (**FQDN** — Fully Qualified Domain Name) читається *справа наліво* з точки зору ієрархії:

`www.example.com.` → `www` (субдомен) . `example` (домен другого рівня) . `com` (TLD) . `` (корінь)

> Зверніть увагу на завершальну крапку — технічно кожне DNS-ім'я закінчується "невидимим" коренем `.`. Браузери та ОС зазвичай приховують цю деталь.

### Основні компоненти ієрархії

| Компонент | Опис |
|---|---|
| **Root (корінь), `.`** | Найвищий рівень ієрархії. Існує 13 логічних груп кореневих серверів (`a.root-servers.net` … `m.root-servers.net`), які фізично реалізовані через сотні anycast-вузлів по всьому світу. Вони не знають кінцевих IP-адрес сайтів — лише знають, куди звернутися за кожним TLD. |
| **TLD (Top-Level Domain) сервери** | Обслуговують домени верхнього рівня: `.com`, `.org`, `.ua`, `.net` і т.д. Знають, які authoritative-сервери відповідають за кожен домен другого рівня в межах цього TLD. |
| **Authoritative Name Server** | Сервер, який зберігає *справжні* (авторитетні) записи конкретної зони (наприклад, `example.com`) — саме тут лежать A, MX, CNAME записи для цього домену. Це "джерело правди". |
| **Recursive Resolver (рекурсивний резолвер)** | DNS-сервер, до якого фактично звертається ваш пристрій (зазвичай наданий провайдером, або публічний, наприклад `8.8.8.8` від Google чи `1.1.1.1` від Cloudflare). Він бере на себе всю "чорнову роботу" — обходить ієрархію (root → TLD → authoritative) від імені клієнта і повертає клієнту вже готову відповідь. |

**Ключова відмінність:** клієнт (ваш ноутбук/телефон) практично ніколи напряму не спілкується з root/TLD/authoritative серверами. Він робить **один** запит до свого рекурсивного резолвера, а вже резолвер виконує всю послідовність запитів по ієрархії.

## Процес розв'язання імені (DNS Resolution) крок за кроком

Розглянемо повний цикл розв'язання імені `www.example.com` "з нуля" (припустимо, кеш резолвера порожній).

```
Клієнт            Recursive Resolver        Root Server         .com TLD Server      example.com Auth NS
  |                       |                       |                     |                     |
  |--(1) Хто www.--------->|                       |                     |                     |
  |   example.com?         |                       |                     |                     |
  |                       |--(2) Перевірка кешу-->  (порожньо)            |                     |
  |                       |                       |                     |                     |
  |                       |--(3) Хто www.example.com?------------------->|                     |
  |                       |<-(4) Не знаю, але------|                     |                     |
  |                       |   ось NS для .com      |                     |                     |
  |                       |                       |                     |                     |
  |                       |--(5) Хто www.example.com?-------------------------------------------->|
  |                       |<-(6) Не знаю сайт, але-------------------------------------------------|
  |                       |   ось NS для example.com                     |                     |
  |                       |                       |                     |                     |
  |                       |--(7) Хто www.example.com?----------------------------------------------------------->|
  |                       |<-(8) Ось A-запис: 93.184.216.34--------------------------------------------------------|
  |                       |                       |                     |                     |
  |                       |--(9) Зберегти у кеші (з урахуванням TTL)     |                     |
  |<-(10) 93.184.216.34---|                       |                     |                     |
  |                       |                       |                     |                     |
```

### Покроково

1. **Клієнт → Recursive Resolver.** Застосунок (браузер, наприклад) звертається до ОС, ОС звертається до налаштованого DNS-резолвера (часто це роутер провайдера, або вручну прописаний `8.8.8.8`/`1.1.1.1`) з **рекурсивним** запитом: "Дай мені, будь ласка, готову IP-адресу для `www.example.com`, зроби всю роботу сам".
2. **Перевірка кешу.** Резолвер спочатку перевіряє, чи немає вже свіжого (не простроченого за TTL) запису в локальному кеші. Якщо є — одразу повертає відповідь клієнту, і процес завершується тут (найпоширеніший сценарій на практиці).
3. **Resolver → Root Server (ітеративний запит).** Якщо кешу немає, резолвер звертається до одного з кореневих серверів: "Хто відповідає за `www.example.com`?"
4. **Root відповідає рефералом (referral).** Кореневий сервер не знає точної відповіді, але знає, які сервери обслуговують `.com`, і повертає їх список (NS-записи + IP-адреси, так звані "glue records").
5. **Resolver → TLD Server (`.com`).** Резолвер звертається до одного з `.com` TLD-серверів з тим самим питанням.
6. **TLD відповідає рефералом.** TLD-сервер не зберігає самі записи сайту, але знає авторитетні NS-сервери для `example.com`, і повертає їх.
7. **Resolver → Authoritative Server (`example.com`).** Резолвер звертається безпосередньо до authoritative-сервера домену `example.com`.
8. **Authoritative Server повертає фінальну відповідь.** Цей сервер зберігає реальний A-запис і повертає `93.184.216.34` разом із TTL.
9. **Кешування.** Резолвер зберігає отриману відповідь у себе в кеші на час, вказаний у TTL запису, — щоб не повторювати весь ланцюжок при наступних запитах (від цього ж або інших клієнтів).
10. **Resolver → Клієнт.** Резолвер повертає готову IP-адресу клієнту, який тепер може встановити TCP-з'єднання (наприклад, HTTPS на порт 443) напряму із сервером `93.184.216.34`.

### Рекурсивний vs. ітеративний запит

Це одне з найпопулярніших уточнюючих питань на співбесіді — важливо чітко розрізняти *роль* сторони, а не плутати терміни.

| | Рекурсивний запит (Recursive) | Ітеративний запит (Iterative) |
|---|---|---|
| **Хто виконує** | Клієнт → Recursive Resolver | Recursive Resolver → Root / TLD / Authoritative |
| **Поведінка сервера** | Сервер зобов'язаний повернути **фінальну** відповідь (або помилку) — сам виконує всю подальшу роботу | Сервер повертає **найкращу відому йому** відповідь: або фінальний запис, або "реферал" (посилання на іншого сервера, який знає більше) |
| **Хто "ходить по ланцюжку"** | Клієнт лише один раз запитує і чекає | Резолвер сам ітеративно обходить кожен рівень ієрархії |
| **Аналогія** | Ви просите друга "дізнайся, будь ласка, номер Олени" — і він сам зробить всі дзвінки, а вам поверне готовий номер | Друг сам телефонує в довідкову, довідкова каже "не знаю, зателефонуй туди-то", і він так крок за кроком доходить до відповіді |

Отже: запит від клієнта до резолвера — **завжди рекурсивний** (клієнт хоче готову відповідь). А запити резолвера до root/TLD/authoritative — **ітеративні** (кожен сервер лише вказує напрямок далі).

## Типи DNS-записів

| Тип | Назва | Призначення | Приклад |
|---|---|---|---|
| **A** | Address | Відображає ім'я хоста на **IPv4**-адресу | `www.example.com → 93.184.216.34` |
| **AAAA** | IPv6 Address | Відображає ім'я хоста на **IPv6**-адресу | `www.example.com → 2606:2800:220:1:248:1893:25c8:1946` |
| **CNAME** | Canonical Name | "Псевдонім" — вказує, що дане ім'я є синонімом іншого імені (не IP!). Використовується для піддоменів, CDN, SaaS-сервісів | `shop.example.com → shops.shopifycloud.com` |
| **MX** | Mail Exchange | Вказує сервер(и), що приймають пошту для домену, з **пріоритетом** (менше число = вищий пріоритет) | `example.com → 10 mail1.example.com, 20 mail2.example.com` |
| **NS** | Name Server | Вказує, які сервери є авторитетними для зони (домену) | `example.com → ns1.example.com, ns2.example.com` |
| **PTR** | Pointer | **Зворотний** запис: IP → ім'я (використовується у спеціальних "reverse zones" типу `in-addr.arpa`) | `34.216.184.93.in-addr.arpa → www.example.com` |
| **TXT** | Text | Довільний текст у зоні; часто для верифікації домену, SPF/DKIM/DMARC (захист від підробки пошти) | `example.com TXT "v=spf1 include:_spf.google.com ~all"` |
| **SOA** | Start of Authority | Метадані зони: хто є "власником", параметри реплікації між серверами зони | (див. нижче) |

### SOA-запис детальніше

`SOA` — це перший запис у будь-якій DNS-зоні, і на співбесіді часто просять перелічити його поля:

```
example.com.  IN  SOA  ns1.example.com. admin.example.com. (
                  2024081501 ; Serial     — номер версії зони (інкрементується при кожній зміні)
                  3600       ; Refresh    — як часто вторинний (slave) сервер має перевіряти оновлення
                  900        ; Retry      — через скільки повторити спробу, якщо Refresh не вдався
                  1209600    ; Expire     — після якого часу без успішного оновлення вторинний сервер вважає дані застарілими й перестає відповідати
                  86400 )    ; Minimum/TTL — TTL за замовчуванням для негативного кешування (NXDOMAIN)
```

| Поле | Значення |
|---|---|
| **Serial** | Версія зони; вторинні сервери порівнюють це число, щоб зрозуміти, чи є новіші дані на первинному сервері |
| **Refresh** | Інтервал, з яким вторинний DNS-сервер перевіряє первинний на предмет оновлень |
| **Retry** | Інтервал повторної спроби, якщо попередня перевірка Refresh не вдалась (первинний сервер недоступний) |
| **Expire** | Максимальний час, протягом якого вторинний сервер продовжує вважати свої дані дійсними без зв'язку з первинним, перш ніж перестати відповідати на запити взагалі |
| **Minimum TTL** | Використовується як TTL для кешування *негативних* відповідей (NXDOMAIN — "такого імені не існує") |

## TTL, кешування, зворотний DNS (Reverse DNS/PTR)

### TTL (Time To Live)

Кожен DNS-запис має значення **TTL** (у секундах), яке визначає, як довго резолвери та клієнти мають право зберігати цей запис у кеші, перш ніж знову звернутися до authoritative-сервера за актуальними даними.

**Компроміс TTL:**

| | Високий TTL (наприклад, 86400 = 24 год) | Низький TTL (наприклад, 60–300 сек) |
|---|---|---|
| **Навантаження на DNS-інфраструктуру** | Менше — записи довго лежать у кеші, менше повторних запитів | Більше — резолвери частіше змушені звертатися за оновленням |
| **Швидкість поширення змін** | Повільна — якщо IP-адреса змінилась, частина клієнтів ще годинами/днями буде звертатись за старою адресою, доки їхній кеш не протухне | Швидка — зміни (наприклад, при аварійному перемиканні на резервний сервер / failover) поширюються буквально за хвилини |
| **Типове застосування** | Стабільні записи, які рідко змінюються (наприклад, MX) | Записи перед плановою міграцією, або сервіси з динамічним/failover DNS (наприклад, GSLB, CDN) |

**Практичне правило:** якщо планується міграція сервера чи зміна IP, TTL зазвичай **заздалегідь знижують** (наприклад, за добу до міграції зменшують TTL з 24 год до 5 хв), щоб зміна швидко розповсюдилась, а вже після завершення міграції TTL повертають до звичайного (вищого) значення.

### Зворотний DNS (Reverse DNS / PTR)

Звичайний ("прямий") DNS-запит перетворює ім'я на IP. **Зворотний** запит робить навпаки: маючи IP-адресу, дізнатися відповідне ім'я хоста.

Технічно це реалізовано через спеціальну "перевернуту" зону `in-addr.arpa` (для IPv4) або `ip6.arpa` (для IPv6), де октети IP-адреси записуються у зворотному порядку:

```
IP:            93.184.216.34
Reverse-зона:  34.216.184.93.in-addr.arpa
Запис:         PTR → www.example.com
```

**Навіщо це потрібно мережевим інструментам моніторингу:**

- При **автоматичному виявленні пристроїв** (network discovery) інструмент типу SolarWinds NPM/NCM сканує підмережу і знаходить IP-адреси активних хостів. Сирі IP-адреси (`10.0.5.23`, `10.0.5.24`, …) незручні для адміністратора.
- Виконавши зворотний DNS-запит (PTR) для кожної знайденої IP, інструмент може показати замість `10.0.5.23` — `switch-core-01.corp.local`, що значно покращує читабельність топології мережі, звітів та алертів.
- Зворотний DNS також використовується для базової перевірки легітимності поштових серверів (deliverability): багато поштових систем перевіряють, чи IP відправника має валідний PTR-запис, що відповідає домену.

## DHCP (Dynamic Host Configuration Protocol)

**DHCP** — протокол, який автоматично видає пристрою, що підключається до мережі, повний комплект IP-налаштувань:

- **IP-адресу**
- **Маску підмережі** (subnet mask)
- **Шлюз за замовчуванням** (default gateway)
- **DNS-сервери**
- **Час оренди адреси** (lease time)
- (опційно) додаткові параметри: домен пошуку (DNS suffix), сервер NTP, WINS тощо.

Без DHCP кожен пристрій довелося б налаштовувати вручну (статична IP-конфігурація) — що абсолютно нереально в масштабі офісу на сотні чи тисячі пристроїв, і призводить до людських помилок (наприклад, конфлікт IP-адрес).

### Аналогія 🏨

Уявіть готель. Ви не приходите з власним номером кімнати — ви підходите на рецепцію (**DHCP-сервер**), і адміністратор автоматично видає вам вільний номер і ключ-картку (**IP-адресу**) на час вашого перебування (**lease time**). Коли ви виїжджаєте (пристрій вимикається / lease спливає), номер звільняється і може бути виданий наступному гостю. Вам не потрібно заздалегідь "володіти" номером — система сама підбирає вільний варіант із доступного пулу (**scope**).

## DORA-процес (DHCP)

Отримання IP-адреси через DHCP відбувається за чотирма кроками, які запам'ятовують за абревіатурою **DORA**: **D**iscover → **O**ffer → **R**equest → **A**cknowledge.

```
Клієнт (без IP)                                          DHCP-сервер(и)
     |                                                          |
     |--(1) DHCPDISCOVER ------------------------------------->|   (broadcast:
     |    src: 0.0.0.0:68                                      |    255.255.255.255:67)
     |    dst: 255.255.255.255:67                               |
     |                                                          |
     |<-(2) DHCPOFFER ------------------------------------------|   (пропозиція IP,
     |    "Пропоную тобі 192.168.1.50,                          |    від кожного сервера,
     |     маска 255.255.255.0, gw 192.168.1.1,                 |    який почув DISCOVER)
     |     DNS 192.168.1.1, lease 24h"                          |
     |                                                          |
     |--(3) DHCPREQUEST --------------------------------------->|   (знову broadcast! —
     |    "Приймаю пропозицію від сервера X,                    |    щоб інші сервери
     |     хочу 192.168.1.50"                                   |    знали, що їхні
     |                                                          |    offer відхилено)
     |                                                          |
     |<-(4) DHCPACK ----------------------------------------------|  (підтвердження оренди —
     |    "Підтверджено: 192.168.1.50 твоя на 24 год"           |   lease фіналізовано)
     |                                                          |
```

### Покроково

1. **DISCOVER.** Пристрій, щойно приєднавшись до мережі, ще не має жодної IP-адреси. Тому він відправляє **широкомовний (broadcast)** пакет `DHCPDISCOVER` з адреси `0.0.0.0` на адресу `255.255.255.255`, порт `67` (сервер слухає на 67, клієнт — на 68): "Чи є тут хтось, хто може дати мені IP-адресу?"
2. **OFFER.** Кожен DHCP-сервер у цій підмережі (їх може бути декілька, наприклад, основний і резервний), який отримав DISCOVER і має вільну адресу в своєму scope, відповідає `DHCPOFFER` — резервує (тимчасово) конкретну адресу для цього клієнта і пропонує її разом із рештою параметрів (маска, шлюз, DNS, lease time).
3. **REQUEST.** Клієнт може отримати кілька OFFER від різних серверів, але вибирає лише один (зазвичай перший, що прийшов). Важливо: клієнт знову відправляє **broadcast** (а не unicast конкретному серверу!) `DHCPREQUEST`, у якому явно вказує, чию пропозицію він приймає. Це потрібно саме тому, що broadcast бачать усі DHCP-сервери в мережі — ті, чию пропозицію не обрали, побачать це повідомлення і зрозуміють, що можуть звільнити зарезервовану для цього клієнта адресу назад у пул.
4. **ACKNOWLEDGE.** Обраний сервер надсилає `DHCPACK` — фінальне підтвердження, що оренда (lease) цієї IP-адреси на вказаний термін офіційно закріплена за клієнтом. Після цього клієнт може використовувати адресу в мережі. (У рідкісних випадках сервер може відповісти `DHCPNAK` — відмовити, якщо, наприклад, адреса вже зайнята — і клієнт повертається до кроку DISCOVER.)

### Поновлення оренди (Lease Renewal): T1 і T2

DHCP-оренда не вічна — вона видається на конкретний **lease time** (наприклад, 24 години). Щоб уникнути втрати адреси в останню секунду, клієнт намагається поновити оренду завчасно, у два етапи:

| Таймер | Момент спрацювання | Поведінка |
|---|---|---|
| **T1 (Renewal Time)** | 50% від lease time (наприклад, через 12 год із 24) | Клієнт надсилає **unicast** `DHCPREQUEST` **напряму** тому самому серверу, який видав оренду, з проханням продовжити її |
| **T2 (Rebinding Time)** | 87.5% від lease time (наприклад, через 21 год із 24) | Якщо оригінальний сервер так і не відповів на T1 (наприклад, вийшов з ладу), клієнт переходить у режим "rebinding" — відправляє **broadcast** `DHCPREQUEST`, сподіваючись, що *будь-який* DHCP-сервер у мережі зможе підтвердити (або продовжити) цю оренду |

Якщо ні T1, ні T2 не дали результату і lease повністю спливає (100% часу) — клієнт втрачає IP-адресу і повертається до початку процесу — **DISCOVER**.

## DHCP Relay/Helper та Scopes

### Проблема: broadcast не проходить через маршрутизатори

Весь DORA-процес (принаймні кроки DISCOVER і REQUEST) побудований на **broadcast**-пакетах (`255.255.255.255`). Але маршрутизатори за замовчуванням **не пересилають broadcast-трафік** між підмережами (це нормальна і бажана поведінка — інакше broadcast-шторми заливали б усю мережу). Це створює проблему: якщо DHCP-сервер фізично знаходиться в іншій підмережі (VLAN), ніж клієнт, — клієнтський DISCOVER-пакет ніколи туди не дійде.

### Рішення: DHCP Relay Agent

**DHCP Relay Agent** (у термінах Cisco — команда `ip helper-address`, що налаштовується на інтерфейсі маршрутизатора/L3-світча зі сторони клієнтської підмережі) вирішує цю проблему:

1. Маршрутизатор "чує" broadcast DHCPDISCOVER від клієнта у своїй підмережі.
2. Замість того, щоб просто відкинути його (як звичайний broadcast), relay-агент **інкапсулює** пакет і пересилає його як **unicast** безпосередньо на IP-адресу центрального DHCP-сервера (можливо, в зовсім іншій підмережі/дата-центрі).
3. Relay-агент додає до пакета своє власне поле **`giaddr`** (gateway IP address) — це підказує DHCP-серверу, з якої підмережі прийшов запит, щоб сервер зміг видати адресу з правильного **scope** для цієї підмережі.
4. Відповідь (OFFER/ACK) сервер надсилає назад тому самому relay-агенту, а той вже доставляє її клієнту.

```
Підмережа A (VLAN 10)                Router/L3 Switch                 Підмережа Б (VLAN 99)
клієнт (без IP)                    (ip helper-address                  DHCP-сервер
     |                               10.99.0.5)                        10.99.0.5
     |--DHCPDISCOVER (broadcast)-------->|                                  |
     |                                    |--DHCPDISCOVER (unicast,          |
     |                                    |   giaddr=10.10.0.1)------------->|
     |                                    |<--DHCPOFFER (unicast)------------|
     |<--DHCPOFFER (broadcast/unicast)----|                                  |
```

Це стандартний і дуже поширений сценарій в enterprise-мережах: **один централізований DHCP-сервер** обслуговує десятки VLAN/підмереж через relay, замість того, щоб мати окремий DHCP-сервер у кожній підмережі.

### Scope (Область/Пул адрес)

**Scope** — це логічне визначення на DHCP-сервері, яке описує:

- Діапазон IP-адрес, доступних для видачі в конкретній підмережі (наприклад, `192.168.10.100` – `192.168.10.200`);
- Параметри, що видаються разом з адресою: маска підмережі, шлюз, DNS-сервери, домен пошуку, lease time тощо;
- Виключення (exclusions) — адреси всередині діапазону, які **не** повинні видаватися динамічно (наприклад, тому що вони вже зайняті статичними адресами принтерів чи серверів).

Один DHCP-сервер зазвичай обслуговує **декілька scope** — по одному на кожну підмережу/VLAN, за яку він відповідає (часто саме завдяки DHCP relay з різних VLAN).

### DHCP Reservation (Резервування)

**DHCP Reservation** — спосіб гарантувати, що конкретний пристрій (за його **MAC-адресою**) завжди отримує **одну й ту саму** IP-адресу через DHCP, навіть попри те, що технічно адреса видається динамічно.

**Навіщо це потрібно:**

- Мережеві принтери, IP-камери, комутатори з management-інтерфейсом, сервери — усі ці пристрої зручніше мати з передбачуваною, постійною адресою (щоб не переналаштовувати посилання/моніторинг щоразу, коли термін оренди закінчується і видається нова адреса).
- На відміну від чисто статичної конфігурації (яку налаштовують вручну на самому пристрої), reservation налаштовується **централізовано на DHCP-сервері** — тобто адміністратор має єдину точку керування і видимості всіх адрес мережі (що особливо важливо для інструментів на кшталт IPAM).

### Приклад 1. Пряме та зворотне розв'язання імен через `System.Net.Dns`

```csharp
using System;
using System.Net;
using System.Net.Sockets;

// Приклад показує:
//  1) пряме розв'язання імені хоста в IP-адреси (A/AAAA records)
//  2) зворотне розв'язання IP-адреси в ім'я хоста (PTR record)

class DnsLookupExample
{
    static void Main()
    {
        string hostname = "www.example.com";

        Console.WriteLine($"Пряме розв'язання (Forward lookup) для '{hostname}':");
        try
        {
            // GetHostAddresses поверне усі IP-адреси, прив'язані до імені
            // (може бути декілька A-записів, і/або AAAA для IPv6)
            IPAddress[] addresses = Dns.GetHostAddresses(hostname);

            foreach (IPAddress addr in addresses)
            {
                string family = addr.AddressFamily == AddressFamily.InterNetworkV6
                    ? "IPv6 (AAAA)"
                    : "IPv4 (A)";
                Console.WriteLine($"  {family}: {addr}");
            }

            // Візьмемо першу IPv4-адресу для демонстрації зворотного пошуку
            IPAddress firstIpv4 = Array.Find(addresses,
                a => a.AddressFamily == AddressFamily.InterNetwork);

            if (firstIpv4 != null)
            {
                Console.WriteLine($"\nЗворотне розв'язання (Reverse lookup / PTR) для '{firstIpv4}':");

                // GetHostEntry для IP-адреси виконує PTR-запит
                // (може кинути SocketException, якщо PTR-запис не існує)
                IPHostEntry entry = Dns.GetHostEntry(firstIpv4);
                Console.WriteLine($"  Ім'я хоста: {entry.HostName}");
            }
        }
        catch (SocketException ex)
        {
            // Типова ситуація: NXDOMAIN (ім'я не існує) або PTR-запис відсутній
            Console.WriteLine($"  ❌ Помилка DNS: {ex.Message} (код: {ex.SocketErrorCode})");
        }
    }
}
```

**Приклад виводу:**

```
Пряме розв'язання (Forward lookup) для 'www.example.com':
  IPv4 (A): 93.184.216.34
  IPv6 (AAAA): 2606:2800:220:1:248:1893:25c8:1946

Зворотне розв'язання (Reverse lookup / PTR) для '93.184.216.34':
  Ім'я хоста: www.example.com
```

### Приклад 2. Демонстрація кешування DNS на рівні ОС

Замість написання низькорівневого парсера сирих DNS-пакетів (що виходить за межі стандартного `System.Net` і легко призводить до помилок у демонстраційному коді), покажемо більш практичну й гарантовано коректну річ: як виглядає ефект кешування DNS на рівні ОС при повторних викликах `Dns.GetHostEntry`.

```csharp
using System;
using System.Diagnostics;
using System.Net;

// Демонструє, що ОС (та резолвер) кешують DNS-відповіді:
// перший виклик — "холодний" (реальний мережевий запит),
// повторні виклики — значно швидші, бо відповідь вже лежить у кеші
// (з урахуванням TTL запису).
class DnsCachingDemo
{
    static void Main()
    {
        string hostname = "www.example.com";
        const int attempts = 5;

        Console.WriteLine($"Вимірюємо час розв'язання '{hostname}' {attempts} разів поспіль:\n");

        for (int i = 1; i <= attempts; i++)
        {
            var sw = Stopwatch.StartNew();
            IPHostEntry entry = Dns.GetHostEntry(hostname);
            sw.Stop();

            Console.WriteLine(
                $"Спроба #{i}: {sw.ElapsedMilliseconds,4} мс " +
                $"-> {entry.AddressList[0]}");
        }

        // Типова картина: перша спроба помітно повільніша (десятки-сотні мс,
        // бо потрібен реальний похід по мережі до резолвера, можливо аж до
        // authoritative-сервера), а наступні — практично миттєві (<1 мс),
        // бо ОС / стек резолвера / локальний DNS-кеш вже містять відповідь.
        //
        // Це саме те, чому: (1) TTL важливий — він контролює, як довго можна
        // довіряти кешу без повторного запиту; (2) в реальному моніторингу
        // варто мірити не лише "чи резолвиться ім'я", а й "скільки це триває" —
        // раптове сповільнення DNS-резолюції часто є раннім індикатором проблем.
    }
}
```

### Приклад 3. Спрощений відправник DHCP DISCOVER (ілюстративний)

> ⚠️ Це **навчальний, спрощений** приклад, що ілюструє лише механіку широкомовної відправки DHCPDISCOVER-пакета. Повноцінна реалізація DHCP-клієнта (на кшталт `dhclient` у Linux або вбудованого клієнта Windows) є значно складнішою: обробка DHCP options (код 53 — тип повідомлення, код 55 — parameter request list, код 61 — client identifier тощо), повторні спроби (retransmission з експоненційною затримкою), обробка OFFER від кількох серверів, підтримка REQUEST/ACK, керування lease (T1/T2 таймери) і т.д. Тут ми лише формуємо і надсилаємо мінімальний BOOTP/DHCP-пакет DISCOVER.

```csharp
using System;
using System.Net;
using System.Net.Sockets;

// Ілюструє лише крок "D" (Discover) з процесу DORA:
// формування мінімального DHCP-пакета та його broadcast-відправку
// на 255.255.255.255:67.
class DhcpDiscoverSender
{
    static void Main()
    {
        byte[] packet = BuildDhcpDiscoverPacket();

        using var socket = new Socket(AddressFamily.InterNetwork,
            SocketType.Dgram, ProtocolType.Udp);

        // Дозволяємо широкомовну відправку — обов'язково для DHCP,
        // адже клієнт ще не має власної IP-адреси і не може
        // відправити unicast конкретному серверу.
        socket.EnableBroadcast = true;

        // Клієнт слухає на порту 68, сервер — на порту 67.
        socket.Bind(new IPEndPoint(IPAddress.Any, 68));

        var broadcastEndpoint = new IPEndPoint(IPAddress.Broadcast, 67);

        socket.SendTo(packet, broadcastEndpoint);
        Console.WriteLine("✅ DHCPDISCOVER надіслано на 255.255.255.255:67");
        Console.WriteLine($"   Розмір пакета: {packet.Length} байт");

        // У реальному клієнті тут був би socket.ReceiveFrom(...) в циклі
        // з таймаутом, очікуючи DHCPOFFER від одного чи кількох серверів.
    }

    // Спрощена структура BOOTP/DHCP-пакета (RFC 2131 / RFC 951).
    // Реальний заголовок BOOTP має фіксовану довжину 236 байт
    // + "magic cookie" (4 байти) + опції (variable length, TLV-формат).
    static byte[] BuildDhcpDiscoverPacket()
    {
        byte[] packet = new byte[300];

        packet[0] = 0x01;                 // op: 1 = BOOTREQUEST (запит від клієнта)
        packet[1] = 0x01;                 // htype: 1 = Ethernet
        packet[2] = 0x06;                 // hlen: довжина MAC-адреси (6 байт)
        packet[3] = 0x00;                 // hops: 0 (заповнюється relay-агентами)

        // xid (transaction ID) — довільний унікальний ідентифікатор,
        // щоб клієнт міг зіставити OFFER із власним DISCOVER
        byte[] xid = BitConverter.GetBytes(new Random().Next());
        Array.Copy(xid, 0, packet, 4, 4);

        // secs (2 байти, offset 8) — скільки секунд минуло з початку спроби
        // flags (2 байти, offset 10) — старший біт: BROADCAST flag = 1,
        // бо клієнт ще не має IP і не може прийняти unicast-відповідь
        packet[10] = 0x80;

        // ciaddr (offset 12, 4 байти) — client IP, поки що 0.0.0.0
        // yiaddr (offset 16, 4 байти) — "your" IP, заповнить сервер у відповіді
        // siaddr (offset 20, 4 байти) — server IP
        // giaddr (offset 24, 4 байти) — relay agent IP, 0.0.0.0 якщо relay немає

        // chaddr (offset 28, 16 байт) — MAC-адреса клієнта (тут — приклад)
        byte[] fakeMac = { 0xDE, 0xAD, 0xBE, 0xEF, 0x00, 0x01 };
        Array.Copy(fakeMac, 0, packet, 28, fakeMac.Length);

        // Magic cookie (offset 236, 4 байти): 99.130.83.99 — позначає
        // початок секції DHCP-опцій (відрізняє DHCP від "чистого" BOOTP)
        byte[] magicCookie = { 99, 130, 83, 99 };
        Array.Copy(magicCookie, 0, packet, 236, 4);

        // DHCP Option 53 (DHCP Message Type) = 1 (DISCOVER)
        packet[240] = 53;  // код опції
        packet[241] = 1;   // довжина значення
        packet[242] = 1;   // значення: 1 = DHCPDISCOVER

        // Option 255 — маркер кінця списку опцій
        packet[243] = 255;

        return packet;
    }
}
```

### Приклад 4. `DnsHealthChecker` — перевірка "здоров'я" DNS-розв'язання для моніторингу

Реалістичний приклад, наближений до того, як інструмент мережевого моніторингу може перевіряти доступність сервісів: розв'язання DNS-імені варто перевіряти **окремо** від фактичної доступності самого сервісу, тому що "сайт не відкривається" іноді насправді означає "не працює саме DNS", а не мережа чи сам сервер.

```csharp
using System;
using System.Collections.Generic;
using System.Diagnostics;
using System.Net;
using System.Threading.Tasks;

// Результат перевірки одного імені хоста.
class DnsHealthResult
{
    public string Hostname { get; init; } = "";
    public bool Success { get; init; }
    public long ElapsedMilliseconds { get; init; }
    public string? ResolvedAddress { get; init; }
    public string? ErrorMessage { get; init; }
}

// Утиліта, яку міг би використовувати модуль моніторингу для перевірки
// того, що критичні для бізнесу доменні імена справно розв'язуються DNS-ом,
// і наскільки швидко це відбувається (сповільнення розв'язання —
// часто ранній сигнал проблем з DNS-інфраструктурою чи провайдером).
class DnsHealthChecker
{
    public async Task<List<DnsHealthResult>> CheckAllAsync(IEnumerable<string> hostnames)
    {
        var results = new List<DnsHealthResult>();

        foreach (string hostname in hostnames)
        {
            results.Add(await CheckOneAsync(hostname));
        }

        return results;
    }

    private async Task<DnsHealthResult> CheckOneAsync(string hostname)
    {
        var sw = Stopwatch.StartNew();
        try
        {
            IPAddress[] addresses = await Dns.GetHostAddressesAsync(hostname);
            sw.Stop();

            return new DnsHealthResult
            {
                Hostname = hostname,
                Success = true,
                ElapsedMilliseconds = sw.ElapsedMilliseconds,
                ResolvedAddress = addresses.Length > 0 ? addresses[0].ToString() : null
            };
        }
        catch (SocketException ex)
        {
            sw.Stop();
            return new DnsHealthResult
            {
                Hostname = hostname,
                Success = false,
                ElapsedMilliseconds = sw.ElapsedMilliseconds,
                ErrorMessage = $"{ex.SocketErrorCode}: {ex.Message}"
            };
        }
    }
}

class Program
{
    static async Task Main()
    {
        var monitoredHosts = new[]
        {
            "www.example.com",
            "www.google.com",
            "nonexistent-host-for-demo-12345.invalid" // навмисно неіснуюче ім'я
        };

        var checker = new DnsHealthChecker();
        List<DnsHealthResult> results = await checker.CheckAllAsync(monitoredHosts);

        Console.WriteLine("=== Звіт про здоров'я DNS-розв'язання ===\n");

        foreach (var r in results)
        {
            if (r.Success)
            {
                // Проста евристика: якщо розв'язання займає підозріло довго
                // (наприклад, > 500 мс), варто підняти окремий "degraded" алерт,
                // навіть якщо формально запит завершився успішно.
                string status = r.ElapsedMilliseconds > 500 ? "⚠️ ПОВІЛЬНО" : "✅ OK";

                Console.WriteLine(
                    $"{status}  {r.Hostname,-40} -> {r.ResolvedAddress,-15} " +
                    $"({r.ElapsedMilliseconds} мс)");
            }
            else
            {
                Console.WriteLine(
                    $"❌ ПОМИЛКА  {r.Hostname,-40} -> {r.ErrorMessage}");
            }
        }
    }
}
```

**Приклад виводу:**

```
=== Звіт про здоров'я DNS-розв'язання ===

✅ OK  www.example.com                          -> 93.184.216.34    (42 мс)
✅ OK  www.google.com                           -> 142.250.186.100  (38 мс)
❌ ПОМИЛКА  nonexistent-host-for-demo-12345.invalid -> HostNotFound: No such host is known
```

Такий підхід — окремий "DNS health" індикатор поряд зі звичайною перевіркою "ping / HTTP 200 OK" — дозволяє моніторинговій системі одразу повідомити саме "проблема в DNS", а не змушувати оператора самостійно з'ясовувати це під час інциденту.

## Реальний сценарій: чому DNS/DHCP важливі для мережевого моніторингу та IPAM

Для компанії, що виробляє продукти мережевого моніторингу та управління (як-от SolarWinds з лінійкою **Orion**, **NPM** — Network Performance Monitor, **NCM** — Network Configuration Manager, **IPAM** — IP Address Manager), DNS та DHCP — це не просто теоретичні протоколи, а щоденна операційна реальність, навколо якої побудована ціла категорія продукту (**IPAM**).

### 1. Конфлікти IP-адрес (IP Address Conflicts)

**Сценарій:** два пристрої в мережі одночасно отримують (або сконфігуровані на) одну й ту саму IP-адресу — наприклад:
- адміністратор вручну прописав статичну адресу `10.0.5.20` на сервері, не знаючи, що вона входить у діапазон DHCP-scope, і DHCP-сервер видав ту саму адресу іншому пристрою;
- два DHCP-сервери в мережі (навмисно чи помилково — наприклад, хтось підключив побутовий Wi-Fi роутер зі своїм DHCP) видають адреси з перетинних діапазонів.

**Наслідки:** непередбачувана поведінка мережі — пристрої по черзі "зникають" і "з'являються", ARP-конфлікти, складна для діагностики переривчаста втрата зв'язку.

**Як IPAM-інструменти допомагають:**
- Ведуть централізований реєстр (inventory) усіх виданих і зарезервованих IP-адрес — і статичних, і DHCP, і reservation — з єдиної точки видимості для всієї організації.
- Активно сканують мережу (ping sweep, SNMP, ARP-таблиці комутаторів) і **порівнюють** фактично виявлені адреси з тим, що "мало б бути" згідно з обліком — і піднімають алерт, щойно виявлено дублікат.
- Дозволяють "зарезервувати" в самому IPAM статичні діапазони, які DHCP-scope не повинен видавати, запобігаючи проблемі ще на етапі планування.

### 2. Вичерпання DHCP-scope (Scope Exhaustion)

**Сценарій:** DHCP-scope для підмережі (наприклад, `192.168.10.100`–`192.168.10.200`, 100 адрес) з часом заповнюється: нові ноутбуки, телефони, IoT-пристрої (принтери, камери, смарт-девайси) підключаються швидше, ніж старі оренди спливають і звільняються. Коли scope вичерпано — новий пристрій, що намагається приєднатись до мережі, **не отримує IP-адресу взагалі** і зазвичай сам собі призначає **APIPA-адресу** `169.254.x.x` — тобто фактично залишається без робочого мережевого підключення.

Це — один із найпоширеніших реальних тікетів у службу підтримки ("не працює Wi-Fi/мережа на новому пристрої", "принтер не в мережі" тощо), причому проблема часто проявляється хаотично: спрацьовує саме для пристроїв, які підключаються останніми (коли вже немає вільних адрес), а старі пристрої з активною орендою продовжують працювати нормально, що плутає непідготовлених адміністраторів.

**Як моніторингові інструменти допомагають:**
- Відстежують **відсоток утилізації** кожного DHCP-scope (наприклад, "used: 92/100 = 92%") і надсилають попереджувальний алерт задовго до повного вичерпання (типовий поріг — 80–90%), даючи адміністратору час розширити діапазон чи скоротити lease time, перш ніж це стане критичним інцидентом.
- Дозволяють бачити тренд утилізації в часі — щоб відрізнити разовий сплеск від системного зростання потреби в адресах (наприклад, компанія масштабується і підмережа стала замалою).

### 3. Зворотний DNS при виявленні пристроїв (Discovery)

Коли система моніторингу автоматично сканує мережу і знаходить нові пристрої (network discovery), вона зазвичай отримує "сирі" факти: IP-адресу, MAC-адресу, відповіді SNMP. Виконуючи **PTR-запит (зворотний DNS)** для кожної знайденої IP-адреси, інструмент може автоматично підставити людяне ім'я хоста (наприклад, `core-switch-floor2.corp.local`) замість голої IP-адреси `10.20.1.5` — це радикально покращує читабельність топологічних карт, списків пристроїв, звітів та сповіщень про інциденти ("Втрачено зв'язок з `core-switch-floor2`" зрозуміліше й швидше сприймається, ніж "Втрачено зв'язок з `10.20.1.5`").

Разом ці три сценарії пояснюють, чому продуктова категорія **IPAM** взагалі існує як окремий, комерційно затребуваний клас ПЗ: вона об'єднує в собі саме управління DHCP-scopes, DNS-записами та обліком IP-простору організації в одному інструменті, замість того, щоб адміністратори вели це вручну в Excel-таблицях (а на практиці — дуже і дуже часто саме так і роблять, що й породжує описані вище проблеми).

## Поширені проблеми та діагностика

| Симптом | Ймовірна причина | Діагностика |
|---|---|---|
| **Пристрій отримав адресу `169.254.x.x` (APIPA)** | DHCP-сервер недоступний, або DHCP-scope вичерпано, або відсутній DHCP relay/`ip helper` між підмережами | `ipconfig /all` — перевірити стан адаптера; перевірити доступність DHCP-сервера; перевірити утилізацію scope на сервері |
| **`nslookup`/`dig` повертає `NXDOMAIN`** | Запис справді не існує в зоні, або клієнт звертається не до того резолвера, або застарілий негативний кеш (TTL з поля SOA Minimum) | `nslookup <ім'я> <конкретний DNS-сервер>` — звернутись напряму до authoritative-сервера, обійшовши кеш проміжного резолвера |
| **Сайт доступний по IP, але недоступний по домену** | Проблема саме в DNS-розв'язанні (неправильний/відсутній A-запис, проблема резолвера), а не в мережевій доступності самого сервера | `ping <IP>` (працює) vs `ping <домен>` (не працює) підтверджує, що мережевий шлях справний, а несправний саме DNS-компонент |
| **DHCP-клієнт в іншій підмережі не отримує адресу** | На маршрутизаторі/L3-світчі відсутній налаштований DHCP Relay Agent (`ip helper-address`) — broadcast DISCOVER не долітає до централізованого DHCP-сервера в іншому VLAN | Перевірити конфігурацію інтерфейсу маршрутизатора на предмет `ip helper-address`; захопити трафік (packet capture) на клієнтському VLAN і перевірити, чи виходить DISCOVER за межі підмережі |
| **Різні клієнти отримують застарілу (протухлу) конфігурацію після зміни IP сервера** | Занадто високий TTL на змінюваному записі; клієнти кешують стару адресу до закінчення TTL | Знизити TTL заздалегідь перед плановою зміною; перевірити `ipconfig /displaydns` на клієнті на предмет застарілого запису |
| **Однаковий IP видано двом пристроям** | Перетин статичного діапазону з DHCP-scope, або кілька DHCP-серверів з конфліктуючими діапазонами (наприклад, "сторонній" роутер у мережі) | Порівняти облік IP (IPAM) з фактичним ARP/ping-скануванням; перевірити наявність несанкціонованих DHCP-серверів (rogue DHCP detection) |

### Корисні утиліти для діагностики

| Команда | Призначення |
|---|---|
| `nslookup <домен>` / `dig <домен>` | Виконати DNS-запит вручну, побачити тип запису, TTL, який сервер відповідав |
| `nslookup <домен> <сервер>` | Виконати запит до **конкретного** DNS-сервера, обходячи локальний кеш/резолвер за замовчуванням |
| `ipconfig /release` | Відмовитись від поточної DHCP-оренди (примусово "здати" IP-адресу) |
| `ipconfig /renew` | Ініціювати новий DORA-цикл і отримати нову оренду IP-адреси |
| `ipconfig /displaydns` | Показати вміст локального DNS-кеша ОС Windows |
| `ipconfig /flushdns` | Очистити локальний DNS-кеш (корисно після зміни запису з боку сервера, щоб не чекати TTL) |

## Питання та відповіді для співбесіди

**1. Поясни процес розв'язання DNS-імені крок за кроком.**
Клієнт звертається до рекурсивного резолвера (провайдера чи публічного, типу 8.8.8.8). Резолвер перевіряє свій кеш; якщо там пусто — послідовно (ітеративно) звертається до кореневого сервера, той повертає реферал на TLD-сервер (`.com`), TLD-сервер повертає реферал на authoritative-сервер домену, а authoritative-сервер вже повертає фінальний запис (наприклад, A-запис з IP-адресою). Резолвер кешує відповідь відповідно до TTL і повертає її клієнту.

**2. Чим рекурсивний запит відрізняється від ітеративного?**
При рекурсивному запиті сервер зобов'язаний повернути повну, фінальну відповідь (сам виконує всю подальшу роботу) — так працює запит клієнта до резолвера. При ітеративному запиті сервер повертає або фінальну відповідь, або "найкраще, що знає" — реферал на іншого, більш обізнаного сервера; так резолвер спілкується з root/TLD/authoritative серверами.

**3. Що таке TTL в DNS і навіщо він потрібен?**
TTL (Time To Live) — час у секундах, протягом якого резолвер/клієнт можуть вважати закешований запис актуальним, не звертаючись повторно до authoritative-сервера. Високий TTL знижує навантаження на DNS-інфраструктуру, але сповільнює поширення змін; низький TTL — навпаки, швидше поширює зміни ціною більшої кількості запитів.

**4. Назви основні типи DNS-записів і їх призначення.**
A (ім'я → IPv4), AAAA (ім'я → IPv6), CNAME (псевдонім на інше ім'я), MX (поштові сервери з пріоритетом), NS (авторитетні name-сервери зони), PTR (IP → ім'я, зворотний запис), TXT (довільний текст — SPF/DKIM/верифікація), SOA (метадані зони — serial/refresh/retry/expire/minimum TTL).

**5. Що таке PTR-запис?**
Запис, що виконує зворотне розв'язання: за IP-адресою повертає доменне ім'я. Зберігається у спеціальній зоні `in-addr.arpa` (IPv4) чи `ip6.arpa` (IPv6), де октети IP записані у зворотному порядку. Використовується, наприклад, для перевірки легітимності поштових серверів і для показу зрозумілих імен хостів у мережевих інструментах замість голих IP.

**6. Опиши DORA-процес DHCP.**
Discover — клієнт без IP надсилає broadcast-запит, шукаючи DHCP-сервер. Offer — сервер(и) пропонують вільну адресу зі свого scope. Request — клієнт broadcast'ом підтверджує, яку саме пропозицію приймає (щоб інші сервери звільнили свої резервовані адреси). Acknowledge — обраний сервер фіналізує оренду (lease).

**7. Чому DHCPREQUEST теж broadcast, а не unicast конкретному серверу?**
Тому що в мережі може бути декілька DHCP-серверів, які всі отримали DISCOVER і надіслали свої OFFER, тимчасово зарезервувавши адреси. Broadcast REQUEST бачать усі ці сервери одночасно — той, кого обрали, підтверджує оренду (ACK), а решта бачать, що їхню пропозицію не прийняли, і звільняють зарезервовані адреси назад у пул.

**8. Що таке DHCP relay і навіщо він потрібен?**
DHCP-повідомлення DISCOVER/REQUEST — broadcast, а маршрутизатори за замовчуванням не пересилають broadcast між підмережами. DHCP Relay Agent (наприклад, `ip helper-address` на Cisco-обладнанні) налаштовується на маршрутизаторі й перетворює отриманий broadcast-запит на unicast-пакет, спрямований безпосередньо на конкретний DHCP-сервер, що може перебувати в зовсім іншій підмережі — це дозволяє мати один централізований DHCP-сервер для багатьох VLAN/підмереж.

**9. Що таке DHCP reservation?**
Механізм, за яким конкретна MAC-адреса завжди отримує ту саму IP-адресу через DHCP. Налаштовується централізовано на DHCP-сервері (на відміну від суто статичної адреси на самому пристрої) і використовується для пристроїв, яким потрібна передбачувана адреса — принтерів, камер, серверів, мережевого обладнання.

**10. Що означає отримання IP-адреси `169.254.x.x`?**
Це APIPA (Automatic Private IP Addressing) — адреса, яку пристрій призначає собі сам, якщо не зміг отримати відповідь від жодного DHCP-сервера (сервер недоступний, scope вичерпано, немає relay до потрібної підмережі). Це ознака того, що DHCP не спрацював, а не проблема самого пристрою.

**11. Чим відрізняються T1 і T2 у DHCP lease renewal?**
T1 (50% від lease time) — клієнт намагається поновити оренду unicast-запитом напряму до оригінального сервера, який видав адресу. T2 (87.5% від lease time) — якщо T1 не дав результату (сервер недоступний), клієнт переходить до broadcast-запиту, сподіваючись отримати підтвердження від будь-якого DHCP-сервера в мережі. Якщо й це не спрацює до 100% lease time — адреса втрачається, і клієнт повертається до DISCOVER.

**12. Що таке DHCP scope?**
Логічна конфігурація на DHCP-сервері для конкретної підмережі: діапазон адрес, доступних для видачі, параметри (маска, шлюз, DNS, lease time), та виключення — адреси всередині діапазону, зарезервовані під статичну конфігурацію і не видавані динамічно.

**13. Що станеться, якщо DHCP-scope вичерпається?**
Нові пристрої, які намагаються приєднатись, не отримають IP-адресу від DHCP і, як правило, самопризначать собі APIPA-адресу (`169.254.x.x`), фактично залишившись без робочого мережевого з'єднання. Це одна з найчастіших причин "раптово перестала працювати мережа тільки для нових пристроїв" — старі пристрої з активною орендою продовжують працювати нормально.

**14. Навіщо мережевим моніторинговим інструментам потрібен зворотний DNS?**
Щоб при автоматичному виявленні пристроїв (discovery) перетворювати "сирі" знайдені IP-адреси на зрозумілі людині імена хостів (наприклад, замість `10.0.5.23` показувати `switch-core-01.corp.local`), що значно покращує читабельність топологій, звітів та сповіщень.

**15. У чому різниця між статичною IP-адресою, DHCP-адресою та DHCP reservation?**
Статична — вручну прописана на самому пристрої, DHCP про неї нічого не знає (ризик конфлікту, якщо потрапляє в діапазон scope). DHCP-адреса — видається динамічно з пулу scope на обмежений термін (lease) і може змінитись після закінчення оренди. DHCP reservation — теж видається через DHCP-протокол (тобто централізовано керується сервером і видно в IPAM), але завжди та сама конкретна адреса для конкретної MAC-адреси — поєднання зручності DHCP і передбачуваності статичної адреси.

**16. Як інструмент моніторингу може виявити конфлікт IP-адрес?**
Порівнюючи облікові дані (те, що зареєстровано в IPAM як видане/зарезервоване) з фактичним станом мережі, отриманим через активне сканування (ping, ARP-таблиці комутаторів, SNMP) — якщо одна адреса одночасно "відповідає" з двома різними MAC-адресами, або якщо статична адреса потрапляє у вільний діапазон активного DHCP-scope, система піднімає алерт про конфлікт.

**17. Чому важливо знизити TTL перед плановою міграцією сервера/зміною IP?**
Тому що клієнти й проміжні резолвери кешують попередню відповідь на час TTL і продовжуватимуть звертатись за старою IP-адресою, доки кеш не протухне. Знизивши TTL заздалегідь (наприклад, за добу до міграції), адміністратор гарантує, що після фактичної зміни запису нова адреса розповсюдиться значно швидше — вже за хвилини, а не за години/дні.

## Підсумок

### DNS — основні типи записів (шпаргалка)

| Тип | Що робить |
|---|---|
| A | ім'я → IPv4 |
| AAAA | ім'я → IPv6 |
| CNAME | псевдонім на інше ім'я |
| MX | поштовий сервер + пріоритет |
| NS | авторитетний name-сервер зони |
| PTR | IP → ім'я (зворотний запис) |
| TXT | довільний текст (SPF/DKIM/верифікація) |
| SOA | метадані зони (serial/refresh/retry/expire/minimum TTL) |

### DORA — DHCP одним рядком

```
DISCOVER (broadcast, клієнт шукає сервер)
   → OFFER (сервер пропонує адресу)
      → REQUEST (broadcast, клієнт підтверджує вибір)
         → ACK (сервер фіналізує оренду)

Renewal:  T1 (50% lease) → unicast до оригінального сервера
          T2 (87.5% lease) → broadcast до будь-якого сервера (fallback)
```

### Порти, які варто пам'ятати напам'ять

| Протокол | Порт | Транспорт |
|---|---|---|
| DNS (звичайні запити) | 53 | UDP (переважно), TCP (для великих відповідей, наприклад AXFR-трансфер зони) |
| DHCP-сервер | 67 | UDP |
| DHCP-клієнт | 68 | UDP |

### Три головні "болі", які пов'язують DNS/DHCP з мережевим моніторингом

1. **Конфлікт IP-адрес** — виявляється звірянням обліку (IPAM) з фактичним станом мережі.
2. **Вичерпання DHCP-scope** — попереджається моніторингом відсотка утилізації scope до досягнення критичного порогу.
3. **PTR/зворотний DNS при discovery** — перетворює "сирі" IP-адреси на зрозумілі імена хостів у топологіях та звітах.
