## Що таке рекурсія?

**Рекурсія** — це техніка, за якої функція розв'язує задачу, викликаючи **саму себе** для розв'язання меншої версії тієї самої задачі. Замість того щоб один раз описати всю послідовність кроків від початку до кінця, рекурсивна функція описує **лише одну "порцію" роботи** і довіряє розв'язання решти — своїй же копії, застосованій до простішого варіанту вхідних даних.

Щоб рекурсія працювала (і, головне, **зупинялась**), кожна коректна рекурсивна функція повинна мати два обов'язкові компоненти:

- **Базовий випадок (base case)** — найпростіший варіант задачі, який розв'язується **напряму**, без подальших рекурсивних викликів. Це та умова, яка зупиняє ланцюжок викликів. Без неї рекурсія не має способу завершитись.
- **Рекурсивний випадок (recursive case)** — крок, який розбиває задачу на **меншу** версію тієї самої задачі плюс якась додаткова робота (об'єднання результату), і викликає саму функцію для цієї меншої версії.

Ключова властивість, яку легко проґавити на перший погляд: рекурсивний випадок повинен **гарантовано наближати** вхідні дані до базового випадку з кожним викликом (менший масив, менше число, коротший рядок, глибше вкладення в дереві тощо). Якщо це наближення відсутнє або зламане логікою — рекурсія ніколи не досягне базового випадку, скільки б цей базовий випадок не був правильно написаний.

### Аналогія: матрьошка

Класична аналогія — **російська матрьошка**. Кожна лялька містить всередині трохи меншу ляльку тієї самої форми — доки не дістанешся до найменшої, суцільної ляльки, яка вже **не відкривається далі**. Розкриваючи матрьошку, ти виконуєш одну й ту саму дію ("відкрити, дістати меншу копію") знову і знову, аж поки не натрапиш на ляльку, яка є базовим випадком — вона просто *є*, її не треба далі розкривати.

Друга корисна аналогія — **пошук визначення слова у словнику**. Ти шукаєш слово "рекурсія", і у визначенні натрапляєш на слово "функція", якого не розумієш — доводиться шукати й його визначення. У визначенні "функції" може трапитись слово "відображення" — знову шукаєш. Це триває, доки не натрапиш на слово, визначене **простими, вже відомими** словами, без потреби шукати щось іще — оце і є базовий випадок для цього ланцюжка пошуків.

### Найпростіший приклад: факторіал

```csharp
// n! = n × (n-1) × (n-2) × ... × 1,   і за означенням 0! = 1
int Factorial(int n)
{
    // Базовий випадок: найпростіша версія задачі,
    // розв'язується напряму, БЕЗ подальшої рекурсії
    if (n <= 1)
    {
        return 1;
    }

    // Рекурсивний випадок: n! = n × (n-1)!
    // Задача звелась до тієї самої задачі, але для (n-1) —
    // тобто на крок ближче до базового випадку
    return n * Factorial(n - 1);
}
```

`Factorial(4)` не обчислює `4 × 3 × 2 × 1` за один прохід — натомість він каже "я поверну `4`, помножене на те, що поверне `Factorial(3)`", а `Factorial(3)` каже те саме про `Factorial(2)`, і так далі, доки `Factorial(1)` не поверне `1` напряму, без жодного подальшого виклику. Саме звідти й починається "розмотування" результату назад угору — детально це показано в наступному розділі.

> 🧩 **Головна ідея розділу:** рекурсія — це не магія і не "інший спосіб мислення", а конкретний інженерний прийом: **звести задачу до її ж меншої копії**, довіряючи, що ця менша копія буде розв'язана так само правильно (за принципом математичної індукції), і мати чітку точку зупинки, коли задача вже настільки проста, що подальше зведення не потрібне.

## Рекурсія і стек викликів

У файлі `../СтруктуриДаних/2-stacks-and-queues.md` вже було піднято зв'язок між рекурсією і стеком — тепер розберемо його детально, механічно, крок за кроком.

Коли функція викликає іншу функцію (або саму себе), середовище виконання (CLR у випадку .NET) виділяє для цього виклику новий **фрейм стека (stack frame)** — блок пам'яті, що містить:

- локальні змінні цього конкретного виклику;
- значення параметрів, з якими цей виклик був зроблений;
- адресу повернення — **місце в коді, куди потрібно повернутись** і продовжити виконання, коли цей виклик завершиться.

Цей фрейм **кладеться (push)** на вершину **call stack** — стека викликів процесу. Коли функція завершується (доходить до `return`), її фрейм **знімається (pop)** зі стека, і виконання продовжується рівно з того місця в коді функції-викликача, звідки був зроблений виклик — з тими значеннями локальних змінних викликача, які були на момент виклику.

Рекурсивний виклик — це виклик функції, яка **сама і є** функцією-викликачем. Тому кожен рекурсивний виклик кладе **ще один** фрейм на стек поверх попереднього, і стек росте вглиб, поки не буде досягнуто базового випадку.

### ASCII-діаграма: зростання і розмотування стека для `Factorial(4)`

**Фаза 1 — занурення (кожен виклик кладе новий фрейм):**

```
Виклик Factorial(4)
─────────────────────────────
│ Factorial(1) n=1           │  ← вершина стека, база: return 1
├─────────────────────────────┤
│ Factorial(2) n=2           │  чекає на результат Factorial(1)
├─────────────────────────────┤
│ Factorial(3) n=3           │  чекає на результат Factorial(2)
├─────────────────────────────┤
│ Factorial(4) n=4           │  чекає на результат Factorial(3)
└─────────────────────────────┘
        (дно стека)
```

Кожен фрейм "заморожений" у стані очікування — він зробив виклик і чекає, поки нижчий (глибший) виклик поверне значення, щоб продовжити свій власний `return n * ...`.

**Фаза 2 — розмотування (кожне повернення знімає фрейм і повертає результат наверх):**

```
Factorial(1) повертає 1              → Factorial(2) отримує 1
Factorial(2) обчислює 2*1=2, повертає → Factorial(3) отримує 2
Factorial(3) обчислює 3*2=6, повертає → Factorial(4) отримує 6
Factorial(4) обчислює 4*6=24, повертає остаточний результат: 24
```

Стек після кожного повернення стає на один фрейм коротшим, доки не спорожніє повністю, а виклик, що ініціював увесь ланцюжок, не отримає фінальне значення `24`.

### StackOverflowException — коли стек закінчується

Стек викликів має **фіксований, обмежений розмір** (типово порядку 1 МБ на потік у .NET за замовчуванням, хоча це можна змінити для окремого потоку). Кожен рекурсивний виклик, який ще не повернувся, займає місце на цьому стеку. Якщо рекурсія:

- **не має базового випадку** взагалі, або
- має базовий випадок, який **ніколи не досягається** через помилку в умові чи в тому, як зменшується вхідне значення, або
- просто **надто глибока** для легітимної задачі (наприклад, рекурсивний прохід по мільйону елементів там, де стек не витримає такої глибини),

— стек продовжує рости без обмеження, поки не вичерпає виділену пам'ять, і середовище виконання кидає `StackOverflowException`. Це прямий, безпосередній наслідок того, що кожен виклик — це реальний фрейм у реальній, обмеженій пам'яті, а не абстрактна "нескінченна" операція.

```csharp
// НЕБЕЗПЕЧНО: відсутній базовий випадок
int BrokenCountdown(int n)
{
    Console.WriteLine(n);
    return BrokenCountdown(n - 1); // ніколи не зупиниться —
                                    // n піде в мінус нескінченність,
                                    // стек переповниться і CLR
                                    // аварійно завершить процес
                                    // із StackOverflowException
}
```

На відміну від більшості винятків у .NET, `StackOverflowException` **не можна перехопити** блоком `try/catch` — переповнення стека завершує весь процес одразу, оскільки середовище виконання вже не має гарантії, що залишилось достатньо стекової пам'яті навіть для коректної обробки винятку. Це ще одна причина, чому правильний базовий випадок — не стилістична деталь, а вимога коректності програми.

## Рекурсія vs Ітерація

Важливий факт, який варто засвоїти на рівні "senior-розуміння": **будь-яке рекурсивне рішення можна переписати ітеративно** — за допомогою явної структури даних "стек" (`Stack<T>`), яку програміст керує вручну, замість того щоб покладатись на неявний call stack середовища виконання. Це не теоретична цікавинка — явний стек буквально виконує ту саму роботу, яку раніше виконував call stack: зберігає "де я зупинився і що робити далі", тільки тепер це видиме, кероване програмістом значення в купі (heap), а не прихована структура рантайму.

### Приклад: факторіал — рекурсивна і ітеративна версії

**Рекурсивна версія** (див. розділ 1) покладається на call stack:

```csharp
int FactorialRecursive(int n)
{
    if (n <= 1) return 1;
    return n * FactorialRecursive(n - 1);
}
```

**Ітеративна версія з явним циклом** — найпростіший варіант, без структури "стек" узагалі, бо факторіал не потребує "пам'ятати" проміжні виклики для об'єднання результату:

```csharp
int FactorialIterative(int n)
{
    int result = 1;
    for (int i = 2; i <= n; i++)
    {
        result *= i;
    }
    return result;
}
```

**Ітеративна версія з явним стеком** — навмисно "механічно" імітує те, що робив call stack, щоб наочно показати відповідність:

```csharp
int FactorialWithExplicitStack(int n)
{
    // Явний стек бере на себе роль call stack:
    // кожен "рекурсивний виклик" стає одним Push
    var pending = new Stack<int>();

    int current = n;
    while (current > 1)
    {
        pending.Push(current); // те, що зробив би виклик Factorial(current)
        current--;
    }

    // "Базовий випадок" — стартове значення для розмотування
    int result = 1;

    // "Розмотування" — те, що робили б послідовні return у рекурсії
    while (pending.Count > 0)
    {
        int value = pending.Pop();
        result *= value;
    }

    return result;
}
```

Ця версія навмисно багатослівна — вона демонструє, що явний `Stack<int>` виконує рівно ту саму роль, яку неявно виконував call stack у рекурсивній версії: накопичення "відкладеної роботи" під час занурення і послідовне її виконання під час розмотування.

### Приклад: сума елементів масиву

```csharp
// Рекурсивна версія
int SumRecursive(int[] array, int index)
{
    if (index >= array.Length) return 0; // базовий випадок: масив вичерпано
    return array[index] + SumRecursive(array, index + 1);
}

// Ітеративна версія — природньо простіша для цієї конкретної задачі,
// оскільки тут немає природної потреби "пам'ятати вкладеність"
int SumIterative(int[] array)
{
    int sum = 0;
    foreach (var value in array)
    {
        sum += value;
    }
    return sum;
}
```

### Чесне порівняння переваг і недоліків

Це не питання "рекурсія краща" чи "ітерація краща" — це інженерний компроміс, який варто розуміти чесно, без догматизму в обидва боки.

| Критерій | Рекурсія | Ітерація |
|---|---|---|
| **Читабельність для природньо рекурсивних задач** (дерева, обхід графів, деякі "розділяй і володарюй") | Часто набагато природніша й коротша — код відображає структуру задачі напряму | Часто вимагає явного стека/черги і "ручної" імітації того, що рекурсія робить безкоштовно |
| **Читабельність для лінійних задач** (сума масиву, факторіал, простий пошук) | Може здаватись зайвим ускладненням заради ускладнення | Зазвичай природніша й очевидніша — простий цикл |
| **Продуктивність** | Накладні витрати на кожен виклик функції (створення фрейму, збереження контексту, повернення) | Немає накладних витрат виклику функції — тільки інкремент лічильника й перехід у циклі |
| **Ризик переповнення стека** | Реальний ризик при глибокій рекурсії (глибокі дерева, великі n без хвостової оптимізації) | Відсутній — явний стек лежить у купі (heap), яка на порядки більша за стек викликів |
| **Пам'ять** | Неявна — кожен фрейм займає місце, поки виклик активний | Явна й контрольована — розробник бачить і контролює структуру даних напряму |

**Практичний висновок:** для задач із **природньою рекурсивною структурою** — обхід дерева, DFS у графі, деякі задачі "розділяй і володарюй" (детально в наступному документі `4-divide-and-conquer.md`) — рекурсія зазвичай дає код, який **прямо відображає** структуру задачі, і це варте невеликих накладних витрат на виклики. Для задач, які по суті **лінійні** (обхід масиву, накопичення суми, простий пошук) — ітерація зазвичай і простіша, і ефективніша, а рекурсія в такому випадку — це ускладнення заради ускладнення, а не заради ясності.

> ⚠️ Важливий нюанс для C#/.NET: на відміну від деяких функціональних мов, **CLR не гарантує оптимізацію хвостової рекурсії (tail-call optimization)** для звичайного JIT x64/x86 у загальному випадку — тобто навіть "правильна" хвостова рекурсія в C# не автоматично перетворюється компілятором на цикл і не усуває ризик переповнення стека для дуже глибокої рекурсії. Покладатись на TCO як на спосіб "безпечно" робити глибоку рекурсію в C# — ненадійна практика.

## Мемоізація рекурсії — уникнення повторних обчислень

Наступна проблема, яку варто побачити ще на рівні рекурсії (перед тим як повністю зайти в динамічне програмування у `6-dynamic-programming.md`), — це **повторне обчислення однакових підзадач**. Класичний приклад, що демонструє це найяскравіше, — наївна рекурсивна реалізація чисел Фібоначчі.

```csharp
// Наївна рекурсивна реалізація
// F(0) = 0, F(1) = 1, F(n) = F(n-1) + F(n-2)
int FibonacciNaive(int n)
{
    if (n <= 1) return n; // базовий випадок
    return FibonacciNaive(n - 1) + FibonacciNaive(n - 2);
}
```

Виглядає невинно і напряму слідує математичному означенню. Але подивимось, скільки разів насправді обчислюється, наприклад, `fib(3)` під час обчислення `fib(5)`:

### ASCII-діаграма: дерево рекурсії для `fib(5)` з повторюваними піддеревами

```
                              fib(5)
                          /            \
                      fib(4)             fib(3)          ← fib(3) тут
                     /      \            /     \            ОБЧИСЛЮЄТЬСЯ
                fib(3)      fib(2)   fib(2)   fib(1)          ВДРУГЕ
               /    \        /   \    /   \
          fib(2)  fib(1) fib(1) fib(0) fib(1) fib(0)
          /   \
      fib(1) fib(0)
```

Зверни увагу: `fib(3)` обчислюється **двічі** (в лівому і правому піддереві `fib(5)`), `fib(2)` обчислюється **тричі**, `fib(1)` і `fib(0)` — багато разів. І це лише для `n=5`. Загальна кількість викликів росте **експоненційно**, `O(2ⁿ)` — кожен виклик породжує ще два виклики, і так углиб на `n` рівнів. Для `n=30` це вже більш ніж мільйон викликів; для `n=40` — уже понад мільярд, що на практиці означає відчутне зависання програми на секунди чи навіть хвилини лише заради обчислення одного числа Фібоначчі.

Причина неефективності — **не** в самій ідеї рекурсії, а в тому, що ті самі підзадачі (той самий `n` для `fib`) розв'язуються знову і знову з нуля, хоча відповідь від попереднього разу вже відома і не зміниться.

### Мемоізація: кешування вже обчислених результатів

**Мемоізація** — це техніка збереження (кешування) результату виклику функції для конкретних вхідних значень, щоб при повторному виклику з тими самими значеннями результат просто **підглядався в кеші**, а не обчислювався заново.

```csharp
// Мемоізована версія — кешуємо результат для кожного n
int FibonacciMemoized(int n, Dictionary<int, long> cache)
{
    if (n <= 1) return n; // базовий випадок

    // Якщо результат для цього n вже обчислений — повертаємо його з кешу,
    // НЕ заглиблюючись у рекурсію знову
    if (cache.TryGetValue(n, out long cached))
    {
        return (int)cached;
    }

    // Інакше обчислюємо, і ОБОВ'ЯЗКОВО зберігаємо результат у кеш
    // перед тим, як повернути його — саме це прибирає повторні обчислення
    int result = FibonacciMemoized(n - 1, cache) + FibonacciMemoized(n - 2, cache);
    cache[n] = result;
    return result;
}
```

З кешуванням кожне значення `fib(k)` обчислюється рівно **один раз** за весь виклик — усі наступні звернення до нього миттєві (`O(1)` підглядання в словнику). Загальна складність падає з `O(2ⁿ)` до `O(n)` — принципова, а не косметична різниця.

> 🔁 **Це лише передвістя, не повне пояснення.** Мемоізація — це "рекурсія зверху вниз (top-down) з кешем", і вона є **одним із двох головних підходів динамічного програмування** (другий — табуляція, "знизу вгору"). Повне, системне пояснення динамічного програмування, класифікації задач із перетинними підзадачами й оптимальною підструктурою, а також порівняння мемоізації з табуляцією — тема окремого документа `6-dynamic-programming.md` далі в цій серії. Тут важливо запам'ятати одне: **якщо рекурсивна функція викликає себе з однаковими аргументами багато разів у різних гілках дерева рекурсії — це сигнал, що варто розглянути кешування**.

## Бектрекінг (Backtracking) — систематичний перебір з відсіканням

**Бектрекінг** — це уточнена форма рекурсивного повного перебору (brute force), яка будує розв'язок **поступово, крок за кроком**, і як тільки стає зрозуміло, що поточний частковий розв'язок **не може** привести до жодного коректного повного розв'язку — негайно "відступає назад" (backtrack) до попереднього кроку і пробує іншу альтернативу, замість того щоб добудовувати завідомо безглуздий шлях до самого кінця і перевіряти його лише в самому кінці.

### Аналогія: навігація в лабіринті

Уяви, що йдеш лабіринтом. На кожному перехресті є кілька напрямків. Наївний повний перебір без бектрекінгу — це піти в один напрямок і йти **аж до самого кінця цього шляху**, навіть якщо через два кроки видно, що це глухий кут, — і лише дійшовши до тупика, зрозуміти, що весь цей шлях був марним, після чого повернутись аж на самий початок і спробувати геть інший маршрут з нуля.

**Бектрекінг же діє розумніше**: щойно ти натрапляєш на глухий кут (або бачиш, що подальший рух гарантовано веде лише в глухі кути), ти одразу повертаєшся до **останнього перехрестя, де в тебе був невипробуваний вибір**, і пробуєш інший напрямок звідти — а не з самого початку лабіринту. Це і є суть бектрекінгу: локальне, негайне відкидання неперспективних гілок, а не сліпе доведення кожного можливого шляху до кінця.

### Загальний шаблон: вибір → дослідження → скасування вибору

Практично будь-яка задача бектрекінгу вкладається в один і той самий рекурсивний шаблон із трьох кроків:

```
Backtrack(частковий_розв'язок):
    якщо частковий_розв'язок повний і коректний:
        зафіксувати/вивести його
        повернутись

    для кожного можливого_наступного_кроку:
        якщо можливого_наступного_кроку є валідним ЗАРАЗ (відсікання):

            1. ВИБІР (choose):
               додати можливого_наступного_кроку до часткового_розв'язку

            2. ДОСЛІДЖЕННЯ (explore):
               рекурсивно викликати Backtrack(оновлений частковий_розв'язок)

            3. СКАСУВАННЯ ВИБОРУ (un-choose):
               прибрати можливого_наступного_кроку з часткового_розв'язку,
               ПОВЕРНУВШИ стан до того, яким він був ДО кроку 1 —
               щоб наступна ітерація цього ж циклу почала
               з чистого стану, а не з "забрудненого" попереднім вибором
```

Крок 3 — **скасування вибору (undo)** — це саме те, що **відрізняє бектрекінг від звичайної рекурсивної переборки без відкату**. Без цього кроку зміни, зроблені для дослідження однієї гілки, "просочуються" в наступні гілки, які виконуються в тому самому циклі, і псують їхні результати. Детальний, конкретний приклад цієї помилки з поламаним і виправленим кодом наведено в розділі 9.

**Відсікання (pruning)** — перевірка "чи можливого_наступного_кроку валиден ЗАРАЗ" **перед** тим, як заглиблюватись у рекурсію для нього. Це і є те, що робить бектрекінг практично набагато швидшим за наївний повний перебір: замість того щоб рекурсивно дослідити цілу гілку й лише в самому кінці зрозуміти, що вона нікуди не веде, бектрекінг перевіряє це **одразу на вході** в гілку і взагалі не витрачає час на дослідження свідомо мертвих шляхів. Теоретична найгірша складність часто лишається експоненційною (адже в найгіршому випадку відсікання може нічого не відсікти), але на практиці для більшості реальних вхідних даних відсікання **різко** скорочує реальний обсяг перебору — інколи на порядки.

## Класичні задачі бектрекінгу

Розберемо три класичні задачі, у кожній явно виділяючи вибір / дослідження / скасування вибору.

### Генерація всіх перестановок (Permutations)

**Задача:** для множини з `n` елементів згенерувати всі `n!` можливих порядків їх розташування.

**Підхід:** на кожному кроці **обираємо** один із ще не використаних елементів як наступний у поточній перестановці, **рекурсивно** добудовуємо решту перестановки з елементів, що залишились, а після повернення з рекурсії **скасовуємо вибір** — позначаємо елемент знову невикористаним, щоб цикл міг спробувати наступний невикористаний елемент на цій самій позиції.

```
Permute(поточна_перестановка, використані):
    якщо поточна_перестановка містить усі n елементів:
        зафіксувати поточну_перестановка як готову перестановку
        повернутись

    для кожного елемента e, який ще НЕ використаний:
        # ВИБІР
        додати e до поточна_перестановка
        позначити e як використаний

        # ДОСЛІДЖЕННЯ
        Permute(поточна_перестановка, використані)

        # СКАСУВАННЯ ВИБОРУ
        видалити e з поточна_перестановка
        позначити e знову як НЕ використаний
```

Без кроку "скасування вибору" елемент `e`, обраний для однієї гілки перебору, лишився б позначеним "використаний" і для наступних, братніх гілок цього ж циклу — тож ці гілки помилково вважали б `e` недоступним, хоча насправді він мав бути доступний для них.

### Генерація всіх підмножин (Subsets / Power Set)

**Задача:** для множини з `n` елементів згенерувати всі `2ⁿ` можливих підмножин (включно з порожньою множиною і самою множиною повністю).

**Підхід:** тут вибір інший — не "який елемент обрати далі", а для **кожного** елемента множини (в порядку їх перегляду): **обираємо** — включити його в поточну підмножину чи ні, і **рекурсуємо в обидва боки**.

```
Subsets(індекс, поточна_підмножина):
    якщо індекс == n (усі елементи розглянуто):
        зафіксувати поточна_підмножина як готову підмножину
        повернутись

    елемент = елементи[індекс]

    # Гілка 1: ВИБІР — включити елемент
    додати елемент до поточна_підмножина
    Subsets(індекс + 1, поточна_підмножина)      # ДОСЛІДЖЕННЯ
    видалити елемент з поточна_підмножина          # СКАСУВАННЯ ВИБОРУ

    # Гілка 2: ВИБІР — НЕ включати елемент
    # (тут "скасовувати" нічого не треба — стан і так не змінювався)
    Subsets(індекс + 1, поточна_підмножина)
```

Показово, що в другій гілці ("не включати") кроку "скасування" не потрібно взагалі, оскільки стан не змінювався — це підкреслює, що "скасування вибору" — це буквально відкат **саме тих** змін, які були зроблені на кроці "вибір", не більше й не менше.

### N Ferziehs (N-Queens) — задача про N ферзів

**Задача:** розставити `N` ферзів на дошці `N×N` так, щоб жоден ферзь не атакував іншого — тобто жодні два ферзі не стоять на одному рядку, одному стовпці чи одній діагоналі.

**Підхід:** оскільки в кожному рядку може бути щонайбільше один ферзь (інакше вони атакують одне одного по рядку), задачу зручно вирішувати рядок за рядком: розставляємо ферзя в поточному рядку, рекурсивно переходимо до наступного рядка; якщо в якомусь рядку **немає жодного валідного стовпця** для розстановки — це і є сигнал відступити (backtrack) до попереднього рядка й спробувати там інший стовпець.

```
SolveQueens(рядок, розстановка):
    якщо рядок == N (усі рядки заповнено):
        зафіксувати розстановка як валідний розв'язок
        повернутись

    для кожного стовпця c від 0 до N-1:
        якщо IsSafe(рядок, c, розстановка):   # ← ВІДСІКАННЯ
            # ВИБІР
            поставити ферзя в (рядок, c)

            # ДОСЛІДЖЕННЯ
            SolveQueens(рядок + 1, розстановка)

            # СКАСУВАННЯ ВИБОРУ
            прибрати ферзя з (рядок, c)
```

Ключова роль **відсікання (`IsSafe`)** тут особливо наочна: перевірка "чи стовпець `c` у поточному рядку не конфліктує з уже розставленими ферзями по стовпцю чи діагоналі" робиться **до** того, як рекурсія взагалі заглибиться в наступний рядок із цим вибором. Без цієї перевірки алгоритм заглиблювався б у явно тупикові гілки (де конфлікт по діагоналі вже гарантований) і виявляв би це лише набагато пізніше, витрачаючи величезну кількість зайвої роботи. Саме завдяки такому ранньому відсіканню N-Queens із бектрекінгом на практиці розв'язується для дошок розміром 8×8, 12×12 і навіть більших за прийнятний час, тоді як сліпий повний перебір усіх `Nᴺ` можливих розстановок ферзів по рядках (без жодної перевірки по ходу) став би непрактичним уже для відносно малих `N`.

## Практичні приклади на C#

### Приклад 1 — факторіал: рекурсія vs ітерація з явним стеком

```csharp
using System;
using System.Collections.Generic;

int callCount = 0;

int FactorialRecursive(int n)
{
    callCount++; // рахуємо кількість фреймів у стеку викликів
    if (n <= 1) return 1;
    return n * FactorialRecursive(n - 1);
}

int FactorialWithExplicitStack(int n)
{
    var pending = new Stack<int>();
    int current = n;
    while (current > 1)
    {
        pending.Push(current);
        current--;
    }

    int result = 1;
    while (pending.Count > 0)
    {
        result *= pending.Pop();
    }
    return result;
}

int n = 10;
callCount = 0;
int recursiveResult = FactorialRecursive(n);
Console.WriteLine($"Рекурсивний результат: {recursiveResult}");
Console.WriteLine($"Кількість фреймів у стеку викликів: {callCount}");

int iterativeResult = FactorialWithExplicitStack(n);
Console.WriteLine($"Ітеративний (явний стек) результат: {iterativeResult}");

// Вивід:
// Рекурсивний результат: 3628800
// Кількість фреймів у стеку викликів: 10
// Ітеративний (явний стек) результат: 3628800
```

Для `n=10` рекурсивна версія створює **10 вкладених фреймів**, які одночасно перебувають на стеку викликів у момент найглибшого занурення (`Factorial(1)`). Для малих `n` це абсолютно нешкідливо, але варто усвідомлювати: якби хтось викликав подібну наївну рекурсію з `n`, що дорівнює сотням тисяч (наприклад, рекурсивний прохід по дуже довгому зв'язному списку "по одному елементу за раз"), це реально ризикує вилитись у `StackOverflowException` — саме тому для потенційно глибокої, лінійної за своєю природою рекурсії ітеративна версія — безпечніший вибір за замовчуванням.

### Приклад 2 — наївний і мемоізований Фібоначчі: порівняння кількості викликів

```csharp
using System;
using System.Collections.Generic;

int naiveCallCount = 0;

long FibonacciNaive(int n)
{
    naiveCallCount++;
    if (n <= 1) return n;
    return FibonacciNaive(n - 1) + FibonacciNaive(n - 2);
}

int memoCallCount = 0;

long FibonacciMemoized(int n, Dictionary<int, long> cache)
{
    memoCallCount++;
    if (n <= 1) return n;

    if (cache.TryGetValue(n, out long cached))
    {
        return cached;
    }

    long result = FibonacciMemoized(n - 1, cache) + FibonacciMemoized(n - 2, cache);
    cache[n] = result;
    return result;
}

int n = 35;

naiveCallCount = 0;
long naiveResult = FibonacciNaive(n);
Console.WriteLine($"Наївний fib({n}) = {naiveResult}, викликів функції: {naiveCallCount}");

memoCallCount = 0;
var cache = new Dictionary<int, long>();
long memoResult = FibonacciMemoized(n, cache);
Console.WriteLine($"Мемоізований fib({n}) = {memoResult}, викликів функції: {memoCallCount}");

// Приблизний вивід (точні числа для наївної версії залежать від n,
// але порядок величини завжди такий):
// Наївний fib(35) = 9227465, викликів функції: 29860703
// Мемоізований fib(35) = 9227465, викликів функції: 69
```

Різниця вражає навіть при поверхневому погляді: наївна версія для `n=35` робить **майже 30 мільйонів** викликів функції, тоді як мемоізована версія — лише **69** (по одному на кожне унікальне значення `0..35`, плюс кілька викликів на "підглядання" в кеш). Обидві версії повертають абсолютно однаковий результат — різниця виключно в тому, скільки зайвої роботи виконується заради того самого результату.

### Приклад 3 — генерація всіх перестановок

```csharp
using System;
using System.Collections.Generic;

void Permute(List<int> elements, List<int> current, bool[] used, List<List<int>> results)
{
    // Базовий випадок: перестановка повністю зібрана
    if (current.Count == elements.Count)
    {
        results.Add(new List<int>(current)); // копія, бо current ще змінюватиметься
        return;
    }

    for (int i = 0; i < elements.Count; i++)
    {
        if (used[i]) continue; // елемент уже задіяний у поточній гілці — пропускаємо

        // 1. ВИБІР
        current.Add(elements[i]);
        used[i] = true;

        // 2. ДОСЛІДЖЕННЯ
        Permute(elements, current, used, results);

        // 3. СКАСУВАННЯ ВИБОРУ — критично важливий крок!
        current.RemoveAt(current.Count - 1);
        used[i] = false;
    }
}

var elements = new List<int> { 1, 2, 3, 4 };
var results = new List<List<int>>();
Permute(elements, new List<int>(), new bool[elements.Count], results);

Console.WriteLine($"Загалом перестановок: {results.Count}"); // 4! = 24
foreach (var perm in results)
{
    Console.WriteLine(string.Join(", ", perm));
}

// Вивід (перші кілька рядків):
// Загалом перестановок: 24
// 1, 2, 3, 4
// 1, 2, 4, 3
// 1, 3, 2, 4
// ... (усього 24 рядки)
```

### Приклад 4 — генерація всіх підмножин (Power Set)

```csharp
using System;
using System.Collections.Generic;

void Subsets(List<int> elements, int index, List<int> current, List<List<int>> results)
{
    // Базовий випадок: усі елементи розглянуто (включено чи ні)
    if (index == elements.Count)
    {
        results.Add(new List<int>(current));
        return;
    }

    int element = elements[index];

    // Гілка 1: ВИБІР — включити елемент
    current.Add(element);
    Subsets(elements, index + 1, current, results); // ДОСЛІДЖЕННЯ
    current.RemoveAt(current.Count - 1);            // СКАСУВАННЯ ВИБОРУ

    // Гілка 2: ВИБІР — не включати елемент (стан не змінювався — нічого скасовувати)
    Subsets(elements, index + 1, current, results); // ДОСЛІДЖЕННЯ
}

var elements = new List<int> { 1, 2, 3 };
var results = new List<List<int>>();
Subsets(elements, 0, new List<int>(), results);

Console.WriteLine($"Загалом підмножин: {results.Count}"); // 2^3 = 8
foreach (var subset in results)
{
    string text = subset.Count == 0 ? "{}" : "{ " + string.Join(", ", subset) + " }";
    Console.WriteLine(text);
}

// Вивід:
// Загалом підмножин: 8
// { 1, 2, 3 }
// { 1, 2 }
// { 1, 3 }
// { 1 }
// { 2, 3 }
// { 2 }
// { 3 }
// {}
```

### Приклад 5 — розв'язання N-Queens з відсіканням

```csharp
using System;
using System.Collections.Generic;

int solutionsFound = 0;
List<int[]> allSolutions = new List<int[]>();

bool IsSafe(int[] placement, int row, int col)
{
    // Перевіряємо конфлікт із УЖЕ розставленими ферзями (рядки 0..row-1)
    for (int prevRow = 0; prevRow < row; prevRow++)
    {
        int prevCol = placement[prevRow];

        // Той самий стовпець
        if (prevCol == col) return false;

        // Та сама діагональ (різниця рядків == різниці стовпців за модулем)
        if (Math.Abs(prevCol - col) == Math.Abs(prevRow - row)) return false;
    }
    return true; // конфліктів немає — розстановка безпечна
}

void SolveQueens(int[] placement, int row, int n)
{
    if (row == n)
    {
        solutionsFound++;
        allSolutions.Add((int[])placement.Clone());
        return;
    }

    for (int col = 0; col < n; col++)
    {
        if (IsSafe(placement, row, col)) // ВІДСІКАННЯ: перевірка перед рекурсією
        {
            // ВИБІР
            placement[row] = col;

            // ДОСЛІДЖЕННЯ
            SolveQueens(placement, row + 1, n);

            // СКАСУВАННЯ ВИБОРУ
            placement[row] = -1;
        }
    }
}

void PrintBoard(int[] placement, int n)
{
    for (int row = 0; row < n; row++)
    {
        var line = new char[n];
        for (int col = 0; col < n; col++)
        {
            line[col] = (placement[row] == col) ? 'Q' : '.';
        }
        Console.WriteLine(new string(line));
    }
}

int n = 8;
var placement = new int[n];
Array.Fill(placement, -1);

SolveQueens(placement, 0, n);

Console.WriteLine($"Знайдено розв'язків для N={n}: {solutionsFound}");
Console.WriteLine("Приклад одного розв'язку:");
PrintBoard(allSolutions[0], n);

// Вивід:
// Знайдено розв'язків для N=8: 92
// Приклад одного розв'язку:
// Q.......
// ....Q...
// .......Q
// .....Q..
// ..Q.....
// ......Q.
// .Q......
// ...Q....
```

Класичний факт: для `N=8` існує рівно **92 різні розв'язки** (12, якщо не рахувати дзеркальні й повернуті варіанти як різні). Без відсікання (`IsSafe`, перевіреного до рекурсії) алгоритм довелось би застосовувати до всіх `8⁸ ≈ 16.7` мільйонів комбінацій розстановок ферзів по рядках і перевіряти кожну **лише в кінці** — з відсіканням реальна кількість досліджуваних часткових розстановок на порядки менша, оскільки переважна більшість гілок відкидається задовго до того, як дошка заповнюється повністю.

## Реальний сценарій: генерація всіх можливих комбінацій знижок для промо-кампанії

Повернімось до архітектури e-commerce системи (див. `ecommerce-architecture-guide.md` і обговорення Strategy/Decorator для знижок у розділах цієї серії, присвячених патернам). Уяви таку постановку задачі від відділу маркетингу:

> "У нас є список кандидатів на акції для майбутньої кампанії: наприклад, `10% знижка на електроніку`, `безкоштовна доставка від $50`, `купи один — другий у подарунок на вибрані товари`, `сезонна знижка 5% на все`, `бонусні бали x2`. Ми хочемо перевірити **всі можливі комбінації** одночасно активних акцій і знайти ту комбінацію, яка максимізує прогнозований прибуток на тестовому наборі замовлень — але з обмеженням: **не більше двох акцій одночасно можуть застосовуватись до одного замовлення** (щоб уникнути надмірного накопичення знижок)."

### Чому це задача бектрекінгу/генерації підмножин, а не простого циклу

На перший погляд може здатись, що досить простого циклу `foreach` по акціях. Але задача насправді просить оцінити **кожну можливу підмножину** акцій (яку саме комбінацію одночасно ввімкнути), а не кожну акцію окремо — і кількість таких підмножин для `n` акцій-кандидатів дорівнює `2ⁿ` (для кожної акції: увімкнена чи ні в цій конкретній комбінації). Це рівно та сама структура, що й генерація підмножин (Power Set) із розділу 6 — тільки замість абстрактних чисел `{1, 2, 3}` елементами множини є об'єкти-стратегії знижок.

Обмеження ("не більше двох акцій одночасно") — це природний кандидат на **відсікання**: щойно часткова комбінація вже містить дві акції, немає сенсу продовжувати рекурсивно розглядати гілки, які додають третю, — таку гілку можна відкинути **одразу**, не добудовуючи її до кінця і не витрачаючи час на повну оцінку прибутку для завідомо недопустимої комбінації.

```csharp
// Спрощена модель: кандидат на акцію з умовною оцінкою впливу на прибуток
class PromoRule
{
    public string Name { get; init; } = "";
    public Func<Order, decimal> EstimatedRevenueImpact { get; init; } = _ => 0m;
}

class Order
{
    public decimal BaseTotal { get; init; }
    public string Category { get; init; } = "";
}

const int MaxStackedPromotions = 2;

decimal bestRevenue = decimal.MinValue;
List<PromoRule> bestCombination = new();

void ExploreCombinations(
    List<PromoRule> candidates,
    int index,
    List<PromoRule> currentCombination,
    List<Order> sampleOrders)
{
    // Базовий випадок: усі кандидати розглянуті — оцінюємо поточну комбінацію
    if (index == candidates.Count)
    {
        decimal totalRevenue = EstimateTotalRevenue(currentCombination, sampleOrders);
        if (totalRevenue > bestRevenue)
        {
            bestRevenue = totalRevenue;
            bestCombination = new List<PromoRule>(currentCombination);
        }
        return;
    }

    var candidate = candidates[index];

    // Гілка "не включати цю акцію" — завжди допустима, без обмежень
    ExploreCombinations(candidates, index + 1, currentCombination, sampleOrders);

    // Гілка "включити цю акцію" — ВІДСІКАННЯ перед рекурсією:
    // якщо вже досягли ліміту стекування — цю гілку взагалі не досліджуємо
    if (currentCombination.Count < MaxStackedPromotions)
    {
        // ВИБІР
        currentCombination.Add(candidate);

        // ДОСЛІДЖЕННЯ
        ExploreCombinations(candidates, index + 1, currentCombination, sampleOrders);

        // СКАСУВАННЯ ВИБОРУ
        currentCombination.RemoveAt(currentCombination.Count - 1);
    }
}

decimal EstimateTotalRevenue(List<PromoRule> combination, List<Order> sampleOrders)
{
    decimal total = 0m;
    foreach (var order in sampleOrders)
    {
        decimal orderRevenue = order.BaseTotal;
        foreach (var rule in combination)
        {
            orderRevenue += rule.EstimatedRevenueImpact(order);
        }
        total += orderRevenue;
    }
    return total;
}
```

Відсікання `if (currentCombination.Count < MaxStackedPromotions)` — це саме те, що не дає алгоритму навіть спробувати дослідити комбінації з трьома й більше одночасними акціями: такі гілки відкидаються на вході, а не після повного перебору й оцінки.

### Чесний масштабний застереження (scope caveat)

Це рішення елегантне і напряму відповідає на бізнес-питання — але важливо **чесно** визнати його межі масштабованості:

- Складність підходу — `O(2ⁿ × m)`, де `n` — кількість акцій-кандидатів, а `m` — розмір тестового набору замовлень, на якому оцінюється кожна комбінація. Експоненційний множник `2ⁿ` означає, що підхід **практично застосовний лише для невеликого `n`** — умовно кажучи, для 10-20 акцій-кандидатів (`2¹⁰ = 1024`, `2²⁰ ≈ мільйон` комбінацій) це ще цілком реально прорахувати; але вже для 40-50 акцій-кандидатів (`2⁴⁰` — понад трильйон) цей самий підхід стає обчислювально нездійсненним у прийнятний час, скільки б потужним не був сервер.
- У реальному маркетинговому відділі кількість одночасно розглянутих кандидатів на акції для однієї кампанії, як правило, справді невелика (одиниці-десятки), тому цей підхід часто застосовний "як є". Але якби бізнес-вимога змінилась (наприклад, "перебрати комбінації з сотень регіональних промо-правил"), чесна сеньйорська відповідь — **не** "запустимо той самий алгоритм на потужнішому сервері", а визнання, що експоненційна природа задачі вимагає **іншого підходу**: евристик, жадібних наближень (`5-greedy-algorithms.md` далі в цій серії), обмеження простору пошуку доменними правилами (наприклад, наперед відомі несумісні категорії акцій), або взагалі відмови від точного перебору на користь наближеної оптимізації.

Це якраз той випадок, коли розуміння того, що "рішення технічно правильне, елегантне, і водночас має жорстку експоненційну межу застосовності" — і є ознакою зрілого інженерного судження, а не лише вміння написати код бектрекінгу.

## Поширені помилки

### Помилка 1 — забутий крок "скасування вибору" в бектрекінгу

Це, мабуть, найпоширеніша й найпідступніша помилка при першому знайомстві з бектрекінгом: код компілюється, навіть іноді видає правдоподібний перший результат — але дає **неправильні** підмножини/перестановки/розстановки, бо стан "просочується" між братніми гілками рекурсії.

**❌ Погано — забутий undo:**

```csharp
void PermuteBroken(List<int> elements, List<int> current, bool[] used, List<List<int>> results)
{
    if (current.Count == elements.Count)
    {
        results.Add(new List<int>(current));
        return;
    }

    for (int i = 0; i < elements.Count; i++)
    {
        if (used[i]) continue;

        current.Add(elements[i]);
        used[i] = true;

        PermuteBroken(elements, current, used, results);

        // ЗАБУТО: current.RemoveAt(current.Count - 1);
        // ЗАБУТО: used[i] = false;
        // Наслідок: після повернення з рекурсії елемент elements[i]
        // назавжди лишається в current і позначений used[i] = true,
        // тому наступні ітерації цього ж циклу for бачать
        // "забруднений" список і брехливо позначений used —
        // результати будуть неповними, з дублюванням і пропущеними варіантами
    }
}
```

**✅ Добре — з правильним undo:**

```csharp
void PermuteFixed(List<int> elements, List<int> current, bool[] used, List<List<int>> results)
{
    if (current.Count == elements.Count)
    {
        results.Add(new List<int>(current));
        return;
    }

    for (int i = 0; i < elements.Count; i++)
    {
        if (used[i]) continue;

        current.Add(elements[i]);
        used[i] = true;

        PermuteFixed(elements, current, used, results);

        // Скасування вибору ПОВЕРТАЄ стан до того, яким він був
        // перед цією ітерацією — наступна ітерація циклу починає "з чистого"
        current.RemoveAt(current.Count - 1);
        used[i] = false;
    }
}
```

Правило, яке варто зробити звичкою: **кожна зміна спільного (mutable) стану, зроблена безпосередньо перед рекурсивним викликом, повинна мати симетричну, точну "відкатну" операцію одразу після нього** — перш ніж цикл перейде до наступної ітерації.

### Помилка 2 — рекурсія без коректного базового випадку (або з недосяжним базовим випадком)

**❌ Погано — базовий випадок є, але недосяжний через помилку в кроці наближення:**

```csharp
int CountdownBroken(int n)
{
    if (n == 0) return 0; // базовий випадок виглядає правильним

    Console.WriteLine(n);
    return CountdownBroken(n); // ПОМИЛКА: викликаємо з тим самим n!
                                // n ніколи не зменшується, тому n == 0
                                // ніколи не настане для n > 0 —
                                // StackOverflowException неминучий
}
```

**✅ Добре — базовий випадок і гарантоване наближення до нього:**

```csharp
int CountdownFixed(int n)
{
    if (n <= 0) return 0; // базовий випадок

    Console.WriteLine(n);
    return CountdownFixed(n - 1); // n ГАРАНТОВАНО зменшується щоразу —
                                    // рано чи пізно досягне <= 0
}
```

Помилка тут не в **відсутності** базового випадку (він написаний), а в тому, що рекурсивний виклик забув зменшити `n` — тобто **не наближає** вхідні дані до умови базового випадку. Це підступніший різновид тієї самої проблеми, ніж просто "забув написати `if`" — код виглядає структурно правильним при побіжному погляді, але логічно ніколи не зупиниться.

### Помилка 3 — немемоізована рекурсія для задачі з перетинними підзадачами при потенційно великому вході

**❌ Ризиковано — виглядає нешкідливо в юніт-тесті з малим n, але є прихованою бомбою сповільненої дії:**

```csharp
// Проходить юніт-тест з n=10 за мілісекунди — здається абсолютно нормальним
long CalculateBonus(int n)
{
    if (n <= 1) return n;
    return CalculateBonus(n - 1) + CalculateBonus(n - 2);
}

// Але якщо ця функція викликається з бізнес-даними, де n може
// дорівнювати, скажімо, "кількість місяців стажу співробітника" (n=40+),
// або, гірше, значення надходить від зовнішнього API без валідації верхньої межі —
// час виконання вибухає експоненційно, і запит, що раніше виконувався
// миттєво, раптом "зависає" на секунди чи хвилини (а при паралельних
// запитах — може покласти сервіс, вичерпавши CPU)
```

**✅ Добре — усвідомлене рішення з мемоізацією (або перехід на ітеративний/табуляційний підхід із `6-dynamic-programming.md`):**

```csharp
long CalculateBonus(int n, Dictionary<int, long> cache)
{
    if (n <= 1) return n;
    if (cache.TryGetValue(n, out long cached)) return cached;

    long result = CalculateBonus(n - 1, cache) + CalculateBonus(n - 2, cache);
    cache[n] = result;
    return result;
}
```

Небезпека цієї помилки саме в тому, що вона **не проявляється** на малих тестових даних — код "проходить рев'ю", проходить юніт-тести, і лише в продакшені, коли реальний вхід виявляється більшим за той, що тестувався розробником, стає видно експоненційний вибух. Це прямий місток до того, чому динамічне програмування (`6-dynamic-programming.md`) — не факультативна тема "для екзотичних задач", а практичний навик розпізнавання перетинних підзадач до того, як вони перетворяться на інцидент.

## Питання для співбесіди за рівнями

### Junior

**1. Що таке рекурсія і які два обов'язкові компоненти вона повинна мати?**

Рекурсія — це функція, яка викликає саму себе для розв'язання меншої версії тієї самої задачі. Обов'язкові компоненти: **базовий випадок** (найпростіша версія задачі, що розв'язується напряму, без подальшої рекурсії, і зупиняє ланцюжок викликів) і **рекурсивний випадок** (крок, що зводить задачу до меншої версії тієї самої задачі й викликає функцію для цієї меншої версії).

**2. Що станеться, якщо забути базовий випадок у рекурсивній функції?**

Функція викликатиме сама себе нескінченно (або доки не буде досягнуто якоїсь випадкової умови зупинки, якщо є). Кожен виклик кладе новий фрейм на стек викликів, стек має обмежений розмір, і рано чи пізно програма впаде з `StackOverflowException`.

**3. Чим рекурсія пов'язана зі стеком викликів?**

Кожен виклик функції (зокрема рекурсивний) створює новий фрейм стека з локальними змінними цього виклику й адресою повернення, і цей фрейм кладеться на call stack. Коли виклик завершується — фрейм знімається зі стека. Рекурсивна функція, що викликає саму себе, вкладає нові фрейми поверх попередніх, поки не досягне базового випадку, а тоді послідовно "розмотує" стек назад.

**4. Наведи простий приклад рекурсивної функції.**

Наприклад, обчислення факторіалу: `Factorial(n) => n <= 1 ? 1 : n * Factorial(n - 1)`. Базовий випадок — `n <= 1`, рекурсивний випадок — `n * Factorial(n - 1)`.

**5. Чи можна будь-яку рекурсивну функцію переписати ітеративно?**

Так. Будь-яку рекурсію можна замінити циклом з явною структурою даних "стек" (`Stack<T>`), яка вручну виконує ту саму роль, що раніше виконував неявний call stack — зберігає "де я зупинився і що робити далі".

**6. Що таке базовий випадок і чому він має бути "найпростішим"?**

Базовий випадок — це варіант задачі, настільки простий, що його можна розв'язати напряму, без подальших рекурсивних викликів. Він має бути найпростішим, бо саме він зупиняє рекурсію — без нього (або якщо він недосяжний) рекурсія триватиме нескінченно (у межах обмеженого стека — до `StackOverflowException`).

**7. Чи можна перехопити `StackOverflowException` блоком `try/catch`?**

Ні. На відміну від більшості винятків у .NET, `StackOverflowException` завершує весь процес одразу і не може бути перехоплений — переповнення стека залишає середовище виконання без гарантій, що є достатньо пам'яті навіть для коректної обробки винятку.

### Middle

**1. Порівняй рекурсивний і ітеративний підхід до однієї задачі за перевагами і недоліками.**

Рекурсія часто дає читабельніший, коротший код для задач із природньою рекурсивною структурою (дерева, обхід графів, деякі задачі "розділяй і володарюй") — код прямо відображає структуру задачі. Але вона має накладні витрати на кожен виклик функції (створення й знищення фрейму) і ризик переповнення стека при глибокій рекурсії. Ітерація не має цих накладних витрат і ризику (явний стек лежить у купі, а не в обмеженому call stack), але для генетично рекурсивних задач часто вимагає незграбної ручної імітації того, що рекурсія робить безкоштовно. Для лінійних задач (сума масиву, простий пошук) ітерація зазвичай і природніша, і ефективніша.

**2. Що таке мемоізація і як вона рятує від експоненційного вибуху наївного Фібоначчі?**

Мемоізація — кешування результату виклику функції для конкретних аргументів, щоб повторний виклик з тими самими аргументами брав результат із кешу замість повторного обчислення. Наївний рекурсивний Фібоначчі обчислює одні й ті самі значення `fib(k)` багато разів у різних гілках дерева рекурсії (наприклад, `fib(3)` обчислюється двічі вже для `fib(5)`), що дає `O(2ⁿ)`. Кешування результату кожного `fib(k)` після першого обчислення гарантує, що кожне унікальне значення обчислюється рівно раз, знижуючи складність до `O(n)`.

**3. Опиши загальний шаблон бектрекінгу (вибір-дослідження-скасування вибору).**

На кожному кроці бектрекінгу перебираються можливі варіанти наступного кроку; для кожного валідного варіанта: (1) **вибір** — застосувати цей варіант, змінивши частковий розв'язок/стан; (2) **дослідження** — рекурсивно викликати ту саму функцію з оновленим станом; (3) **скасування вибору** — відкатити зміни, зроблені на кроці "вибір", повернувши стан до того, яким він був до нього, щоб наступна ітерація циклу почала з чистого стану. Крок 3 — те, що відрізняє бектрекінг від наївного повного перебору без відкату.

**4. Чим бектрекінг відрізняється від повного перебору без відсікання?**

Повний перебір без відсікання добудовує кожен можливий шлях/комбінацію до самого кінця і перевіряє валідність лише в самому кінці. Бектрекінг перевіряє валідність часткового розв'язку **до** заглиблення в рекурсію для нього (відсікання/pruning) і негайно відмовляється від гілки, щойно видно, що вона не може привести до валідного повного розв'язку — не витрачаючи час на її повне дослідження. Теоретична найгірша складність часто лишається тією самою, але реальна кількість досліджуваних варіантів на практиці зазвичай на порядки менша.

**5. Наведи приклад задачі, де рекурсія природньо простіша за ітерацію, і поясни чому.**

Обхід дерева (наприклад, in-order обхід бінарного дерева пошуку) — рекурсивна версія напряму відображає рекурсивну природу самої структури дерева (кожне піддерево — це саме по собі дерево), тоді як ітеративна версія вимагає явного стека для ручного відстеження "куди повернутись" після обробки піддерева — по суті, ручного відтворення того, що рекурсія робить неявно через call stack.

**6. Яка складність генерації всіх підмножин множини з n елементів, і чому саме така?**

`O(2ⁿ)` за кількістю підмножин (і принаймні стільки ж за часом, щоб їх усі згенерувати) — для кожного з n елементів є рівно два варіанти (включити чи ні), і ці вибори незалежні один від одного, тому загальна кількість комбінацій — добуток `2 × 2 × ... × 2` (n разів) = `2ⁿ`.

**7. Чи завжди мемоізація доречна для рекурсивної функції? Коли вона НЕ дає виграшу?**

Ні, не завжди. Мемоізація дає виграш лише тоді, коли рекурсія має **перетинні підзадачі** — тобто одні й ті самі аргументи зустрічаються повторно в різних гілках дерева рекурсії (як у Фібоначчі). Якщо кожен рекурсивний виклик отримує унікальні аргументи, яких більше ніде не зустріне (наприклад, класичний обхід відсортованого масиву методом бінарного пошуку, чи стандартний прохід по дереву без повторних відвідин вузлів), кешування нічого не заощадить, а лише додасть накладні витрати на роботу зі словником-кешем і зайву пам'ять.

### Senior

**1. Поясни, чому забутий крок "скасування вибору" в бектрекінгу призводить до неправильних результатів, на конкретному прикладі.**

У циклі перебору варіантів на одному рівні рекурсії кожна ітерація очікує, що стан (частковий розв'язок, масив "використано" тощо) на її вході — це саме той стан, який був **до** попередньої ітерації цього циклу, а не той, що залишився **після** дослідження попередньої гілки рекурсії. Якщо крок "скасування вибору" пропущено, зміни, зроблені для дослідження попередньої гілки, залишаються в стані, коли починається наступна ітерація — і та ітерація помилково "успадковує" чужі зміни. Конкретно в задачі генерації перестановок: якщо після рекурсивного виклику `Permute` не зняти позначку `used[i] = false` і не видалити елемент з `current`, то наступна ітерація циклу `for` вважатиме елемент `i` й надалі зайнятим (хоча насправді розглядається зовсім інша гілка, де він мав би бути доступним), і — окремо — сам список `current` міститиме зайвий елемент від попередньої (уже завершеної) гілки, тож усі наступні перестановки в цьому циклі будуть або пропущені, або матимуть неправильну (задовгу чи з дублікатами) довжину. Результат — неповний або спотворений набір перестановок, і що підступніше — перші кілька результатів часто виглядають правильними, тож помилка виявляється не одразу.

**2. Спроєктуй розв'язок для генерації всіх допустимих комбінацій промо-акцій з обмеженням на стекування, оцінивши масштабованість підходу.**

Розв'язання — рекурсивний перебір підмножин (як у розділі 8): для кожної акції-кандидата рекурсивно розглядаємо дві гілки (включити/не включити), з відсіканням гілки "включити", якщо поточна комбінація вже досягла ліміту стекування (наприклад, 2 акції). У базовому випадку (усі кандидати розглянуті) оцінюємо метрику (прогнозований прибуток) для зібраної комбінації на тестовому наборі замовлень і зберігаємо найкращу. Складність — `O(2ⁿ × m)`, де n — кількість акцій-кандидатів, m — розмір тестового набору замовлень для оцінки кожної комбінації. Масштабованість: практично прийнятно для n порядку 10-20 (`2ⁿ` від ~тисячі до мільйона комбінацій); для десятків акцій (40+) підхід стає обчислювально нездійсненним через експоненційне зростання, і варто або звузити простір пошуку доменними обмеженнями (наприклад, наперед відомі взаємовиключні категорії акцій, що дозволяє відсікати цілі групи комбінацій ще раніше), або перейти на наближені/евристичні методи (жадібний підхід, локальний пошук), усвідомлено жертвуючи гарантією знаходження глобально оптимальної комбінації заради здійсненності за прийнятний час.

**3. Порівняй трудову вартість (складність) наївної рекурсії, мемоізованої рекурсії, і повністю ітеративного розв'язку для однієї задачі.**

На прикладі Фібоначчі: наївна рекурсія — `O(2ⁿ)` за часом, `O(n)` за пам'яттю (глибина стека викликів). Мемоізована рекурсія (top-down DP) — `O(n)` за часом (кожне унікальне значення обчислюється раз), `O(n)` за пам'яттю (кеш плюс глибина стека). Повністю ітеративний розв'язок (bottom-up, часто зване табуляцією) — також `O(n)` за часом, і може бути навіть `O(1)` за додатковою пам'яттю, якщо зберігати лише два останні обчислені значення замість повного масиву чи словника — оскільки для обчислення `fib(k)` потрібні лише `fib(k-1)` і `fib(k-2)`, а не всі попередні значення одночасно. Тобто мемоізація рятує від експоненційного часу, але ітеративний підхід додатково рятує від зайвої пам'яті на кеш і від накладних витрат виклику функцій та ризику переповнення стека — це і є причина, чому в продакшн-коді для простих лінійних перетинних підзадач часто обирають саме ітеративну табуляцію, а не мемоізовану рекурсію, хоча асимптотично за часом вони рівні.

**4. Коли ти свідомо перетворив би рекурсивний розв'язок на ітеративний у реальному продакшн-коді, і чому?**

Переважно у трьох ситуаціях: (1) коли глибина рекурсії залежить від розміру вхідних даних, який контролюється зовнішнім джерелом (запит користувача, дані з бази, файл невідомого розміру) і теоретично може перевищити безпечну глибину стека — тут ризик `StackOverflowException` неприйнятний для продакшену, і явний стек чи цикл повністю усувають цей ризик; (2) коли профілювання показує, що накладні витрати на виклики функцій (створення фреймів) реально впливають на продуктивність гарячого шляху (hot path), що виконується мільйони разів на секунду; (3) коли задача насправді лінійна за своєю природою (не має істотної вкладеної/деревовидної структури), і рекурсія в такому випадку не додає ясності, а лише додає накладні витрати без вигоди — там ітеративний варіант і простіший, і безпечніший за замовчуванням. Водночас для задач із дійсно природньою рекурсивною структурою (обхід дерева, DFS графа обмеженої й контрольованої глибини) свідомо залишив би рекурсію — переписування на явний стек заради "безпеки" там, де глибина вже гарантовано обмежена бізнес-логікою (наприклад, дерево категорій каталогу з максимум 5 рівнями вкладеності), додало б складності коду без реальної вигоди.

**5. Чому теоретична найгірша складність бектрекінгу часто лишається експоненційною навіть попри відсікання, і як це узгодити з тим, що на практиці він "набагато швидший"?**

Відсікання прибирає гілки, які **гарантовано** не ведуть до валідного розв'язку, як тільки це стає визначеним — але в найгіршому теоретичному випадку (наприклад, вхідні дані спеціально підібрані так, щоб мінімізувати ефект відсікання, або сама задача за своєю природою має мало можливостей для раннього відкидання) кількість гілок, які доводиться дослідити, і далі може зростати експоненційно з розміром входу — тому асимптотична верхня межа (Big O у найгіршому випадку) для NP-важких задач на кшталт N-Queens чи повного перебору комбінацій зазвичай і лишається експоненційною. Але на практиці для типових, "не зловмисно підібраних" вхідних даних відсікання відкидає переважну більшість гіпотетично можливих гілок задовго до того, як вони були б повністю досліджені — тому реальний, емпіричний час виконання на практичних вхідних даних часто на порядки менший за теоретичну верхню межу. Це узгоджується так само, як O(n²) сортування вставками може бути швидшим за Θ(n log n) сортування на майже відсортованих даних: асимптотика описує гарантію в найгіршому випадку, а не гарантовану поведінку на кожному конкретному вході.

**6. Яка різниця між "перетинними підзадачами" (яка виправдовує мемоізацію) і задачами, де рекурсивні виклики просто "схожі за структурою", але не перетинаються?**

Перетинні підзадачі — це коли **той самий** виклик (з тими самими аргументами) насправді буде зроблений повторно з різних гілок дерева рекурсії, як `fib(3)` у `fib(5)` — тут результат одного виклику можна безпечно повторно використати для іншого. "Схожі за структурою, але не перетинаються" — це коли кожен рекурсивний виклик хоч і виконує ту саму функцію з тим самим кодом, але отримує **унікальний** набір аргументів, який більше ніколи не повториться в жодній іншій гілці — наприклад, рекурсивний обхід кожного вузла унікального дерева (кожен вузол відвідується рівно раз) чи рекурсивний бінарний пошук (кожен виклик звужує діапазон унікально, без повторів). У другому випадку мемоізація не заощадить жодного повторного обчислення — кеш просто ніколи не "влучить" (cache hit), а лише додасть накладні витрати на його підтримку. Розрізнення цих двох випадків — ключовий діагностичний крок перед тим, як застосовувати мемоізацію чи повне динамічне програмування.

### Компактний скелет шаблону бектрекінгу

```csharp
void Backtrack(State state, List<Result> results)
{
    if (IsComplete(state))
    {
        results.Add(BuildResult(state));
        return;
    }

    foreach (var candidate in GetCandidates(state))
    {
        if (!IsValid(state, candidate)) continue; // ВІДСІКАННЯ

        Apply(state, candidate);      // 1. ВИБІР
        Backtrack(state, results);    // 2. ДОСЛІДЖЕННЯ
        Undo(state, candidate);       // 3. СКАСУВАННЯ ВИБОРУ — обов'язково!
    }
}
```

### Наївна vs мемоізована vs ітеративна: складність на прикладі Фібоначчі

| Підхід | Час | Додаткова пам'ять | Ризик переповнення стека |
|---|---|---|---|
| Наївна рекурсія | O(2ⁿ) | O(n) — глибина стека | Так, при великому n |
| Мемоізована рекурсія (top-down DP) | O(n) | O(n) — кеш + глибина стека | Так, при великому n (глибина рекурсії не змінилась) |
| Повністю ітеративна (bottom-up, табуляція) | O(n) | O(1), якщо зберігати лише останні два значення | Немає |

Три ключові ідеї цього документа, які прямо готують ґрунт для решти серії: (1) рекурсія — це зведення задачі до її ж меншої копії плюс базовий випадок, і вона фізично реалізується через call stack, чий обмежений розмір робить некоректну рекурсію реальним ризиком, а не абстрактною небезпекою; (2) бектрекінг додає до простої рекурсії дисципліну "вибір → дослідження → скасування вибору" з відсіканням, перетворюючи наївний повний перебір на практично ефективний систематичний пошук; (3) кешування результатів перетинних підзадач (мемоізація) — це місток від "рекурсія просто працює" до "рекурсія працює ефективно", і саме ця ідея розгортається повністю в наступному документі про динамічне програмування, тоді як ідея зведення задачі до менших підзадач без перетину готує ґрунт для документа про "розділяй і володарюй".
