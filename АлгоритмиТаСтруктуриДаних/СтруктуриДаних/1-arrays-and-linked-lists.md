## Масив (Array) — базова структура

**Масив** — це найпростіша й водночас найфундаментальніша структура даних: **суцільний (неперервний) блок пам'яті**, в якому послідовно, "впритул" один до одного, розміщені елементи **однакового розміру**.

Саме два ключові слова — *суцільний* і *однакового розміру* — і дають масиву його головну суперсилу: **доступ до будь-якого елемента за індексом за O(1)**, незалежно від того, чи масив має 10 елементів, чи 10 мільйонів.

### Чому доступ за індексом — це O(1): адресна арифметика

Це питання, яке регулярно ставлять на співбесідах сіньйорського рівня: *"Чому `arr[i]` — це O(1), а не O(n)? Адже щоб дістатися до 47-го елемента, треба ж якось 'дійти' до нього?"*

Відповідь — ні, не треба "йти". Комп'ютеру не потрібно перебирати елементи від 0-го до 47-го, щоб дістатися 47-го. Йому достатньо **обчислити адресу** цього елемента за формулою:

```
адреса_елемента = базова_адреса_масиву + (індекс × розмір_одного_елемента)
```

Приклад: масив `int[]` (де `int` займає 4 байти) починається за адресою `1000`. Тоді:

| Індекс | Обчислення | Адреса |
|---|---|---|
| 0 | 1000 + (0 × 4) | 1000 |
| 1 | 1000 + (1 × 4) | 1004 |
| 5 | 1000 + (5 × 4) | 1020 |
| 47 | 1000 + (47 × 4) | 1188 |

Щоб отримати елемент з індексом 47, процесору не потрібно "проходити повз" елементи 0–46 — він одразу обчислює `1000 + 47×4 = 1188` (одне множення й одне додавання — обидві операції виконуються за фіксований, незалежний від розміру масиву час) і читає 4 байти за цією адресою. Це і є суть **O(1) — довільного (random access) доступу**.

Переконаємось у цьому наочно: якщо взяти реальний масив `int[]` у C# та вивести справжні адреси його елементів у пам'яті (через `unsafe`-код і вказівники), різниця між сусідніми адресами буде рівно 4 байти (розмір `int`):

```csharp
int[] numbers = { 10, 20, 30, 40, 50, 60 };

unsafe
{
    fixed (int* basePtr = numbers)
    {
        for (int i = 0; i < numbers.Length; i++)
        {
            IntPtr addr = (IntPtr)(basePtr + i);
            Console.WriteLine($"numbers[{i}] = {numbers[i]}, адреса = 0x{addr.ToInt64():X}");
        }
    }
}
```

Реальний вивід (адреси, звісно, будуть іншими на вашій машині — пам'ять виділяється в різних місцях щоразу, — але **крок між ними завжди буде 4 байти**):

```
numbers[0] = 10, адреса = 0x1998600BB50
numbers[1] = 20, адреса = 0x1998600BB54
numbers[2] = 30, адреса = 0x1998600BB58
numbers[3] = 40, адреса = 0x1998600BB5C
numbers[4] = 50, адреса = 0x1998600BB60
numbers[5] = 60, адреса = 0x1998600BB64
```

`BB50 → BB54 → BB58 → BB5C → BB60 → BB64` — кожен наступний елемент рівно на `0x4` (тобто 4 байти) далі за попередній. Це не збіг, а пряме підтвердження формули `адреса = база + індекс × розмір_елемента`.

> Складність аналізу Big O (включно з поняттям амортизованої складності) детально розібрана в документі [`0-complexity-analysis-big-o.md`](../0-complexity-analysis-big-o.md) — тут ми спираємось на неї, а не переказуємо заново.

### Аналогія: ряд однакових шафок-локерів

Уявіть довгий ряд однакових пронумерованих шафок у роздягальні спортзалу — усі шафки мають абсолютно однакову ширину, і вони стоять впритул одна до одної без проміжків. Якщо вам потрібна шафка №47, ви **не перевіряєте шафки 1, 2, 3, ..., 46**, щоб її знайти. Ви точно знаєте: якщо перша шафка починається біля вхідних дверей, а кожна шафка завширшки 40 см, то шафка №47 знаходиться рівно за `47 × 40` см від дверей. Ви йдете туди напряму.

Це і є масив: однакові за розміром елементи, розташовані впритул, дозволяють обчислити позицію будь-якого елемента миттєво, без перебору.

### Ціна цієї суперсили: фіксований розмір

Плата за цю властивість — **масив у "класичному" розумінні (і `int[]` / `T[]` у C#) має фіксований розмір**, який задається один раз при створенні:

```csharp
int[] fixedArray = new int[5]; // рівно 5 int-ів, ні більше, ні менше
```

Оскільки елементи лежать впритул один до одного в пам'яті, "розширити" масив на місці неможливо — сусідні байти пам'яті вже можуть бути зайняті чимось іншим. Щоб "додати" елемент понад початковий розмір, потрібно виділити **новий, більший** блок пам'яті і скопіювати туди всі старі елементи — а це вже O(n) операція. Саме цю проблему і вирішує динамічний масив, розглянутий у наступному розділі.

## Динамічний масив (Dynamic Array, List\<T\>)

**Динамічний масив** — це надбудова над звичайним масивом, яка вирішує головну проблему попереднього розділу: обмежений, фіксований розмір. У C# це `List<T>` (а також `ArrayList` у застарілому нетипізованому вигляді).

### Як це влаштовано зсередини

Всередині `List<T>` лежить звичайнісінький масив `T[]` (внутрішнє приватне поле, історично називається `_items`). У `List<T>` є дві різні властивості, які часто плутають:

- **`Count`** — скільки елементів **логічно** зберігається у списку зараз (те, що бачить користувач).
- **`Capacity`** — який **фактичний розмір** має внутрішній масив `_items` (скільки елементів може вміститися, перш ніж знадобиться новий масив).

Зазвичай `Capacity >= Count`: список тримає "запас" вільних комірок наперед, щоб не доводилось перестворювати масив на кожен `Add`.

Коли викликається `list.Add(x)`:

1. Якщо `Count < Capacity` — є вільне місце, елемент просто записується в `_items[Count]`, і `Count` збільшується на 1. Це справжнє O(1).
2. Якщо `Count == Capacity` — місця більше немає. `List<T>` виділяє **новий**, зазвичай **удвічі більший** масив, копіює туди всі старі елементи (O(n) операція), і вже потім дописує новий елемент.

Другий випадок трапляється рідко (лог₂(n) разів на n вставок), тому детальний **амортизований аналіз** — чому в середньому `Add` усе одно вважається O(1), навіть попри періодичні "дорогі" перестворення масиву — вже був розібраний на прикладі саме динамічного масиву в документі [`0-complexity-analysis-big-o.md`](../0-complexity-analysis-big-o.md). Тут ми цей висновок використовуємо як даність: **`Add` в кінець — амортизований O(1)** — і зосереджуємось на практичних наслідках цього факту.

Ось як реально виглядає ріст `Capacity` при послідовних `Add` (виміряно на .NET, `List<int>`, починаючи з порожнього списку):

```csharp
var list = new List<int>();
int lastCapacity = -1;
for (int i = 0; i < 20; i++)
{
    list.Add(i);
    if (list.Capacity != lastCapacity)
    {
        Console.WriteLine($"Count = {list.Count,2}, Capacity = {list.Capacity}");
        lastCapacity = list.Capacity;
    }
}
```

Реальний вивід:

```
Count =  1, Capacity = 4
Count =  5, Capacity = 8
Count =  9, Capacity = 16
Count = 17, Capacity = 32
```

Добре видно стратегію подвоєння: `4 → 8 → 16 → 32`. Кожне подвоєння — це одна O(n)-копія, але вона стається дедалі рідше відносно загальної кількості елементів, тому в середньому на елемент витрачається O(1).

### Практичний наслідок №1: кінець списку — дешево, початок і середина — дорого

Це та деталь, яку junior-розробники часто недооцінюють, і яка регулярно стає причиною прихованих проблем із продуктивністю (див. розділ 7 нижче):

- **`list.Add(x)`** (вставка в кінець) — амортизований **O(1)**. Просто пишемо в наступну вільну комірку.
- **`list.Insert(0, x)`** (вставка на початок) — **O(n)**. Щоб звільнити комірку з індексом 0, потрібно **зсунути всі існуючі елементи на одну позицію вправо**, і лише потім записати новий елемент у звільнену комірку 0.
- **`list.Insert(k, x)`** (вставка в середину, позиція `k`) — так само **O(n)**: зсуваються всі елементи від позиції `k` і далі.
- **`list.RemoveAt(0)`** — так само **O(n)**: усі елементи після видаленого зсуваються на одну позицію вліво, щоб "закрити дірку".

Чому так? Тому що масив (і внутрішній масив `List<T>`) — це суцільний блок пам'яті **без дірок**. Якщо ви хочете вставити елемент десь усередині, а елементи мають лежати впритул один до одного (це і дає їм O(1)-доступ за індексом!), то єдиний спосіб звільнити місце — фізично посунути всі наступні елементи в пам'яті.

Наочно (вставка `X` на позицію 1 в масив `[A, B, C, D]`):

```
До вставки:     [ A ][ B ][ C ][ D ][ _ ]
                        ↓ зсув вправо
Після зсуву:    [ A ][ _ ][ B ][ C ][ D ]
                     ↓ запис X
Результат:      [ A ][ X ][ B ][ C ][ D ]
```

Кожен з елементів `B`, `C`, `D` довелося фізично перемістити в пам'яті — і що довший список, то більше елементів доведеться зсунути. Це і є те саме O(n), яке при частих вставках на початок непомітно перетворює на позір "простий" код на серйозну проблему продуктивності.

## Зв'язний список: однозв'язний та двозв'язний

**Зв'язний список (Linked List)** підходить до тієї самої задачі "зберігати послідовність елементів" з протилежного боку. Замість суцільного блока пам'яті, зв'язний список складається з окремих **вузлів (nodes)**, розкиданих будь-де в пам'яті, кожен з яких містить:

- саме значення (`Value` / `Data`);
- посилання (вказівник) на **наступний** вузол (`Next`) — для однозв'язного списку;
- додатково посилання на **попередній** вузол (`Previous`) — для двозв'язного списку.

### Однозв'язний список (Singly-Linked List)

```
 head
  |
  v
[ 10 | •─┐]     [ 20 | •─┐]     [ 30 | •─┐]     [ 40 | null ]
          └────>          └────>          └────>
   Value  Next     Value  Next     Value  Next     Value  Next
```

Кожен вузол знає лише, "хто наступний". Щоб дістатися до третього елемента, потрібно пройти: `head → вузол(10) → вузол(20) → вузол(30)`. Немає способу "стрибнути" одразу до третього вузла — тільки прохід по ланцюжку посилань, починаючи з `head`.

### Двозв'язний список (Doubly-Linked List)

```
        head                                                    tail
         |                                                        |
         v                                                        v
null <──[•│10│•]<───>[•│20│•]<───>[•│30│•]<───>[•│40│•]──> null
         Prev│Next     Prev│Next     Prev│Next     Prev│Next
```

Тут кожен вузол додатково зберігає посилання на **попередній** вузол, тому обхід можливий в обидва боки — від `head` до `tail`, і навпаки. У .NET це реалізовано як `LinkedList<T>`.

### Головна відмінність від масиву: немає суцільної пам'яті

Вузли зв'язного списку **не зобов'язані лежати поруч у пам'яті** — кожен вузол виділяється окремо (наприклад, через `new Node<T>(...)`) і може опинитися будь-де в купі (heap). Єдине, що "тримає список разом" — це ланцюжок посилань `Next` (і `Previous` для двозв'язного).

Це докорінно змінює компроміси:

- **Вставка/видалення в ВІДОМІЙ позиції — O(1).** Якщо у вас вже є посилання на вузол, після якого (чи перед яким) треба вставити новий елемент, — це просто **перелінковування кількох вказівників**, без жодних копіювань чи зсувів сусідніх елементів (яких тут просто немає — це не суцільний блок пам'яті).
- **Але щоб ДІСТАТИСЯ до цієї позиції — потрібен O(n) обхід.** На відміну від масиву, у зв'язного списку **немає** довільного доступу за індексом за O(1). Немає формули "адреса = база + індекс × розмір", бо елементи не лежать по порядку в пам'яті — єдиний спосіб дістатися до n-го елемента — пройти по посиланнях від `head` n разів. Саме тому в `LinkedList<T>` у .NET **немає** індексатора `[i]` — мова навмисно не дає вам ілюзії, що `list[5]` — це дешева операція.

Отже, "O(1) вставка" зв'язного списку — це насправді **O(1) вставка за умови, що позиція вставки вже відома** (наприклад, ви вже тримаєте посилання на потрібний вузол — скажімо, отримане під час ітерації). Якщо позицію ще треба знайти (наприклад, "вставити перед елементом зі значенням 42"), пошук цієї позиції коштує O(n), і тоді загальна вартість операції "знайти + вставити" — усе одно O(n).

## Масив vs Зв'язний список — коли що обирати

Це питання, яке нечасто має "єдину правильну відповідь" — правильний вибір залежить від **реального патерна доступу до даних** у вашому застосунку, а не від абстрактної "теоретичної кращості" однієї структури над іншою.

### Крок 1: Яким є патерн доступу?

- **Частий довільний доступ за індексом** (`data[i]`, "дай мені 47-й елемент", сортування, бінарний пошук, доступ за id-масивом) → **масив / `List<T>`**. Це саме та задача, для якої масив спроєктовано — O(1) доступ.
- **Частi вставки/видалення в довільних, але вже ВІДОМИХ позиціях** (наприклад, у вас є ітератор/посилання на вузол, отримане в процесі обходу, і ви часто вставляєте/видаляєте "тут, поруч з поточною позицією", а довільний доступ за індексом вам практично не потрібен) → **зв'язний список**. Класичні приклади: реалізація LRU-кеша (вузол переміщується в голову/хвіст списку за O(1), маючи посилання на нього), список подій редактора тексту (курсор — це, по суті, вузол), деякі реалізації планувальників задач.
- **Здебільшого послідовний обхід від початку до кінця, рідкісні модифікації** → обидві структури підійдуть однаково добре за Big O; тут вирішальним стає наступний фактор.

### Крок 2: Не забути про cache locality (локальність кешу) — фактор, який Big O не бачить

Це, мабуть, найважливіший **практичний** нюанс, який часто випускають з уваги, дивлячись лише на асимптотичну складність. Сучасні процесори не читають пам'ять байт за байтом — вони читають **кеш-лініями** (зазвичай 64 байти) і активно **передбачають (prefetch)**, що знадобиться далі.

- **Масив: контактна пам'ять → кеш-дружній.** Коли процесор читає `arr[0]`, він одночасно підвантажує в кеш і сусідні `arr[1]`, `arr[2]`, ... (усе, що влізло в ту саму 64-байтову кеш-лінію). Коли цикл дійде до `arr[1]`, `arr[2]` — ці дані вже в кеші L1/L2, і читання буде майже миттєвим (кеш-хіт). Prefetcher процесора також розпізнає послідовний патерн доступу і заздалегідь підвантажує наступні кеш-лінії.
- **Зв'язний список: вузли розкидані по купі → "стрибки по пам'яті" (pointer chasing).** Кожен вузол міг бути виділений у зовсім іншому місці пам'яті. Перехід від одного вузла до наступного (`current = current.Next`) — це, по суті, стрибок у непередбачувану адресу пам'яті. Із високою ймовірністю це буде **кеш-промах (cache miss)**, і процесору доведеться чекати на повільніше звернення до оперативної пам'яті (яка на порядки повільніша за кеш L1/L2).

**Практичний наслідок:** навіть у ситуаціях, де Big O теоретично "на боці" зв'язного списку (наприклад, вставка в середину — O(1) для списку проти O(n) для масиву), на практиці **масив нерідко виявляється швидшим** — аж доки список чи елементи не стануть по-справжньому великими. Причина проста: константа перед O(n) у масиву (швидке, кеш-дружнє копіювання суміжних байтів, яке до того ж часто векторизується процесором) може бути настільки малою, що навіть "лінійна" операція над масивом на кількох тисячах елементів виконується швидше за "миттєву" O(1)-операцію над зв'язним списком, розтягнуту по непередбачуваних ділянках пам'яті. Це відомий практичний результат (його неодноразово демонстрував, зокрема, Бьярне Страуструп у доповідях про продуктивність `std::vector` проти `std::list`) — і, за нашими власними вимірюваннями нижче (Приклад 4), різниця на реальних задачах буває колосальною, хоч і **не завжди в бік масиву** — все залежить від конкретної операції.

Важливо розуміти межі цього ефекту: коли елементи **дуже великі** (наприклад, вставка структури в кілька кілобайт усередину масиву означає копіювання кілобайтів даних на кожен зсув) або список **дуже довгий і вставки в середину відбуваються часто в гарячому шляху виконання**, теоретична перевага зв'язного списку (O(1) без копіювання даних елемента) починає переважувати вартість "стрибків по пам'яті". Але для типових випадків — маленькі елементи (числа, короткі структури, посилання на об'єкти) і списки до сотень тисяч елементів — масив/`List<T>` у C# частіше виявляється практичним вибором за замовчуванням.

### Підсумок рішення

| Питання | Якщо "так" |
|---|---|
| Чи потрібен частий доступ за індексом (`data[i]`)? | **Масив / `List<T>`** |
| Чи потрібен бінарний пошук, сортування "на місці", LINQ по індексу? | **Масив / `List<T>`** |
| Чи вставки/видалення відбуваються здебільшого за вже наявним посиланням на вузол (ітератор, курсор), а не за індексом? | **Зв'язний список** |
| Чи елементи маленькі, а список — не величезний? | **Масив / `List<T>`** (виграє за рахунок cache locality навіть при O(n)-операціях) |
| Чи потрібна передбачувана O(1) вартість вставки/видалення без жодних "шпильок" затримки (наприклад, у real-time системах, де раптовий O(n)-зсув масиву може викликати помітний "лаг")? | **Зв'язний список** |

## Порівняльна таблиця операцій

| Операція | Масив (фіксований) | Динамічний масив (`List<T>`) | Однозв'язний список | Двозв'язний список (`LinkedList<T>`) |
|---|---|---|---|---|
| Доступ за індексом `[i]` | O(1) | O(1) | O(n) — немає індексатора, потрібен обхід | O(n) — немає індексатора, потрібен обхід |
| Пошук (непосортований масив/список) | O(n) | O(n) | O(n) | O(n) |
| Вставка в кінець | не підтримується (фіксований розмір) | амортизований O(1) | O(1), якщо тримати `tail`-посилання; інакше O(n) | O(1) (є `AddLast`, завжди тримає `Last`) |
| Вставка на початок | не підтримується | O(n) — зсув усіх елементів | O(1) (`AddFirst`) | O(1) (`AddFirst`) |
| Вставка в середину (позиція вже відома — є вузол/індекс) | O(n) — зсув елементів | O(n) — зсув елементів | O(1) саме релінкування, **але** O(n), щоб дістатись до позиції з `head`, якщо позиції ще немає "в руках" | O(1) саме релінкування за наявним посиланням на вузол |
| Видалення з кінця | не підтримується | O(1), якщо просто "забути" останній елемент | O(n) — потрібно дійти до передостаннього вузла, щоб оновити його `Next` | O(1) (`RemoveLast`, є пряме посилання `Last`/`Last.Previous`) |
| Видалення з початку | не підтримується | O(n) — зсув усіх елементів | O(1) (`RemoveFirst`) | O(1) (`RemoveFirst`) |
| Видалення в середині за **наявним** посиланням на вузол | O(n) — зсув елементів | O(n) — зсув елементів | O(n) — навіть маючи вузол, треба пройти від `head`, щоб знайти **попередній** вузол (у однозв'язному списку немає `Previous`!) | **O(1)** — вузол сам знає і `Next`, і `Previous`, релінкування без пошуку |
| Видалення в середині, коли позицію ще треба **знайти** | O(n) пошук + O(n) зсув = O(n) | O(n) пошук + O(n) зсув = O(n) | O(n) пошук + O(1) релінк = O(n) | O(n) пошук + O(1) релінк = O(n) |
| Вартість зміни розміру (resize) | — (неможливо) | амортизовано O(1) на елемент (епізодичне O(n) копіювання, детально — у [`0-complexity-analysis-big-o.md`](../0-complexity-analysis-big-o.md)) | не потрібно — кожен вузол виділяється окремо | не потрібно — кожен вузол виділяється окремо |
| Пам'ять "накладних витрат" на елемент | немає (лише самі дані) | немає (крім невикористаної `Capacity`) | +1 посилання (`Next`) на вузол + окремий об'єкт у купі | +2 посилання (`Next`, `Previous`) на вузол + окремий об'єкт у купі |
| Локальність кешу (cache locality) | відмінна | відмінна | погана — вузли розкидані по купі | погана — вузли розкидані по купі |

**Ключовий рядок для співбесіди:** видалення в середині за наявним посиланням на вузол — це той рідкісний випадок, де двозв'язний список дає справжню, беззаперечну перевагу O(1) там, де масив і навіть однозв'язний список змушені платити O(n).

## Практичні приклади на C#

### Приклад 1: фіксований масив

Демонструє O(1)-доступ за індексом і те, що масив у C# **не може** вирости понад початковий розмір — для "додавання" елемента потрібно вручну створити новий, більший масив і скопіювати дані.

```csharp
int[] numbers = new int[5] { 10, 20, 30, 40, 50 };

// O(1) доступ за індексом — миттєво, незалежно від розміру масиву
Console.WriteLine(numbers[3]); // 40

// numbers[5] = 60;  // ← IndexOutOfRangeException! Масив не можна "розширити" на місці.

// Щоб "додати" елемент, доводиться вручну створювати новий масив і копіювати старі дані —
// це вже O(n) операція, яку List<T> ховає від нас (див. наступний приклад).
int[] resized = new int[numbers.Length + 1];
Array.Copy(numbers, resized, numbers.Length);
resized[^1] = 60;
numbers = resized;

foreach (var x in numbers)
{
    Console.Write(x + " ");
}
Console.WriteLine();
```

Реальний вивід:

```
40
10 20 30 40 50 60
```

### Приклад 2: однозв'язний список з нуля

Спрощена, але повноцінна реалізація однозв'язного списку: клас `Node<T>` (значення + посилання на наступний вузол) та `SimpleLinkedList<T>` з методами `AddFirst`, `AddLast`, `Remove` і власним ітератором через `IEnumerable<T>` / `yield return`, що дозволяє використовувати список у `foreach` так само природно, як і будь-яку вбудовану колекцію .NET.

Це прямий практичний приклад патерна **Iterator**, детально розібраного в документі [`iterator-pattern-csharp.md`](../../Поведінкові/iterator-pattern-csharp.md) з папки `Поведінкові/`: клієнтський код (`foreach`) не знає і не повинен знати, що всередині — ланцюжок вузлів із посиланнями `Next`, а не масив. Він отримує уніфікований інтерфейс обходу через `GetEnumerator()`.

```csharp
public class Node<T>
{
    public T Value;
    public Node<T>? Next;

    public Node(T value) => Value = value;
}

public class SimpleLinkedList<T> : IEnumerable<T>
{
    private Node<T>? _head;
    private Node<T>? _tail;
    public int Count { get; private set; }

    // O(1) — просто перелінковуємо head, зсуву елементів немає
    public void AddFirst(T value)
    {
        var node = new Node<T>(value) { Next = _head };
        _head = node;
        if (_tail == null) _tail = node; // список був порожнім
        Count++;
    }

    // O(1) — завдяки тому, що ми тримаємо посилання на _tail
    public void AddLast(T value)
    {
        var node = new Node<T>(value);
        if (_tail == null)
        {
            _head = _tail = node;
        }
        else
        {
            _tail.Next = node;
            _tail = node;
        }
        Count++;
    }

    // O(n) — потрібно пройти список, щоб знайти елемент і його попередника
    public bool Remove(T value)
    {
        Node<T>? previous = null;
        Node<T>? current = _head;

        while (current != null)
        {
            if (EqualityComparer<T>.Default.Equals(current.Value, value))
            {
                if (previous == null)
                    _head = current.Next;          // видаляємо перший вузол
                else
                    previous.Next = current.Next;  // "перестрибуємо" видалений вузол

                if (current == _tail)
                    _tail = previous;               // оновлюємо tail, якщо видалили останній

                Count--;
                return true;
            }
            previous = current;
            current = current.Next;
        }
        return false;
    }

    // Реалізація Iterator-патерна через yield return — компілятор сам згенерує
    // повноцінний клас-стейт-машину IEnumerator<T> під капотом.
    public IEnumerator<T> GetEnumerator()
    {
        var current = _head;
        while (current != null)
        {
            yield return current.Value;
            current = current.Next;
        }
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

Демонстрація використання:

```csharp
var list = new SimpleLinkedList<string>();
list.AddLast("б");
list.AddLast("в");
list.AddFirst("а"); // тепер список: а -> б -> в

foreach (var item in list)
{
    Console.WriteLine(item);
}

list.Remove("б"); // список: а -> в

Console.WriteLine("Після Remove(\"б\"):");
foreach (var item in list)
{
    Console.WriteLine(item);
}
```

Реальний вивід:

```
а
б
в
Після Remove("б"):
а
в
```

Зверніть увагу: `Remove("б")` — це O(n) навіть попри те, що це "однозв'язний список" з нібито дешевими видаленнями — тому що спершу потрібно **знайти** елемент, проходячи список від `head`.

### Приклад 3: двозв'язний список

Тут головна ідея — показати різницю між однозв'язним і двозв'язним списком саме там, де вона проявляється найяскравіше: **видалення вузла, коли на нього вже є пряме посилання** (наприклад, отримане раніше під час ітерації чи збережене окремо для швидкого доступу — типовий патерн для LRU-кешів).

```csharp
public class DoublyNode<T>
{
    public T Value;
    public DoublyNode<T>? Next;
    public DoublyNode<T>? Previous;

    public DoublyNode(T value) => Value = value;
}

public class SimpleDoublyLinkedList<T> : IEnumerable<T>
{
    private DoublyNode<T>? _head;
    private DoublyNode<T>? _tail;
    public int Count { get; private set; }

    public DoublyNode<T> AddLast(T value)
    {
        var node = new DoublyNode<T>(value);
        if (_tail == null)
        {
            _head = _tail = node;
        }
        else
        {
            node.Previous = _tail;
            _tail.Next = node;
            _tail = node;
        }
        Count++;
        return node; // повертаємо посилання на вузол — саме воно й дає O(1)-видалення далі
    }

    // O(1) — САМЕ ТУТ полягає перевага двозв'язного списку.
    // Вузол уже знає і Next, і Previous — шукати попередника НЕ потрібно.
    public void RemoveNode(DoublyNode<T> node)
    {
        if (node.Previous != null) node.Previous.Next = node.Next;
        else _head = node.Next; // видаляємо head

        if (node.Next != null) node.Next.Previous = node.Previous;
        else _tail = node.Previous; // видаляємо tail

        Count--;
    }

    public IEnumerator<T> GetEnumerator()
    {
        var current = _head;
        while (current != null)
        {
            yield return current.Value;
            current = current.Next;
        }
    }

    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}
```

Для контрасту — ось як виглядало б те саме видалення "за вузлом" в **однозв'язному** списку з Прикладу 2. Проблема в тому, що `Node<T>` там **не має** `Previous` — тому навіть маючи посилання на вузол, який хочемо видалити, ми не можемо O(1)-релінкнути список, бо не знаємо, хто на нього посилається (`Next`) з попереднього вузла. Доводиться все одно проходити список від `head`, щоб знайти цього попередника:

```csharp
// Однозв'язний список: навіть МАЮЧИ посилання на вузол nodeToRemove,
// доводиться шукати його ПОПЕРЕДНИКА обходом від head — бо Node<T> не знає Previous.
public bool RemoveByNode(Node<T> nodeToRemove)
{
    if (_head == nodeToRemove)
    {
        _head = nodeToRemove.Next;
        if (_tail == nodeToRemove) _tail = null;
        Count--;
        return true;
    }

    var current = _head; // ← O(n): змушені йти від початку, щоб знайти previous
    while (current?.Next != null)
    {
        if (current.Next == nodeToRemove)
        {
            current.Next = nodeToRemove.Next;
            if (_tail == nodeToRemove) _tail = current;
            Count--;
            return true;
        }
        current = current.Next;
    }
    return false;
}
```

Демонстрація роботи двозв'язного списку:

```csharp
var list = new SimpleDoublyLinkedList<int>();
var node1 = list.AddLast(1);
var node2 = list.AddLast(2);
var node3 = list.AddLast(3);
// список: 1 <-> 2 <-> 3

list.RemoveNode(node2); // O(1) — маємо пряме посилання на вузол 2, пошук не потрібен

foreach (var item in list)
{
    Console.WriteLine(item);
}
```

Реальний вивід:

```
1
3
```

**Висновок:** саме через відсутність `Previous` в однозв'язному списку `LinkedList<T>` у .NET реалізовано як **двозв'язний** — це дає бібліотеці змогу пропонувати O(1) `Remove(LinkedListNode<T>)`, що й є головною практичною причиною використовувати `LinkedList<T>`, а не писати власний однозв'язний список.

### Приклад 4: бенчмарк

Порівняємо на реальному вимірюванні (`Stopwatch`) дві операції, що виглядають схоже, але мають кардинально різну складність: вставку в **початок** `List<T>` (O(n) — зсув усіх елементів) проти `LinkedList<T>.AddFirst` (O(1) — просто новий вузол стає новим `head`).

```csharp
using System.Diagnostics;

int n = 50_000;

var list = new List<int>();
var sw = Stopwatch.StartNew();
for (int i = 0; i < n; i++)
{
    list.Insert(0, i); // O(n) на кожен виклик — усі попередні елементи зсуваються
}
sw.Stop();
Console.WriteLine($"List<T>.Insert(0, x) x{n}: {sw.ElapsedMilliseconds} ms");

var linked = new LinkedList<int>();
sw.Restart();
for (int i = 0; i < n; i++)
{
    linked.AddFirst(i); // O(1) на кожен виклик — просто новий вузол-голова
}
sw.Stop();
Console.WriteLine($"LinkedList<T>.AddFirst(x) x{n}: {sw.ElapsedMilliseconds} ms");
```

Реальний вимірюваний вивід (.NET 10, Release-збірка; конкретні мілісекунди залежать від заліза, але **порядок відмінності** — ні):

```
List<T>.Insert(0, x) x50000: 200 ms
LinkedList<T>.AddFirst(x) x50000: 2 ms
```

Подвоївши `n` до 100 000, різниця стає ще виразнішою — і тут проявляється саме O(n) на виклик (сумарно O(n²) для `List<T>`) проти O(n) сумарно (O(1) на виклик) для `LinkedList<T>`:

```
List<T>.Insert(0, x) x100000: 711 ms
LinkedList<T>.AddFirst(x) x100000: 5 ms
```

Зверніть увагу: подвоєння `n` для `List<T>.Insert(0, ...)` збільшило час приблизно в **3.5 рази** (200 → 711 мс) — це і є característика O(n²)-поведінки (сумарна вартість n вставок по O(n) кожна), тоді як для `LinkedList<T>.AddFirst` час виріс лише пропорційно до `n` (2 → 5 мс, приблизно вдвічі) — точнісінько як і передбачає O(n) сумарної складності (O(1) на виклик).

Це саме той випадок, де Big O не бреше і практично точно передбачає поведінку: коли операція справді O(n) *за виклик* і викликається `n` разів у циклі, сумарна вартість — O(n²), і на великих `n` це стає катастрофічно повільним, попри те, що кожен окремий виклик `list.Insert(0, x)` — це "всього лише" один рядок коду.

## Реальний сценарій: чому вибір структури даних вплинув на продуктивність черги завдань

Уявімо типову ситуацію в реальному проєкті. Команда реалізує **фоновий обробник завдань (background job processor)**: різні частини системи додають завдання в чергу, а окремий воркер-потік у циклі забирає завдання з початку черги й обробляє їх.

Розробник, не задумуючись глибоко про внутрішню структуру, обирає найзвичніший інструмент — `List<Job>`:

```csharp
// ПРОБЛЕМНА реалізація
private readonly List<Job> _jobs = new();

public void Enqueue(Job job) => _jobs.Add(job); // додаємо в кінець — виглядає нормально

public Job? Dequeue()
{
    if (_jobs.Count == 0) return null;

    var job = _jobs[0];       // беремо перше завдання
    _jobs.RemoveAt(0);        // ← ОСЬ ТУТ ПРИХОВАНА ПРОБЛЕМА
    return job;
}
```

На перший погляд, код абсолютно робочий і навіть виглядає ідіоматично: "додай у кінець, забери з початку" — класична поведінка черги (FIFO). На невеликих обсягах (десятки-сотні завдань) усе працює швидко, і в тестах/на ранніх стадіях продукту ніхто нічого не помічає.

### Що відбувається під капотом

Проблема — саме в `_jobs.RemoveAt(0)`. Як розібрано в розділі 2, видалення з **початку** `List<T>` — це **O(n)**: усі елементи, що залишились (з індексами 1, 2, 3, ...), фізично зсуваються на одну позицію вліво в тому самому внутрішньому масиві, щоб "закрити дірку" на позиції 0.

Поки в черзі одиниці чи десятки завдань, O(n) для n≈50 — це наносекунди, непомітно. Але з часом, коли система під навантаженням і черга виростає до тисяч чи десятків тисяч необроблених завдань (наприклад, під час пікового навантаження, чи коли обробка завдань тимчасово сповільнилась через залежний зовнішній сервіс), картина міняється кардинально:

- Кожен виклик `Dequeue()` тепер зсуває **тисячі** елементів.
- Оскільки `Dequeue()` викликається знову й знову в циклі воркера — по одному разу на кожне завдання, — сумарна вартість обробки всієї черги стає **O(n²)**, а не очікуваного O(n).
- Симптом у продакшені виглядає загадково: "обробник завдань став раптово гальмувати, хоча код не змінювався" — насправді просто **виросла довжина черги**, і квадратична природа `RemoveAt(0)` почала домінувати.

Це підступний баг саме тому, що він **не ламає функціональність** — усе працює правильно, лише повільно, і повільність зростає непропорційно (нелінійно) з розміром черги, тому в маленьких тестових середовищах проблему майже неможливо помітити.

### Виправлення №1: LinkedList\<T\>

Найпряміше виправлення — замінити `List<Job>` на `LinkedList<Job>`, де `AddLast` (постановка в чергу) і `RemoveFirst` (забір із черги) — обидві операції **O(1)**:

```csharp
private readonly LinkedList<Job> _jobs = new();

public void Enqueue(Job job) => _jobs.AddLast(job);  // O(1)

public Job? Dequeue()
{
    if (_jobs.First == null) return null;

    var job = _jobs.First.Value;
    _jobs.RemoveFirst(); // O(1) — просто новий head, без жодних зсувів
    return job;
}
```

Це вирішує проблему продуктивності: тепер обробка всієї черги з n завдань коштує O(n) сумарно, а не O(n²).

### Виправлення №2 (кращий, ідіоматичний варіант): Queue\<T\>

Насправді ж патерн доступу "додай у кінець, забери з початку" — це не просто "черга, яку ми зібрали з підручного матеріалу", а **точний опис абстракції `Queue<T>`**, спеціально спроєктованої в .NET саме для цього сценарію (FIFO — First In, First Out):

```csharp
private readonly Queue<Job> _jobs = new();

public void Enqueue(Job job) => _jobs.Enqueue(job); // O(1) амортизований
public Job? Dequeue() => _jobs.Count > 0 ? _jobs.Dequeue() : null; // O(1)
```

`Queue<T>` у .NET реалізовано як **кільцевий буфер (circular buffer)** над масивом — це дає йому і переваги масиву (компактність, cache locality), і O(1) для операцій саме на обох кінцях, без потреби в окремих вузлах-об'єктах для кожного елемента (як у `LinkedList<T>`). Це, як правило, найкращий вибір для класичної черги завдань — і саме `Queue<T>` (разом зі `Stack<T>`) детально розбирається в наступному документі цієї серії, [`2-stacks-and-queues.md`](./2-stacks-and-queues.md).

**Мораль:** проблема виникла не тому, що `List<T>` — "погана" структура даних, а тому, що вона була застосована для патерна доступу (часте видалення з початку), для якого вона за своєю природою не пристосована. Правильний вибір структури даних під конкретний патерн доступу — і є суттю цього документа.

## Поширені помилки

### Помилка 1: `Insert(0, ...)` / `RemoveAt(0)` у циклі — прихована O(n²)

Це саме та помилка, яку ми детально розібрали в розділі 7. Виклик, що виглядає як "проста O(1) операція", насправді ховає O(n) вартість, і в циклі це непомітно перетворюється на O(n²).

❌ **Погано:**

```csharp
var recentEvents = new List<Event>();

void OnNewEvent(Event e)
{
    recentEvents.Insert(0, e); // O(n) на КОЖЕН виклик — усі елементи зсуваються
    if (recentEvents.Count > 100)
        recentEvents.RemoveAt(recentEvents.Count - 1);
}
```

✅ **Добре** — якщо семантично потрібна саме черга/стек, використовуйте призначену для цього структуру:

```csharp
var recentEvents = new LinkedList<Event>();

void OnNewEvent(Event e)
{
    recentEvents.AddFirst(e); // O(1)
    if (recentEvents.Count > 100)
        recentEvents.RemoveLast(); // O(1) — LinkedList<T> завжди тримає Last
}
```

Або, якщо порядок насправді не важливий (просто потрібні "останні 100 подій", а не строгий порядок вставки), можна взагалі уникнути вставки на початок, додаючи в кінець і читаючи з кінця.

### Помилка 2: обирати `LinkedList<T>` "за замовчуванням", бо "вставка O(1)" — без урахування контексту

Junior/middle-розробник, прочитавши таблицю Big O, часто робить висновок: "у LinkedList вставка O(1), а в List — O(n) при вставці на початок, отже LinkedList кращий за замовчуванням". Це ігнорує дві речі, розібрані в розділі 4: (1) доступ за індексом у `LinkedList<T>` стає O(n) — тож будь-який код, що потребує `list[i]` або бінарного пошуку, різко деградує; (2) навіть там, де Big O формально на боці `LinkedList<T>`, погана локальність кешу (cache locality) часто робить його повільнішим на практиці для типових розмірів даних і маленьких елементів.

❌ **Погано** — вибір "з голови", без вимірювання, для типового сценарію (переважно послідовний обхід + рідкісні вставки в кінець):

```csharp
// "LinkedList має O(1) вставку, тож візьмемо його" — але тут ніде немає
// вставки в середину за вже наявним вузлом, лише послідовний обхід і Add у кінець!
var scores = new LinkedList<int>();
foreach (var raw in incomingScores)
    scores.AddLast(raw);

// А тут раптом знадобився доступ за індексом — і це вже O(n) замість O(1)
int median = GetElementAt(scores, scores.Count / 2); // O(n) обхід замість scores[i]
```

✅ **Добре** — для цього патерна доступу (послідовне заповнення + періодичний доступ за індексом) `List<T>` буде і простішим, і швидшим на практиці:

```csharp
var scores = new List<int>();
foreach (var raw in incomingScores)
    scores.Add(raw);

int median = scores[scores.Count / 2]; // O(1), і ще й кеш-дружньо
```

**Правильний підхід:** обирати структуру даних, виходячи з реального патерна доступу (розділ 4), а в неоднозначних або critical-path випадках — **виміряти** на реальних даних (`Stopwatch`, BenchmarkDotNet), а не покладатися лише на теоретичну Big O, як показано в Прикладі 4.

### Помилка 3: не задавати `Capacity` наперед, коли приблизний розмір відомий

Якщо заздалегідь відомо (або можна оцінити), скільки елементів приблизно буде в списку, ігнорування конструктора з параметром `capacity` призводить до **зайвих** циклів "виділити новий масив удвічі більший → скопіювати все → викинути старий масив" під час заповнення.

❌ **Погано:**

```csharp
// Ми точно знаємо, що прийде рівно 10 000 записів (наприклад, читаємо з БД з відомим Count),
// але список стартує з дефолтною Capacity і росте через 12+ перевиділень і копіювань
var results = new List<Record>();
foreach (var row in ReadAllRows()) // рівно 10 000 рядків
    results.Add(row);
```

✅ **Добре:**

```csharp
// Одразу виділяємо масив потрібного розміру — жодних проміжних перевиділень і копіювань
var results = new List<Record>(capacity: 10_000);
foreach (var row in ReadAllRows())
    results.Add(row);
```

Це не змінює асимптотичну складність (`Add` усе одно амортизований O(1)), але прибирає реальні, вимірювані накладні витрати на повторні виділення пам'яті й копіювання — особливо помітно на великих колекціях або в гарячих ділянках коду (hot path), де ці "приховані" O(n)-копіювання додаються сотні чи тисячі разів.

## Питання для співбесіди за рівнями

### Junior

**1. Чим масив відрізняється від зв'язного списку?**

Масив — це суцільний блок пам'яті з елементами однакового розміру, розташованими впритул; доступ за індексом обчислюється напряму (O(1)), але розмір фіксований. Зв'язний список — це набір окремих вузлів, розкиданих по пам'яті, з'єднаних посиланнями; вставка/видалення в уже відомій позиції дешева (O(1)), але доступу за індексом за O(1) немає — потрібен послідовний обхід від початку.

**2. Яка складність доступу до елемента масиву за індексом і чому?**

O(1). Адреса елемента обчислюється за формулою `база + індекс × розмір_елемента` — це одна арифметична операція, час якої не залежить від розміру масиву чи значення індексу.

**3. Що таке однозв'язний список?**

Структура даних, де кожен елемент (вузол) містить значення і посилання лише на **наступний** вузол. Обхід можливий тільки в один бік — від голови (`head`) до кінця (`null`).

**4. Яка складність вставки на початок масиву проти зв'язного списку?**

Для масиву (і `List<T>`) — O(n), бо всі наявні елементи потрібно зсунути на одну позицію, щоб звільнити місце в позиції 0. Для зв'язного списку — O(1): достатньо створити новий вузол і зробити його новою головою (`head`), перелінкувавши лише одне посилання.

**5. Чому не можна просто "додати елемент" у звичайний масив `int[]` у C#, коли він заповнений?**

Тому що масив у C# має фіксований розмір, заданий при створенні. Елементи лежать впритул один до одного в пам'яті, тому "розширити" масив на місці неможливо — сусідні байти пам'яті можуть бути вже зайняті. Потрібно виділити новий, більший масив і скопіювати туди старі дані — саме це автоматично робить `List<T>` під капотом.

**6. Що таке `Count` і `Capacity` у `List<T>` — чим вони відрізняються?**

`Count` — скільки елементів фактично зберігається в списку зараз. `Capacity` — який розмір має внутрішній масив, тобто скільки елементів може вміститись, перш ніж знадобиться нове, більше виділення пам'яті. `Capacity` завжди `>= Count`.

### Middle

**1. Як влаштований `List<T>` зсередини?**

Всередині лежить приватний масив `T[]`. `Add` записує елемент у наступну вільну комірку (якщо `Count < Capacity`) — це O(1). Коли масив заповнюється (`Count == Capacity`), виділяється новий масив (зазвичай удвічі більший), усі елементи копіюються туди (O(n)), і лише тоді додається новий елемент. Завдяки тому, що таке перевиділення відбувається дедалі рідше відносно загальної кількості вставок, у середньому (амортизовано) `Add` усе одно O(1) — детальний доказ цього наведено в `0-complexity-analysis-big-o.md`.

**2. Чим однозв'язний список відрізняється від двозв'язного?**

У однозв'язному кожен вузол зберігає посилання лише на наступний вузол (`Next`) — обхід можливий тільки вперед. У двозв'язному кожен вузол додатково зберігає посилання на попередній вузол (`Previous`), що дозволяє обхід в обидва боки й, що найважливіше, **O(1) видалення вузла за наявним на нього посиланням** без потреби шукати попередника окремим обходом (саме тому `LinkedList<T>` у .NET реалізовано як двозв'язний).

**3. Чому іноді масив швидший за зв'язний список на практиці, попри гіршу теоретичну складність (Big O)?**

Через локальність кешу (cache locality). Елементи масиву лежать суцільно в пам'яті, тому процесор підвантажує їх у кеш-лініями наперед і рідко "промахується" повз кеш при послідовному доступі. Вузли зв'язного списку розкидані по купі, тому кожен перехід `current = current.Next` — це, по суті, стрибок у непередбачувану ділянку пам'яті, з високою ймовірністю кеш-промаху, що на порядок повільніше за звернення до даних, які вже в кеші. Для невеликих елементів і помірних розмірів колекції ця константа часто переважує теоретичну перевагу O(1) операцій зв'язного списку над O(n) операціями масиву.

**4. Коли варто заздалегідь вказати `Capacity` для `List<T>`?**

Коли приблизний фінальний розмір колекції відомий заздалегідь (наприклад, `Count` результату запиту до БД, розмір вхідного масиву, який копіюється в новий список). Це не змінює асимптотичну складність, але усуває реальні, вимірювані витрати на повторні перевиділення внутрішнього масиву й копіювання елементів під час заповнення.

**5. Які операції в `LinkedList<T>` є O(1), а які — O(n), і чому в ньому немає індексатора `[i]`?**

O(1): `AddFirst`, `AddLast`, `RemoveFirst`, `RemoveLast`, а також `Remove(LinkedListNode<T> node)`, якщо вже маємо посилання на конкретний вузол. O(n): доступ за "логічним номером" елемента (потрібен обхід від `First`), пошук елемента за значенням. Індексатора немає навмисно — щоб не створювати ілюзію, ніби `list[i]` — це дешева операція, як у масиву; розробник має усвідомлено писати явний обхід і розуміти його вартість.

**6. Що станеться з продуктивністю, якщо викликати `list.Insert(0, x)` у циклі n разів?**

Кожен виклик коштує O(n) (зсув усіх наявних елементів), і виконується він n разів — сумарна складність O(n²). Це класичний прихований "квадратичний" антипатерн, який непомітний на малих обсягах даних, але критично сповільнює систему при рості колекції.

### Senior

**1. Поясни, чому доступ до елемента масиву за індексом — O(1) на рівні адресної арифметики.**

Масив — це суцільний блок пам'яті, у якому всі елементи мають однаковий, наперед відомий розмір у байтах. Адреса будь-якого елемента обчислюється за формулою `адреса = базова_адреса + індекс × розмір_елемента` — це одне множення й одне додавання, час виконання яких є константним і не залежить ані від значення індексу, ані від розміру масиву. Тому процесору не потрібно "проходити" через попередні елементи, щоб дістатися потрібного — досить обчислити адресу й напряму звернутись за нею до пам'яті (або, якщо дані вже в кеші, — до кешу). Саме ця властивість — фіксований розмір елемента плюс суцільність розташування — і є необхідною умовою для O(1) довільного доступу; вона ж і є причиною, чому масив не може мати елементи змінного розміру чи "дірки" без втрати цієї властивості.

**2. Спроєктуй чергу завдань і обґрунтуй вибір структури даних для неї.**

Черга завдань потребує двох операцій на протилежних кінцях: постановка нового завдання ("в кінець") і забір найстарішого завдання для обробки ("з початку") — тобто класична FIFO-семантика. Наївний вибір `List<Job>` із `RemoveAt(0)` для забору — пастка: видалення з початку `List<T>` коштує O(n) через зсув усіх елементів, і при рості черги до тисяч завдань обробка всієї черги стає O(n²) (детальний розбір — у розділі 7 цього документа). Правильний вибір — `Queue<T>`, реалізована в .NET як кільцевий буфер над масивом: вона поєднує компактність і кеш-дружність масиву з O(1)-вартістю операцій на обох кінцях (`Enqueue`/`Dequeue`), без потреби виділяти окремий об'єкт-вузол на кожен елемент, як довелося б робити з `LinkedList<T>`. `LinkedList<T>` теж підійшла б за Big O (O(1) `AddLast`/`RemoveFirst`), але для типової черги без потреби у вставці/видаленні в довільній середній позиції `Queue<T>` — і простіший, і, як правило, практично швидший вибір завдяки локальності кешу. Якщо ж додатково потрібна пріоритетність (обробляти не строго в порядку надходження, а за пріоритетом), правильним вибором стане вже інша структура — `PriorityQueue<T>` (як правило, на основі бінарної купи), що виходить за межі цього документа.

**3. Наведи реальний приклад, де теоретично гірша за Big O структура даних насправді працює швидше на практиці, і поясни чому.**

Класичний приклад — вставка чи видалення в середині послідовності на помірних обсягах даних (скажімо, до кількох десятків-сотень тисяч невеликих елементів): `List<T>.Insert(k, x)` — O(n) через фізичний зсув елементів, тоді як `LinkedList<T>` формально дає O(1) релінкування вузла, якщо позиція вже відома. Проте на практиці, коли позицію ще треба знайти обходом від голови (типова ситуація, якщо немає збереженого посилання на потрібний вузол), реальна вартість `LinkedList<T>` теж стає O(n) — і при цьому кожен крок обходу є потенційним кеш-промахом через розкиданість вузлів по купі, тоді як O(n)-зсув елементів `List<T>` — це послідовне, кеш-дружнє й часто векторизоване копіювання суміжних байтів пам'яті. У результаті `List<T>` нерідко виявляється швидшим у "гонитві" з `LinkedList<T>` навіть у сценаріях, де на папері зв'язний список мав би вигравати — і це саме те, що ми виміряли (щоправда, на протилежному прикладі — вставці в голову) у Прикладі 4: різниця в порядки величини, і не завжди на користь структури з "кращим" Big O для конкретного випадку без урахування контексту (для того конкретного прикладу, де позиція вставки завжди відома наперед — голова списку, — `LinkedList<T>` таки виграв беззаперечно; ключовий висновок — перевіряти на реальних даних, а не покладатись лише на асимптотику).

**4. Порівняй trade-off cache locality проти теоретичної складності операцій при виборі структури даних для великого обсягу даних.**

Big O описує, як зростає **кількість елементарних операцій** зі збільшенням розміру вхідних даних, але навмисно ігнорує сталий множник (константу) перед цією кількістю — а саме в цій константі й ховається вплив апаратного забезпечення, зокрема ієрархії кешів процесора. Масив, завдяки суцільному розташуванню в пам'яті, майже завжди отримує в рази менший множник на операцію через високу частку кеш-хітів і успішну роботу апаратного prefetcher'а; зв'язний список, через розкиданість вузлів по купі, отримує значно більший множник через часті кеш-промахи (pointer chasing), кожен з яких коштує на порядки більше тактів процесора, ніж звернення до вже кешованих даних. На малих обсягах даних (усе влазить у кеш L1/L2 в обох випадках) різниця в множниках малопомітна, і Big O непогано передбачає реальну поведінку. Але на **великих обсягах** — коли дані масиву вже не влазять у кеш і послідовний доступ починає впиратись у пропускну здатність оперативної пам'яті (яка, утім, усе одно значно ефективніше використовується при послідовному, передбачуваному доступі, ніж при випадкових стрибках) — розрив між "теоретично кращою" за Big O структурою (зв'язний список для вставок/видалень) і "практично швидшою" (масив, завдяки кеш-дружності) не зникає, а найчастіше **тільки посилюється**: кожен окремий кеш-промах при "стрибку по посиланнях" коштує дедалі дорожче відносно швидкості самого процесора, тоді як послідовне зчитування масиву продовжує ефективно використовувати пропускну здатність пам'яті. Тому для по-справжньому великих обсягів даних правильний інженерний підхід — не покладатись сліпо ні на "теоретично краще Big O", ні на інтуїцію "масив завжди швидший", а вимірювати на реальних даних і реальному апаратному забезпеченні (профілювання, лічильники кеш-промахів, `BenchmarkDotNet`), особливо в критичних для продуктивності ділянках коду.

## Підсумок

### Швидкий довідник: Big O операцій

| Операція | Масив (фіксований) | `List<T>` | Однозв'язний список | `LinkedList<T>` (двозв'язний) |
|---|---|---|---|---|
| Доступ за індексом `[i]` | O(1) | O(1) | O(n) | O(n) |
| Пошук (непосортований) | O(n) | O(n) | O(n) | O(n) |
| Вставка в кінець | — | амортизований O(1) | O(1)/O(n)* | O(1) |
| Вставка на початок | — | O(n) | O(1) | O(1) |
| Вставка в середину (позиція відома) | O(n) | O(n) | O(1) релінк / O(n) якщо шукати | O(1) релінк / O(n) якщо шукати |
| Видалення з кінця | — | O(1) | O(n)** | O(1) |
| Видалення з початку | — | O(n) | O(1) | O(1) |
| Видалення в середині (є вузол) | O(n) | O(n) | O(n)*** | **O(1)** |
| Cache locality | відмінна | відмінна | погана | погана |

\* O(1), якщо тримати посилання на `tail`; інакше потрібен обхід до кінця.
\*\* потрібно дійти до передостаннього вузла, щоб оновити його `Next` на `null`.
\*\*\* навіть маючи вузол, треба знайти попередника обходом від `head`, бо `Next`-only вузол не знає `Previous`.

### Чек-лист вибору: масив чи зв'язний список?

1. **Чи потрібен частий доступ за індексом, бінарний пошук чи сортування?** → так, майже завжди → **масив / `List<T>`**.
2. **Чи елементи маленькі, а колекція не величезна?** → так → **масив / `List<T>`** (виграє завдяки cache locality навіть там, де O(n) теоретично гірше за O(1)).
3. **Чи вставки/видалення відбуваються переважно за вже наявним посиланням на вузол (ітератор/курсор), а не за індексом чи пошуком?** → так → **зв'язний список** (і саме двозв'язний, якщо потрібне видалення без обходу).
4. **Чи патерн доступу — "додай у кінець, забери з початку" (FIFO) або "додай/забери з одного кінця" (LIFO)?** → це не "масив vs список" питання взагалі — використовуйте призначені абстракції `Queue<T>` / `Stack<T>` (детально — у наступному документі серії, [`2-stacks-and-queues.md`](./2-stacks-and-queues.md)).
5. **Сумніваєтесь, яка структура швидша для вашого конкретного випадку?** → не покладайтесь лише на Big O з таблиці вище — **виміряйте** (`Stopwatch`, `BenchmarkDotNet`) на реалістичних для вашої задачі розмірах даних, як показано в Прикладі 4.
