## Замість вступу: місток з попереднього файлу

У файлі [`1-arrays-and-linked-lists.md`](./1-arrays-and-linked-lists.md) ми закінчили сценарієм про **чергу задач** (job queue): систему, яка приймає завдання у порядку надходження й обробляє їх у тому ж порядку, а наївна реалізація на основі `List<T>` з `RemoveAt(0)` для вилучення елемента з початку виявилася прихованою бомбою уповільненого дії — O(n) на кожне вилучення замість очікуваного O(1), непомітне на тестових даних і катастрофічне під навантаженням у production.

Це не випадковість, а природний наступний крок: масиви й однозв'язні списки — це "сирий будівельний матеріал", а **стек** і **черга** — це вже конкретні **абстрактні типи даних (ADT)**, які накладають дисципліну на те, *як* можна додавати й вилучати елементи. Ця дисципліна — не обмеження заради обмеження, а те, що дозволяє гарантувати O(1) для базових операцій, якщо структуру реалізовано правильно (а неправильна реалізація на кшталт `List<T>.RemoveAt(0)` якраз і порушує цю гарантію).

У цьому файлі ми розберемо: стек (LIFO) та його "невидиму" присутність практично в кожній програмі через call stack; чергу (FIFO) та правильну O(1)-реалізацію через кільцевий буфер; двосторонню чергу (deque); та практичні сценарії — від перевірки дужок до Undo/Redo в текстовому редакторі.

## 1. Стек (Stack) — LIFO

**Стек (Stack)** — це структура даних, яка працює за принципом **LIFO (Last In, First Out — останній прийшов, перший вийшов)**. Елемент, доданий останнім, буде вилучений першим.

### Базові операції

| Операція | Опис | Складність |
|---|---|---|
| `Push(x)` | Додати елемент `x` на вершину стека | O(1) |
| `Pop()` | Вилучити та повернути елемент з вершини стека | O(1) |
| `Peek()` / `Top()` | Подивитись елемент на вершині, не вилучаючи його | O(1) |
| `IsEmpty()` | Перевірити, чи стек порожній | O(1) |
| `Count` / `Size` | Кількість елементів у стеці | O(1) |

Усі базові операції стека — O(1), і це не випадковість, а прямий наслідок обмеження: працювати можна **лише з одним кінцем** структури (вершиною). Немає потреби зсувати елементи чи шукати щось у середині — просто додати/забрати "зверху".

### Аналогія з реального життя

Уявіть **стос тарілок** у шафі чи на роздачі в їдальні. Ви можете:
- покласти нову тарілку **тільки зверху** стосу (`Push`);
- взяти тарілку **тільки зверху** стосу (`Pop`);
- подивитись, яка тарілка зверху, не забираючи її (`Peek`).

Ви фізично не можете витягнути тарілку з середини стосу, не знявши спочатку всі тарілки над нею. Саме це обмеження — і жодне інше — визначає стек як структуру даних.

### Реалізація в C#

У .NET стек реалізований у `System.Collections.Generic.Stack<T>` — на основі динамічного масиву (аналогічно до `List<T>`, з амортизованим O(1) для `Push` за рахунок подвоєння ємності при переповненні):

```csharp
var stack = new Stack<int>();

stack.Push(1);   // [1]
stack.Push(2);   // [1, 2]
stack.Push(3);   // [1, 2, 3]  <- вершина

Console.WriteLine(stack.Peek()); // 3 (не видаляє)
Console.WriteLine(stack.Pop());  // 3 (видаляє і повертає)
Console.WriteLine(stack.Pop());  // 2

Console.WriteLine(stack.Count);  // 1
```

### Де стек ховається "невидимо" в програмному забезпеченні

Це найважливіша концептуальна частина цього розділу: стек — не просто структура даних із бібліотеки, яку ви явно оголошуєте. Він працює **під капотом** практично в кожній програмі, яку ви пишете.

#### 1. Стек викликів (Call Stack) — і рекурсія

Коли метод викликає інший метод, середовище виконання (CLR у випадку .NET) створює **фрейм стека (stack frame)** — блок пам'яті, що містить:
- адресу повернення (куди повернутись після завершення викликаного методу);
- параметри методу;
- локальні змінні методу;
- (іноді) збережені регістри процесора.

Цей фрейм **проштовхується (push)** на call stack при вході в метод і **знімається (pop)** при виході з нього. Це буквально стек у строгому сенсі LIFO: останній викликаний метод завершується першим.

```csharp
void A()
{
    Console.WriteLine("Вхід в A");
    B();
    Console.WriteLine("Вихід з A");
}

void B()
{
    Console.WriteLine("Вхід в B");
    C();
    Console.WriteLine("Вихід з B");
}

void C()
{
    Console.WriteLine("Вхід в C");
}

// Стан call stack у момент виконання C():
//   ┌─────────┐
//   │ Frame C │  <- вершина (виконується зараз)
//   ├─────────┤
//   │ Frame B │
//   ├─────────┤
//   │ Frame A │
//   ├─────────┤
//   │ Frame Main │
//   └─────────┘
```

**Рекурсія** — це прямий, буквальний наслідок існування call stack: кожен рекурсивний виклик додає новий фрейм на стек, і жоден із них не звільняється, поки не завершиться найглибший (базовий) виклик. Саме тому рекурсія природно моделює задачі, що самі мають "стекову" структуру (обхід дерева, розбір вкладених структур).

**Stack Overflow — це буквально те, що написано в назві.** Кожен потік має фіксований, обмежений розмір стека (типово 1 МБ для потоку в .NET за замовчуванням). Якщо рекурсія занадто глибока (або нескінченна через відсутність/помилку в базовому випадку), кількість фреймів на call stack перевищує виділений розмір пам'яті — і середовище виконання аварійно завершує роботу з `StackOverflowException`. Це не абстрактна метафора — стек викликів займає реальну пам'ять, і ця пам'ять реально закінчується.

#### 2. Історія скасування дій (Undo history)

Найпростіший спосіб реалізувати Undo — зберігати кожну виконану дію (або знімок стану) у стеку. Скасування (`Undo`) — це `Pop()` з цього стека. Це напряму пов'язано з двома патернами проєктування з папки `Поведінкові/` цього репозиторію:

- **[Memento](../../Поведінкові/memento-pattern-csharp.md)** — патерн, що описує *як* коректно зберігати знімок стану, не порушуючи інкапсуляцію об'єкта; стек знімків (`Stack<Memento>`) — це типова структура даних, яку використовує "Caretaker" (доглядач історії) з цього патерну.
- **[Command](../../Поведінкові/command-pattern-csharp.md)** — патерн, де кожна дія користувача інкапсулюється в об'єкт-команду з методами `Execute()`/`Undo()`; стек виконаних команд дозволяє скасовувати їх у зворотному порядку (LIFO — останню виконану дію скасовуємо першою).

Детальний робочий приклад реалізації Undo/Redo двома стеками — у [розділі 7](#7-реальний-сценарій-реалізація-undoredo-для-текстового-редактора-двома-стеками) цього документа.

#### 3. Обчислення виразів та розбір (parsing)

Стек — природний інструмент для задач, де потрібно "пам'ятати, що ми ще не закрили":

- **Перевірка збалансованості дужок** — `(`, `[`, `{` — класична задача, де кожна відкриваюча дужка проштовхується в стек, а кожна закриваюча має відповідати вершині стека (детальна реалізація — у [прикладі 1 розділу 6](#6-практичні-приклади-на-c)).
- **Перетворення інфіксного запису в постфіксний (Shunting-yard алгоритм)** — наприклад, вираз `3 + 4 * 2` (інфіксний, звичний людині) перетворюється на `3 4 2 * +` (постфіксний, зручний для обчислення машиною). Алгоритм використовує стек для тимчасового зберігання операторів, доки не визначиться їхній пріоритет відносно наступних символів.
- **Обчислення постфіксного виразу** — маючи вираз у постфіксній формі, достатньо одного стека: числа проштовхуються в стек, а зустрівши оператор, знімаються два верхні числа, застосовується операція, і результат повертається назад у стек.
- **Розбір вкладених структур** — JSON, XML, синтаксичні дерева компіляторів — усе це природно розбирається за допомогою (явного або неявного, через рекурсію) стека, оскільки вкладеність — це і є стекова структура: щоб закрити зовнішній рівень, спочатку треба закрити всі внутрішні.

## 2. Черга (Queue) — FIFO

**Черга (Queue)** — це структура даних, яка працює за принципом **FIFO (First In, First Out — перший прийшов, перший вийшов)**. Елемент, доданий першим, буде вилучений першим.

### Базові операції

| Операція | Опис | Складність (за правильної реалізації) |
|---|---|---|
| `Enqueue(x)` | Додати елемент `x` у кінець черги | O(1) |
| `Dequeue()` | Вилучити та повернути елемент з початку черги | O(1) |
| `Peek()` | Подивитись елемент на початку черги, не вилучаючи його | O(1) |
| `IsEmpty()` | Перевірити, чи черга порожня | O(1) |
| `Count` | Кількість елементів у черзі | O(1) |

**Ключове застереження, яке прямо продовжує проблему з попереднього файлу серії:** ці O(1) гарантії справедливі лише для *правильної* реалізації черги. Якщо реалізувати чергу наївно поверх `List<T>`, викликаючи `RemoveAt(0)` для `Dequeue()`, ви отримаєте **O(n)** замість O(1) — саме та помилка, яку ми детально розібрали в кінці `1-arrays-and-linked-lists.md`. `RemoveAt(0)` змушує зсунути всі інші `n - 1` елементів на одну позицію вліво, щоб заповнити звільнене місце на початку масиву. На малих чергах ви цього не помітите; на черзі з десятками тисяч елементів під навантаженням це перетворюється на квадратичну (O(n²)) деградацію продуктивності всієї системи чергового опрацювання.

Справжня O(1)-реалізація черги вимагає однієї з двох стратегій:
1. **Однозв'язний список** зі збереженими вказівниками на голову *і* хвіст — `Enqueue` додає новий вузол в кінець (O(1), маючи вказівник на хвіст), `Dequeue` знімає вузол з початку (O(1), маючи вказівник на голову). Саме так, до речі, влаштована `Queue<T>` не в .NET (там інша реалізація — див. нижче), а, наприклад, у мовах, де черга явно будується на `LinkedList`.
2. **Кільцевий буфер (circular buffer)** на основі масиву фіксованого розміру з індексами `head`/`tail`, що "заворачиваются" по колу. Це найпоширеніший і найефективніший з точки зору використання пам'яті та кеша процесора підхід — детально розібраний у [розділі 3](#3-кільцевий-буфер-circular-buffer--ефективна-реалізація-черги-на-масиві).

.NET-реалізація `System.Collections.Generic.Queue<T>` використовує саме другий підхід — кільцевий буфер на масиві, що динамічно розширюється при заповненні (аналогічно до `List<T>`, але без зсування елементів при `Dequeue`).

```csharp
var queue = new Queue<string>();

queue.Enqueue("Клієнт А"); // [А]
queue.Enqueue("Клієнт Б"); // [А, Б]
queue.Enqueue("Клієнт В"); // [А, Б, В]

Console.WriteLine(queue.Peek());    // "Клієнт А" (перший у черзі, не видаляє)
Console.WriteLine(queue.Dequeue()); // "Клієнт А" (обслужили, видаляємо)
Console.WriteLine(queue.Dequeue()); // "Клієнт Б"

Console.WriteLine(queue.Count); // 1 (залишився "Клієнт В")
```

### Аналогія з реального життя

Черга — це буквально **черга/лінія в магазині**. Перша людина, що стала в чергу, обслуговується першою (`Dequeue`). Нові люди приєднуються в кінець черги (`Enqueue`). Ніхто (у чесній системі) не проходить поперед когось, хто прийшов раніше — саме це і є FIFO.

### Реальні застосування черги

- **Планування задач (task/job scheduling)** — сервер обробки фонових завдань (наприклад, надсилання email, генерація звітів) отримує завдання й ставить їх у чергу, обробляючи в порядку надходження — саме той сценарій job queue, з яким закінчився попередній файл серії.
- **Обхід графа в ширину (BFS — Breadth-First Search)** — алгоритм BFS використовує чергу для обробки вершин "хвиля за хвилею": спочатку обробляються всі сусіди стартової вершини, потім усі сусіди сусідів, і так далі. Детальний розбір BFS і його застосувань (пошук найкоротшого шляху в незваженому графі, перевірка зв'язності) — у майбутньому файлі цієї серії, присвяченому обходу графів.
- **Спулери друку (print spoolers)** — документи, надіслані на друк, стають у чергу і друкуються в порядку надходження, незалежно від того, з якого застосунку чи комп'ютера вони прийшли.
- **Черги повідомлень (message queues) / брокери подій** — концептуально та ж сама ідея FIFO, але в розподіленому масштабі: RabbitMQ, Apache Kafka, Azure Service Bus, AWS SQS. Це прямий місток до обговорення поліглотної персистентності та черг повідомлень/шини подій у серії про бази даних цього репозиторію (файли про поліглотну персистентність та про розподілені транзакції/Saga-патерн у папці `БазиДаних/NoSQL`), де черги повідомлень використовуються саме для того, щоб розв'язати сервіси в часі: продюсер кладе повідомлення в чергу й одразу продовжує роботу, а консюмер забирає повідомлення й обробляє його у власному темпі, гарантуючи (залежно від налаштувань брокера) порядок обробки та доставку принаймні один раз.

## 3. Кільцевий буфер (Circular Buffer) — ефективна реалізація черги на масиві

### Проблема наївної реалізації черги на масиві

Уявімо, що ми намагаємось реалізувати чергу на звичайному масиві фіксованого розміру, тримаючи лише індекс `tail` (куди додавати наступний елемент), а `Dequeue` реалізуємо одним із двох "наївних" способів:

**Варіант А: зсув елементів при кожному Dequeue.**
Після вилучення елемента з позиції 0 всі інші елементи зсуваються на одну позицію вліво, щоб "голова" черги завжди була в індексі 0. Це рівно та сама проблема, що й `List<T>.RemoveAt(0)` — O(n) на кожен `Dequeue`.

**Варіант Б: просто рухати вказівник head вперед, ніколи не зсуваючи.**
`Dequeue` просто збільшує `head` на 1, не чіпаючи інші елементи. `Dequeue` стає O(1) — але з'являється нова проблема: місце в масиві зліва від `head` **ніколи не звільняється й ніколи не використовується повторно**. Після достатньої кількості циклів enqueue/dequeue `tail` "впирається" у кінець масиву, і хоча логічно в черзі може бути мало елементів (або й жодного), фізично ми не можемо додати новий елемент, бо `tail` вийшов за межі масиву — доводиться або виділяти новий, більший масив (марно витрачаючи пам'ять на "мертву зону" зліва), або відмовляти в `Enqueue`, хоча черга логічно не переповнена.

### Рішення: кільцевий буфер (Circular Buffer / Ring Buffer)

Ідея кільцевого буфера елегантна: масив фіксованого розміру трактується як **логічно замкнутий у кільце** — після останнього індексу (`capacity - 1`) наступним "логічно" йде знову індекс `0`. Це досягається арифметикою за модулем (`% capacity`) при просуванні індексів `head` та `tail`.

```
Кільцевий буфер ємністю 6, елементи A, B, C вже додані (head=0, tail=3):

  індекс:   0    1    2    3    4    5
          ┌────┬────┬────┬────┬────┬────┐
          │ A  │ B  │ C  │    │    │    │
          └────┴────┴────┴────┴────┴────┘
            ↑                   ↑
          head                tail (наступний Enqueue сюди)

Dequeue() двічі -> видаляємо A, потім B. head рухається вперед:

  індекс:   0    1    2    3    4    5
          ┌────┬────┬────┬────┬────┬────┐
          │    │    │ C  │    │    │    │
          └────┴────┴────┴────┴────┴────┘
                        ↑         ↑
                      head       tail

Enqueue(D), Enqueue(E), Enqueue(F) -> tail рухається до кінця масиву:

  індекс:   0    1    2    3    4    5
          ┌────┬────┬────┬────┬────┬────┐
          │    │    │ C  │ D  │ E  │ F  │
          └────┴────┴────┴────┴────┴────┘
                        ↑                ↑
                      head          tail = 6 mod 6 = 0  <- ЗАВЕРНУВСЯ!

Enqueue(G) -> tail = 0, тобто пишемо в самий початок масиву,
              який вже звільнений (A і B давно вилучені):

  індекс:   0    1    2    3    4    5
          ┌────┬────┬────┬────┬────┬────┐
          │ G  │    │ C  │ D  │ E  │ F  │
          └────┴────┴────┴────┴────┴────┘
            ↑           ↑
          tail=1      head=2

Черга логічно містить: C, D, E, F, G (у цьому порядку FIFO) —
фізично вони "обгортаються" через кінець масиву назад до початку.
```

Формули просування індексів (при ємності `capacity`):

```csharp
tail = (tail + 1) % capacity;   // після Enqueue
head = (head + 1) % capacity;   // після Dequeue
```

Завдяки цьому і `Enqueue`, і `Dequeue` залишаються **строго O(1)** — незалежно від того, скільки циклів "заповнення-спорожнення" вже відбулося, і без жодного зсування елементів чи витраченої "мертвої" пам'яті.

### Проблема неоднозначності "повний чи порожній" (full/empty ambiguity)

Тут виникає підступна, класична проблема кільцевих буферів: **коли `head == tail`, чи означає це, що буфер порожній, чи що він повний?**

Розгляньмо: спочатку `head == tail == 0` — буфер порожній. Але якщо ми додамо `capacity` елементів (заповнимо буфер повністю), `tail` після останнього `Enqueue` знову дорівнюватиме `head` (обійшовши по колу весь масив і "наздогнавши" голову)! Умова `head == tail` виявляється **однаковою** і для порожнього, і для повністю заповненого буфера — просто перевіряючи індекси, ми не можемо розрізнити ці два протилежні стани.

Є два стандартні способи вирішення цієї проблеми:

**Спосіб 1 (найпоширеніший): окреме поле-лічильник `count`.**
Замість того, щоб визначати "порожній/повний" виключно через порівняння `head` і `tail`, тримаємо окреме поле `count`, яке явно інкрементується при `Enqueue` й декрементується при `Dequeue`. Тоді:
- буфер порожній, коли `count == 0`;
- буфер повний, коли `count == capacity`;
- `head == tail` саме по собі більше нічого не означає окремо від значення `count`.

Це найпростіший, найнадійніший і найпоширеніший підхід на практиці (саме він використаний у прикладі `CircularQueue<T>` у [розділі 6](#6-практичні-приклади-на-c)).

**Спосіб 2: свідомо "жертвувати" одним слотом масиву.**
Альтернативний підхід — виділити масив розміром `capacity + 1` і домовитись, що буфер вважається повним, коли `(tail + 1) % capacity == head` (тобто коли між `tail` і `head` залишається рівно один незаповнений слот), а порожнім — коли `head == tail`, як і раніше. Це дозволяє однозначно розрізняти стани без окремого поля `count`, ціною одного "завжди порожнього" слота масиву, який ніколи не використовується для зберігання даних. Цей підхід трохи економніший по кількості полів структури, але менш інтуїтивний і рідше зустрічається в навчальних матеріалах та типових бібліотечних реалізаціях — на співбесідах достатньо впевнено пояснити спосіб 1 і згадати спосіб 2 як альтернативу.

## 4. Двостороння черга (Deque)

**Deque (Double-Ended Queue, вимовляється "дек")** — структура даних, що підтримує додавання й вилучення елементів **з обох кінців** за O(1):

| Операція | Опис | Складність |
|---|---|---|
| `AddFirst(x)` / `PushFront(x)` | Додати елемент на початок | O(1) |
| `AddLast(x)` / `PushBack(x)` | Додати елемент у кінець | O(1) |
| `RemoveFirst()` / `PopFront()` | Вилучити елемент з початку | O(1) |
| `RemoveLast()` / `PopBack()` | Вилучити елемент з кінця | O(1) |
| `PeekFirst()` / `PeekLast()` | Подивитись перший/останній елемент | O(1) |

### Аналогія з реального життя

Deque — це **колода карт**, з якої можна брати чи додавати карти **як зверху, так і знизу**. На відміну від стосу тарілок (стек — лише зверху) чи черги в магазині (тільки з одного кінця приходять, з іншого йдуть), колода карт у ваших руках дозволяє однаково зручно працювати з обома кінцями.

### Deque у .NET

.NET додав спеціалізований тип `System.Collections.Generic.Deque<T>`, що надає O(1) операції з обох кінців на основі внутрішнього кільцевого буфера (той самий принцип, що й у розділі 3, але з можливістю "завертати" в обидва боки). До появи виділеного типу deque традиційно реалізовували через `LinkedList<T>` (двозв'язний список), де `AddFirst`/`AddLast`/`RemoveFirst`/`RemoveLast` — усі O(1) завдяки збереженим вказівникам на голову *і* хвіст списку, хоча й з додатковими накладними витратами пам'яті на вказівники кожного вузла та гіршою локальністю кеша порівняно з масивом.

```csharp
var deque = new Deque<int>();

deque.PushBack(2);   // [2]
deque.PushBack(3);   // [2, 3]
deque.PushFront(1);  // [1, 2, 3]
deque.PushFront(0);  // [0, 1, 2, 3]

Console.WriteLine(deque.PeekFront()); // 0
Console.WriteLine(deque.PeekBack());  // 3

deque.PopFront(); // видаляє 0 -> [1, 2, 3]
deque.PopBack();  // видаляє 3 -> [1, 2]
```

### Навіщо потрібен deque

**1. Одна структура — і стек, і черга.**
Оскільки deque підтримує O(1) операції з обох кінців, його можна використовувати як стек (працюючи лише з одним кінцем через `PushBack`/`PopBack`) або як чергу (`PushBack` + `PopFront`) — не тримаючи в проєкті дві окремі спеціалізовані структури, якщо потрібна гнучкість.

**2. Алгоритми "ковзного вікна" (sliding window) — і зокрема монотонний деск.**
Deque — ключова структура даних для класу задач "sliding window" (ковзне вікно): коли потрібно ефективно підтримувати якусь агреговану властивість (максимум, мінімум, суму) над вікном фіксованого чи змінного розміру, що "ковзає" вздовж масиву чи потоку даних. Детальний розбір технік ковзного вікна — у майбутньому файлі цієї серії, присвяченому технікам роботи з масивами, але вже зараз варто назвати класичний **senior-рівня алгоритм "монотонний деск" (monotonic deque)**, що розв'язує задачу "sliding window maximum" (знайти максимум у кожному вікні розміру `k` при проходженні масиву) за загальний час O(n) замість наївних O(n·k): у deque підтримується спадна послідовність індексів-кандидатів на максимум, і кожен елемент масиву додається й видаляється з deque не більше одного разу за весь прохід.

## 5. Порівняльна таблиця: Stack vs Queue vs Deque vs Priority Queue

| Структура | Порядок вилучення | Push/Enqueue | Pop/Dequeue | Peek | Доступ до довільного елемента | Типова реалізація |
|---|---|---|---|---|---|---|
| **Stack** | LIFO (останній прийшов — перший вийшов) | O(1) (з одного кінця) | O(1) (з одного кінця) | O(1) | O(n) | Динамічний масив |
| **Queue** | FIFO (перший прийшов — перший вийшов) | O(1) (в кінець) | O(1) (з початку) | O(1) | O(n) | Кільцевий буфер / зв'язний список |
| **Deque** | Довільний — обидва кінці рівноправні | O(1) (з обох кінців) | O(1) (з обох кінців) | O(1) (з обох кінців) | O(n) | Кільцевий буфер / двозв'язний список |
| **Priority Queue** | За пріоритетом (найменший/найбільший елемент першим, незалежно від порядку додавання) | O(log n) | O(log n) | O(1) | O(n) | Бінарна купа (heap) |

**Priority Queue (черга з пріоритетами)** заслуговує на окрему увагу: на відміну від Stack/Queue/Deque, порядок вилучення тут визначається **не порядком додавання**, а явним пріоритетом кожного елемента (наприклад, "терміновість" завдання чи вага ребра в алгоритмі Дейкстри). Це принципово інша внутрішня структура (як правило, бінарна купа — heap), з іншими гарантіями складності (O(log n), а не O(1), для вставки та вилучення екстремального елемента) — тому вона розглядається окремо, детально, у майбутньому файлі цієї серії `5-heaps-and-priority-queues.md`, присвяченому купам.

## 6. Практичні приклади на C#

### Приклад 1 — Перевірка збалансованості дужок за допомогою стека

Класична задача співбесід: перевірити, чи є всі дужки в рядку правильно збалансованими та вкладеними (`(`, `[`, `{` мають відповідну закриваючу пару в правильному порядку).

```csharp
using System;
using System.Collections.Generic;

public static class BracketValidator
{
    private static readonly Dictionary<char, char> Pairs = new()
    {
        [')'] = '(',
        [']'] = '[',
        ['}'] = '{',
    };

    public static bool IsBalanced(string input)
    {
        var stack = new Stack<char>();

        foreach (char c in input)
        {
            if (c is '(' or '[' or '{')
            {
                // Відкриваюча дужка - просто запам'ятовуємо її на вершині стека.
                stack.Push(c);
            }
            else if (c is ')' or ']' or '}')
            {
                // Закриваюча дужка має відповідати тій, що зараз на вершині стека.
                if (stack.Count == 0 || stack.Pop() != Pairs[c])
                {
                    return false; // або стек порожній (нема чому закривати),
                                  // або типи дужок не збігаються
                }
            }
            // усі інші символи (літери, цифри, пробіли) ігноруються
        }

        // Якщо в кінці стек не порожній - лишились незакриті відкриваючі дужки.
        return stack.Count == 0;
    }
}

public static class Program
{
    public static void Main()
    {
        string[] tests =
        {
            "(a + b) * [c - d]",   // валідний
            "{[()()]}",             // валідний, глибока вкладеність
            "(a + b",               // невалідний: незакрита (
            "a + b)",               // невалідний: зайва закриваюча )
            "([)]",                 // невалідний: неправильний порядок закриття
            "",                     // валідний (порожній рядок - тривіально збалансований)
        };

        foreach (var test in tests)
        {
            bool result = BracketValidator.IsBalanced(test);
            string status = result ? "✅ ВАЛІДНИЙ" : "❌ НЕВАЛІДНИЙ";
            Console.WriteLine($"\"{test}\" -> {status}");
        }
    }
}

// Вивід:
// "(a + b) * [c - d]" -> ✅ ВАЛІДНИЙ
// "{[()()]}" -> ✅ ВАЛІДНИЙ
// "(a + b" -> ❌ НЕВАЛІДНИЙ
// "a + b)" -> ❌ НЕВАЛІДНИЙ
// "([)]" -> ❌ НЕВАЛІДНИЙ
// "" -> ✅ ВАЛІДНИЙ
```

Пояснення логіки на випадку `"([)]"`: бачимо `(` — Push на стек `['(']`. Бачимо `[` — Push, стек `['(', '[']`. Бачимо `)` — знімаємо вершину стека, це `[`, а очікували `(` для закриття `)` — невідповідність, повертаємо `false`. Саме тому важливий порядок: `[)` — це неправильна вкладеність, хоча обидва типи дужок присутні в рядку.

### Приклад 2 — Власна реалізація CircularQueue<T> на кільцевому буфері

Реалізуємо чергу фіксованої ємності "з нуля" на основі кільцевого буфера з розділу 3, наочно демонструючи "заворачивание" (wrap-around) індексів.

```csharp
using System;

public class CircularQueue<T>
{
    private readonly T[] _buffer;
    private int _head; // індекс першого елемента (той, що вийде наступним при Dequeue)
    private int _tail; // індекс, куди буде записаний НАСТУПНИЙ елемент при Enqueue
    private int _count; // скільки елементів фактично зберігається (вирішує full/empty ambiguity)

    public CircularQueue(int capacity)
    {
        if (capacity <= 0)
            throw new ArgumentException("Ємність має бути додатною", nameof(capacity));

        _buffer = new T[capacity];
        _head = 0;
        _tail = 0;
        _count = 0;
    }

    public int Capacity => _buffer.Length;
    public int Count => _count;
    public bool IsEmpty => _count == 0;
    public bool IsFull => _count == _buffer.Length;

    public void Enqueue(T item)
    {
        if (IsFull)
            throw new InvalidOperationException("Черга заповнена - неможливо додати елемент");

        _buffer[_tail] = item;
        _tail = (_tail + 1) % _buffer.Length; // ключовий момент: "заворачивание" по колу
        _count++;
    }

    public T Dequeue()
    {
        if (IsEmpty)
            throw new InvalidOperationException("Черга порожня - неможливо видалити елемент");

        T item = _buffer[_head];
        _buffer[_head] = default!; // прибираємо посилання, щоб уникнути витоку пам'яті (для reference-типів)
        _head = (_head + 1) % _buffer.Length; // так само "заворачивание"
        _count--;
        return item;
    }

    public void PrintState()
    {
        Console.WriteLine($"  head={_head}, tail={_tail}, count={_count}, capacity={Capacity}");
    }
}

public static class Program
{
    public static void Main()
    {
        var queue = new CircularQueue<char>(4); // невелика ємність, щоб швидко побачити wrap-around

        Console.WriteLine("Enqueue A, B, C:");
        queue.Enqueue('A');
        queue.Enqueue('B');
        queue.Enqueue('C');
        queue.PrintState(); // head=0, tail=3, count=3, capacity=4

        Console.WriteLine("Dequeue двічі (видаляємо A, B):");
        Console.WriteLine($"  видалено: {queue.Dequeue()}"); // A
        Console.WriteLine($"  видалено: {queue.Dequeue()}"); // B
        queue.PrintState(); // head=2, tail=3, count=1

        Console.WriteLine("Enqueue D, E, F (tail завернеться через кінець масиву):");
        queue.Enqueue('D'); // tail: 3 -> 0 (wrap-around!)
        queue.Enqueue('E'); // tail: 0 -> 1
        queue.Enqueue('F'); // tail: 1 -> 2 (буфер тепер повний: count == capacity == 4)
        queue.PrintState(); // head=2, tail=2, count=4  <- head == tail, але це ПОВНИЙ буфер, не порожній!

        Console.WriteLine("Спорожнюємо чергу повністю, у правильному FIFO-порядку:");
        while (!queue.IsEmpty)
        {
            Console.WriteLine($"  видалено: {queue.Dequeue()}");
        }
        // Вивід: C, D, E, F - саме в тому порядку, у якому елементи були додані
    }
}
```

Зверніть увагу на стан `head=2, tail=2, count=4` у виводі — це і є та сама ситуація "`head == tail`", яка сама по собі неоднозначна (могла б означати і порожній буфер), але поле `count` однозначно каже нам, що буфер **повний**, а не порожній.

### Приклад 3 — Call stack як фізична структура даних: рекурсія і StackOverflowException

Цей приклад демонструє, що call stack — не абстракція, а реальна, обмежена за розміром структура даних, зростання якої можна безпосередньо спостерігати.

```csharp
using System;

public static class CallStackDemo
{
    // Безпечна демонстрація: обмежена глибина, яка друкує кожен фрейм при вході й виході,
    // наочно показуючи LIFO-порядок call stack (розкрутка йде у зворотному порядку до заглиблення).
    public static void RecurseAndPrint(int depth, int maxDepth)
    {
        Console.WriteLine($"{new string('>', depth)} Вхід, глибина={depth} (Push фрейму)");

        if (depth >= maxDepth)
        {
            Console.WriteLine($"{new string('>', depth)} Базовий випадок досягнуто, розкручуємось назад");
            return;
        }

        RecurseAndPrint(depth + 1, maxDepth);

        Console.WriteLine($"{new string('<', depth)} Вихід, глибина={depth} (Pop фрейму)");
    }

    // НЕБЕЗПЕЧНО, лише для ілюстрації - НЕ запускати без обмеження глибини!
    // Демонструє, чому необмежена рекурсія без базового випадку
    // (або з базовим випадком, недосяжним для великих вхідних даних)
    // рано чи пізно вичерпає виділений розмір стека потоку (типово ~1 МБ)
    // і призведе до StackOverflowException, яку навіть неможливо перехопити
    // блоком try/catch - CLR аварійно завершує процес, бо стек - фізично скінченний ресурс.
    private static void UnboundedRecursion(long counter)
    {
        // Кожен виклик додає новий фрейм (return-адреса + параметр counter) на call stack.
        // Немає жодного базового випадку - фрейми накопичуються нескінченно,
        // поки не закінчиться пам'ять, виділена під стек потоку.
        UnboundedRecursion(counter + 1);
    }

    public static void Main()
    {
        Console.WriteLine("=== Безпечна демонстрація обмеженої рекурсії (глибина 4) ===");
        RecurseAndPrint(0, 4);

        Console.WriteLine();
        Console.WriteLine("=== Концептуальна демонстрація StackOverflowException ===");
        Console.WriteLine("Виклик UnboundedRecursion(0) без обмеження глибини призведе до того,");
        Console.WriteLine("що call stack накопичить мільйони фреймів (кожен ~кілька десятків байт)");
        Console.WriteLine("і вичерпає виділений розмір стека потоку (~1 МБ за замовчуванням у .NET).");
        Console.WriteLine("CLR аварійно завершить процес з StackOverflowException,");
        Console.WriteLine("яку НЕМОЖЛИВО перехопити try/catch - це не звичайний керований виняток,");
        Console.WriteLine("а сигнал про те, що фізичний ресурс (пам'ять стека) вичерпано.");
        // UnboundedRecursion(0); // <- свідомо закоментовано: реально завершило б процес аварійно
    }
}

// Вивід безпечної частини:
// === Безпечна демонстрація обмеженої рекурсії (глибина 4) ===
//  Вхід, глибина=0 (Push фрейму)
// > Вхід, глибина=1 (Push фрейму)
// >> Вхід, глибина=2 (Push фрейму)
// >>> Вхід, глибина=3 (Push фрейму)
// >>>> Вхід, глибина=4 (Push фрейму)
// >>>> Базовий випадок досягнуто, розкручуємось назад
// >>> Вихід, глибина=3 (Pop фрейму)
// >> Вихід, глибина=2 (Pop фрейму)
// > Вихід, глибина=1 (Pop фрейму)
//  Вихід, глибина=0 (Pop фрейму)
```

Зверніть увагу на симетрію виводу: порядок "Вихід" (розкрутка стека) — точне дзеркальне відображення порядку "Вхід" (заглиблення). Це і є LIFO у чистому вигляді: фрейм глибини 4 увійшов останнім — і вийшов першим.

### Приклад 4 — Queue<T> для обробки "хвиль" тікетів підтримки (симуляція BFS-подібної обробки)

Демонструє збереження строгого порядку FIFO при обробці задач "хвилями" — концептуально те саме, що відбувається під час обходу графа в ширину (BFS), де кожна "хвиля" — це вершини одного рівня віддаленості від старту.

```csharp
using System;
using System.Collections.Generic;

public record SupportTicket(int Id, string Customer, string Issue);

public static class TicketProcessor
{
    public static void Main()
    {
        var tickets = new Queue<SupportTicket>();

        // Тікети надходять у довільні моменти часу, у порядку виникнення проблем.
        tickets.Enqueue(new SupportTicket(1, "Іван",   "Не працює вхід в акаунт"));
        tickets.Enqueue(new SupportTicket(2, "Марія",  "Питання щодо оплати"));
        tickets.Enqueue(new SupportTicket(3, "Олег",   "Помилка 500 при завантаженні файлу"));
        tickets.Enqueue(new SupportTicket(4, "Ганна",  "Запит на повернення коштів"));

        Console.WriteLine($"У черзі {tickets.Count} тікетів. Починаємо обробку хвилями по 2 тікети.");

        int wave = 1;
        while (tickets.Count > 0)
        {
            Console.WriteLine($"\n--- Хвиля {wave} ---");

            // Обробляємо до 2 тікетів за хвилю - точно так само, як BFS обробляє
            // всі вершини поточного рівня, перш ніж перейти до наступного рівня.
            int processedInWave = 0;
            while (tickets.Count > 0 && processedInWave < 2)
            {
                SupportTicket ticket = tickets.Dequeue(); // строго FIFO: найстаріший тікет - перший
                Console.WriteLine($"  Обробка тікету #{ticket.Id} від {ticket.Customer}: \"{ticket.Issue}\"");
                processedInWave++;
            }

            wave++;
        }

        Console.WriteLine("\nУсі тікети оброблено в порядку надходження (FIFO збережено).");
    }
}

// Вивід:
// У черзі 4 тікетів. Починаємо обробку хвилями по 2 тікети.
//
// --- Хвиля 1 ---
//   Обробка тікету #1 від Іван: "Не працює вхід в акаунт"
//   Обробка тікету #2 від Марія: "Питання щодо оплати"
//
// --- Хвиля 2 ---
//   Обробка тікету #3 від Олег: "Помилка 500 при завантаженні файлу"
//   Обробка тікету #4 від Ганна: "Запит на повернення коштів"
//
// Усі тікети оброблено в порядку надходження (FIFO збережено).
```

## 7. Реальний сценарій: реалізація Undo/Redo для текстового редактора двома стеками

Це один із найпоширеніших практичних застосувань стека, і водночас — пряме продовження [патерну Memento](../../Поведінкові/memento-pattern-csharp.md) з папки `Поведінкові/` цього репозиторію: там детально пояснено, *як* коректно й інкапсульовано зберігати знімок стану об'єкта; тут ми зосередимося саме на *структурі даних*, яка організовує історію цих знімків.

### Ідея: два стеки

- **`_undoStack`** — стек знімків стану *до* кожної виконаної дії. `Undo` знімає верхній знімок звідси й застосовує його.
- **`_redoStack`** — стек знімків стану, які були "скасовані" через `Undo", але можуть бути повернені назад через `Redo`.

Правила:
1. При виконанні **нової дії** (наприклад, введення тексту): поточний стан проштовхується в `_undoStack`, а **`_redoStack` повністю очищається** (нова дія "перекреслює" стару історію redo — це важливо: не можна повернутись "вперед" до дії, яка більше не є майбутнім поточної гілки історії).
2. При **Undo**: знімаємо верхній стан з `_undoStack`, проштовхуємо *поточний* стан у `_redoStack`, після чого застосовуємо знятий стан як новий поточний.
3. При **Redo**: знімаємо верхній стан з `_redoStack`, проштовхуємо *поточний* стан у `_undoStack`, після чого застосовуємо знятий стан як новий поточний.

```csharp
using System;
using System.Collections.Generic;

public class TextEditor
{
    private readonly Stack<string> _undoStack = new();
    private readonly Stack<string> _redoStack = new();
    private string _content = string.Empty;

    public string Content => _content;

    public void Type(string text)
    {
        _undoStack.Push(_content);   // зберігаємо стан ДО зміни
        _redoStack.Clear();          // нова дія скасовує будь-яку "майбутню" історію redo
        _content += text;
    }

    public void Undo()
    {
        if (_undoStack.Count == 0)
        {
            Console.WriteLine("  (нічого скасовувати)");
            return;
        }

        _redoStack.Push(_content);        // поточний стан переходить у redo
        _content = _undoStack.Pop();      // повертаємось до попереднього стану
    }

    public void Redo()
    {
        if (_redoStack.Count == 0)
        {
            Console.WriteLine("  (нічого повертати)");
            return;
        }

        _undoStack.Push(_content);        // поточний стан повертається в undo
        _content = _redoStack.Pop();      // повторно застосовуємо скасовану дію
    }
}
```

### Покроковий розбір послідовності дій

```csharp
var editor = new TextEditor();

editor.Type("Привіт");        // 1
editor.Type(", світе");       // 2
editor.Undo();                 // 3
editor.Type("!");              // 4 (нова дія після Undo - redo стирається!)
editor.Undo();                 // 5
editor.Redo();                 // 6
```

| Крок | Дія | `Content` після дії | `_undoStack` (вершина зліва) | `_redoStack` (вершина зліва) |
|---|---|---|---|---|
| 0 | (початок) | `""` | `[]` | `[]` |
| 1 | `Type("Привіт")` | `"Привіт"` | `["" ]` | `[]` |
| 2 | `Type(", світе")` | `"Привіт, світе"` | `["Привіт", ""]` | `[]` |
| 3 | `Undo()` | `"Привіт"` | `[""]` | `["Привіт, світе"]` |
| 4 | `Type("!")` | `"Привіт!"` | `["Привіт", ""]` | `[]` ← **очищено!** |
| 5 | `Undo()` | `"Привіт"` | `[""]` | `["Привіт!"]` |
| 6 | `Redo()` | `"Привіт!"` | `["Привіт", ""]` | `[]` |

Ключовий момент на кроці 4: після `Undo()` на кроці 3 у `_redoStack` лежав знімок `"Привіт, світе"` — теоретично його можна було б "повернути" через `Redo()`. Але коли користувач замість цього виконує **нову** дію (`Type("!")`), цей потенційний redo втрачає сенс: неможливо одночасно мати дві різні "майбутні" гілки історії (одну — де ми повернули `", світе"`, іншу — де ми додали `"!"`). Тому `_redoStack` очищається при будь-якій новій дії — це стандартна, очікувана поведінка практично в кожному текстовому редакторі.

### Той самий механізм — навігація "назад/вперед" у браузері

Важливо усвідомити: **навігація "Назад"/"Вперед" у веб-браузері побудована на точно такому ж механізмі двох стеків.** Стек "Назад" містить історію відвіданих сторінок; перехід на нову сторінку додає поточну в стек "Назад" і **очищає** стек "Вперед" (тому кнопка "Вперед" стає неактивною одразу після переходу за новим посиланням); натискання "Назад" знімає сторінку зі стека "Назад" і кладе поточну в стек "Вперед"; натискання "Вперед" робить дзеркальну операцію. Це не просто схожий приклад — це буквально та сама структура даних і той самий алгоритм, застосований до іншого домену.

## 8. Поширені помилки

### Помилка 1: Реалізація черги на `List<T>` з `RemoveAt(0)` для Dequeue

```csharp
// ПОГАНО: приховане O(n) на кожен виклик Dequeue замість очікуваного O(1).
// Це та сама помилка, розібрана в кінці 1-arrays-and-linked-lists.md -
// вона майже завжди непомітна на тестових даних (де черга рідко перевищує
// кілька десятків елементів) і катастрофічна в production під навантаженням,
// де черга регулярно містить тисячі елементів.
public class NaiveQueue<T>
{
    private readonly List<T> _items = new();

    public void Enqueue(T item) => _items.Add(item); // це О(1) (амортизовано) - тут проблеми немає

    public T Dequeue()
    {
        T item = _items[0];
        _items.RemoveAt(0); // О(n): усі елементи зсуваються на одну позицію вліво!
        return item;
    }
}
```

```csharp
// ДОБРЕ: використовуйте вбудований Queue<T> (кільцевий буфер під капотом, O(1) Dequeue)
public class ProperQueue<T>
{
    private readonly Queue<T> _items = new();

    public void Enqueue(T item) => _items.Enqueue(item); // О(1)
    public T Dequeue() => _items.Dequeue();               // О(1) - без жодного зсування
}

// Або, якщо потрібна власна реалізація з конкретних причин (наприклад,
// фіксована ємність без динамічного розширення) - кільцевий буфер з розділу 3.
```

**Як розпізнати цю помилку при код-рев'ю:** будь-який виклик `RemoveAt(0)`, `Remove` за значенням із початку списку, чи `list.GetRange(1, list.Count - 1)` у гарячому шляху виконання — сигнал перевірити реальну складність операції.

### Помилка 2: Відсутність перевірки на порожню структуру перед Pop()/Dequeue()

```csharp
// ПОГАНО: у "щасливому шляху" тестування черга/стек ніколи не бувають порожні
// в момент виклику Pop()/Dequeue() - і помилка непомітна місяцями,
// доки в production не станеться гонка станів (race condition) чи неочікуваний
// edge case (наприклад, два потоки одночасно спорожнили чергу),
// і виклик впаде з необробленим InvalidOperationException.
public class TaskProcessor
{
    private readonly Queue<string> _tasks = new();

    public string GetNextTask()
    {
        return _tasks.Dequeue(); // впаде з InvalidOperationException, якщо черга порожня!
    }
}
```

```csharp
// ДОБРЕ: завжди явно перевіряти й обробляти порожній стан,
// навіть якщо "в тестах такого не траплялося".
public class TaskProcessor
{
    private readonly Queue<string> _tasks = new();

    public bool TryGetNextTask(out string? task)
    {
        return _tasks.TryDequeue(out task); // TryDequeue доступний у сучасних версіях .NET
        // або вручну:
        // if (_tasks.Count == 0) { task = null; return false; }
        // task = _tasks.Dequeue();
        // return true;
    }
}
```

Ця помилка особливо підступна тому, що "порожня черга" — не рідкісний крайовий випадок у теорії, а абсолютно нормальний, очікуваний стан у production (наприклад, черга завдань, яка тимчасово вичерпалась, поки очікує на нові завдання) — і код, написаний без цієї перевірки, "працює" рівно доти, доки хтось не спробує забрати завдання з порожньої черги в невдалий момент.

### Помилка 3: Необмежена рекурсія без урахування скінченного розміру call stack

```csharp
// ПОГАНО: рекурсивний обхід, який працює на тестових даних (глибина ~100),
// але вхідні дані в production можуть мати глибину в десятки чи сотні тисяч
// (наприклад, дуже довгий однозв'язний список, глибоко вкладена структура JSON
// від зовнішнього API, чи "витягнуте в лінію" дерево - фактично список).
// Кожен рекурсивний виклик - це новий фрейм на call stack, і рано чи пізно
// (для достатньо великого входу) станеться StackOverflowException,
// яку неможливо перехопити try/catch - процес аварійно завершиться.
public int CountNodes(Node? node)
{
    if (node is null) return 0;
    return 1 + CountNodes(node.Next); // необмежена глибина рекурсії = розмір списку
}
```

```csharp
// ДОБРЕ: перетворення на ітеративний підхід за допомогою явного стека
// (або, як у цьому конкретному прикладі з лінійним обходом, простого циклу) -
// пам'ять для явного стека виділяється в купі (heap), а не в обмеженому
// стеку потоку, тож глибина "рекурсії" обмежена лише доступною оперативною
// пам'яттю, а не жорстким лімітом розміру стека потоку (~1 МБ).
public int CountNodes(Node? head)
{
    int count = 0;
    Node? current = head;
    while (current is not null)
    {
        count++;
        current = current.Next;
    }
    return count;
}

// Для складніших рекурсивних алгоритмів (наприклад, обхід дерева чи графа),
// де просту заміну на цикл зробити неможливо, стандартний прийом -
// замінити НЕЯВНИЙ стек викликів (call stack) на ЯВНИЙ Stack<T>,
// зберігаючи в ньому те, що інакше зберігалося б у параметрах
// і локальних змінних рекурсивних викликів:
public int CountNodesExplicitStack(Node? head)
{
    var stack = new Stack<Node>();
    if (head is not null) stack.Push(head);

    int count = 0;
    while (stack.Count > 0)
    {
        Node current = stack.Pop();
        count++;
        if (current.Next is not null) stack.Push(current.Next);
    }
    return count;
}
```

Це не гіпотетичний ризик "про всяк випадок" — це реальна причина production-інцидентів: рекурсивний парсер, який чудово працював на тестових JSON-документах, падає з `StackOverflowException` на документі від стороннього постачальника з незвично глибокою вкладеністю; рекурсивний обхід дерева категорій каталогу товарів падає, коли хтось випадково (чи зловмисно) створює ланцюжок категорій довжиною в тисячі рівнів. Стандартний, надійний фікс — саме заміна неявного call stack на явний `Stack<T>`, розміщений у купі, а не обмеженому стеку потоку.

## 9. Питання для співбесіди за рівнями

### Junior рівень

**1. Чим стек відрізняється від черги?**
Стек працює за принципом LIFO (Last In, First Out) — останній доданий елемент вилучається першим, як стос тарілок. Черга працює за принципом FIFO (First In, First Out) — перший доданий елемент вилучається першим, як черга в магазині. Це протилежні дисципліни доступу до елементів.

**2. Що таке LIFO і FIFO?**
LIFO (Last In, First Out) — "останній прийшов, перший вийшов" — властивість стека. FIFO (First In, First Out) — "перший прийшов, перший вийшов" — властивість черги. Обидва — акроніми, що описують порядок, у якому елементи вилучаються відносно порядку, в якому вони були додані.

**3. Наведи приклад використання стека з реального життя.**
Стос тарілок (можна брати/класти лише зверху); історія скасування дій (Ctrl+Z) у редакторі; кнопка "Назад" у браузері; call stack під час виконання програми — кожен виклик функції додає фрейм на стек, а завершення функції знімає його.

**4. Наведи приклад використання черги з реального життя.**
Черга людей на касі в магазині; черга завдань на друк у принтера (спулер друку); черга повідомлень у системі обробки замовлень — перше замовлення надійшло, перше й обробляється.

**5. Яка складність Push/Pop/Enqueue/Dequeue?**
За правильної реалізації всі чотири операції — O(1): і `Push`/`Pop` стека, і `Enqueue`/`Dequeue` черги (за умови, що черга реалізована через кільцевий буфер чи зв'язний список зі збереженим вказівником на хвіст, а не наївно через `List<T>.RemoveAt(0)`).

**6. Чи можна подивитись елемент у середині стека чи черги без його вилучення?**
Формально ADT "стек" і "черга" **не надають** такої операції — доступ дозволений лише до одного (стек) чи обох (deque) кінців. Якщо потрібен довільний доступ до середини — це ознака того, що варто використовувати інший ADT (наприклад, масив, список чи deque, залежно від задачі), а не намагатись "обійти" обмеження стека/черги.

**7. Що станеться, якщо викликати Pop() на порожньому стеці чи Dequeue() на порожній черзі?**
Стандартна поведінка бібліотечних реалізацій (`Stack<T>.Pop()`, `Queue<T>.Dequeue()` у .NET) — викинути `InvalidOperationException`. Тому перед вилученням завжди варто перевіряти `Count > 0` або використовувати безпечні альтернативи на кшталт `TryPop()`/`TryDequeue()`.

### Middle рівень

**1. Як реалізувати чергу на масиві ефективно (кільцевий буфер)?**
Замість зсування елементів при вилученні (O(n)) чи "залишання мертвої зони" на початку масиву, використовується масив фіксованого розміру з двома індексами — `head` (початок черги) і `tail` (куди додати наступний елемент), які просуваються за модулем розміру масиву (`(index + 1) % capacity`). Коли `tail` доходить до кінця масиву, наступне значення індексу "заворачивается" назад до 0, дозволяючи повторно використовувати звільнені (вилучені через `head`) слоти масиву. Це дає O(1) для `Enqueue` і `Dequeue` без зсування й без витрати пам'яті на невикористовувані слоти. Ключова складність — проблема "full/empty ambiguity" (`head == tail` може означати і порожній, і повний буфер), яка вирішується окремим полем `count` або навмисним "жертвуванням" одного слота.

**2. Що таке deque і коли він потрібен?**
Deque (double-ended queue) — структура даних, що дозволяє O(1) додавання й вилучення з **обох** кінців одночасно (на відміну від стека — лише один кінець, чи черги — додавання в один кінець, вилучення з іншого). Потрібен, коли: (а) алгоритму потрібна гнучкість використовувати одну структуру і як стек, і як чергу; (б) реалізується технікА ковзного вікна, зокрема "монотонний деск" для задач на кшталт sliding window maximum, де елементи можуть вилучатися як зі старого (лівого), так і, під час підтримки монотонності, з нового (правого) кінця вікна.

**3. Поясни зв'язок між рекурсією і стеком викликів.**
Кожен рекурсивний виклик функції створює новий фрейм на call stack (стек викликів), що містить параметри, локальні змінні та адресу повернення. Фрейми накопичуються в LIFO-порядку в міру заглиблення рекурсії й знімаються (розкручуються) у зворотному порядку в міру завершення викликів. Оскільки розмір стека потоку фіксований і обмежений (типово ~1 МБ), надто глибока (чи нескінченна) рекурсія вичерпує цю пам'ять і призводить до `StackOverflowException` — необробного винятку, що аварійно завершує процес.

**4. Як реалізувати Undo/Redo двома стеками?**
Тримати два стеки: `_undoStack` (знімки станів "до" кожної дії) і `_redoStack` (скасовані знімки, доступні для повернення). Виконання нової дії проштовхує поточний стан у `_undoStack` і **очищає** `_redoStack` (нова дія робить попередню "майбутню" історію redo недійсною). `Undo` знімає стан з `_undoStack`, кладе поточний стан у `_redoStack`, застосовує знятий стан. `Redo` робить дзеркальну операцію. Це той самий механізм, що лежить в основі навігації "Назад"/"Вперед" у браузерах.

**5. Чому Stack<T> і Queue<T> у .NET не реалізовані через LinkedList<T> "для простоти"?**
Тому що масив (навіть із додатковою логікою кільцевого буфера для черги) дає кращу продуктивність на практиці завдяки локальності даних у кеші процесора (cache locality) — елементи масиву лежать у пам'яті послідовно, тоді як вузли зв'язного списку розкидані по купі й вимагають розіменування вказівника при кожному переході, що суттєво повільніше на реальному залізі, попри однакову асимптотичну складність O(1). Динамічний масив також не має накладних витрат пам'яті на зберігання вказівників `Next`/`Prev` для кожного елемента.

**6. Яка різниця між Peek() і Pop() (або Dequeue())?**
`Peek()` лише повертає значення елемента на "активному" кінці структури (вершина стека чи початок черги), не змінюючи структуру. `Pop()`/`Dequeue()` повертає те саме значення, **але й вилучає** цей елемент зі структури, зменшуючи її розмір на один. Плутанина між ними — джерело помилок, коли код очікує, що елемент вилучено, а насправді лише переглянуто (чи навпаки).

### Senior рівень

**1. Спроєктуй ефективну структуру даних для sliding-window задачі, що вимагає швидкого доступу до максимуму у вікні.**
Наївний підхід — для кожного положення вікна розміру `k` перебирати всі `k` елементів і шукати максимум — дає O(n·k). Ефективне рішення — **монотонний деск (monotonic deque)**: deque зберігає **індекси** елементів (не самі значення) у порядку, що гарантує спадання відповідних значень від переднього до заднього кінця. При русі вікна вперед: (1) з переднього кінця видаляються індекси, що вийшли за межі поточного вікна; (2) з заднього кінця видаляються всі індекси, чиї значення **менші або рівні** новому елементу (вони вже ніколи не можуть стати максимумом, поки новий, більший елемент присутній у вікні) — і новий індекс додається в кінець. Максимум поточного вікна завжди перебуває на передньому кінці deque. Кожен елемент масиву додається в deque рівно один раз і видаляється з нього щонайбільше один раз за весь прохід, тому загальна складність — амортизовано O(n) для всього масиву, а не для одного вікна.

**2. Поясни повну проблему full/empty ambiguity в кільцевому буфері та як її вирішити.**
Коли кільцевий буфер реалізований лише через два індекси `head`/`tail` без додаткової інформації, стан `head == tail` виникає у двох принципово різних, але нерозрізнюваних без додаткової інформації ситуаціях: (1) буфер щойно ініціалізовано або повністю спорожнено (жодного елемента); (2) буфер заповнений повністю (`tail` "обійшов" весь масив по колу й "наздогнав" `head` рівно після додавання останнього можливого елемента). Обидва випадки дають однакове порівняння індексів, тому саме порівняння `head == tail` недостатнє, щоб визначити стан буфера. Два стандартні розв'язки: (а) **окреме поле `count`**, яке явно інкрементується/декрементується при кожній операції — найпростіший, найпоширеніший підхід, що додає одне ціле поле, але усуває будь-яку неоднозначність; (б) **виділення масиву на один елемент більше за логічну ємність** і визначення "повний" як `(tail + 1) % (capacity + 1) == head`, залишаючи один слот масиву постійно невикористаним як "буфер безпеки" — трохи менше пам'яті на службові поля, але постійно втрачений один слот масиву й менш очевидна для читання логіка. У продакшн-коді (наприклад, кільцеві буфери в мережевих стеках, аудіо/відео буферизації) частіше зустрічається варіант (а) через простоту й читабельність, хоча варіант (б) економніший, коли розмір елемента набагато більший за розмір цілочисельного поля лічильника (рідкісний практичний випадок).

**3. Наведи реальний випадок, коли рекурсивний алгоритм довелося перетворити на ітеративний через явний стек, щоб уникнути StackOverflowException.**
Типовий сценарій: рекурсивний обхід дерева (наприклад, дерева категорій, файлової системи, чи AST при парсингу) чудово проходив усі тести з розумною глибиною вкладеності (до кількох сотень рівнів), але у production зустрівся вхід зі значно більшою глибиною — наприклад, JSON- чи XML-документ від зовнішньої системи з тисячами рівнів вкладеності, або "виродженою" структурою дерева, фактично перетвореною в довгий лінійний ланцюжок (worst case для дерева — фактично список). Рекурсивний обхід падав з `StackOverflowException`, яку неможливо перехопити (`try/catch` тут безсилий — CLR завершує процес аварійно, оскільки вичерпання стека потоку — не звичайний керований виняток). Фікс: заміна рекурсії на цикл із явним `Stack<T>` (чи `Stack<(Node, int state)>` для складніших обходів, де потрібно пам'ятати "де ми зупинились" при поверненні до вузла), де стек виділяється в купі (heap) і обмежений лише доступною оперативною пам'яттю, а не жорстким і набагато меншим лімітом розміру стека потоку. Додатковий бонус такого переходу — можливість збільшити розмір стека вручну (наприклад, запустивши обхід в окремому потоці з явно заданим більшим розміром стека через конструктор `Thread`), але це паліативне рішення, що просто відсуває межу, а не усуває першопричину — структурна заміна на явний стек є єдиним справді надійним рішенням для необмежених за глибиною вхідних даних.

**4. Порівняй продуктивність черги на LinkedList проти кільцевого буфера на масиві.**
Обидві реалізації дають асимптотично однакову складність O(1) для `Enqueue`/`Dequeue`, але на практиці кільцевий буфер на масиві зазвичай суттєво швидший через кілька факторів: **локальність даних (cache locality)** — елементи масиву розташовані в пам'яті послідовно, тому процесор ефективно передзавантажує (prefetch) сусідні елементи в кеш, тоді як вузли зв'язного списку розкидані по купі в довільних адресах, і кожен перехід `Next`/`Prev` — це, ймовірно, промах кеша (cache miss); **накладні витрати пам'яті** — кожен вузол зв'язного списку містить додаткові вказівники (`Next`, іноді `Prev`) і заголовок об'єкта (для reference-типів у керованих середовищах, як .NET), тоді як масив зберігає лише самі дані елементів; **тиск на збирач сміття (GC)** — кожен `Enqueue` у зв'язному списку виділяє новий об'єкт-вузол у купі, збільшуючи кількість алокацій і, відповідно, роботу GC, тоді як кільцевий буфер перевикористовує вже виділений масив без нових алокацій на кожну операцію (за винятком рідкісного розширення ємності). Зв'язний список має перевагу лише тоді, коли розмір черги вкрай непередбачуваний і схильний до різких, частих коливань між дуже малим і дуже великим розміром, а memory footprint при простої (idle) критично важливий — кільцевий буфер фіксованого чи "з розширенням, без стиснення" розміру може тримати виділеною пам'ять під пікове навантаження навіть коли черга майже порожня, поки хтось явно не викличе стиснення ємності.

**5. Чи можна реалізувати стек на основі двох черг, або чергу на основі двох стеків? Навіщо це взагалі потрібне питання на співбесіді?**
Так, обидва перетворення можливі й є класичною вправою для перевірки глибокого розуміння того, чим структури відрізняються не на рівні API, а на рівні фундаментальної семантики доступу. Черга на основі двох стеків: `_inStack` приймає всі нові елементи (`Push`); коли потрібно `Dequeue`, якщо `_outStack` порожній — перекласти **всі** елементи з `_inStack` в `_outStack` (це інвертує їхній порядок на протилежний, з LIFO на LIFO, що в сумі дає ефект FIFO), після чого `Pop()` з `_outStack` дає елемент у правильному FIFO-порядку; складність — O(1) амортизовано (кожен елемент перекладається з одного стека в інший рівно один раз за весь час свого життя в структурі, а не при кожному виклику). Це питання цінне на співбесіді не тому, що таку реалізацію справді варто використовувати в production (там завжди краще взяти готовий, оптимізований `Queue<T>` чи `Stack<T>`), а тому, що воно перевіряє, чи кандидат розуміє LIFO/FIFO на рівні механіки перестановки елементів, а не просто запам'ятав назви методів API.

## 10. Підсумок

### Базові операції — шпаргалка

| Структура | Головна операція додавання | Головна операція вилучення | Порядок | Peek |
|---|---|---|---|---|
| **Stack** | `Push` (на вершину) | `Pop` (з вершини) | LIFO | `Peek` (вершина) |
| **Queue** | `Enqueue` (в кінець) | `Dequeue` (з початку) | FIFO | `Peek` (початок) |
| **Deque** | `PushFront`/`PushBack` | `PopFront`/`PopBack` | довільний (обидва кінці) | `PeekFirst`/`PeekLast` |

Усі операції вище — **O(1)** за умови правильної реалізації (кільцевий буфер чи зв'язний список зі збереженими вказівниками на потрібні кінці). O(n) з'являється **тільки** як наслідок неправильної реалізації (наприклад, `List<T>.RemoveAt(0)` для `Dequeue`).

### Кільцевий буфер — швидка довідка

- Проблема наївного масиву: зсування при вилученні (O(n)) АБО невикористовувана "мертва зона" на початку масиву.
- Рішення: `index = (index + 1) % capacity` для просування `head` і `tail` по колу.
- Пастка: `head == tail` неоднозначно (порожній чи повний?) → вирішується окремим полем `count` (найпоширеніше) або "жертвуванням" одного слота масиву.

### Типові реальні застосування — швидка довідка

| Структура | Типове застосування |
|---|---|
| **Stack** | Call stack і рекурсія; Undo/Redo (Memento/Command); навігація "Назад" в браузері; перевірка збалансованості дужок; перетворення інфікс→постфікс |
| **Queue** | Планування фонових задач (job queue); BFS-обхід графа; спулери друку; брокери повідомлень (RabbitMQ, Kafka) та Saga-оркестрація |
| **Deque** | Гнучка структура "і стек, і черга" в одному; ковзне вікно (sliding window); монотонний деск для sliding window maximum |
| **Priority Queue** | (окремий файл `5-heaps-and-priority-queues.md`) — задачі з пріоритетом замість порядку надходження: алгоритм Дейкстри, планувальники з пріоритетами, топ-K задачі |

Головний висновок цього файлу — той самий, що й у попередньому: **асимптотична складність структури даних визначається не назвою API, а фактичною реалізацією**. `Queue<T>` в .NET дає справжній O(1) `Dequeue`, тому що всередині це кільцевий буфер, а не тому, що метод називається "Dequeue". Розуміння цього — межа між джуном, який просто викликає методи бібліотеки, і мідлом/сіньйором, який розуміє, чому саме ці методи швидкі, і вміє помітити момент, коли "зручна" реалізація (на кшталт `List<T>.RemoveAt(0)`) непомітно ламає ці гарантії.
