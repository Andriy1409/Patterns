## Навіщо розуміти внутрішній устрій, якщо є SQL?

SQL — це декларативна мова. Ти пишеш `SELECT * FROM Orders WHERE CustomerId = 42`, і база даних сама вирішує, *як* дістати ці дані: який індекс використати, скільки сторінок диску прочитати, чи закешовано ці дані в пам'яті, чи потрібно чекати на блокування іншої транзакції. Це і є сила абстракції — розробнику не потрібно вручну керувати файлами на диску, вказівниками чи блокуваннями пам'яті.

Але саме тут виникає межа між "middle, який пише робочий SQL" і "senior, який розуміє, чому цей SQL повільний". Абстракція SQL чудово працює, поки все йде добре. Коли щось починає гальмувати, "зависає" під навантаженням, втрачає дані після збою сервера, або поводиться незрозуміло під час паралельних транзакцій — розуміння того, що відбувається *під* абстракцією, стає єдиним способом поставити правильний діагноз.

### Аналогія: водій і автомеханік-тюнер 🚗

Звичайний водій керує автомобілем, не знаючи, як влаштований двигун внутрішнього згоряння: натиснув газ — машина їде, натиснув гальмо — зупиняється. Цього достатньо для 95% ситуацій на дорозі.

Але є ситуації, коли поверхневого знання недостатньо:
- Механік, що готує гоночний автомобіль, повинен розуміти, чому саме зростає температура двигуна на високих обертах, і як зміна складу палива вплине на детонацію.
- Водій, у якого раптом заглух двигун на трасі, не зможе полагодити машину, знаючи лише "натиснути газ".

Так само із СУБД:
- Middle-розробник пише коректні SQL-запити, знає індекси на рівні "додай індекс — стане швидше".
- Senior-інженер розуміє, **чому** індекс прискорює запит (менше сторінок читається з диску), **чому** COMMIT іноді займає мілісекунди, а іноді секунди (fsync у WAL), і **чому** та сама схема бази раптом починає "гальмувати" рівно тоді, коли таблиця перевищує обсяг оперативної пам'яті сервера.

### Важливе застереження

Мета цього документа — **концептуальне й архітектурне** розуміння того, що відбувається всередині реляційної СУБД (PostgreSQL, MySQL/InnoDB, SQL Server, Oracle). Це **не** посібник "напиши власний движок бази даних із нуля". Реальні промислові рушії — це мільйони рядків коду, роками відточені інженерами з вузькою спеціалізацією саме на storage engines. Наша ціль інша: щоб коли senior-інженер бачить повільний запит, дивний план виконання чи інцидент після збою сервера, у нього в голові був **правильний ментальний контейнер**, у який покласти причину — сторінка, буферний пул, WAL, checkpoint, MVCC-версія рядка — а не чорна магія.

## Сторінки (Pages) — базова одиниця зберігання

Реляційна СУБД не зберігає дані "рядок за рядком" на диску як текстовий файл. Замість цього дані фізично розкладені по файлах у вигляді **сторінок (pages)** — блоків фіксованого розміру, які є **базовою одиницею вводу-виводу (I/O)** для всієї системи.

Типові розміри сторінки в популярних СУБД:

| СУБД | Розмір сторінки за замовчуванням |
|---|---|
| PostgreSQL | 8 KB |
| SQL Server | 8 KB |
| MySQL / InnoDB | 16 KB |
| Oracle | 8 KB (типово, налаштовується) |
| SQLite | 4 KB (налаштовується) |

### Ключовий принцип: I/O завжди відбувається цілими сторінками

Це найважливіша ідея цього розділу: **навіть якщо тобі потрібен один-єдиний рядок, СУБД зчитує з диску всю сторінку, на якій цей рядок фізично зберігається.** Не можна прочитати "половину сторінки" чи "лише потрібні байти" — диск (і файлова система) оперують блоками, і СУБД спроєктована відповідно до цього обмеження.

Наслідок для практики: якщо в таблиці рядки товсті (багато колонок, великі `TEXT`/`VARCHAR` поля), то на одну сторінку 8 KB влазить менше рядків — а отже, той самий запит, що сканує N рядків, змушений прочитати більше сторінок з диску. Саме тому **кількість рядків на сторінку — це реальний фактор продуктивності**, а не абстрактна деталь реалізації:

- Таблиця з вузькими рядками (наприклад, `int id, int status, datetime created_at`) — на сторінці 8 KB може вміститись сотні рядків → повне сканування таблиці на мільйон рядків читає порівняно небагато сторінок.
- Таблиця з широкими рядками (велике поле `description TEXT`, JSON-блоб на кілька KB) — на сторінці вміщується лише кілька десятків рядків → те саме сканування вимагає читання значно більшої кількості сторінок.

Це один з аргументів на користь **нормалізації** та виносу рідко використовуваних "товстих" колонок в окрему таблицю: основна таблиця лишається вузькою й компактною, і типові запити (які не потребують товстого поля) читають менше сторінок.

### Структура сторінки (спрощена схема)

Хоча деталі різняться між СУБД, загальна структура сторінки в переважній більшості реляційних рушіїв дуже схожа:

```
┌──────────────────────────────────────────────────────────┐
│                    ЗАГОЛОВОК СТОРІНКИ (Page Header)      │
│  - номер сторінки (page id)                              │
│  - контрольна сума (checksum)                            │
│  - LSN (Log Sequence Number) — посилання на WAL          │
│  - кількість рядків, вказівник на вільне місце           │
├──────────────────────────────────────────────────────────┤
│                                                          │
│   Row 1  [id=101, name="Alice", status="active", ...]    │
│   ─────────────────────────────────────────────────────  │
│   Row 2  [id=102, name="Bob",   status="active", ...]    │
│   ─────────────────────────────────────────────────────  │
│   Row 3  [id=103, name="Carol", status="pending", ...]   │
│                                                          │
│                     (дані рядків ростуть згори вниз)     │
│                                                          │
│                    ░░░░░░░░░░░░░░░░░░░░░░░░░             │
│                    ░░  ВІЛЬНЕ МІСЦЕ (Free)  ░░           │
│                    ░░░░░░░░░░░░░░░░░░░░░░░░░             │
│                                                          │
│                  (масив слотів росте знизу вгору)        │
├──────────────────────────────────────────────────────────┤
│  Slot Array / Row Offsets (масив зсувів рядків)          │
│  [ offset→Row1 | offset→Row2 | offset→Row3 | ... ]       │
└──────────────────────────────────────────────────────────┘
                     Розмір сторінки: 8 KB (наприклад)
```

Пояснення ключових елементів:

- **Заголовок сторінки (Page Header)** — метадані: номер сторінки, контрольна сума для виявлення пошкоджень, посилання на останній пов'язаний запис WAL (LSN — про це нижче), кількість зайнятих слотів.
- **Дані рядків** — фактичний вміст рядків, зазвичай ростуть від початку сторінки вниз (після заголовка).
- **Вільне місце (Free Space)** — незайнята область посередині; коли вона вичерпується, новий рядок вже не влазить на цю сторінку, і СУБД виділяє нову сторінку (або, при `UPDATE`, може статись "row migration"/"forwarding" — перенесення рядка на іншу сторінку, якщо оновлений рядок побільшав).
- **Масив слотів / зсувів рядків (Slot Array)** — росте від кінця сторінки догори назустріч даним. Це рівень непрямої адресації: зовнішні структури (наприклад, індекс) не посилаються напряму на "байт 4032 у сторінці", а на "слот №2 у сторінці №774". Це дозволяє СУБД **переміщувати й ущільнювати рядки всередині сторінки** (наприклад, при видаленні рядка) без потреби оновлювати всі зовнішні посилання — досить оновити лише запис у масиві слотів.

> 💾 Саме завдяки непрямій адресації через слоти операція `VACUUM`/`DEFRAGMENT` всередині сторінки (стиснення вільного місця після видалень) не ламає індекси, які вказують на цю сторінку.

### Що з великими рядками, що не влазять в одну сторінку?

Якщо рядок (наприклад, з великим `TEXT`/`BLOB`-полем) не вміщується цілком в одну сторінку, СУБД використовує механізм **overflow-сторінок** (в PostgreSQL це називається **TOAST** — *The Oversized-Attribute Storage Technique*, в InnoDB — **off-page storage** для великих BLOB/TEXT). Основна сторінка зберігає лише невеликий "заголовок" рядка з посиланням на ланцюжок додаткових сторінок, де фізично лежить великий вміст. Це ще один аргумент, чому "товсті" колонки з великим вмістом варто виносити в окремі таблиці свідомо, а не покладатись на автоматичний overflow — доступ до overflow-сторінок додає додаткові I/O-операції.

## Буферний пул (Buffer Pool / Page Cache)

Диск (навіть найшвидший NVMe SSD) на кілька порядків повільніший за оперативну пам'ять. Приблизні орієнтири (не потрібно запам'ятовувати точні цифри, важливий сам порядок величин):

| Операція | Приблизна затримка |
|---|---|
| Доступ до RAM | ~100 наносекунд |
| Доступ до NVMe SSD | ~10–100 мікросекунд (у 100–1000 разів повільніше за RAM) |
| Випадковий доступ до звичайного HDD | ~5–10 мілісекунд (у 50 000–100 000 разів повільніше за RAM) |

З огляду на цю різницю, кожна серйозна СУБД тримає у пам'яті кеш нещодавно використаних сторінок — **буферний пул** (в PostgreSQL — `shared_buffers`, в InnoDB — `innodb_buffer_pool_size`, в SQL Server — Buffer Pool / Buffer Cache). Коли запит потребує сторінку даних:

1. СУБД спочатку перевіряє, чи ця сторінка вже є в буферному пулі (**cache hit**) — якщо так, дані повертаються з пам'яті практично миттєво.
2. Якщо сторінки немає (**cache miss**), СУБД читає її з диску, кладе копію в буферний пул, і лише потім повертає дані запиту.

```
┌───────────────────────────────────────────────────────────┐
│                     ЗАПИТ (SELECT ...)                     │
└───────────────────────────┬─────────────────────────────────┘
                             ▼
                 ┌───────────────────────┐
                 │  Сторінка є в буфер-  │   так    ┌─────────────┐
                 │  ному пулі (RAM)?     ├─────────▶│  Cache HIT  │
                 └───────────┬───────────┘          │  (швидко)   │
                             │ ні                   └─────────────┘
                             ▼
                 ┌───────────────────────┐
                 │  Читання сторінки     │
                 │  з диска (повільно)   │
                 └───────────┬───────────┘
                             ▼
                 ┌───────────────────────┐
                 │  Покласти копію в     │
                 │  буферний пул         │
                 └───────────┬───────────┘
                             ▼
                       Cache MISS (повільно)
```

### Dirty pages (брудні сторінки)

Коли транзакція виконує `UPDATE`/`INSERT`/`DELETE`, зміна спочатку застосовується до копії сторінки **в буферному пулі** (в пам'яті), а не одразу записується на диск. Така змінена, але ще не записана на диск сторінка називається **dirty page (брудна сторінка)**.

Брудні сторінки зберігаються в пам'яті й записуються ("скидаються", *flush*) на диск пізніше — фоновим процесом (в PostgreSQL — `background writer` / `checkpointer`, в InnoDB — page cleaner threads), а не синхронно на кожен `UPDATE`. Це дає величезний виграш у продуктивності: якщо один і той самий рядок змінюється кілька разів поспіль, диск отримує лише фінальний результат один раз, а не кожну проміжну зміну окремо.

> ⚠️ Важливо не плутати: те, що зміна ще не записана на диск у вигляді сторінки даних, **не означає**, що транзакція не є durable (стійкою) після коміту. Гарантію Durability забезпечує окремий механізм — WAL (розділ нижче). Сторінки даних можуть "відставати" від реального стану на диску якийсь час, і це нормально та безпечно.

### Витіснення сторінок (Eviction) — LRU-подібна стратегія

Буферний пул має фіксований розмір (обмежений оперативною пам'яттю, виділеною СУБД). Коли пул заповнений і потрібно завантажити нову сторінку, СУБД повинна вирішити, яку зі старих сторінок витіснити (evict).

Класичний підхід — **LRU (Least Recently Used)** або його модифікації: витісняється сторінка, до якої найдовше не звертались. Реальні СУБД використовують ускладнені варіанти LRU, щоб уникнути характерних проблем:

- **PostgreSQL** використовує алгоритм **Clock Sweep** (варіація "second-chance" LRU): кожна сторінка має лічильник "звернень" (`usage_count`); "стрілка годинника" обходить буфери по колу, зменшуючи лічильник, і витісняє першу сторінку з лічильником 0.
- **MySQL/InnoDB** використовує модифікований LRU зі списком **"young"** та **"old"** сегментів, щоб одноразове масове сканування таблиці (наприклад, `SELECT * FROM big_table` для звіту) не "вимило" з кешу дані, які активно й регулярно використовуються звичайним трафіком застосунку.

Якщо витісняється **брудна** сторінка, її спершу обов'язково потрібно записати на диск (flush) — інакше зміна буде втрачена назавжди.

### Чому "робочий набір влазить у RAM" — один з найпотужніших важелів продуктивності

Це, мабуть, найважливіший практичний висновок цього розділу:

> Якщо весь **робочий набір даних** (working set) — тобто сторінки, до яких реально звертаються активні запити — вміщується в буферний пул, майже всі читання обслуговуються з пам'яті (cache hit), і база даних працює на порядки швидше, ніж коли доводиться постійно ходити на диск.

Класична **war story**, яку розповідає майже кожен senior-інженер, що працював з базами даних під навантаженням:

> Таблиця `Orders` росла собі рік, все працювало швидко — індекси на місці, запити оптимізовані. А потім, приблизно тоді, коли таблиця (разом із її індексами) перевищила обсяг оперативної пам'яті, виділеної під буферний пул, продуктивність **різко**, не поступово, а стрибком, впала. Той самий запит, той самий план виконання — але тепер значна частина сторінок, потрібних запиту, вже не поміщається в кеш одночасно, і кожен новий запит змушує вимивати з пам'яті сторінки, потрібні наступному запиту. СУБД потрапляє в режим постійного "перетирання" кешу (thrashing), і диск-I/O стає домінуючим фактором часу виконання запиту.

Детальний розбір цього сценарію — у розділі 8 нижче.

## Write-Ahead Log (WAL) — як гарантується Durability

Це один із класичних тем "junior вміє написати транзакцію, senior розуміє, чому COMMIT безпечний навіть якщо сервер вимкнути електрику через мілісекунду після нього".

### Проблема, яку вирішує WAL

Пригадаймо: зміни від `UPDATE`/`INSERT`/`DELETE` спочатку застосовуються лише до копії сторінки **в буферному пулі** (в пам'яті), а фізичний запис на диск відкладається на потім заради продуктивності. Але тоді виникає критичне питання: **якщо сервер аварійно вимкнеться (збій живлення, падіння процесу) одразу після COMMIT, а змінена сторінка ще не встигла записатись на диск — чи не втратиться закомічена зміна?**

Якби це було так, СУБД порушувала б властивість **Durability** з ACID (докладно розібрано в документі про транзакції та ізоляцію цієї серії): дані закомієної транзакції зобов'язані пережити збій.

### Ключовий принцип WAL

**Write-Ahead Logging** вирішує цю проблему елегантно: перед тим, як змінити фактичну сторінку даних, СУБД спочатку записує **запис про намір змінити ці дані** у окремий, послідовний, append-only (лише дозапис) лог-файл — і цей запис у логі **обов'язково має бути фізично скинутий на диск (fsync) ДО того, як транзакція вважається закомієною** й клієнту повертається підтвердження успіху.

Формулюючи це як правило:

> **Жоден запис не може бути закомічений клієнту, поки відповідний WAL-запис не гарантовано лежить на диску.**

Сама ж зміна фактичної сторінки даних на диску може статись значно пізніше — фоновим процесом, асинхронно, без поспіху.

### Чому це швидше, ніж записувати сторінки даних напряму при кожному коміті?

Це ключове "чому" цього розділу, яке варто вміти пояснити на співбесіді своїми словами:

- **WAL-запис — це послідовний (sequential) дозапис** в кінець одного файлу. Послідовний запис на диск — навіть на обертовому HDD — надзвичайно швидкий, тому що головці диска не потрібно "стрибати" між різними ділянками (а на SSD послідовний запис теж ефективніший завдяки більшим блокам і меншій фрагментації на рівні контролера).
- **Записи фактичних сторінок даних, натомість, розкидані по всьому файлу бази даних** — сторінка таблиці `Orders` може лежати в зовсім іншому місці диска, ніж сторінка пов'язаного індексу чи іншого рядка тієї ж таблиці. Записувати їх на диск при кожному коміті означало б **випадковий (random) I/O** — а випадковий запис на порядки повільніший за послідовний, особливо на обертових дисках, де потрібно фізично переміщати головку.
- Отже: замість того, щоб на кожен `COMMIT` виконувати повільний випадковий запис (можливо, кількох) сторінок даних, СУБД виконує один швидкий послідовний запис невеликого WAL-запису — а фактичні сторінки даних "наздоганяють" пізніше, батчами, коли це вигідніше з точки зору I/O-патернів (більше змін можна об'єднати в одне фізичне записування тієї самої сторінки).

### WAL і відновлення після збою (crash recovery)

Після аварійного перезапуску СУБД читає WAL і виконує дві операції:

1. **REDO (повторення)** — для кожної транзакції, яка за даними WAL була закомічена, але чиї зміни в сторінках даних ще не встигли зафіксуватись на диску до збою — повторно застосувати ці зміни з логу до сторінок даних.
2. **UNDO (відкат)** — для транзакцій, які на момент збою ще **не** були закомічені (наприклад, сервер впав посеред виконання) — скасувати будь-які часткові зміни, які встигли потрапити в сторінки даних, щоб база даних лишалась у консистентному стані.

Це напряму реалізує гарантію **Durability** з ACID: клієнт отримав підтвердження коміту → значить, відповідний запис фізично лежить у WAL на диску → значить, навіть після миттєвого збою СУБД гарантовано зможе відновити цю зміну під час REDO при наступному старті. Клієнту ніколи не буде "збрехано" про успішний коміт.

### Діаграма послідовності: WAL-запис → комміт → фоновий flush → checkpoint

```
Клієнт          Транзакційний       WAL (диск,          Сторінки даних      Checkpoint
                менеджер            послідовний файл)   (буферний пул→диск)  процес
  │                   │                     │                    │                │
  │  BEGIN; UPDATE...  │                     │                    │                │
  ├──────────────────▶│                     │                    │                │
  │                   │  Змінити сторінку   │                    │                │
  │                   │  в буферному пулі   │                    │                │
  │                   │  (dirty page,       │                    │                │
  │                   │   ще НЕ на диску)   │                    │                │
  │                   ├─────────────────────┼───────────────────▶│                │
  │                   │                     │                    │                │
  │      COMMIT       │                     │                    │                │
  ├──────────────────▶│                    │                    │                │
  │                   │  Записати WAL-запис │                    │                │
  │                   │  ПОСЛІДОВНО         │                    │                │
  │                   ├────────────────────▶│                    │                │
  │                   │                     │ fsync() —          │                │
  │                   │                     │ гарантовано на диску│                │
  │                   │◀────────────────────┤                    │                │
  │  "OK, закомічено" │                     │                    │                │
  │◀──────────────────┤                     │                    │                │
  │                   │                     │                    │                │
  │            (клієнт продовжує роботу, сторінка даних все ще dirty в RAM)       │
  │                   │                     │                    │                │
  │                   │                     │       ... минає час ...             │
  │                   │                     │                    │                │
  │                   │                     │   Фоновий writer   │                │
  │                   │                     │   зливає dirty     │                │
  │                   │                     │   сторінки на диск │                │
  │                   │                     │◀───────────────────┤                │
  │                   │                     │                    │                │
  │                   │                     │             CHECKPOINT: усі dirty    │
  │                   │                     │             сторінки до цієї точки   │
  │                   │                     │             гарантовано на диску     │
  │                   │                     │◀───────────────────────────────────┤
  │                   │                     │   Старі WAL-записи до checkpoint    │
  │                   │                     │   більше не потрібні для recovery — │
  │                   │                     │   можна архівувати/видалити         │
  │                   │                     │◀───────────────────────────────────┤
```

Ключовий висновок з діаграми: **COMMIT чекає лише на запис у WAL, а не на запис фактичної сторінки даних.** Саме тому коміт — швидка операція (один послідовний запис невеликого обсягу), навіть якщо змінена сторінка даних величезна або розкидана по диску.

## Checkpointing

Якщо WAL постійно росте і ніколи не "спорожнюється", виникають дві проблеми:

1. **Необмежене зростання лог-файлу** — диск рано чи пізно закінчиться.
2. **Необмежений час відновлення після збою** — якщо WAL містить записи за останні півроку роботи, після збою СУБД довелось би відтворювати (REDO) пів року змін, перш ніж база даних знову стане доступною. Це неприйнятно повільно для будь-якої production-системи.

**Checkpoint** — це операція, яка вирішує обидві проблеми: СУБД гарантує, що **всі dirty-сторінки, змінені до певного моменту часу (checkpoint LSN), фізично записані на диск**. Після завершення checkpoint:

- WAL-записи, зроблені **до** цього checkpoint, більше не потрібні для crash recovery (адже відповідні зміни вже гарантовано лежать у файлах даних) — їх можна безпечно видалити, заархівувати (для backup/point-in-time recovery) чи перевикористати місце під нові записи.
- У разі збою після цього моменту, СУБД потрібно буде виконати REDO лише для записів **після** останнього успішного checkpoint — а не з самого початку історії WAL. Це прямо обмежує (і прогнозовано скорочує) час відновлення після збою.

Checkpoint виконується періодично у фоновому режимі (за часом, за обсягом накопичених WAL-записів, або вручну командою на кшталт `CHECKPOINT` у PostgreSQL). Це компроміс: занадто часті checkpoint-и створюють додаткове навантаження на диск (багато записів сторінок за короткий час — сплеск I/O), занадто рідкі — збільшують обсяг WAL і час потенційного відновлення. Тюнінг частоти checkpoint — реальна операційна задача для баз даних під високим навантаженням запису (наприклад, `checkpoint_timeout` і `max_wal_size` у PostgreSQL).

```
Час  ───────────────────────────────────────────────────────▶

WAL:  [txn1][txn2][txn3]▓▓CHECKPOINT▓▓[txn4][txn5][txn6]  ← поточний момент
                          ▲
                          └─ все, що ДО цієї точки, гарантовано на диску.
                             Старі WAL-записи ([txn1..txn3]) можна прибрати.
                             У разі збою ЗАРАЗ — REDO лише [txn4], [txn5], [txn6].
```

## MVCC на рівні зберігання (як це реалізовано фізично)

У документі цієї серії про транзакції та рівні ізоляції вже розглядалась концептуальна ідея **MVCC (Multi-Version Concurrency Control)**: замість блокування рядків на читання, СУБД дозволяє різним транзакціям бачити різні "версії" одного й того ж рядка одночасно, залежно від моменту, коли транзакція почалась. Тут ми йдемо на рівень глибше й розглядаємо, **як саме ці версії фізично зберігаються на диску** — і тут існують дві принципово різні архітектурні школи.

### Підхід 1: PostgreSQL — множинні фізичні версії рядка "на місці"

У PostgreSQL кожен `UPDATE` **не змінює рядок на місці**. Замість цього створюється **абсолютно нова фізична копія рядка** (нова версія) десь на сторінці (можливо, на тій самій, можливо на іншій, якщо місця не вистачає), а стара версія позначається як "застаріла", але фізично **лишається на диску**.

Кожна версія рядка має приховані системні поля-мітки видимості:

- `xmin` — ідентифікатор транзакції, яка **створила** цю версію рядка.
- `xmax` — ідентифікатор транзакції, яка **видалила/замінила** цю версію рядка (або порожньо, якщо версія ще актуальна).

Коли транзакція читає рядок, вона перевіряє ці мітки відносно свого власного "знімку" (snapshot) активних транзакцій: чи видима їй ця конкретна версія рядка, з огляду на те, коли ця версія була створена/видалена відносно моменту старту транзакції-читача. Так реалізується "знімок даних станом на момент початку транзакції" без єдиного блокування на читання.

Проблема цього підходу: **старі версії рядків не зникають самі по собі**. Вони накопичуються на диску як "мертві рядки" (dead tuples), займаючи місце і сповільнюючи сканування таблиці (адже сканеру доводиться "проходити повз" застарілі версії, перевіряти їхню видимість і відкидати). Для очищення цих застарілих версій у PostgreSQL існує спеціальний процес — **`VACUUM`**.

`VACUUM` фізично звільняє місце, зайняте мертвими версіями рядків (роблячи його доступним для повторного використання новими рядками на тій самій сторінці), і оновлює статистику планувальника запитів. Є й `VACUUM FULL`, який повністю переписує таблицю, стискаючи її фізично й повертаючи вільне місце операційній системі — але це вимагає ексклюзивного блокування таблиці на час виконання.

### Підхід 2: Rollback-сегменти / Undo-лог (Oracle, InnoDB у MySQL)

Інша школа — та, якою користуються Oracle (rollback segments) і InnoDB у MySQL (undo log): тут **актуальна версія рядка оновлюється на місці** (in-place update) у самій сторінці даних, а **стара версія переноситься в окрему структуру — undo log (журнал відкату)**.

Коли інша транзакція, яка стартувала раніше й повинна бачити старіший знімок даних, читає цей рядок — вона знаходить в основній сторінці вже **нову** версію, помічає, що ця версія "надто нова" для її знімку, і **йде в undo log**, щоб реконструювати ту версію рядка, яка була актуальна на момент старту цієї транзакції.

Тут проблема не в розростанні основної таблиці (вона лишається компактною — на місці завжди лежить лише одна, актуальна версія), а в тому, що **довгі транзакції змушують зберігати старі записи в undo log довше**, ніж хотілося б — undo log не може бути очищений (усічений), поки є хоч одна активна транзакція, якій потенційно потрібна стара версія. Довга транзакція, що "висить" відкритою (наприклад, забутий інтерактивний сеанс без коміту), може призвести до сильного розростання undo tablespace в Oracle чи InnoDB.

### Порівняльна таблиця двох фізичних стратегій MVCC

| Критерій | PostgreSQL (нові версії "на місці") | Oracle / InnoDB (undo log / rollback segments) |
|---|---|---|
| Де зберігається стара версія рядка | Прямо в таблиці, поруч з новою версією | В окремій структурі — undo tablespace / rollback segment |
| Що відбувається при `UPDATE` | Створюється нова фізична копія рядка; стара лишається помітною як "мертва" | Рядок змінюється на місці; стара версія копіюється в undo log |
| Наслідок для основної таблиці | Таблиця може "розбухати" (bloat) старими версіями | Основна таблиця лишається компактною |
| Механізм очищення | `VACUUM` (ручний/автоматичний `autovacuum`) | Автоматичне усічення undo-сегментів, коли старі версії більше нікому не потрібні |
| Головний операційний ризик | Table/index bloat при вимкненому/недостатньо агресивному `autovacuum` | Розростання undo tablespace при довгих відкритих транзакціях ("ORA-01555: snapshot too old" — класична помилка Oracle) |
| Вартість `UPDATE` | Вища (нова фізична копія повного рядка + оновлення індексів, що вказують на нову версію) | Нижча для основного шляху (оновлення на місці), але є вартість запису в undo log |
| Вартість читання старої версії | Пряма — стара версія вже лежить у самій таблиці | Опосередкована — потрібно реконструювати версію з undo log |

### Практичний операційний нюанс: чому `VACUUM` — реальна головна біль у продакшн PostgreSQL

Це класичний **senior-рівня гоча (gotcha)**: якщо `autovacuum` не встигає (наприклад, через дуже високу частоту `UPDATE`/`DELETE` на великій таблиці, або через неправильно налаштовані пороги запуску), мертві версії рядків накопичуються швидше, ніж очищаються. Наслідки:

- Таблиця фізично займає значно більше місця на диску, ніж "логічно" потрібно для збереження актуальних даних (**table bloat**).
- Індекси теж "розбухають" (**index bloat**), бо вказують і на мертві версії теж.
- Плани запитів планувальника (query planner) можуть ставати неоптимальними — статистика (яку оновлює `VACUUM ANALYZE`) застаріває, і планувальник неправильно оцінює селективність фільтрів.
- У найгіршому крайньому випадку — вичерпання лічильника транзакцій (**transaction ID wraparound**) — критична проблема, що вимагає екстреного втручання й може призвести до зупинки прийому нових записів у базу даних, поки не буде виконаний примусовий `VACUUM FREEZE`.

Тому моніторинг `autovacuum` і статистики "мертвих рядків" (`n_dead_tup` у `pg_stat_user_tables`) — це не "необов'язкове адміністрування", а реальна операційна необхідність для будь-якої production-бази PostgreSQL з високим навантаженням запису.

## Практичні приклади на SQL та C#

Ця тема більш архітектурна, ніж типовий CRUD-код — тому приклади нижче побудовані навколо ідеї **спостереження й аналізу** внутрішнього устрою реальної бази даних, а також невеликих ілюстративних симуляцій у C#, які роблять абстрактні концепції відчутними в коді.

### Приклад 1 — Як senior-інженер реально "заглядає" всередину бази даних (SQL)

**PostgreSQL: розмір таблиці/індексів і статистика "мертвих" рядків**

```sql
-- Фізичний розмір таблиці (тільки дані, без індексів)
SELECT pg_size_pretty(pg_relation_size('orders')) AS table_size;

-- Повний розмір таблиці разом з усіма її індексами й TOAST-даними
SELECT pg_size_pretty(pg_total_relation_size('orders')) AS total_size;

-- Скільки в середньому рядків вміщується на одну сторінку (8 KB) —
-- показник "щільності" зберігання, прямо впливає на кількість I/O при скануванні
SELECT
    relname,
    reltuples::bigint AS estimated_rows,
    relpages,
    round(reltuples / NULLIF(relpages, 0), 1) AS avg_rows_per_page
FROM pg_class
WHERE relname = 'orders';

-- Статистика живих/мертвих рядків і час останнього VACUUM —
-- ключовий запит для діагностики table bloat
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_tuple_pct,
    last_vacuum,
    last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

Якщо `dead_tuple_pct` стабільно високий (наприклад, понад 20%), а `last_autovacuum` — давно, це прямий сигнал: таблиця розбухає, `autovacuum` не встигає, і продуктивність запитів на цю таблицю з часом деградуватиме.

**SQL Server: фізична статистика фрагментації індексу/сторінок**

```sql
-- Фрагментація індексу та щільність сторінок для таблиці Orders
SELECT
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    ips.avg_page_space_used_in_percent
FROM sys.dm_db_index_physical_stats(
        DB_ID(), OBJECT_ID('dbo.Orders'), NULL, NULL, 'DETAILED'
     ) AS ips
JOIN sys.indexes AS i
     ON ips.object_id = i.object_id AND ips.index_id = i.index_id;
```

Високий `avg_fragmentation_in_percent` (скажімо, понад 30%) — сигнал, що індекс варто перебудувати (`REBUILD`/`REORGANIZE`), бо фрагментовані сторінки означають зайві випадкові читання з диска замість послідовних.

### Приклад 2 — Ілюстративна симуляція `Page` + `BufferPool` у C#

Це **не** production-реалізація, а спрощена модель, щоб зробити абстрактні поняття "брудна сторінка" і "витіснення" відчутними в коді.

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

// Спрощена модель сторінки даних
public class Page
{
    public int PageId { get; }
    public List<string> Rows { get; } = new();
    public bool IsDirty { get; set; } = false;
    public DateTime LastAccessed { get; set; } = DateTime.UtcNow;

    public Page(int pageId) => PageId = pageId;

    public void ModifyRow(string newRow)
    {
        Rows.Add(newRow);
        IsDirty = true; // зміна ще тільки в пам'яті — не записана на "диск"
        LastAccessed = DateTime.UtcNow;
    }
}

// Спрощена модель буферного пулу з фіксованою ємністю та LRU-витісненням
public class BufferPool
{
    private readonly int _capacity;
    private readonly Dictionary<int, Page> _pages = new();
    // Симулюємо "диск" простим словником page_id -> вміст
    private readonly Dictionary<int, List<string>> _disk = new();

    public BufferPool(int capacity) => _capacity = capacity;

    public Page LoadPage(int pageId)
    {
        if (_pages.TryGetValue(pageId, out var cached))
        {
            Console.WriteLine($"[Cache HIT] Сторінка {pageId} вже в буферному пулі.");
            cached.LastAccessed = DateTime.UtcNow;
            return cached;
        }

        Console.WriteLine($"[Cache MISS] Сторінка {pageId} відсутня — читаємо з \"диска\".");

        if (_pages.Count >= _capacity)
            EvictLeastRecentlyUsed();

        var page = new Page(pageId);
        if (_disk.TryGetValue(pageId, out var diskRows))
            page.Rows.AddRange(diskRows);

        _pages[pageId] = page;
        return page;
    }

    private void EvictLeastRecentlyUsed()
    {
        var victim = _pages.Values.OrderBy(p => p.LastAccessed).First();

        if (victim.IsDirty)
        {
            Console.WriteLine($"[Flush] Сторінка {victim.PageId} \"брудна\" — записуємо на \"диск\" перед витісненням.");
            _disk[victim.PageId] = new List<string>(victim.Rows);
        }

        Console.WriteLine($"[Evict] Сторінка {victim.PageId} витіснена з буферного пулу.");
        _pages.Remove(victim.PageId);
    }
}

public class Demo
{
    public static void Run()
    {
        var pool = new BufferPool(capacity: 2); // навмисно мала ємність для демонстрації

        var page1 = pool.LoadPage(1);
        page1.ModifyRow("Order #101 -> status=Shipped"); // сторінка 1 стає dirty

        var page2 = pool.LoadPage(2);
        page2.ModifyRow("Order #205 -> status=Paid");

        // Завантаження третьої сторінки при ємності пулу = 2
        // змусить витіснити найдавнішу за використанням (page1) — і скинути її на "диск", бо вона dirty
        var page3 = pool.LoadPage(3);

        // Повторне звернення до page1 -> знову MISS, бо її щойно витіснили
        pool.LoadPage(1);
    }
}
```

Очікуваний консольний вивід (спрощено):

```
[Cache MISS] Сторінка 1 відсутня — читаємо з "диска".
[Cache MISS] Сторінка 2 відсутня — читаємо з "диска".
[Cache MISS] Сторінка 3 відсутня — читаємо з "диска".
[Flush] Сторінка 1 "брудна" — записуємо на "диск" перед витісненням.
[Evict] Сторінка 1 витіснена з буферного пулу.
[Cache MISS] Сторінка 1 відсутня — читаємо з "диска".
```

Навіть у такій спрощеній моделі видно ключову ідею: зміна (`ModifyRow`) не викликає негайного запису на "диск" — вона позначає сторінку `dirty`, а фактичний запис відбувається лише коли сторінку потрібно витіснити з обмеженого за розміром пулу.

### Приклад 3 — Ілюстративна "міні-WAL" симуляція у C#

Демонструє основний принцип WAL у мініатюрі: спершу запис наміру в послідовний лог, потім (окремо) застосування до "даних", і `Recover()`, що показує, як відбувається REDO після симульованого "збою".

```csharp
using System;
using System.Collections.Generic;

public record WalEntry(int TransactionId, string Key, string NewValue, bool Committed);

public class MiniWalDatabase
{
    private readonly List<WalEntry> _walLog = new();       // "диск": послідовний, append-only лог
    private readonly Dictionary<string, string> _dataStore = new(); // "сторінки даних" в пам'яті

    public void ExecuteTransaction(int txnId, string key, string newValue)
    {
        // Крок 1: спочатку запис наміру у WAL (симуляція fsync на послідовний файл)
        _walLog.Add(new WalEntry(txnId, key, newValue, Committed: false));
        Console.WriteLine($"[WAL] Записано намір: txn={txnId}, {key} -> {newValue}");

        // Крок 2: COMMIT -> помічаємо запис committed. У РЕАЛЬНІЙ СУБД саме тут
        // клієнт отримує підтвердження, і саме тут WAL-запис гарантовано на диску.
        var idx = _walLog.FindLastIndex(e => e.TransactionId == txnId);
        _walLog[idx] = _walLog[idx] with { Committed = true };
        Console.WriteLine($"[COMMIT] Транзакція {txnId} закомічена (WAL гарантує durability).");

        // Крок 3: застосування до "сторінки даних" (могло б бути відкладено фоновим процесом,
        // тут для наочності робимо одразу).
        _dataStore[key] = newValue;
    }

    // Симулюємо збій: сторінки даних у пам'яті "зникають" (втрачені, не встигли на диск),
    // але WAL, як послідовний файл, який ми вважаємо вже фізично на диску, — залишається.
    public void SimulateCrash()
    {
        Console.WriteLine("\n*** СИМУЛЯЦІЯ ЗБОЮ: дані в пам'яті втрачені, WAL лишається на диску ***\n");
        _dataStore.Clear();
    }

    // Recovery: REDO всіх закомічених транзакцій з WAL
    public void Recover()
    {
        Console.WriteLine("[Recovery] Починаємо відтворення (REDO) з WAL...");
        foreach (var entry in _walLog)
        {
            if (entry.Committed)
            {
                _dataStore[entry.Key] = entry.NewValue;
                Console.WriteLine($"[REDO] Відтворено: {entry.Key} -> {entry.NewValue} (з txn {entry.TransactionId})");
            }
            else
            {
                Console.WriteLine($"[SKIP/UNDO] Транзакція {entry.TransactionId} НЕ була закомічена — пропускаємо.");
            }
        }
        Console.WriteLine("[Recovery] Завершено.");
    }

    public void PrintState()
    {
        Console.WriteLine("\nПоточний стан даних:");
        foreach (var kv in _dataStore)
            Console.WriteLine($"  {kv.Key} = {kv.Value}");
    }
}

public class WalDemo
{
    public static void Run()
    {
        var db = new MiniWalDatabase();

        db.ExecuteTransaction(txnId: 1, key: "order:101", newValue: "status=Shipped");
        db.ExecuteTransaction(txnId: 2, key: "order:205", newValue: "status=Paid");

        db.PrintState(); // дані ще "живі" в пам'яті

        db.SimulateCrash(); // імітуємо збій — дані в пам'яті пропадають

        db.PrintState(); // порожньо!

        db.Recover(); // WAL рятує ситуацію — REDO відновлює закомічені зміни

        db.PrintState(); // дані знову на місці
    }
}
```

Очікуваний консольний вивід (скорочено):

```
[WAL] Записано намір: txn=1, order:101 -> status=Shipped
[COMMIT] Транзакція 1 закомічена (WAL гарантує durability).
[WAL] Записано намір: txn=2, order:205 -> status=Paid
[COMMIT] Транзакція 2 закомічена (WAL гарантує durability).

Поточний стан даних:
  order:101 = status=Shipped
  order:205 = status=Paid

*** СИМУЛЯЦІЯ ЗБОЮ: дані в пам'яті втрачені, WAL лишається на диску ***


Поточний стан даних:

[Recovery] Починаємо відтворення (REDO) з WAL...
[REDO] Відтворено: order:101 -> status=Shipped (з txn 1)
[REDO] Відтворено: order:205 -> status=Paid (з txn 2)
[Recovery] Завершено.

Поточний стан даних:
  order:101 = status=Shipped
  order:205 = status=Paid
```

Ця мініатюрна симуляція демонструє ключову ідею WAL буквально в 30 рядках коду: **дані в "сторінках" можуть зникнути, але доки лог наміру закомічених змін фізично існує — жодна закомічена транзакція не втрачається.**

## Реальний сценарій: чому продуктивність різко впала після росту таблиці

Уяви типову ситуацію в реальній компанії: команда розробила адмін-панель для внутрішнього використання, з дашбордом, що показує останні замовлення з таблиці `Orders` (JOIN з `Customers` і `OrderItems`). Перший рік після запуску все працювало ідеально — сторінка адмінки відкривалась миттєво, запити виконувались за одиниці мілісекунд.

Потім, приблизно через рік (таблиця `Orders` виросла з кількох сотень тисяч до, скажімо, 40 мільйонів рядків), продуктивність **раптово** — не поступово, а майже стрибком — впала: той самий запит, що виконувався за 20 мс, тепер стабільно виконується за 2-3 секунди. Код запиту не змінювався. Індекси на місці. Що трапилось?

### Покроковий розбір причини (типовий хід думок senior-інженера)

1. **Перевірка плану виконання (`EXPLAIN ANALYZE`)** — план той самий, що й рік тому: індекс використовується правильно, JOIN виконується за розумною стратегією. Отже, проблема не в оптимізаторі запитів чи відсутньому індексі — план не змінився.

2. **Перевірка I/O-метрик** — і ось тут виявляється ключове: раніше запит майже повністю обслуговувався з буферного пулу (`shared_buffers_hit_ratio` близько 99%), а тепер значна частка сторінок читається безпосередньо з диска (`heap blocks read` замість `heap blocks hit` різко зросло).

3. **Причина**: рік тому вся таблиця `Orders` разом з її індексами вміщувалась у виділений буферний пул сервера (наприклад, 8 GB RAM під СУБД якраз покривали тодішній обсяг даних). Тепер, коли таблиця виросла в десятки разів, **робочий набір даних (working set) більше не вміщується в буферний пул одночасно**. СУБД змушена постійно вимивати з кешу одні сторінки, щоб завантажити інші — і кожен новий запит частково "виштовхує" сторінки, потрібні наступному запиту.

4. **Наслідок**: запит, який раніше читав дані практично повністю з RAM (наносекунди-мікросекунди на сторінку), тепер регулярно змушений робити **випадкові читання з диска** (мілісекунди на сторінку, особливо якщо диск мережевий — наприклад, SAN або хмарний блоковий том із обмеженим IOPS). Помножене на кількість сторінок, які потрібно прочитати для JOIN трьох таблиць по мільйонах рядків — і секунди замість мілісекунд стають цілком логічним результатом, а не аномалією.

### Чому це виглядає як "різкий обрив", а не поступова деградація

Це важливий нюанс, який варто вміти пояснити: поки робочий набір **вміщується** в буферний пул — продуктивність залишається стабільно високою незалежно від того, чи таблиця виросла на 10% чи на 200%, бо все одно обслуговується з RAM. Але щойно робочий набір **перестає** вміщатись — навіть невеликий приріст (умовно, ще один місяць даних) різко змінює характер навантаження з "переважно RAM" на "переважно диск". Це не лінійна деградація, а порогова, стрибкоподібна зміна поведінки системи — саме тому вона застає команди зненацька: "ми ж нічого не міняли, а стало вдесятеро повільніше".

### Сеньйорські відповіді на цю проблему

- **Кращі індекси, що зменшують кількість сторінок, які потрібно торкнутись.** Покривні (covering) індекси, що включають усі потрібні запиту колонки, дозволяють обійтись без додаткового звернення до основної таблиці (avoid a bookmark/key lookup) — менше сторінок = менше I/O навіть при cache miss.
- **Партиціювання й архівування застарілих даних.** Якщо адмінці реально потрібні лише останні 90 днів замовлень, а решта — історичний архів, варто винести стару частину в окрему (архівну) таблицю чи партицію. "Гаряча" робоча таблиця лишається компактною й із високою ймовірністю продовжує вміщуватись у буферний пул.
- **Вертикальне масштабування (більше RAM).** Іноді найпростіше й найдешевше рішення — банально збільшити обсяг оперативної пам'яті сервера бази даних (і відповідно розмір буферного пулу), щоб робочий набір знову повністю вміщувався в кеш. Це не "неправильне" рішення — для деяких навантажень це найбільш економічно виправданий крок.
- **Перегляд самого запиту й денормалізація для гарячих шляхів.** Якщо дашборд справді потребує лише агрегованих даних (наприклад, кількість замовлень за статусами за останній тиждень), можливо, варто матеріалізувати цю агрегацію окремо (кешована таблиця, оновлювана батчем), а не рахувати "наживо" по мільйонах рядків щоразу.

### Класична пастка: "у мене на dev все летить"

Один із найпоширеніших сеньйорських уроків: **продуктивність на dev/staging середовищі з тестовими даними (сотні чи тисячі рядків) абсолютно нічого не гарантує щодо продакшену з мільйонами рядків**, тому що на dev дані практично завжди вміщуються в буферний пул повністю, незалежно від якості індексів чи схеми. Проблеми, пов'язані з нестачею буферного пулу, випадковим I/O й неефективними планами запитів на великих обсягах даних, **за визначенням не можуть проявитись** на малих тестових наборах — вони проявляються лише при реалістичних (чи хоча б порівнянних за порядком величини) обсягах даних. Тому серйозні команди інвестують у тестування продуктивності на репрезентативних за обсягом копіях даних (чи синтетично згенерованих наборах відповідного масштабу) ще до релізу в продакшн.

## Поширені помилки

**Помилка 1: Покладатись на продуктивність dev/staging як на прогноз для продакшену**

❌ **Погано:** "На стейджингу запит виконується миттєво (100 тестових рядків), тож у продакшені (мільйони рядків) з ним теж усе буде гаразд."

✅ **Добре:** Тестувати продуктивність критичних запитів на копії даних, порівнянній за обсягом і формою розподілу з реальним продакшеном (чи хоча б з реалістично згенерованими даними того ж порядку величини), особливо перш ніж покладатись на конкретний індекс/план запиту в production.

**Помилка 2: Ігнорувати `VACUUM`/обслуговування таблиць у PostgreSQL**

❌ **Погано:** Вимкнути чи послабити `autovacuum` "щоб не заважав продуктивності", не моніторити `n_dead_tup`, і виявити проблему лише тоді, коли таблиця вже роздулась у кілька разів більше за логічно потрібний обсяг, а плани запитів деградували через застарілу статистику.

✅ **Добре:** Моніторити `pg_stat_user_tables` (частку мертвих рядків, час останнього `autovacuum`), тюнити пороги `autovacuum` для таблиць із високою частотою `UPDATE`/`DELETE`, і за потреби виконувати позапланове обслуговування (`VACUUM ANALYZE`, у крайньому випадку `VACUUM FULL` у вікно з низьким навантаженням).

**Помилка 3: Не розрізняти вартість частих дрібних випадкових записів проти рідших великих пакетних**

❌ **Погано:** Виконувати мільйони окремих `UPDATE`-запитів по одному рядку в циклі застосунку (наприклад, оновлювати статус кожного замовлення окремим запитом у циклі `foreach`), кожен з яких — окрема транзакція з окремим WAL-flush/fsync.

✅ **Добре:** Групувати зміни в **пакети (batches)** — один `UPDATE ... WHERE id IN (...)` чи `UPDATE ... FROM (VALUES ...)` для тисяч рядків за раз, обгорнутий в одну транзакцію. Це не лише зменшує кількість fsync-операцій на WAL (кожен commit синхронного fsync — реальна затримка), а й дозволяє СУБД ефективніше об'єднувати зміни dirty-сторінок перед записом на диск, замість того щоб записувати (і checkpoint-ити) одну й ту саму сторінку багато разів поспіль за короткий проміжок часу.

**Помилка 4: Плутати "дані вже змінені" з "дані вже на диску"**

❌ **Погано:** Вважати, що якщо `UPDATE` виконано без помилки (до `COMMIT`), зміна вже "у безпеці", або, навпаки, панікувати, що дані "втрачені", бо файл бази даних на диску ще не відображає щойно закомічену зміну (хоча WAL вже записаний).

✅ **Добре:** Розуміти чіткий поділ відповідальності: WAL відповідає за durability закомічених транзакцій, а фактичний стан сторінок даних на диску — лише "фонова, відкладена в часі" консистентна копія, яка гарантовано наздожене WAL під час наступного checkpoint або відновлення після збою.

**Помилка 5: Ігнорувати "товщину" рядка при проєктуванні схеми гарячих таблиць**

❌ **Погано:** Класти велике `TEXT`/JSON-поле (наприклад, повний вміст email-листа чи лог запиту) прямо в основну "гарячу" таблицю, якою активно користується весь застосунок для звичайних операційних запитів.

✅ **Добре:** Виносити рідко читані "товсті" колонки в окрему таблицю (1:1 зв'язок), щоб основна таблиця лишалась компактною — більше рядків на сторінку, менше сторінок для сканування типових запитів, вища ймовірність, що вся гаряча таблиця вміщується в буферний пул.

## Питання для співбесіди за рівнями

### Рівень Middle

**1. Що таке сторінка (page) у контексті СУБД?**

Сторінка — це фіксований за розміром блок даних на диску (типово 8 KB у PostgreSQL/SQL Server, 16 KB у InnoDB), який є базовою одиницею вводу-виводу: СУБД завжди читає й записує диск цілими сторінками, ніколи окремими рядками чи байтами. Сторінка містить заголовок з метаданими, дані кількох рядків та масив зсувів (slot array), що вказує на позицію кожного рядка всередині сторінки.

**2. Навіщо потрібен буферний пул?**

Тому що доступ до оперативної пам'яті на порядки швидший за доступ до диска. Буферний пул — це область пам'яті, де СУБД кешує нещодавно використані сторінки, щоб уникнути повторного дорогого читання з диска при повторному зверненні до тих самих даних. Коли потрібна сторінка вже є в пулі — це cache hit (швидко); коли немає — cache miss (потрібне читання з диска).

**3. Що таке "брудна сторінка" (dirty page)?**

Сторінка в буферному пулі, дані якої були змінені (`UPDATE`/`INSERT`/`DELETE`) в пам'яті, але зміни ще не записані (скинуті) на диск. Брудні сторінки записуються на диск пізніше — фоновим процесом або під час checkpoint, а не синхронно на кожну зміну.

**4. Що таке WAL і яку властивість ACID він забезпечує?**

WAL (Write-Ahead Log) — це послідовний, append-only лог-файл, куди СУБД записує намір змінити дані ще до того, як фактично змінити сторінку даних на диску. Правило: `COMMIT` вважається успішним лише після того, як відповідний WAL-запис гарантовано зафіксований на диску. Це напряму реалізує властивість **Durability** з ACID — закомічені зміни гарантовано переживають збій сервера, оскільки їх завжди можна відтворити (REDO) з WAL.

**5. Що таке checkpoint?**

Точка в часі, до якої СУБД гарантує, що всі змінені (dirty) сторінки фізично записані на диск. Після checkpoint WAL-записи до цієї точки більше не потрібні для відновлення після збою й можуть бути видалені/заархівовані. Checkpoint обмежує і розмір WAL, і потенційний час відновлення після збою.

**6. Чим cache hit відрізняється від cache miss у контексті буферного пулу?**

Cache hit — потрібна сторінка вже в буферному пулі, дані повертаються практично миттєво з RAM. Cache miss — сторінки немає в пулі, потрібне повільніше читання з диска, після чого копія кладеться в пул для майбутніх звернень.

**7. Чому "товщина" рядка (кількість і розмір колонок) впливає на продуктивність запитів?**

Тому що на сторінку фіксованого розміру (наприклад, 8 KB) вміщується обмежена кількість рядків. Чим "товщі" рядки, тим менше їх на сторінку — а отже, той самий обсяг логічних даних вимагає читання більшої кількості сторінок з диска чи буферного пулу, що напряму збільшує I/O-навантаження запиту.

### Рівень Senior

**1. Поясни, чому послідовний запис у WAL швидший за випадковий запис у сторінки даних.**

Послідовний запис (sequential write) означає дозапис даних одразу один за одним в кінець файлу без переміщення "голови" запису між різними ділянками диска — на обертовому HDD це критично, бо фізичне переміщення головки — найповільніша частина операції; на SSD послідовний запис теж ефективніший через кращу утилізацію внутрішніх буферів контролера й менший знос через фрагментацію. Сторінки даних, навпаки, розкидані по всьому файлу бази даних відповідно до логічного розташування таблиць/індексів — запис змін напряму в них при кожному коміті означав би постійні випадкові записи (random I/O) в довільні місця файлу, що на порядки повільніше за один послідовний дозапис невеликого WAL-запису. Тому WAL дозволяє СУБД підтверджувати коміт клієнту дуже швидко (лише за ціну одного послідовного flush), а фактичні дорожчі випадкові записи сторінок відкласти на потім і виконати batched, ефективніше.

**2. Опиши два різні фізичні підходи до реалізації MVCC (PostgreSQL vs rollback-segment).**

PostgreSQL створює нову фізичну копію рядка при кожному `UPDATE`, лишаючи стару версію на диску позначеною як застарілу (через приховані поля `xmin`/`xmax`) — очищення виконує окремий процес `VACUUM`. Це означає, що таблиця може "розбухати" (bloat) старими версіями, якщо `VACUUM`/`autovacuum` не встигає за темпом змін. Oracle та InnoDB (MySQL), навпаки, оновлюють рядок **на місці** в основній сторінці, а стару версію переносять в окрему структуру — undo log/rollback segment; транзакції, яким потрібна старіша версія, реконструюють її з undo log. Тут основна таблиця лишається компактною, але довгі відкриті транзакції можуть надовго "заморожувати" необхідність зберігати старі undo-записи, спричиняючи розростання undo tablespace (класична помилка Oracle "snapshot too old").

**3. Чому VACUUM важливий у PostgreSQL і що станеться, якщо його ігнорувати?**

`VACUUM` очищує мертві версії рядків (dead tuples), що накопичуються через архітектуру MVCC PostgreSQL, де кожен `UPDATE`/`DELETE` лишає стару версію фізично на диску. Якщо `autovacuum` не встигає (наприклад, через дуже інтенсивний запис і замалі пороги запуску), відбувається table bloat (таблиця займає значно більше місця, ніж логічно потрібно) та index bloat, статистика планувальника застаріває, що веде до неоптимальних планів запитів, а в крайньому випадку — до вичерпання лічильника ідентифікаторів транзакцій (transaction ID wraparound), критичної проблеми, здатної зупинити прийом нових записів у базу даних до примусового `VACUUM FREEZE`.

**4. Поясни, чому продуктивність запиту може різко впасти, коли таблиця перестає вміщатись у пам'ять.**

Поки весь робочий набір даних (таблиця з індексами, до яких реально звертаються запити) вміщується в буферний пул, практично всі читання обслуговуються з RAM (cache hit) — швидкість стабільно висока незалежно від невеликих коливань обсягу даних. Щойно робочий набір перевищує розмір буферного пулу, СУБД змушена постійно витісняти одні сторінки, щоб завантажити інші (thrashing), і значна частка звернень перетворюється на випадкові читання з диска — які на порядки повільніші за RAM. Оскільки перехід відбувається не поступово, а по факту перевищення фізичного ліміту пам'яті, деградація виглядає як різкий, пороговий "обрив" продуктивності, а не плавне уповільнення пропорційно росту таблиці.

**5. Як checkpoint впливає на час відновлення після збою?**

Checkpoint гарантує, що всі dirty-сторінки до певного моменту фізично на диску, тому WAL-записи до цього моменту вже не потрібні для REDO. Відповідно, у разі збою СУБД потрібно відтворити (REDO) лише ту частину WAL, яка накопичилась **після** останнього успішного checkpoint. Чим рідше виконується checkpoint, тим більший обсяг WAL накопичується між checkpoint-ами і тим довше потенційно триватиме REDO при відновленні після збою — це прямий компроміс між навантаженням від частих checkpoint-ів (сплески I/O при масовому записі dirty-сторінок) і прогнозованим часом простою після аварії.

**6. Спроєктуй стратегію діагностики, коли продакшн-запит раптово почав виконуватись у 10 разів довше без явних змін коду.**

Систематичний підхід: (1) Перевірити, чи змінився план виконання запиту (`EXPLAIN ANALYZE` зараз проти збереженого попереднього плану чи бейзлайну) — зміна плану оптимізатора (наприклад, через застарілу статистику чи зміну параметрів) часто є першопричиною. (2) Якщо план не змінився — перевірити метрики буферного пулу/кешу (cache hit ratio, кількість фізичних читань з диска на цей запит) — це вкаже, чи проблема в тому, що робочий набір перестав вміщатись у пам'ять. (3) Перевірити зростання обсягу таблиці й індексів у часі (чи не перетнула таблиця критичний поріг розміру відносно буферного пулу, чи є проблема table/index bloat через недостатній `VACUUM`/обслуговування). (4) Перевірити конкурентні навантаження — чи не зросла паралельна конкуренція за ті самі ресурси (блокування, contention, конкуренція за I/O з іншими важкими фоновими задачами — backup, batch-job, аналітичний запит). (5) Перевірити інфраструктурний рівень — чи не деградував сам диск/мережа (наприклад, throttling IOPS у хмарному сховищі після вичерпання burst-кредитів). Лише пройшовши ці кроки методично, а не гадаючи навмання, можна впевнено локалізувати першопричину — і саме це відрізняє senior-діагностику від спроб "просто додати ще один індекс і сподіватись".

## Підсумок

**Швидкий довідник (cheat-sheet):**

- **Сторінка (Page)** — фіксований блок диску (типово 8–16 KB), базова одиниця I/O; СУБД завжди читає й пише цілі сторінки, ніколи окремі рядки. Кількість рядків на сторінку напряму залежить від "товщини" рядка і впливає на продуктивність сканувань.
- **Буферний пул (Buffer Pool)** — кеш сторінок в оперативній пам'яті, що усуває потребу повторно читати диск для "гарячих" даних. Робочий набір, що вміщується в буферний пул — один з найпотужніших важелів продуктивності бази даних; коли він перестає вміщатись, продуктивність падає різко, порогово, а не поступово.
- **WAL (Write-Ahead Log)** — послідовний, append-only лог намірів змінити дані, який записується на диск **до** підтвердження коміту клієнту. Реалізує Durability з ACID: закомічені зміни гарантовано можна відтворити (REDO) після збою, навіть якщо фактичні сторінки даних ще не встигли синхронізуватись з диском.
- **Checkpoint** — точка, до якої гарантовано всі dirty-сторінки записані на диск; обмежує розмір WAL і час потенційного відновлення після збою, дозволяючи безпечно прибирати старі WAL-записи.

**Порівняння фізичних стратегій MVCC:**

| Критерій | PostgreSQL | Oracle / InnoDB |
|---|---|---|
| Де зберігається стара версія | Прямо в таблиці, поруч з новою | В окремому undo log / rollback segment |
| Механізм очищення | `VACUUM` / `autovacuum` | Автоматичне усічення undo-сегментів |
| Головний операційний ризик | Table/index bloat | Розростання undo tablespace при довгих транзакціях |

Ключова ідея всього документа: SQL — це зручна абстракція, але справжнє розуміння продуктивності, надійності й поведінки бази даних під навантаженням приходить лише тоді, коли інженер може подумки "спуститись" на рівень сторінок, буферного пулу й WAL — і зрозуміти, що саме там реально відбувається, коли виконується звичайний `SELECT` чи `COMMIT`.
