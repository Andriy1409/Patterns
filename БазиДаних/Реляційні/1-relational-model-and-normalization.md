## 1. Що таке реляційна модель даних?

**Реляційна модель даних** — це спосіб організації даних у вигляді набору **таблиць (relations)**, де кожна таблиця має чітко визначену структуру стовпців, а рядки таблиці представляють окремі записи (сутності або зв'язки між ними). Модель була запропонована Едгаром Коддом (Edgar F. Codd) у 1970 році і базується на математичному апараті — теорії множин та **реляційній алгебрі**.

### Базові терміни

| Реляційний термін | Практичний аналог | Пояснення |
|---|---|---|
| **Relation (відношення)** | Таблиця (table) | Набір рядків з однаковою структурою стовпців |
| **Tuple (кортеж)** | Рядок (row / record) | Один конкретний запис у таблиці |
| **Attribute (атрибут)** | Стовпець (column / field) | Іменована характеристика сутності |
| **Domain (домен)** | Тип даних + обмеження | Множина допустимих значень атрибута |
| **Schema (схема)** | Структура БД | Опис усіх таблиць, стовпців, типів, обмежень і зв'язків |
| **Degree** | Кількість стовпців | Кількість атрибутів у відношенні |
| **Cardinality** | Кількість рядків | Кількість кортежів у відношенні |

### Аналогія з реального життя

Уявіть добре організований набір **Excel-таблиць (spreadsheets)**, де:

- Кожен аркуш (`Customers`, `Orders`, `Products`) має **строгу, незмінну структуру стовпців** — не можна в один рядок вписати "Ім'я, Прізвище", а в інший — просто "ПІБ одним текстом".
- У кожному аркуші є **однозначний ідентифікуючий стовпець** (наприклад, `CustomerId`), за яким можна миттєво і без сумнівів знайти конкретний рядок.
- Аркуші **пов'язані між собою** через посилання (в `Orders` є стовпець `CustomerId`, що вказує на конкретний рядок в `Customers`) — замість того, щоб копіювати всю інформацію про клієнта в кожен рядок замовлення.
- Будь-яка зміна структури (додати новий стовпець) стосується **одразу всіх рядків** аркуша — це і є жорстка, передбачувана схема (schema).

Це принципова відмінність від, наприклад, довільного текстового документа чи "купи JSON-файлів різної форми" — у реляційній моделі форма даних зафіксована і гарантована **до** того, як ви туди щось записали.

### Чому реляційні БД домінували десятиліттями

1. **Математична строгість.** Реляційна алгебра (selection, projection, join, union, difference тощо) дає формальну основу для мови запитів (SQL — це, по суті, декларативна обгортка над реляційною алгеброю та численням кортежів). Це означає, що результат запиту передбачуваний і оптимізований за строгими правилами, а не "як пощастить".
2. **ACID-гарантії.** Реляційні СУБД (PostgreSQL, SQL Server, Oracle, MySQL/InnoDB) історично першими надали надійні транзакційні гарантії: Atomicity, Consistency, Isolation, Durability. Для фінансових операцій, замовлень, бронювань це критично.
3. **Цілісність даних "з коробки".** Первинні та зовнішні ключі, обмеження `UNIQUE`, `CHECK`, `NOT NULL` — все це дозволяє **базі даних самій** гарантувати коректність даних, а не покладатися виключно на код застосунку.
4. **Зрілість екосистеми.** 50+ років розвитку означають зрілі оптимізатори запитів, індекси (B-tree, hash, GiST, GIN), інструменти резервного копіювання, реплікації, моніторингу, стандартизовану мову (SQL), величезну кількість фахівців на ринку.
5. **Нормалізація як інструмент проти дублювання.** Модель природно підтримує розбиття даних так, щоб кожен факт зберігався **рівно один раз** — це і є тема цього документа.

> 💡 Реляційна модель не "застаріла" з появою NoSQL — вона залишається кращим вибором там, де потрібна строга структура, складні зв'язки між сутностями та транзакційна цілісність (банкінг, ERP, бухгалтерія, замовлення). NoSQL вирішує **інші** проблеми (горизонтальне масштабування, гнучка/змінна схема, надвисокий throughput) ціною відмови від частини реляційних гарантій.

## 2. Ключі: Primary, Foreign, Candidate, Unique, Composite

Ключі — це фундамент, на якому тримається цілісність реляційної моделі. Розберемо кожен тип на прикладі невеликої e-commerce схеми: `Customers`, `Orders`, `OrderItems`, `Products`.

### 2.1. Candidate Key (потенційний ключ)

**Candidate key** — це будь-який стовпець (або мінімальна комбінація стовпців), значення якого **унікальне для кожного рядка** і теоретично могло б використовуватись для ідентифікації запису. У таблиці може бути кілька candidate keys.

Приклад для `Customers`:
- `CustomerId` (штучний числовий ідентифікатор) — candidate key.
- `Email` (якщо гарантовано унікальний) — теж candidate key.
- Комбінація `Passport Series + Passport Number` — теж candidate key.

Із усіх candidate keys обирається **один**, який стає **Primary Key**, решта залишаються потенційними — їх часто захищають через `UNIQUE`-обмеження.

### 2.2. Primary Key (первинний ключ, PK)

**Primary Key** — це обраний candidate key, який офіційно ідентифікує рядок у таблиці. Вимоги:

- **Унікальність** — жодні два рядки не можуть мати однакове значення PK.
- **Не-`NULL`** — PK не може бути невідомим.
- **Незмінність (бажано)** — значення PK не повинно змінюватись протягом життя запису (звідси й перевага **сурогатних ключів**, див. розділ 9).
- Кожна таблиця має **рівно один** Primary Key (хоча він може складатись з кількох стовпців — composite key).

```sql
CREATE TABLE Customers (
    CustomerId INT IDENTITY(1,1) PRIMARY KEY, -- сурогатний PK
    Email      NVARCHAR(255) NOT NULL
);
```

### 2.3. Foreign Key (зовнішній ключ, FK)

**Foreign Key** — це стовпець (або набір стовпців) в одній таблиці, що посилається на Primary Key (або Unique Key) в іншій (чи тій самій) таблиці. FK — механізм, яким СУБД забезпечує **референційну цілісність (referential integrity)**: неможливо вставити рядок, що посилається на неіснуючий батьківський запис, і (за замовчуванням) неможливо видалити батьківський запис, поки на нього є посилання.

```sql
CREATE TABLE Orders (
    OrderId    INT IDENTITY(1,1) PRIMARY KEY,
    CustomerId INT NOT NULL,
    OrderDate  DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(CustomerId)
);
```

Якщо спробувати вставити `Orders` рядок із `CustomerId = 9999`, якого немає в `Customers`, СУБД **відхилить** операцію — це і є референційна цілісність "з коробки", без єдиного рядка коду в застосунку.

### 2.4. Unique Key / Unique Constraint (унікальне обмеження)

**Unique constraint** гарантує унікальність значень стовпця, **не** роблячи цей стовпець головним ідентифікатором таблиці. На відміну від PK, unique-стовпець **може** приймати `NULL` (зазвичай одне `NULL`-значення дозволене, залежно від СУБД).

```sql
ALTER TABLE Customers
    ADD CONSTRAINT UQ_Customers_Email UNIQUE (Email);
```

Типовий сценарій: `CustomerId` — PK (сурогатний, використовується у зв'язках), а `Email` — unique-обмежений candidate key (використовується для логіну, але не для зв'язків з іншими таблицями).

### 2.5. Composite Key (складений ключ)

**Composite key** — ключ, що складається **з двох і більше стовпців разом**, коли жоден зі стовпців окремо не є унікальним, але їх комбінація — так.

Класичний приклад — таблиця-зв'язка `OrderItems` (описана детальніше в розділі 3):

```sql
CREATE TABLE OrderItems (
    OrderId   INT NOT NULL,
    ProductId INT NOT NULL,
    Quantity  INT NOT NULL CHECK (Quantity > 0),
    UnitPrice DECIMAL(10,2) NOT NULL,
    CONSTRAINT PK_OrderItems PRIMARY KEY (OrderId, ProductId), -- composite PK
    CONSTRAINT FK_OrderItems_Orders   FOREIGN KEY (OrderId)   REFERENCES Orders(OrderId),
    CONSTRAINT FK_OrderItems_Products FOREIGN KEY (ProductId) REFERENCES Products(ProductId)
);
```

Тут `OrderId` сам по собі не унікальний (в одному замовленні кілька товарів), `ProductId` сам по собі теж не унікальний (один товар зустрічається в багатьох замовленнях) — але пара `(OrderId, ProductId)` унікальна: одне замовлення не може містити один і той самий товар двічі окремими рядками.

### 2.6. Зведена схема з усіма типами ключів

```
┌───────────────────────────┐
│       Customers           │
├───────────────────────────┤
│ PK  CustomerId  (INT)     │
│ UQ  Email       (NVARCHAR)│  ← candidate key, unique, не PK
│     FullName    (NVARCHAR)│
│     Phone       (NVARCHAR)│
└───────────────────────────┘
            │ 1
            │
            │ N
┌───────────────────────────┐
│         Orders            │
├───────────────────────────┤
│ PK  OrderId     (INT)     │
│ FK  CustomerId  (INT)  ───┼───► Customers.CustomerId
│     OrderDate   (DATETIME)│
└───────────────────────────┘
            │ 1
            │
            │ N
┌─────────────────────────┐          ┌───────────────────────────┐
│       OrderItems        │          │        Products           │
├─────────────────────────┤          ├───────────────────────────┤
│ PK,FK  OrderId    (INT) ┼───────►  │ PK  ProductId   (INT)     │
│ PK,FK  ProductId  (INT) ┼─────────►│     Name        (NVARCHAR)│
│        Quantity   (INT) │          │     Price       (DECIMAL) │
│        UnitPrice  (DEC) │          │ FK  CategoryId  (INT)     │
└─────────────────────────┘          └────────────┬──────────────┘
                                                   │ N
                                                   │
                                                   │ 1
                                     ┌────────────────────────────┐
                                     │        Categories          │
                                     ├────────────────────────────┤
                                     │ PK  CategoryId  (INT)      │

```

Позначення: **PK** = Primary Key, **FK** = Foreign Key, **UQ** = Unique constraint, **PK,FK** = стовпець одночасно є частиною composite PK і одночасно FK (типова ситуація в junction-таблицях).

## 3. Зв'язки між таблицями: 1:1, 1:N, N:M

Зв'язки (relationships) описують, як рядки однієї таблиці співвідносяться з рядками іншої. Існує три базові кардинальності.

### 3.1. One-to-One (1:1)

Кожен рядок таблиці A відповідає **рівно одному** (або нулю) рядку таблиці B, і навпаки.

**Приклад:** `Employee` ↔ `EmployeeProfile`. Основна таблиця містить часто використовувані поля (ім'я, посада), а рідко потрібні "важкі" або чутливі дані (біографія, скан документів, банківські реквізити) виносяться в окрему таблицю — з міркувань продуктивності (не тягнути великі поля при кожному `SELECT * FROM Employee`) або безпеки (окремі права доступу).

```sql
CREATE TABLE Employees (
    EmployeeId INT IDENTITY PRIMARY KEY,
    FullName   NVARCHAR(200) NOT NULL,
    JobTitle   NVARCHAR(100)
);

CREATE TABLE EmployeeProfiles (
    EmployeeId INT PRIMARY KEY, -- одночасно FK і PK ⇒ гарантує 1:1
    Biography  NVARCHAR(MAX),
    BankIban   NVARCHAR(34),
    CONSTRAINT FK_EmployeeProfiles_Employees
        FOREIGN KEY (EmployeeId) REFERENCES Employees(EmployeeId)
);
```

Ключовий трюк 1:1: `EmployeeId` в `EmployeeProfiles` є **одночасно** первинним і зовнішнім ключем (не окремий autoincrement-стовпець). Саме це гарантує, що на одного `Employee` може існувати щонайбільше один `EmployeeProfile`.

```
Employees                    EmployeeProfiles
┌───────────────┐            ┌──────────────────┐
│ PK EmployeeId │──1─────1──►│ PK,FK EmployeeId │
│    FullName   │            │       Biography  │
│    JobTitle   │            │       BankIban   │
└───────────────┘            └──────────────────┘
```

### 3.2. One-to-Many (1:N)

Один рядок таблиці A може відповідати **багатьом** рядкам таблиці B, але кожен рядок B відповідає лише **одному** рядку A.

**Приклад:** `Customer` ↔ `Order`. Один клієнт робить багато замовлень, але кожне конкретне замовлення належить рівно одному клієнту.

Реалізується просто: FK-стовпець розміщується на стороні "N" (у `Orders`), без потреби в окремій таблиці-зв'язці:

```
Customers                Orders
┌───────────────┐        ┌──────────────────┐
│ PK CustomerId │──1───N─│ FK CustomerId    │
│    Email      │        │ PK OrderId       │
└───────────────┘        │    OrderDate     │
                         └──────────────────┘
```

### 3.3. Many-to-Many (N:M)

Багато рядків таблиці A можуть відповідати багатьом рядкам таблиці B, і навпаки.

**Приклад:** `Order` ↔ `Product`. Одне замовлення містить кілька товарів, і один і той самий товар зустрічається в багатьох замовленнях.

**Чому одного FK недостатньо для N:M?** FK-стовпець може зберігати лише **одне** значення посилання на рядок. Якби ми спробували покласти `ProductId` прямо в `Orders`, замовлення могло б містити лише один товар. А якби поклали `OrderId` в `Products`, товар міг би належати лише одному замовленню — що суперечить реальності (той самий товар купують у десятках замовлень). Тобто **на жодній зі сторін зв'язку не можна одним стовпцем виразити "багато"**.

Розв'язання — **junction table** (проміжна / асоціативна таблиця, також "bridge table"), яка перетворює один зв'язок N:M на **два** зв'язки 1:N:

```
Orders            OrderItems             Products
┌───────────┐    ┌──────────────────┐    ┌────────────┐
│PK OrderId │─1─N│PK,FK OrderId     │    │PK ProductId│
│           │    │PK,FK ProductId ──┼─N─1│            │
└───────────┘    │     Quantity     │    └────────────┘
                 │     UnitPrice    │
                 └──────────────────┘
```

`OrderItems` — це і є та junction-таблиця з розділу 2.5: композитний PK `(OrderId, ProductId)` одночасно є двома FK. Кожен рядок `OrderItems` — це "один товар в одному замовленні", і саме через накопичення таких рядків замовлення "стає" пов'язаним з багатьма товарами, а товар — з багатьма замовленнями.

Junction-таблиця також природне місце для **атрибутів самого зв'язку** — `Quantity` і `UnitPrice` не належать ні `Order`, ні `Product` окремо, вони описують саме факт "цей товар у цьому замовленні".

## 4. Нормалізація — покроковий розбір

**Нормалізація** — це процес структурування таблиць реляційної БД так, щоб зменшити (в ідеалі — усунути) надлишковість даних і **аномалії** оновлення/вставки/видалення. Розберемо на наскрізному прикладі: почнемо з "плаского" (flat) денормалізованого відображення замовлень, побачимо проблеми, а потім крок за кроком нормалізуємо.

### 4.0. Вихідна (денормалізована) таблиця

```
OrdersFlat
┌────────┬────────────┬───────────────┬───────────────┬──────────────────────┬───────────┬──────────┬────────────┐
│OrderId │CustomerName│CustomerPhone  │CustomerCity   │Products              │TotalPrice │ProductMgr│MgrEmail    │
├────────┼────────────┼───────────────┼───────────────┼──────────────────────┼───────────┼──────────┼────────────┤
│ 1      │Іван Петров │+380671112233  │Київ           │Клавіатура, Мишка     │ 1450      │Олена К.  │o.k@shop.ua │
│ 2      │Іван Петров │+380671112233  │Київ           │Монітор               │ 6200      │Ігор С.   │i.s@shop.ua │
│ 3      │Марія Ткач  │+380509998877  │Львів          │Клавіатура            │ 950       │Олена К.  │o.k@shop.ua │
└────────┴────────────┴───────────────┴───────────────┴──────────────────────┴───────────┴──────────┴────────────┘
```

Уже на цьому прикладі видно кілька проблем: клас товарів записаний одним рядком через кому, а дані про клієнта та менеджера продукту повторюються в кожному замовленні. Розберемо аномалії детально.

### Аномалії денормалізованої таблиці

| Тип аномалії | Приклад проблеми |
|---|---|
| **Insert-аномалія** | Щоб додати новий товар "Навушники", яким ще ніхто не купив, потрібно **вигадати фіктивне замовлення** — без `OrderId` товар просто нема куди вставити, бо товари і замовлення не розділені. |
| **Update-аномалія** | Якщо Іван Петров змінює номер телефону, потрібно оновити **обидва** рядки (1 і 2). Якщо оновити лише один — дані стають суперечливими: один і той самий клієнт має два різні телефони в БД. |
| **Delete-аномалія** | Якщо видалити замовлення №3 (єдине замовлення Марії Ткач), **зникає вся інформація про клієнтку Марію** — її ім'я, телефон, місто — хоча ми хотіли видалити лише замовлення, а не клієнта. |

Саме ці три класи проблем нормалізація і усуває.

### 4.1. Перша нормальна форма (1NF)

**Правило:** усі значення атрибутів мають бути **атомарними** (неподільними), і не повинно бути таблиць-у-таблиці чи повторюваних груп (repeating groups) в одному стовпці.

Порушення в нашому прикладі — стовпець `Products`, що містить `"Клавіатура, Мишка"` — список у одному текстовому полі. Це заважає: неможливо ефективно знайти "всі замовлення з Мишкою", неможливо порахувати кількість кожного товару, неможливо застосувати FK-обмеження до "одного з елементів рядка".

**Виправлення:** винести кожен товар замовлення в окремий рядок:

```
Orders1NF
┌────────┬────────────┬──────────────┬────────────┬───────────┬──────────┬───────────┬────────────┐
│OrderId │CustomerName│CustomerPhone │CustomerCity│Product    │Price     │ProductMgr │MgrEmail    │
├────────┼────────────┼──────────────┼────────────┼───────────┼──────────┼───────────┼────────────┤
│ 1      │Іван Петров │+380671112233 │Київ        │Клавіатура │ 450      │Олена К.   │o.k@shop.ua │
│ 1      │Іван Петров │+380671112233 │Київ        │Мишка      │ 1000     │Олена К.   │o.k@shop.ua │
│ 2      │Іван Петров │+380671112233 │Київ        │Монітор    │ 6200     │Ігор С.    │i.s@shop.ua │
│ 3      │Марія Ткач  │+380509998877 │Львів       │Клавіатура │ 950      │Олена К.   │o.k@shop.ua │
└────────┴────────────┴──────────────┴────────────┴───────────┴──────────┴───────────┴────────────┴
```

Тепер кожна комірка містить одне атомарне значення. Але зверніть увагу — тепер `OrderId` **сам по собі більше не унікальний** (використовується двічі для замовлення №1). Первинний ключ цієї таблиці тепер складений: `(OrderId, Product)`. Це підводить нас до наступної проблеми.

### 4.2. Друга нормальна форма (2NF)

**Правило:** таблиця вже в 1NF, і **кожен неключовий атрибут повністю залежить від усього складеного первинного ключа**, а не лише від його частини (немає **часткової залежності**, partial dependency). 2NF стосується лише таблиць із **композитним** первинним ключем — якщо PK складається з одного стовпця, 2NF автоматично виконується.

У `Orders1NF` композитний PK — `(OrderId, Product)`. Перевіримо залежності:

- `Price` залежить від **обох** частин ключа (ціна товару в конкретному замовленні) — ✅ ОК.
- `CustomerName`, `CustomerPhone`, `CustomerCity` залежать **тільки від `OrderId`** (клієнт визначається замовленням, а не товаром) — це **часткова залежність**, порушення 2NF.
- `ProductMgr`, `MgrEmail` залежать **тільки від `Product`** (менеджер відповідає за товар незалежно від замовлення) — теж часткова залежність.

**Виправлення:** розбити таблицю так, щоб атрибути, які залежать лише від частини ключа, переїхали у власні таблиці, ключем яких є саме ця частина:

```
Orders                          OrderItems                        Products
┌────────┬────────────┬───────┐┌────────┬───────────┬──────┐    ┌───────────┬──────────┬───────────┐
│OrderId │CustomerName│...    ││OrderId │Product     │Price│    │Product    │ProductMgr│MgrEmail   │
├────────┼────────────┼───────┤├────────┼───────────┼──────┤    ├───────────┼──────────┼───────────┤
│1       │Іван Петров │...    ││1       │Клавіатура  │450  │    │Клавіатура │Олена К.  │o.k@shop.ua│
│2       │Іван Петров │...    ││1       │Мишка       │1000 │    │Мишка      │Олена К.  │o.k@shop.ua│
│3       │Марія Ткач  │...    ││2       │Монітор     │6200 │    │Монітор    │Ігор С.   │i.s@shop.ua│
└────────┴────────────┴───────┘│3       │Клавіатура  │950  │    └───────────┴──────────┴───────────┘
                               └────────┴───────────┴──────┘
```

Тепер `Orders` (PK = `OrderId`), `OrderItems` (PK = `(OrderId, Product)`, залежить від обох), `Products` (PK = `Product`) — часткових залежностей більше немає.

### 4.3. Третя нормальна форма (3NF)

**Правило:** таблиця вже в 2NF, і **немає транзитивних залежностей** — неключові атрибути залежать **тільки** від первинного ключа, а не від інших неключових атрибутів ("the key, the whole key, and nothing but the key").

Подивимось на `Products`: `ProductMgr` і `MgrEmail` формально залежать від `Product` (PK), але насправді `MgrEmail` залежить від **`ProductMgr`**, а вже `ProductMgr` залежить від `Product`. Це і є **транзитивна залежність**: `Product → ProductMgr → MgrEmail`.

Проблема на практиці: якщо Олена К. змінить email, доведеться оновлювати його в **кожному** товарі, за який вона відповідає — знову update-аномалія, лише перенесена на менший масштаб.

**Виправлення:** винести менеджерів у власну таблицю:

```
Products                          ProductManagers
┌───────────┬──────────────┐    ┌──────────────┬────────────┐
│Product    │ProductMgrId  │───►│ProductMgrId  │MgrEmail    │
├───────────┼──────────────┤    ├──────────────┼────────────┤
│Клавіатура │1             │    │1             │o.k@shop.ua │
│Мишка      │1             │    │2             │i.s@shop.ua │
│Монітор    │2             │    └──────────────┴────────────┘
└───────────┴──────────────┘
```

Тепер `MgrEmail` зберігається **один раз** на менеджера, а не дублюється для кожного товару, за який він відповідає. Це вже практично та сама схема, що й в розділі 2 (`Products` → `Categories`, за аналогією).

### 4.4. Boyce-Codd нормальна форма (BCNF)

**Правило:** BCNF — це посилена версія 3NF. Формально: для кожної функціональної залежності `X → Y` у таблиці, `X` повинен бути **суперключем** (superkey) — тобто визначати весь рядок. 3NF робить виняток для деяких випадків, коли `Y` є частиною candidate key; BCNF такого винятку не робить.

Різниця проявляється рідко, зазвичай коли в таблиці є **кілька перекривних candidate keys**. Класичний приклад:

Таблиця `CourseAssignment` (репетитор навчає предмет; кожен репетитор викладає лише один предмет, але предмет можуть викладати кілька репетиторів):

```
CourseAssignment
┌──────────┬───────────┬────────┐
│ Student  │ Subject   │ Tutor  │
├──────────┼───────────┼────────┤
│ Оля      │ Математика│ Іван   │
│ Оля      │ Фізика    │ Петро  │
│ Дмитро   │ Математика│ Іван   │
└──────────┴───────────┴────────┘
```

Тут candidate keys — `(Student, Subject)` і `(Student, Tutor)` (обидва унікально визначають рядок). Але існує залежність `Tutor → Subject` (кожен репетитор веде лише один предмет) — а `Tutor` **не є суперключем** сам по собі. Формально таблиця вже в 3NF (бо `Subject` входить до складу candidate key `(Student, Subject)`), але **не** в BCNF, бо ліва частина залежності (`Tutor`) не суперключ.

Наслідок — та сама аномалія: якщо Іван почне викладати інший предмет, доведеться оновити **кожен** рядок, де він фігурує як `Tutor`.

**Виправлення (декомпозиція до BCNF):**

```
TutorSubject                    StudentTutor
┌────────┬──────────┐          ┌──────────┬────────┐
│ Tutor  │ Subject  │          │ Student  │ Tutor  │
├────────┼──────────┤          ├──────────┼────────┤
│ Іван   │Математика│          │ Оля      │ Іван   │
│ Петро  │Фізика    │          │ Оля      │ Петро  │
└────────┴──────────┘          │ Дмитро   │ Іван   │
                               └──────────┴────────┘
```

> ⚠️ BCNF — це компроміс: декомпозиція до BCNF іноді робить **неможливим** зберегти всі оригінальні функціональні залежності без додаткових обмежень (join dependency). На практиці більшість промислових схем зупиняються на 3NF — цього достатньо в переважній більшості випадків, а BCNF-порушення трапляються рідко і усвідомлено толеруються.

### 4.5. 4NF та 5NF — коротко, для повноти

Це рівні, про які senior-інженер повинен **знати про існування**, але на практиці застосовує вкрай рідко:

- **4NF (Fourth Normal Form)** усуває **багатозначні залежності (multi-valued dependencies)** — ситуацію, коли в одній таблиці незалежно одна від одної існують дві множинні характеристики сутності (наприклад, у співробітника є кілька мов програмування **і** кілька хобі, і якщо їх записати в одну таблицю прямим декартовим добутком рядків — виникає надлишковість, не пов'язана з функціональними залежностями). Рішення — розбити на дві окремі таблиці-зв'язки.
- **5NF (Fifth Normal Form, PJ/NF)** усуває **join-залежності (join dependencies)** — ситуації, коли таблицю можна безвтратно розкласти на три і більше менші таблиці, але не можна на дві. Зустрічається вкрай рідко, здебільшого в теоретичних прикладах (наприклад, зв'язок "постачальник постачає товар для проєкту", де не будь-яка пара з трьох комбінацій валідна).

На співбесідах достатньо **впізнати терміни** й пояснити суть однією фразою — глибока практична імплементація 4NF/5NF в реальних проєктах трапляється рідко.

### 4.6. Зведена таблиця аномалій "до" і "після"

| Аномалія | До нормалізації (`OrdersFlat`) | Після нормалізації (Customers/Orders/OrderItems/Products) |
|---|---|---|
| **Insert** | Не можна додати товар без фіктивного замовлення | ✅ Новий товар вставляється в `Products` незалежно від замовлень |
| **Update** | Зміна телефону клієнта вимагає оновити N рядків | ✅ Телефон зберігається один раз у `Customers`, оновлюється одним `UPDATE` |
| **Delete** | Видалення єдиного замовлення клієнта стирає дані про клієнта | ✅ Видалення `Order` не зачіпає рядок `Customer` |

## 5. Денормалізація — коли і навіщо порушувати правила

Нормалізація не безкоштовна: кожен додатковий рівень розбиття таблиць означає, що для отримання "повної картини" (наприклад, замовлення разом з іменем клієнта, назвами товарів і категорією) потрібно виконати **JOIN** кількох таблиць. JOIN — не безкоштовна операція: це додаткове навантаження на планувальник запитів, додаткові I/O-звернення, додаткові індексні пошуки.

**Денормалізація** — свідоме, контрольоване порушення правил нормальних форм заради продуктивності читання, зазвичай ціною:

- **Надлишковості (redundancy)** — той самий факт зберігається в кількох місцях.
- **Ризику неузгодженості (consistency risk)** — якщо забути оновити всі копії, дані розійдуться.
- **Додаткового місця на диску (storage cost)** — зазвичай незначний фактор порівняно з двома попередніми.

### Типові ситуації, де денормалізація — правильне senior-рішення

1. **Read-heavy звітні (reporting) таблиці.** Якщо звіт про продажі за місяць читають тисячі разів на день, а дані змінюються раз на добу (нічний ETL), є сенс матеріалізувати денормалізовану таблицю `MonthlySalesReport` замість того, щоб кожного разу перераховувати JOIN + GROUP BY на льоту.

2. **Кешовані обчислені агрегати.** Класичний приклад — зберігати `Customer.TotalOrders` або `Product.AverageRating` **прямо в таблиці**, а не рахувати `COUNT(*)` / `AVG(Rating)` при кожному запиті сторінки. На сторінці зі списком із 50 товарів рахувати `AVG` по таблиці відгуків (можливо, мільйони рядків) для кожного з 50 товарів — дорого; зберігати вже готове число — дешево читати, трохи дорожче й складніше підтримувати в актуальному стані (оновлювати при кожному новому відгуку, або періодичним фоновим job'ом).

3. **Star-schema / Data Warehouse дизайн.** У сховищах даних (data warehouses) для аналітичних навантажень (OLAP) свідомо використовують **денормалізовані fact- та dimension-таблиці** (наприклад, у `FactSales` можуть дублюватись `ProductCategoryName`, `CustomerCountry` тощо прямо в fact-таблиці або в широких dimension-таблицях), бо аналітичні запити оптимізовані під швидке читання великих обсягів, а не під транзакційну точність (OLTP-логіка тут не потрібна — дані вже "застигли" після ETL).

### Явний trade-off

| | Нормалізована схема | Денормалізована схема |
|---|---|---|
| Швидкість `SELECT` для складних вибірок | Повільніше (потрібні JOIN) | Швидше (дані вже "плоскі") |
| Швидкість/безпечність `INSERT`/`UPDATE` | Швидше і безпечніше (один факт — одне місце) | Повільніше/ризикованіше (треба оновити кілька копій) |
| Ризик неузгодженості даних | Низький | Є, потребує додаткової дисципліни (тригери, фонові job'и, event-driven оновлення) |
| Обсяг даних на диску | Менший | Більший |
| Складність підтримки коду | Простіша модель даних | Потрібна явна логіка синхронізації копій |

### Коли це правильний виклик, а коли — передчасна оптимізація

✅ **Правильний виклик:** ви **виміряли** реальне навантаження (наприклад, профайлером запитів або APM), побачили, що конкретний JOIN виконується мільйони разів на день і є вузьким місцем, і свідомо йдете на компроміс з чіткою стратегією підтримки актуальності (тригер, фонова задача, event sourcing, `SaveChanges`-хук в ORM).

❌ **Передчасна оптимізація:** денормалізація "про всяк випадок", ще до того, як з'явилося реальне навантаження чи виміряна проблема продуктивності. Це класичний антипатерн: ви платите ціну (ризик неузгодженості, складніший код) без доведеної вигоди. Правило: **спочатку нормалізуйте, потім денормалізуйте точково — там, де є конкретна, виміряна причина.**

## 6. Практичні приклади на SQL та C#

### Приклад 1 — DDL для нормалізованої e-commerce схеми

```sql
-- Категорії товарів (довідник, ієрархія не показана для простоти)
CREATE TABLE Categories (
    CategoryId   INT IDENTITY(1,1) PRIMARY KEY,       -- сурогатний PK
    Name         NVARCHAR(100)   NOT NULL,
    CONSTRAINT UQ_Categories_Name UNIQUE (Name)         -- назва категорії унікальна (candidate key)
);

-- Товари
CREATE TABLE Products (
    ProductId    INT IDENTITY(1,1) PRIMARY KEY,       -- сурогатний PK, не залежить від бізнес-даних
    Sku          NVARCHAR(50)    NOT NULL,             -- бізнес-ідентифікатор товару (артикул)
    Name         NVARCHAR(200)   NOT NULL,
    Price        DECIMAL(10,2)   NOT NULL CHECK (Price >= 0),
    CategoryId   INT             NOT NULL,
    AverageRating DECIMAL(3,2)   NULL,                  -- свідомо денормалізоване поле (розділ 5/7)
    CONSTRAINT UQ_Products_Sku UNIQUE (Sku),             -- SKU — унікальний, але не PK (може змінюватись рідко)
    CONSTRAINT FK_Products_Categories
        FOREIGN KEY (CategoryId) REFERENCES Categories(CategoryId)
);

-- Клієнти
CREATE TABLE Customers (
    CustomerId   INT IDENTITY(1,1) PRIMARY KEY,
    Email        NVARCHAR(255)   NOT NULL,
    FullName     NVARCHAR(200)   NOT NULL,
    Phone        NVARCHAR(20)    NULL,
    CONSTRAINT UQ_Customers_Email UNIQUE (Email)         -- email не може повторюватись у двох клієнтів
);

-- Замовлення (сторона "1" у зв'язку 1:N з Customers)
CREATE TABLE Orders (
    OrderId      INT IDENTITY(1,1) PRIMARY KEY,
    CustomerId   INT             NOT NULL,
    OrderDate    DATETIME2       NOT NULL DEFAULT SYSUTCDATETIME(),
    Status       NVARCHAR(20)    NOT NULL DEFAULT 'Pending',
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(CustomerId)
        ON DELETE NO ACTION -- замовлення з історією не можна видаляти каскадно разом з клієнтом
);

-- Junction-таблиця для N:M між Orders і Products
CREATE TABLE OrderItems (
    OrderId      INT             NOT NULL,
    ProductId    INT             NOT NULL,
    Quantity     INT             NOT NULL CHECK (Quantity > 0),
    UnitPrice    DECIMAL(10,2)   NOT NULL, -- фіксуємо ціну на момент замовлення (ціна товару може згодом змінитись)
    CONSTRAINT PK_OrderItems PRIMARY KEY (OrderId, ProductId), -- composite PK
    CONSTRAINT FK_OrderItems_Orders
        FOREIGN KEY (OrderId) REFERENCES Orders(OrderId)
        ON DELETE CASCADE, -- видалення замовлення забирає й його позиції
    CONSTRAINT FK_OrderItems_Products
        FOREIGN KEY (ProductId) REFERENCES Products(ProductId)
        ON DELETE NO ACTION -- товар не можна видалити, якщо він фігурує в чиїхось замовленнях
);
```

**Коментар до вибору обмежень:**
- `CustomerId`, `OrderId`, `ProductId`, `CategoryId` — сурогатні PK (`IDENTITY`), не прив'язані до змінних бізнес-даних.
- `Email`, `Sku`, `Categories.Name` — candidate keys, захищені `UNIQUE`, але не є PK (щоб зміна email чи SKU не ламала посилання з інших таблиць).
- `OrderItems` фіксує `UnitPrice` окремо від `Products.Price` — це навмисне, невелике "денормалізоване" рішення: ціна товару в момент покупки має **зберегтись назавжди**, навіть якщо `Products.Price` згодом зміниться.
- `ON DELETE CASCADE` на `OrderItems → Orders` логічний (позиції належать замовленню), а `ON DELETE NO ACTION` на `Orders → Customers` та `OrderItems → Products` — свідомий захист від випадкового каскадного знищення історичних даних.

### Приклад 2 — та сама предметна область ДО нормалізації (демонстрація update-аномалії)

```sql
CREATE TABLE OrdersFlat (
    OrderId       INT,
    CustomerName  NVARCHAR(200),
    CustomerPhone NVARCHAR(20),
    ProductName   NVARCHAR(200),
    Quantity      INT,
    UnitPrice     DECIMAL(10,2)
);

INSERT INTO OrdersFlat VALUES
    (1, N'Іван Петров', N'+380671112233', N'Клавіатура', 1, 450),
    (2, N'Іван Петров', N'+380671112233', N'Монітор',    1, 6200),
    (3, N'Марія Ткач',  N'+380509998877', N'Клавіатура', 2, 450);
```

Тепер відтворимо реальний баг. Клієнт Іван Петров дзвонить у підтримку і повідомляє новий номер телефону. Оператор оновлює **лише те замовлення, яке відкрите на екрані** (замовлення №1):

```sql
UPDATE OrdersFlat
SET CustomerPhone = N'+380991234567'
WHERE OrderId = 1;
```

Перевіримо стан таблиці:

```sql
SELECT OrderId, CustomerName, CustomerPhone FROM OrdersFlat WHERE CustomerName = N'Іван Петров';
```

```
OrderId | CustomerName | CustomerPhone
--------+---------------+------------------
1       | Іван Петров   | +380991234567   <- новий номер
2       | Іван Петров   | +380671112233   <- старий номер!! (не оновили)
```

**Ось конкретний баг, який спричиняє денормалізація:** один і той самий клієнт тепер має **два різні номери телефону** в базі, залежно від того, яке замовлення відкрити. Немає жодного способу дізнатись, який з них "правильний", не питаючи клієнта ще раз. У нормалізованій схемі (Приклад 1) телефон зберігається **один раз** у `Customers.Phone`, тому `UPDATE Customers SET Phone = ... WHERE CustomerId = ...` миттєво і безпечно оновлює його для **всіх** замовлень клієнта одночасно — фізично неможливо отримати суперечність.

### Приклад 3 — EF Core: Fluent API для нормалізованої схеми

```csharp
using Microsoft.EntityFrameworkCore;

public class Category
{
    public int CategoryId { get; set; }
    public string Name { get; set; } = null!;
    public List<Product> Products { get; set; } = new();
}

public class Product
{
    public int ProductId { get; set; }
    public string Sku { get; set; } = null!;
    public string Name { get; set; } = null!;
    public decimal Price { get; set; }
    public decimal? AverageRating { get; set; } // денормалізований кеш (розділ 5)

    public int CategoryId { get; set; }
    public Category Category { get; set; } = null!;

    public List<OrderItem> OrderItems { get; set; } = new();
}

public class Customer
{
    public int CustomerId { get; set; }
    public string Email { get; set; } = null!;
    public string FullName { get; set; } = null!;
    public string? Phone { get; set; }

    public List<Order> Orders { get; set; } = new();
}

public class Order
{
    public int OrderId { get; set; }
    public DateTime OrderDate { get; set; }
    public string Status { get; set; } = "Pending";

    public int CustomerId { get; set; }
    public Customer Customer { get; set; } = null!;

    public List<OrderItem> Items { get; set; } = new();
}

// Клас-зв'язка для N:M (composite key моделюється явно)
public class OrderItem
{
    public int OrderId { get; set; }
    public Order Order { get; set; } = null!;

    public int ProductId { get; set; }
    public Product Product { get; set; } = null!;

    public int Quantity { get; set; }
    public decimal UnitPrice { get; set; }
}

public class ShopDbContext : DbContext
{
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Product> Products => Set<Product>();
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();
    public DbSet<OrderItem> OrderItems => Set<OrderItem>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // ---- Category ----
        modelBuilder.Entity<Category>(e =>
        {
            e.HasKey(c => c.CategoryId);
            e.HasIndex(c => c.Name).IsUnique(); // candidate key, не PK
        });

        // ---- Product ----
        modelBuilder.Entity<Product>(e =>
        {
            e.HasKey(p => p.ProductId);
            e.HasIndex(p => p.Sku).IsUnique();
            e.Property(p => p.Price).HasColumnType("decimal(10,2)");

            e.HasOne(p => p.Category)          // 1:N Category -> Products
             .WithMany(c => c.Products)
             .HasForeignKey(p => p.CategoryId)
             .OnDelete(DeleteBehavior.Restrict);
        });

        // ---- Customer ----
        modelBuilder.Entity<Customer>(e =>
        {
            e.HasKey(c => c.CustomerId);
            e.HasIndex(c => c.Email).IsUnique();
        });

        // ---- Order ----
        modelBuilder.Entity<Order>(e =>
        {
            e.HasKey(o => o.OrderId);

            e.HasOne(o => o.Customer)          // 1:N Customer -> Orders
             .WithMany(c => c.Orders)
             .HasForeignKey(o => o.CustomerId)
             .OnDelete(DeleteBehavior.Restrict);
        });

        // ---- OrderItem (junction-таблиця для N:M Order <-> Product) ----
        modelBuilder.Entity<OrderItem>(e =>
        {
            e.HasKey(oi => new { oi.OrderId, oi.ProductId }); // composite PK

            e.HasOne(oi => oi.Order)
             .WithMany(o => o.Items)
             .HasForeignKey(oi => oi.OrderId)
             .OnDelete(DeleteBehavior.Cascade);

            e.HasOne(oi => oi.Product)
             .WithMany(p => p.OrderItems)
             .HasForeignKey(oi => oi.ProductId)
             .OnDelete(DeleteBehavior.Restrict);

            e.Property(oi => oi.UnitPrice).HasColumnType("decimal(10,2)");
        });
    }
}
```

Кожен елемент Fluent API безпосередньо відображає реляційну концепцію: `HasKey` → Primary/Composite Key, `HasIndex(...).IsUnique()` → Unique constraint, `HasForeignKey` + `HasOne/WithMany` → Foreign Key і кардинальність 1:N, а пара `HasOne/WithMany` "в обидва боки" через проміжну сутність `OrderItem` → N:M.

### Приклад 4 — ADO.NET: транзакційна вставка та JOIN-запит

```csharp
using System;
using System.Data;
using Microsoft.Data.SqlClient;

class Program
{
    static void Main()
    {
        const string connectionString = "Server=localhost;Database=ShopDb;Trusted_Connection=True;TrustServerCertificate=True;";

        using var connection = new SqlConnection(connectionString);
        connection.Open();

        using SqlTransaction transaction = connection.BeginTransaction();

        try
        {
            // 1. Вставляємо замовлення і одразу отримуємо згенерований OrderId
            int orderId;
            using (var cmd = new SqlCommand(
                @"INSERT INTO Orders (CustomerId, OrderDate, Status)
                  OUTPUT INSERTED.OrderId
                  VALUES (@CustomerId, SYSUTCDATETIME(), 'Pending');",
                connection, transaction))
            {
                cmd.Parameters.AddWithValue("@CustomerId", 1);
                orderId = (int)cmd.ExecuteScalar();
            }

            // 2. Вставляємо позиції замовлення (junction-таблиця)
            var items = new (int ProductId, int Quantity, decimal UnitPrice)[]
            {
                (101, 1, 450m),   // Клавіатура
                (102, 1, 1000m),  // Мишка
            };

            foreach (var item in items)
            {
                using var cmd = new SqlCommand(
                    @"INSERT INTO OrderItems (OrderId, ProductId, Quantity, UnitPrice)
                      VALUES (@OrderId, @ProductId, @Quantity, @UnitPrice);",
                    connection, transaction);

                cmd.Parameters.AddWithValue("@OrderId", orderId);
                cmd.Parameters.AddWithValue("@ProductId", item.ProductId);
                cmd.Parameters.AddWithValue("@Quantity", item.Quantity);
                cmd.Parameters.AddWithValue("@UnitPrice", item.UnitPrice);
                cmd.ExecuteNonQuery();
            }

            transaction.Commit(); // атомарно: або все замовлення записується, або нічого
            Console.WriteLine($"Замовлення #{orderId} успішно створено.");
        }
        catch (Exception ex)
        {
            transaction.Rollback();
            Console.WriteLine($"Помилка, транзакцію відкочено: {ex.Message}");
            return;
        }

        // 3. Читаємо замовлення назад через JOIN трьох таблиць
        using var selectCmd = new SqlCommand(
            @"SELECT o.OrderId, c.FullName, p.Name AS ProductName, oi.Quantity, oi.UnitPrice
              FROM Orders o
              JOIN Customers c   ON c.CustomerId = o.CustomerId
              JOIN OrderItems oi ON oi.OrderId   = o.OrderId
              JOIN Products p    ON p.ProductId  = oi.ProductId
              WHERE o.CustomerId = @CustomerId
              ORDER BY o.OrderId;",
            connection);
        selectCmd.Parameters.AddWithValue("@CustomerId", 1);

        using var reader = selectCmd.ExecuteReader();
        while (reader.Read())
        {
            Console.WriteLine(
                $"Замовлення #{reader["OrderId"]} | {reader["FullName"]} | " +
                $"{reader["ProductName"]} x{reader["Quantity"]} = {reader["UnitPrice"]} грн");
        }
    }
}
```

**Приклад виводу в консолі:**

```
Замовлення #7 успішно створено.
Замовлення #7 | Іван Петров | Клавіатура x1 = 450 грн
Замовлення #7 | Іван Петров | Мишка x1 = 1000 грн
```

Транзакція гарантує, що якщо вставка другої позиції (`OrderItems`) провалиться (наприклад, через порушення FK, якщо `ProductId` не існує), відкотиться **і** вставка самого `Order` — база даних ніколи не залишиться в проміжному, неконсистентному стані (замовлення без жодної позиції).

## 7. Реальний сценарій: проєктування схеми великого інтернет-магазину

Уявімо, що вас, як senior-інженера, попросили спроєктувати схему БД для великого маркетплейсу: категорії товарів (з підкатегоріями), товари з варіантами (розмір/колір), замовлення, клієнти, відгуки, теги товарів. Розберемо хід міркувань.

### 7.1. Категорії — самопосилання (self-referencing) 1:N

Категорії формують дерево (`Електроніка` → `Ноутбуки` → `Ігрові ноутбуки`). Це моделюється однією таблицею із FK на саму себе:

```sql
CREATE TABLE Categories (
    CategoryId       INT IDENTITY PRIMARY KEY,
    Name             NVARCHAR(100) NOT NULL,
    ParentCategoryId INT NULL,
    CONSTRAINT FK_Categories_Parent
        FOREIGN KEY (ParentCategoryId) REFERENCES Categories(CategoryId)
);
```

`ParentCategoryId IS NULL` означає кореневу категорію. Це 1:N зв'язок, де "1" і "N" — рядки **тієї самої** таблиці.

### 7.2. Товари з варіантами — окрема таблиця `ProductVariants`

Товар "Футболка" сам по собі не продається — продається конкретна комбінація "Футболка, розмір M, колір синій", кожна зі своєю ціною, залишком на складі та SKU. Тому `Product` (загальний опис, назва, бренд, категорія) відокремлюється від `ProductVariant` (1:N — один товар має багато варіантів):

```sql
CREATE TABLE ProductVariants (
    VariantId  INT IDENTITY PRIMARY KEY,
    ProductId  INT NOT NULL,
    Size       NVARCHAR(20) NULL,
    Color      NVARCHAR(30) NULL,
    Sku        NVARCHAR(50) NOT NULL,
    StockQty   INT NOT NULL DEFAULT 0,
    Price      DECIMAL(10,2) NOT NULL,
    CONSTRAINT UQ_ProductVariants_Sku UNIQUE (Sku),
    CONSTRAINT FK_ProductVariants_Products
        FOREIGN KEY (ProductId) REFERENCES Products(ProductId)
);
```

`OrderItems` тоді посилається саме на `VariantId`, а не на `ProductId` напряму — бо саме конкретний варіант замовляють і саме для нього списують складський залишок.

### 7.3. Теги товарів — класичний N:M з junction-таблицею

Один товар може мати кілька тегів (`"розпродаж"`, `"новинка"`, `"еко"`), і кожен тег застосовується до багатьох товарів — типовий N:M, як і `Orders`↔`Products` в розділі 3:

```sql
CREATE TABLE Tags (
    TagId INT IDENTITY PRIMARY KEY,
    Name  NVARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE ProductTags (
    ProductId INT NOT NULL,
    TagId     INT NOT NULL,
    CONSTRAINT PK_ProductTags PRIMARY KEY (ProductId, TagId),
    CONSTRAINT FK_ProductTags_Products FOREIGN KEY (ProductId) REFERENCES Products(ProductId),
    CONSTRAINT FK_ProductTags_Tags     FOREIGN KEY (TagId)     REFERENCES Tags(TagId)
);
```

### 7.4. Де денормалізація виправдана: `Product.AverageRating`

Сторінка листингу товарів показує 40-60 товарів одночасно, кожен зі своїм середнім рейтингом. Якщо рахувати `AVG(Rating)` з таблиці `Reviews` (мільйони рядків для популярного магазину) **на кожен запит сторінки**, це дорого і повільно масштабується.

Рішення senior-рівня: додати `Products.AverageRating` (і, можливо, `Products.ReviewsCount`) як **кешовані, обчислені** поля:

```sql
ALTER TABLE Products ADD AverageRating DECIMAL(3,2) NULL;
ALTER TABLE Products ADD ReviewsCount  INT NOT NULL DEFAULT 0;
```

Оновлення відбувається **не** при кожному читанні, а при **записі** нового відгуку — або одразу (тригер / застосунок оновлює агрегат у тій же транзакції), або фоновою задачею з невеликою затримкою (eventual consistency прийнятна для рейтингу — секунда затримки не критична для бізнесу):

```sql
UPDATE Products
SET AverageRating = (SELECT AVG(CAST(Rating AS DECIMAL(3,2))) FROM Reviews WHERE ProductId = @ProductId),
    ReviewsCount   = (SELECT COUNT(*) FROM Reviews WHERE ProductId = @ProductId)
WHERE ProductId = @ProductId;
```

Це свідоме, точкове порушення 3NF (`AverageRating` технічно транзитивно залежить від рядків іншої таблиці) заради відчутного виграшу в продуктивності найгарячішого (read-heavy) шляху застосунку.

### 7.5. Де нормалізація критична і без винятків: фінансові/замовлення дані

`OrderItems.UnitPrice`, `Orders.Status`, історія платежів — тут **жодних компромісів**. Причина: якщо ціна товару в замовленні залежить від того, "яку копію ми випадково прочитали", це не просто незручність (як застарілий рейтинг), а **юридична та фінансова проблема** — розбіжність у сумі до сплати, суперечки з клієнтами, помилки в бухгалтерській звітності. Тому:

- `Orders`, `OrderItems`, `Payments` тримаються в строгій 3NF (мінімум) з повним набором FK-обмежень.
- Ціна товару **фіксується** в момент замовлення (`OrderItems.UnitPrice`), а не обчислюється "на льоту" з поточного `Products.Price` — це не порушення нормалізації, а моделювання **історичного факту**, який має власне право на існування окремо від поточного стану товару.
- Будь-яка денормалізація тут (наприклад, кешування `Order.TotalAmount`) супроводжується **строгими транзакційними гарантіями** оновлення (той самий `UPDATE`, що змінює `OrderItems`, у тій самій транзакції перераховує `Order.TotalAmount`).

### Підсумок ходу міркувань

| Зв'язок / поле | Тип рішення | Обґрунтування |
|---|---|---|
| `Categories` (дерево) | Self-referencing 1:N | Природна ієрархічна структура |
| `Product` ↔ `ProductVariant` | 1:N | Варіант — самостійна одиниця продажу зі своєю ціною/залишком |
| `Product` ↔ `Tag` | N:M через `ProductTags` | Класичний junction-патерн |
| `Product.AverageRating` | Денормалізація (кеш) | Read-heavy сторінка, точність до секунди не критична |
| `OrderItems.UnitPrice` | Строга нормалізація + фіксація історичного факту | Фінансові дані не терплять анomалій чи перерахунку заднім числом |

## 8. Порівняльна таблиця: рівні нормалізації

| Форма | Правило | Що запобігає | Приклад порушення |
|---|---|---|---|
| **1NF** | Усі значення атомарні, немає повторюваних груп/списків в одному стовпці | Неможливість фільтрувати/індексувати окремі елементи "списку в одній комірці" | Стовпець `Products = "Клавіатура, Мишка"` |
| **2NF** | 1NF + немає часткової залежності неключових атрибутів від частини composite PK | Дублювання атрибутів, що стосуються лише частини складеного ключа | `CustomerName` залежить лише від `OrderId`, а не від повного `(OrderId, Product)` |
| **3NF** | 2NF + немає транзитивної залежності (неключовий атрибут залежить від іншого неключового атрибута) | Дублювання даних, "прив'язаних" не до PK, а до іншого поля таблиці | `MgrEmail` залежить від `ProductMgr`, а не напряму від `Product` |
| **BCNF** | Для кожної залежності `X → Y`, `X` — суперключ | Аномалії у таблицях із кількома перекривними candidate keys | `Tutor → Subject`, але `Tutor` не суперключ у `(Student, Subject, Tutor)` |
| **4NF** | Немає незалежних багатозначних залежностей (multi-valued dependencies) в одній таблиці | Декартів добуток двох незалежних множинних характеристик сутності | Одна таблиця одночасно зберігає "мови програмування" і "хобі" співробітника |

## 9. Поширені помилки

### Помилка 1 — надмірна нормалізація "заради нормалізації"

Розбиття даних настільки дрібно, що для найпростішого читання потрібен JOIN 7-8 таблиць, хоча в реальному використанні ці дані **завжди** читаються разом і **майже ніколи** не оновлюються окремо.

❌ **Погано:**
```
Address → City → Region → Country → Continent  (окрема таблиця для кожного рівня, навіть Continent)
```
Щоб просто показати "місто, країна" на сторінці замовлення, потрібен JOIN 5 таблиць, хоча континент і навіть регіон практично ніколи не використовуються самостійно і не змінюються.

✅ **Добре:**
```sql
CREATE TABLE Addresses (
    AddressId INT PRIMARY KEY,
    City      NVARCHAR(100),
    Region    NVARCHAR(100),
    Country   NVARCHAR(100)
);
```
Тримати `City`/`Region`/`Country` як прості текстові стовпці в одній таблиці — цілком прийнятний, свідомий вибір, якщо ці дані не потребують окремого управління (наприклад, довідника країн зі своїми атрибутами) чи власних FK-звʼязків з іншими сутностями. **Senior-судження**: нормалізувати варто там, де є реальна повторюваність і реальна потреба в незалежному оновленні — не "про всяк випадок".

### Помилка 2 — відсутність FK-обмежень, покладання лише на код застосунку

❌ **Погано:**
```sql
CREATE TABLE Orders (
    OrderId    INT PRIMARY KEY,
    CustomerId INT -- немає FOREIGN KEY! цілісність "гарантується" лише кодом C#
);
```
Якщо хоч один шлях запису в цю таблицю (ручний скрипт, міграція даних, інший сервіс, помилка в коді) не пройде через "правильний" рівень застосунку, з'являються **orphaned rows** — замовлення, що посилаються на неіснуючих клієнтів. Такі рядки згодом ламають звіти, JOIN-и повертають менше рядків, ніж очікується (INNER JOIN просто "губить" сирітські записи), а налагодження стає болючим постфактум.

✅ **Добре:**
```sql
CREATE TABLE Orders (
    OrderId    INT PRIMARY KEY,
    CustomerId INT NOT NULL,
    CONSTRAINT FK_Orders_Customers FOREIGN KEY (CustomerId) REFERENCES Customers(CustomerId)
);
```
БД сама відхилить некоректний запис незалежно від того, звідки і як він надійшов — це один з головних аргументів "за" реляційну модель (розділ 1).

### Помилка 3 — природний ключ (natural key) замість сурогатного (surrogate key) як PK

❌ **Погано:**
```sql
CREATE TABLE Customers (
    Email NVARCHAR(255) PRIMARY KEY, -- природний ключ як PK
    FullName NVARCHAR(200)
);
```
Проблема виникає, коли клієнт **змінює email** (а це трапляється — зміна домену компанії, перехід на інший поштовий сервіс). Оскільки `Email` — PK, на нього посилаються десятки FK в інших таблицях (`Orders.CustomerEmail`, `Reviews.CustomerEmail` тощо). Зміна email вимагає **каскадного оновлення** значення PK у всіх залежних таблицях одночасно — операція дорога, ризикована, а в деяких СУБД/конфігураціях взагалі заборонена або вимагає тимчасового вимкнення FK-перевірок.

✅ **Добре:**
```sql
CREATE TABLE Customers (
    CustomerId INT IDENTITY PRIMARY KEY, -- сурогатний ключ, ніколи не змінюється
    Email      NVARCHAR(255) NOT NULL UNIQUE, -- бізнес-унікальність зберігається окремо
    FullName   NVARCHAR(200)
);
```
`CustomerId` ніколи не залежить від бізнес-даних клієнта і тому ніколи не потребує зміни. Email захищений `UNIQUE`-обмеженням (бізнес-правило "email унікальний" виконується), але зміна email — це просто `UPDATE` одного значення в одному рядку однієї таблиці, без каскадних наслідків для FK в інших таблицях.

### Помилка 4 (додатково) — ігнорування типів даних і `NULL`-семантики в ключах

❌ **Погано:** зберігати FK як `NVARCHAR`, коли на іншому кінці — `INT` (порівняння рядків повільніше за числа, помилки на кшталт `'1'` vs `'01'`), або дозволяти `NULL` в composite PK-стовпцях, забуваючи, що семантика "невідомого" ключа зазвичай непередбачувана.

✅ **Добре:** узгоджені типи даних по обидва боки FK-зв'язку, `NOT NULL` на всіх стовпцях, що входять до PK (вимога стандарту SQL — PK не може містити `NULL`).

## 10. Питання для співбесіди за рівнями

### Junior

**1. Що таке первинний ключ (Primary Key)?**
Стовпець (або набір стовпців), що однозначно ідентифікує кожен рядок таблиці, не може бути `NULL` і не повторюється в жодному іншому рядку.

**2. Чим первинний ключ відрізняється від унікального обмеження (Unique Constraint)?**
Обидва гарантують унікальність, але таблиця може мати лише **один** Primary Key, тоді як `UNIQUE`-обмежень може бути декілька. Крім того, PK не допускає `NULL`, а `UNIQUE` зазвичай допускає одне `NULL`-значення.

**3. Що таке зовнішній ключ (Foreign Key) і навіщо він потрібен?**
Це стовпець, який посилається на первинний ключ іншої таблиці. Він потрібен, щоб СУБД сама підтримувала референційну цілісність — не дозволяла вставити запис, що посилається на неіснуючий рядок, і захищала від "сирітських" записів.

**4. Що таке 1NF простими словами?**
Кожна комірка таблиці повинна містити одне неподільне значення — не список, не кілька значень через кому, не вкладену структуру.

**5. Чим відрізняється рядок (row) від стовпця (column) у реляційній таблиці?**
Стовпець — це визначена характеристика (атрибут) усіх записів таблиці (наприклад, `Email`); рядок — конкретний окремий запис зі значеннями для кожного стовпця.

**6. Що таке composite key?**
Первинний (або унікальний) ключ, що складається з двох і більше стовпців, комбінація яких унікальна, хоча жоден зі стовпців окремо унікальним не є.

**7. Навіщо потрібна нормалізація найпростішими словами?**
Щоб кожен факт зберігався в базі даних один раз, а не дублювався — це запобігає ситуаціям, коли ту саму інформацію потрібно оновлювати в кількох місцях одночасно.

### Middle

**1. Поясни різницю між 2NF і 3NF.**
2NF усуває **часткову** залежність — коли неключовий атрибут залежить лише від **частини** складеного первинного ключа. 3NF йде далі й усуває **транзитивну** залежність — коли неключовий атрибут залежить не від PK напряму, а від іншого неключового атрибута. Тобто 2NF стосується виключно таблиць із composite PK, а 3NF актуальна для будь-якої таблиці незалежно від структури ключа.

**2. Навіщо потрібна junction-таблиця для зв'язку many-to-many?**
Тому що звичайний FK-стовпець може зберігати лише одне посилання. Якщо покласти FK на "багато" сторони одного зі зв'язків, ми втратимо можливість виразити "багато" з іншого боку. Junction-таблиця розкладає один N:M зв'язок на два зв'язки 1:N, де кожен рядок junction-таблиці представляє окрему пару "сутність A + сутність B", і, за потреби, зберігає власні атрибути самого зв'язку (наприклад, `Quantity`, `UnitPrice`).

**3. Коли варто денормалізувати схему?**
Коли є виміряна, реальна проблема продуктивності читання (не гіпотетична), зазвичай на read-heavy шляхах — звітність, кешовані агрегати (рейтинги, лічильники), аналітичні star-схеми. Денормалізація завжди супроводжується явною стратегією підтримки узгодженості копій даних (тригер, транзакційне оновлення, фонова синхронізація) — інакше це просто джерело майбутніх багів.

**4. Чим сурогатний ключ (surrogate key) відрізняється від природного (natural key)?**
Природний ключ — це бізнес-атрибут, що вже існує в предметній області (email, номер паспорта, SKU) і теоретично унікально ідентифікує сутність. Сурогатний ключ — штучно згенероване значення (`IDENTITY`, `GUID`), що не несе бізнес-змісту і **ніколи** не потребує зміни. Природні ключі ризиковані як PK, бо якщо бізнес-значення колись зміниться, доведеться каскадно оновлювати всі FK, що на нього посилаються.

**5. Що таке референційна цілісність (referential integrity) і як вона забезпечується?**
Це гарантія, що всі зовнішні ключі посилаються на реально існуючі рядки в батьківських таблицях. Забезпечується `FOREIGN KEY`-обмеженнями на рівні СУБД, які автоматично відхиляють вставку "сирітського" запису і контролюють поведінку при видаленні батьківського рядка (`CASCADE`, `RESTRICT`, `SET NULL` тощо).

**6. Що таке транзитивна залежність і чим вона небезпечна?**
Ситуація, коли неключовий атрибут A залежить не напряму від PK, а через інший неключовий атрибут B (`PK → B → A`). Небезпечна тим, що той самий факт (`A` для конкретного значення `B`) дублюється в кожному рядку, де зустрічається це значення `B`, що призводить до update-аномалій — потрібно оновлювати кілька рядків замість одного.

**7. Чи можна мати кілька зовнішніх ключів в одній таблиці?**
Так, таблиця може мати скільки завгодно FK-стовпців, кожен з яких посилається на свою (або одну й ту саму) батьківську таблицю — типовий приклад: junction-таблиця з двома FK.

### Senior

**1. Спроєктуй схему для великого маркетплейсу з товарами, варіантами, категоріями і тегами — поясни свої рішення.**
Категорії моделюються self-referencing 1:N зв'язком (`ParentCategoryId → CategoryId`) для підтримки довільної глибини дерева. Товар (`Product`, загальний опис) відокремлюється від `ProductVariant` (конкретна комбінація розмір/колір зі своєю ціною і залишком), бо саме варіант — одиниця продажу і складського обліку. Теги — класичний N:M через junction-таблицю `ProductTags`, оскільки один товар має кілька тегів і навпаки. Ключове рішення: `OrderItems` посилається саме на `VariantId`, а не на `ProductId`, і фіксує ціну на момент замовлення окремим полем — це не порушення нормалізації, а моделювання історичного факту, що має власне право на існування незалежно від поточного стану товару.

**2. Коли ти свідомо порушив би 3NF і чому?**
Найтиповіший випадок — кешування обчислюваних агрегатів на read-heavy шляхах, наприклад `Product.AverageRating` замість `AVG()` по мільйонах рядків `Reviews` при кожному завантаженні сторінки листингу. Це технічно транзитивна залежність (рейтинг залежить від чужої таблиці), але виправдана, якщо (а) шлях читання значно "гарячіший" за шлях запису, (б) прийнятна невелика затримка узгодженості (eventual consistency), і (в) є чіткий механізм оновлення кешованого значення при кожному новому відгуку. Я б **не** порушував 3NF для фінансових/транзакційних таблиць (замовлення, платежі) — там ціна помилки (юридичні, бухгалтерські наслідки) переважує будь-який виграш у швидкості.

**3. Як нормалізація впливає на продуктивність запитів при рості масштабу?**
Нормалізація мінімізує обсяг даних і гарантує коректність запису (менше даних для оновлення, менше блокувань під час `UPDATE`), але кожен додатковий рівень розбиття означає додатковий JOIN при читанні. При невеликому обсязі даних це непомітно — оптимізатор і індекси легко тримають кілька JOIN-ів у пам'яті. При рості масштабу (мільйони/мільярди рядків, високий QPS) JOIN-и, особливо через кілька таблиць з великою кардинальністю, стають вузьким місцем, і саме тоді з'являється сенс у точковій денормалізації, матеріалізованих в'юхах (materialized views), кешуванні на рівні застосунку або читанні з реплік, оптимізованих під конкретний звітний запит.

**4. Що таке BCNF і чим він відрізняється від 3NF на прикладі?**
BCNF вимагає, щоб для кожної функціональної залежності `X → Y` ліва частина `X` була суперключем — тобто визначала весь рядок таблиці. 3NF робить виняток: залежність допустима, навіть якщо `X` не суперключ, за умови що `Y` є частиною якогось candidate key. Різниця проявляється в таблицях з кількома перекривними candidate keys — класичний приклад: `(Student, Subject, Tutor)`, де кожен репетитор (`Tutor`) веде лише один предмет (`Tutor → Subject`), але `Tutor` сам по собі не candidate key. Таблиця формально в 3NF (бо `Subject` входить у candidate key `(Student, Subject)`), але порушує BCNF, і потребує декомпозиції на `TutorSubject` і `StudentTutor`, щоб усунути прихований дублікат `Tutor → Subject`.

**5. Опиши компроміс між нормалізацією та продуктивністю в контексті read-heavy vs write-heavy навантаження.**
У write-heavy сценаріях (banking-транзакції, бронювання, черги замовлень) нормалізація майже завжди виграє: кожен факт зберігається один раз, оновлення атомарні й дешеві, немає ризику розсинхронізації копій під конкурентним записом. У read-heavy сценаріях (каталог товарів, звітність, дашборди аналітики) вартість JOIN-ів при кожному читанні може переважити вигоду від чистоти моделі, і тоді виправдана точкова денормалізація або окремий read-model (наприклад, за принципом CQRS — окрема, денормалізована модель читання, синхронізована подіями з нормалізованою моделлю запису). Головне правило senior-рівня: рішення про денормалізацію приймається **після** вимірювання реального навантаження на конкретному шляху, а не як загальний архітектурний принцип "з самого початку".

**6. Як ти пояснив би джуну, чому не варто одразу денормалізовувати "для швидкості"?**
Тому що денормалізація — це завжди угода: ти купуєш швидкість читання ціною ризику неузгодженості і додаткової складності коду підтримки копій. Без виміряної проблеми ця угода невигідна — ти платиш складністю за вигоду, якої, можливо, ніколи не знадобиться, а в майбутньому ця "зайва" денормалізація стане джерелом важко відтворюваних багів (розбіжність кешованого значення з реальним станом). Правильний порядок: спроєктувати нормалізовану схему, виміряти реальні вузькі місця під навантаженням, і денормалізувати точково, там, де це дійсно дає вимірний виграш.

## 11. Підсумок

### 🗂️ Нормальні форми — шпаргалка

| Форма | Коротке правило |
|---|---|
| 1NF | Атомарні значення, без списків в одній комірці |
| 2NF | 1NF + немає часткової залежності від частини composite PK |
| 3NF | 2NF + немає транзитивної залежності через інший неключовий атрибут |
| BCNF | Кожна ліва частина функціональної залежності — суперключ |
| 4NF / 5NF | Немає незалежних багатозначних / join-залежностей (рідко застосовується на практиці) |

### 🔑 Типи ключів — шпаргалка

| Тип ключа | Суть |
|---|---|
| Candidate Key | Будь-яка комбінація стовпців, що потенційно унікально ідентифікує рядок |
| Primary Key | Обраний candidate key, офіційний ідентифікатор рядка, `NOT NULL` + унікальний |
| Foreign Key | Посилання на PK іншої (чи тієї самої) таблиці, забезпечує референційну цілісність |
| Unique Key | Унікальність без статусу головного ідентифікатора |
| Composite Key | Ключ з кількох стовпців разом |
| Surrogate Key | Штучний PK (`IDENTITY`/`GUID`), не залежить від бізнес-даних — рекомендований підхід |
| Natural Key | PK на основі реального бізнес-атрибута — ризикований, якщо може змінюватись |

### ✅ Чек-лист рішення "нормалізувати чи денормалізувати"

1. **За замовчуванням — нормалізуй до 3NF.** Це базова, безпечна відправна точка для будь-якої нової схеми.
2. **Чи є FK-обмеження на кожному логічному зв'язку?** Якщо ні — додай, не покладайся лише на код застосунку.
3. **Чи є реальна, виміряна проблема продуктивності** на конкретному запиті/шляху? Якщо немає — не денормалізуй "про всяк випадок".
4. **Чи дані фінансові/транзакційні (гроші, замовлення, платежі, історія)?** Тримай їх у строгій нормалізованій формі без винятків.
5. **Чи є read-heavy шлях із прийнятною eventual consistency** (рейтинги, лічильники, звіти)? Тоді точкова денормалізація з чіткою стратегією оновлення (тригер / транзакція / фонова задача) — виправданий вибір.
6. **Чи PK — сурогатний, а не природний бізнес-атрибут?** Якщо PK — email/SSN/артикул, який теоретично може змінитись, розглянь перехід на сурогатний ключ.
7. **Чи не занадто дрібно розбита схема** (JOIN 7-8 таблиць для тривіального читання даних, які завжди йдуть разом і рідко оновлюються окремо)? Якщо так — можливо, варто об'єднати частину таблиць назад.
