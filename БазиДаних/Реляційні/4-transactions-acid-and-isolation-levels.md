## 1. Що таке транзакція?

**Транзакція (transaction)** — це група з однієї або кількох операцій над базою даних (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), яка виконується як **єдина неподільна одиниця роботи (unit of work)**. Це означає одну просту, але критично важливу річ:

> **Або виконуються ВСІ операції транзакції, або не виконується ЖОДНА.**

Немає проміжного стану "виконалось наполовину", який може побачити хтось інший або який може залишитись у базі даних назавжди.

### Аналогія з реального життя: банківський переказ

Уявімо, що ви переказуєте 1000 грн з рахунку A на рахунок B. Ця, здавалося б, одна дія "переказ" насправді складається з двох окремих операцій над базою даних:

1. **Списати** 1000 грн з рахунку A (`UPDATE accounts SET balance = balance - 1000 WHERE id = 'A'`)
2. **Зарахувати** 1000 грн на рахунок B (`UPDATE accounts SET balance = balance + 1000 WHERE id = 'B'`)

Якщо станеться збій (виключення в коді, обрив з'єднання з БД, падіння сервера) **між** кроком 1 і кроком 2 — гроші будуть списані з A, але ніколи не з'являться на B. Гроші просто "зникнуть у нікуди". Це неприпустимо для будь-якої фінансової системи (та й для більшості інших доменів теж).

Транзакція вирішує цю проблему: обидва `UPDATE` загортаються в один блок `BEGIN TRANSACTION ... COMMIT`. Якщо все пройшло успішно — застосовуються обидві зміни одразу (`COMMIT`). Якщо десь на шляху сталася помилка — **відкочуються (`ROLLBACK`)** обидві зміни, і база даних повертається до стану, який був до початку транзакції, ніби переказу взагалі не було.

```sql
BEGIN TRANSACTION;

UPDATE accounts SET balance = balance - 1000 WHERE id = 'A';
UPDATE accounts SET balance = balance + 1000 WHERE id = 'B';

COMMIT; -- або ROLLBACK, якщо щось пішло не так
```

### Життєвий цикл транзакції

```
BEGIN TRANSACTION
      |
      v
  [операція 1]
      |
      v
  [операція 2]
      |
      v
  [операція N]
      |
      +----------------------+
      |                      |
      v                      v
 усе успішно            сталася помилка
      |                      |
      v                      v
   COMMIT                ROLLBACK
 (зміни постійні)   (усі зміни скасовано,
                      стан як "до BEGIN")
```

Ключові команди у більшості СУБД (PostgreSQL, SQL Server, MySQL, Oracle):

| Команда | Призначення |
|---|---|
| `BEGIN` / `START TRANSACTION` | Почати нову транзакцію |
| `COMMIT` | Зафіксувати всі зміни назавжди |
| `ROLLBACK` | Скасувати всі зміни, зроблені в транзакції |
| `SAVEPOINT` | Створити "точку відкату" всередині транзакції для часткового rollback |

Саме для того, щоб такі транзакції поводились передбачувано в будь-якій СУБД, і був сформульований набір властивостей **ACID** — про нього далі.

## 2. ACID — детальний розбір кожної властивості

**ACID** — це акронім чотирьох властивостей, які гарантує (або має гарантувати) кожна транзакція в надійній реляційній СУБД:

- **A** — Atomicity (Атомарність)
- **C** — Consistency (Узгодженість)
- **I** — Isolation (Ізольованість)
- **D** — Durability (Довговічність)

Це одна з найпопулярніших тем на співбесідах з баз даних — і не просто так: розуміння ACID "на пальцях" (просто розшифрувати абревіатуру) відрізняє джуніора від людини, яка справді розуміє, *чому* база даних поводиться так, а не інакше під навантаженням.

### 2.1 Atomicity (Атомарність)

**Означення:** транзакція виконується за принципом "все або нічого" (all-or-nothing). Або застосовуються абсолютно всі зміни транзакції, або жодна з них.

Атомарність — це саме та властивість, яку ми проілюстрували в розділі 1 на прикладі банківського переказу:

```sql
BEGIN TRANSACTION;

UPDATE accounts SET balance = balance - 1000 WHERE id = 'A'; -- крок 1: списання
-- <-- якщо застосунок впаде саме тут...
UPDATE accounts SET balance = balance + 1000 WHERE id = 'B'; -- крок 2: зарахування

COMMIT;
```

Без атомарності, якщо застосунок аварійно завершиться між кроком 1 і кроком 2, база даних залишиться у стані, де 1000 грн зникло безслідно (списано з A, не зараховано на B). **З атомарністю** СУБД гарантує: якщо `COMMIT` не відбувся успішно (наприклад, через crash), при перезапуску/відновленні (recovery) незакомічена транзакція буде **автоматично відкочена**, і рахунок A поверне собі ці 1000 грн, ніби переказу не було взагалі.

**Що забезпечує атомарність технічно:** журнал транзакцій (write-ahead log / undo log), про який детальніше — в розділі 2.4 та в окремому документі серії про внутрішню будову сховища.

### 2.2 Consistency (Узгодженість)

**Означення:** транзакція переводить базу даних з одного **валідного (consistent)** стану в інший **валідний** стан, не порушуючи жодного з визначених правил цілісності даних — обмежень `FOREIGN KEY`, `CHECK`, `UNIQUE`, `NOT NULL`, тригерів, та бізнес-правил, закладених у самій транзакції.

Приклад: якщо в схемі є обмеження "баланс рахунку не може бути від'ємним" (`CHECK (balance >= 0)`), і транзакція намагається зняти більше грошей, ніж є на рахунку, — СУБД **відхилить** цю транзакцію (порушення `CHECK`-constraint), і вона буде автоматично відкочена. База даних ніколи не залишиться в стані, де баланс від'ємний, порушуючи цим власне ж правило.

```sql
CREATE TABLE accounts (
    id CHAR(1) PRIMARY KEY,
    balance NUMERIC(12,2) NOT NULL CHECK (balance >= 0)
);

BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 1000 WHERE id = 'A';
-- якщо після цього balance стане від'ємним -> CHECK constraint violation
-- -> транзакція автоматично відкочується, узгодженість збережено
COMMIT;
```

Важливо розуміти: **Consistency в ACID не є чимось, що "робить" сама СУБД активно** — швидше, це побічний ефект правильної роботи Atomicity + Isolation + правильно визначених обмежень схеми. СУБД гарантує, що *якщо* усі ваші constraints визначені коректно, то жодна транзакція (за умови атомарності й ізоляції) не зможе залишити базу в невалідному стані. Але саму "бізнес-логіку" узгодженості (наприклад, "сума дебету і кредиту в бухгалтерській проводці має дорівнювати нулю") усе одно визначає розробник — через схему, constraints, тригери або код застосунку.

#### ⚠️ Важливе розмежування: Consistency в ACID ≠ Consistency в CAP theorem

Це одна з найчастіших плутанин на senior-рівні співбесідах, тому варто зафіксувати її явно:

| | **Consistency в ACID** | **Consistency в CAP theorem** |
|---|---|---|
| Про що йдеться | Дані відповідають **бізнес-правилам/обмеженням схеми** (constraints, FK, CHECK) | Усі вузли/репліки розподіленої системи бачать **однакові (найсвіжіші) дані** в один момент часу |
| Контекст | Одна транзакція, одна база даних | Розподілена система з кількома вузлами/репліками |
| Що порушується | `CHECK`, `FOREIGN KEY`, `UNIQUE` тощо | Читання застарілих (stale) даних з різних реплік |
| Приклад порушення | Від'ємний баланс рахунку | Вузол A вже отримав `write`, а вузол B при читанні ще повертає старе значення |

Це **два зовсім різних поняття**, які випадково використовують те саме слово "Consistency". Плутанина настільки поширена, що знання цієї різниці саме по собі є хорошим індикатором глибшого розуміння систем на співбесіді. Детальніше про CAP theorem і розподілені системи — в окремих документах серії про NoSQL та розподілені бази даних.

### 2.3 Isolation (Ізольованість)

**Означення:** результат виконання кількох одночасних (concurrent) транзакцій має бути таким, **як якщо б** вони виконувались одна за одною, послідовно (serially) — навіть якщо насправді СУБД виконує їх паралельно заради продуктивності. Транзакції не повинні "бачити" проміжні, незакомічені зміни одна одної.

Це найскладніша й найцікавіша з чотирьох властивостей ACID — саме тому весь захід далі (розділи 3, 4 та 5 цього документа) присвячений детальному розбору того, *які проблеми виникають*, коли ізоляція недостатня, і *які механізми* СУБД використовують, щоб її забезпечити на різних рівнях суворості.

Коротко: на практиці **повна** ізоляція (як ніби транзакції справді виконуються строго послідовно) — це найдорожчий за продуктивністю варіант. Тому SQL-стандарт визначає кілька **рівнів ізоляції** (isolation levels), які дозволяють свідомо обміняти частину гарантій ізоляції на більшу пропускну здатність (throughput). Це — тема розділу 4.

### 2.4 Durability (Довговічність)

**Означення:** щойно транзакція успішно завершилась командою `COMMIT`, її результат **гарантовано збережений** і переживе будь-який наступний збій — падіння процесу СУБД, вимкнення живлення, перезавантаження операційної системи. Навіть якщо сервер аварійно вимкнеться через мілісекунду після `COMMIT`, після перезапуску дані, які були закомічені, будуть на місці.

**Як це технічно реалізовано (коротко):** переважна більшість СУБД використовують механізм, що зветься **Write-Ahead Log (WAL)** (в PostgreSQL так і зветься; в SQL Server — transaction log; в MySQL/InnoDB — redo log). Ідея проста:

1. Перед тим як фізично змінити сторінку даних на диску, СУБД **спочатку** записує запис про цю зміну в послідовний, append-only лог-файл (WAL).
2. Запис у WAL **fsync**-иться (примусово скидається) на диск **до того**, як `COMMIT` вважається успішним і підтверджується клієнту.
3. Реальні файли даних (heap/index pages) можуть оновитись на диску **пізніше**, асинхронно (checkpoint) — це нормально й не порушує довговічність, бо якщо станеться збій, СУБД при старті прочитає WAL і **повторно накотить (redo)** усі закомічені, але ще не застосовані до основних файлів зміни.

```
Клієнт: COMMIT
   |
   v
СУБД: записати запис транзакції у WAL --> fsync на диск --> ПІДТВЕРДИТИ COMMIT клієнту
   |
   v
(пізніше, асинхронно) застосувати зміни до основних файлів даних (checkpoint)
```

Саме тому durability тісно пов'язана з надійністю самого диска/файлової системи: якщо СУБД сконфігурована ігнорувати fsync заради швидкості (наприклад, `synchronous_commit = off` в PostgreSQL, або `innodb_flush_log_at_trx_commit = 0` в MySQL), durability **свідомо послаблюється** заради продуктивності — і це важливий компроміс, який інженер має розуміти, а не вмикати "за замовчуванням" без роздумів.

> 📌 Глибоке занурення в будову WAL, checkpoints, buffer pool та внутрішню архітектуру сховища СУБД — тема окремого документа цієї серії, присвяченого внутрішній будові реляційних баз даних. Тут ми зупиняємось на рівні "що потрібно знати про durability, щоб розуміти транзакції та ACID в цілому".

### 2.5 Підсумкова таблиця ACID

| Властивість | Що гарантує | Що ламається без неї | Реальний приклад збою |
|---|---|---|---|
| **Atomicity** | Транзакція виконується повністю або не виконується взагалі | Часткові, "напівзроблені" зміни застрягають у базі назавжди | Гроші списані з рахунку A, але не зараховані на B через crash застосунку між двома `UPDATE` |
| **Consistency** | Дані завжди відповідають визначеним constraints/бізнес-правилам | У базі з'являються логічно неможливі стани (сирітські записи, від'ємні баланси) | `FOREIGN KEY` видалено з коду валідації → в таблиці `orders` з'являється `customer_id`, якого не існує в `customers` |
| **Isolation** | Паралельні транзакції не заважають одна одній так, ніби вони виконуються послідовно | Одна транзакція бачить "чужі" незакомічені або нестабільні проміжні дані | Транзакція A читає баланс, який транзакція B ще не закомітила й потім відкочує (dirty read) |
| **Durability** | Закомічені дані виживають будь-який наступний збій | Підтверджена клієнту транзакція "губиться" після перезапуску сервера | Клієнту показано "Оплату прийнято", сервер БД падає через секунду, а COMMIT так і не був записаний на диск |

## 3. Проблеми паралельного виконання (Concurrency Anomalies)

Коли кілька транзакцій виконуються **одночасно** (а не строго послідовно одна за одною), без належного контролю з боку СУБД можуть виникнути кілька класичних аномалій. Розуміння цих чотирьох аномалій — обов'язкова передумова для розуміння рівнів ізоляції (розділ 4), бо кожен рівень ізоляції визначається саме через те, **які з цих аномалій він запобігає**.

Позначення в прикладах нижче: **T-A** — транзакція A, **T-B** — транзакція B. Час рухається зверху вниз.

### 3.1 Dirty Read

**Dirty Read (брудне читання)** — коли транзакція читає дані, які інша транзакція ще **не закомітила** (uncommitted), і ця інша транзакція потім робить `ROLLBACK`. У результаті перша транзакція прочитала значення, якого "ніколи не існувало" з точки зору бази даних.

```
Час  | T-A (читає)                        | T-B (пише)
-----|------------------------------------|------------------------------------
 t1  |                                    | BEGIN TRANSACTION
 t2  |                                    | UPDATE accounts
     |                                    |   SET balance = 5000
     |                                    |   WHERE id = 'A'
     |                                    | -- ще НЕ закомічено!
 t3  | BEGIN TRANSACTION                  |
 t4  | SELECT balance FROM accounts       |
     |   WHERE id = 'A'                   |
     | --> отримує 5000 (!)               |
 t5  |                                    | ROLLBACK
     |                                    | -- balance повертається
     |                                    |    до попереднього значення, напр. 1000
 t6  | -- T-A вважає, що баланс = 5000,   |
     |    хоча насправді (і завжди був)   |
     |    він = 1000                      |
```

**Наслідок:** T-A прийняла рішення (наприклад, дозволила зняття коштів) на основі значення, яке ніколи насправді не було в базі даних. Це найнебезпечніша й найгрубіша аномалія — жодна серйозна СУБД не дозволяє її за замовчуванням.

### 3.2 Non-Repeatable Read

**Non-Repeatable Read (неповторюване читання)** — коли транзакція читає **один і той самий рядок двічі**, і між цими двома читаннями значення змінюється, бо інша транзакція встигла його змінити й **закомітити**.

```
Час  | T-A                                | T-B
-----|------------------------------------|------------------------------------
 t1  | BEGIN TRANSACTION                   |
 t2  | SELECT balance FROM accounts        |
     |   WHERE id = 'A'                    |
     | --> отримує 1000                    |
 t3  |                                     | BEGIN TRANSACTION
 t4  |                                     | UPDATE accounts SET balance = 2000
     |                                     |   WHERE id = 'A'
 t5  |                                     | COMMIT  -- зміна закомічена!
 t6  | SELECT balance FROM accounts        |
     |   WHERE id = 'A'                    |
     | --> тепер отримує 2000 (!)          |
     | -- те саме читання в тій самій      |
     |    транзакції дало інший результат  |
 t7  | COMMIT                              |
```

**Ключова відмінність від dirty read:** тут T-B **успішно закомітила** свою зміну — це не "брудні", а цілком легітимні, вже застосовані дані. Проблема лише в тому, що T-A очікувала стабільності даних *у межах своєї власної транзакції*, а отримала два різних значення для того самого рядка.

### 3.3 Phantom Read

**Phantom Read (фантомне читання)** — схоже на non-repeatable read, але стосується не одного конкретного рядка, а **набору рядків**, які відповідають певній умові (`WHERE`). Транзакція виконує один і той самий **діапазонний запит** двічі та отримує різний **набір** рядків (з'явились нові рядки — "фантоми" — або зникли старі), бо інша транзакція вставила/видалила відповідний рядок і закомітила це між двома запитами.

```
Час  | T-A                                       | T-B
-----|-------------------------------------------|------------------------------------
 t1  | BEGIN TRANSACTION                          |
 t2  | SELECT * FROM orders                       |
     |   WHERE status = 'pending'                 |
     | --> отримує 5 рядків                       |
 t3  |                                             | BEGIN TRANSACTION
 t4  |                                             | INSERT INTO orders (status, ...)
     |                                             |   VALUES ('pending', ...)
 t5  |                                             | COMMIT  -- новий рядок закомічено
 t6  | SELECT * FROM orders                        |
     |   WHERE status = 'pending'                  |
     | --> тепер отримує 6 рядків (!)              |
     | -- з'явився "фантомний" рядок,              |
     |    якого не було при першому читанні        |
 t7  | COMMIT                                      |
```

**Відмінність від non-repeatable read:** non-repeatable read — про зміну значення **конкретного, вже прочитаного рядка**. Phantom read — про зміну **складу набору рядків**, що задовольняють умові `WHERE` (з'явились/зникли рядки, яких раніше в результаті не було або, навпаки, були). Це тонка, але важлива різниця, яку часто плутають — і саме тому вона окремо запитується на middle/senior співбесідах (див. розділ 10).

### 3.4 Lost Update

**Lost Update (втрачене оновлення)** — коли дві транзакції **обидві читають те саме значення**, обидві обчислюють нове значення на основі прочитаного, і обидві намагаються його записати. Друге успішне записування **мовчки перезаписує** результат першого, і зміни першої транзакції безслідно втрачаються — навіть попри те, що обидві транзакції окремо "коректно" закомітились без жодної помилки.

Це — найкласичніший реальний баг у застосунках із паралельним редагуванням: **два користувачі редагують той самий запис одночасно, і "переможе" той, хто зберіг останнім**.

```
Час  | T-A (Користувач 1)                 | T-B (Користувач 2)
-----|------------------------------------|------------------------------------
 t1  | BEGIN TRANSACTION                   |
 t2  | SELECT stock FROM products          |
     |   WHERE id = 42                     |
     | --> отримує stock = 10              |
 t3  |                                     | BEGIN TRANSACTION
 t4  |                                     | SELECT stock FROM products
     |                                     |   WHERE id = 42
     |                                     | --> теж отримує stock = 10
 t5  | -- T-A вирішує: "продали 3 шт,      |
     |    новий stock = 10 - 3 = 7"        |
     | UPDATE products SET stock = 7       |
     |   WHERE id = 42                     |
 t6  | COMMIT   -- stock = 7                |
 t7  |                                     | -- T-B вирішує (на основі СТАРОГО
     |                                     |    значення 10): "продали 2 шт,
     |                                     |    новий stock = 10 - 2 = 8"
     |                                     | UPDATE products SET stock = 8
     |                                     |   WHERE id = 42
 t8  |                                     | COMMIT   -- stock = 8 (!)
-----|------------------------------------|------------------------------------
     | Підсумок: продано 3 + 2 = 5 шт,     |
     | але stock зменшився лише на 2       |
     | (з 10 до 8), бо запис T-A (stock=7) |
     | був повністю перезаписаний і        |
     | "втрачений" без жодного попередження|
```

**Чому це особливо небезпечно:** на відміну від dirty read і non-repeatable read, тут **немає жодної помилки чи винятку** — обидва `COMMIT` проходять успішно. Проблема суто логічна й "тиха" (silent) — саме тому lost update так важко помітити під час тестування (він проявляється лише під реальним паралельним навантаженням) і саме тому це одне з найважливіших питань на senior-рівні (детальний розбір запобігання — у розділах 5, 7.3, 8 і 10).

## 4. Рівні ізоляції (Isolation Levels)

SQL-стандарт визначає **чотири рівні ізоляції**, які СУБД може застосувати до транзакції. Кожен наступний рівень **суворіший** за попередній: він запобігає більшій кількості аномалій із розділу 3, але коштує дорожче в термінах конкурентності (concurrency) — блокування, очікування (blocking) або відхилення транзакцій з подальшим retry.

Синтаксис встановлення рівня ізоляції (стандартний SQL, підтримується більшістю СУБД):

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- або: READ UNCOMMITTED | REPEATABLE READ | SERIALIZABLE

BEGIN TRANSACTION;
-- ... запити ...
COMMIT;
```

### 4.1 Read Uncommitted

**Найслабший** рівень ізоляції. Транзакція може читати **незакомічені** зміни інших транзакцій.

- **Запобігає:** нічому.
- **Дозволяє:** dirty read, non-repeatable read, phantom read, lost update.

На практиці цей рівень практично не використовується в сучасних застосунках через ризик dirty read. **PostgreSQL**, до речі, взагалі не реалізує його по-справжньому: `READ UNCOMMITTED` у PostgreSQL мапиться на поведінку `READ COMMITTED` (PostgreSQL просто ніколи фізично не показує незакомічені дані, навіть якщо його попросити). А от **SQL Server** та **MySQL** реалізують `READ UNCOMMITTED` буквально (в MySQL/InnoDB через so-called "dirty reads" при читанні без блокувань).

### 4.2 Read Committed

Транзакція бачить **лише закомічені** дані — вона ніколи не прочитає незакомічені зміни іншої транзакції. Але кожен новий запит (`SELECT`) у межах транзакції може побачити **новіші** закомічені дані, якщо інша транзакція встигла закомітити зміну між двома запитами.

- **Запобігає:** dirty read.
- **Дозволяє:** non-repeatable read, phantom read, lost update.

Це **рівень ізоляції за замовчуванням** у більшості популярних СУБД: **PostgreSQL** та **SQL Server** (Oracle також). Причина популярності проста — це хороший компроміс: він виключає найгрубішу й найнебезпечнішу аномалію (dirty read), при цьому залишаючись достатньо "дешевим" за конкурентністю для більшості звичайних CRUD-навантажень.

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE id = 'A'; -- бачить лише закомічені дані
-- ... інша транзакція встигає закомітити зміну балансу ...
SELECT balance FROM accounts WHERE id = 'A'; -- може повернути ІНШЕ значення
COMMIT;
```

### 4.3 Repeatable Read

Якщо транзакція вже прочитала якийсь рядок, повторне читання **того самого рядка** в межах цієї ж транзакції гарантовано поверне **те саме значення**, незалежно від того, скільки інших транзакцій встигли його змінити й закомітити в цей час.

- **Запобігає:** dirty read, non-repeatable read.
- **Дозволяє:** phantom read (у класичному, "паперовому" визначенні стандарту SQL — хоча деякі СУБД, зокрема **PostgreSQL**, у своїй реалізації `REPEATABLE READ` на основі MVCC фактично запобігають і phantom read теж, що суворіше за мінімальні вимоги стандарту — детальніше в розділі 5.2).

Це рівень ізоляції за замовчуванням у **MySQL/InnoDB**.

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE id = 'A'; -- отримали 1000
-- ... інша транзакція міняє й комітить balance ...
SELECT balance FROM accounts WHERE id = 'A'; -- ГАРАНТОВАНО знову 1000
COMMIT;
```

### 4.4 Serializable

**Найсуворіший** рівень ізоляції. Гарантує, що результат виконання набору паралельних транзакцій буде **еквівалентний** якомусь можливому **послідовному (serial)** порядку їх виконання — так, ніби транзакції взагалі не перетинались у часі.

- **Запобігає:** dirty read, non-repeatable read, phantom read, lost update (у більшості реалізацій).
- **Дозволяє:** нічого з класичних аномалій — але це коштує **найдорожче** за конкурентністю.

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;
SELECT * FROM orders WHERE status = 'pending'; -- набір рядків "заморожено"
-- ... будь-яка інша транзакція, що вставляє відповідний рядок,
--     або буде заблокована, або її COMMIT провалиться з помилкою serialization failure
COMMIT;
```

На практиці `SERIALIZABLE` реалізується одним із двох способів (залежно від СУБД): або через **суворіше блокування діапазонів** (range locks / predicate locks), або через **оптимістичний підхід виявлення конфліктів** (Serializable Snapshot Isolation, SSI — так робить PostgreSQL), коли транзакція виконується оптимістично, а в момент `COMMIT` СУБД перевіряє, чи не було конфлікту серіалізації, і якщо так — відхиляє транзакцію з помилкою `40001 serialization_failure`, яку застосунок повинен **перехопити й повторити (retry)**.

### 4.5 Зведена таблиця рівнів ізоляції

| Рівень ізоляції | Dirty Read | Non-Repeatable Read | Phantom Read | Lost Update | Типовий default у |
|---|:---:|:---:|:---:|:---:|---|
| **Read Uncommitted** | ❌ можливий | ❌ можливий | ❌ можливий | ❌ можливий | — (рідко використовується) |
| **Read Committed** | ✅ запобігає | ❌ можливий | ❌ можливий | ❌ можливий | PostgreSQL, SQL Server, Oracle |
| **Repeatable Read** | ✅ запобігає | ✅ запобігає | ❌ можливий (за стандартом)* | ❌ можливий** | MySQL/InnoDB |
| **Serializable** | ✅ запобігає | ✅ запобігає | ✅ запобігає | ✅ запобігає | — (використовується вибірково) |

\* У PostgreSQL `REPEATABLE READ` реалізовано через MVCC-снапшот на рівні всієї транзакції, що фактично унеможливлює й phantom read теж (це суворіше, ніж вимагає стандарт SQL) — але офіційно рівень все одно називається `REPEATABLE READ`, а не `SERIALIZABLE`, бо інші тонші аномалії (write skew) все ще можливі.
\** Lost update запобігається на `REPEATABLE READ`/`SERIALIZABLE` лише в тому сенсі, що **другий** `UPDATE` отримає помилку конфлікту (наприклад, `could not serialize access`) замість мовчазного перезапису — але це вимагає, щоб застосунок або сама СУБД справді виявила конфлікт двох записів у той самий рядок; поведінка залежить від конкретної СУБД і сценарію (детальніше — розділ 8).

### 4.6 Фундаментальний компроміс

Тут криється ключова ідея всього розділу 4, яку варто сформулювати явно:

> **Чим вищий рівень ізоляції → тим більше гарантій коректності, але тим менше конкурентності (concurrency).**

"Менше конкурентності" означає одне з двох, залежно від механізму реалізації (розділ 5):

- **Більше блокувань і очікування (blocking):** транзакції змушені чекати одна одну, зменшується пропускна здатність системи (throughput), зростає ризик deadlock (розділ 6).
- **Більше відхилених транзакцій із подальшим retry:** особливо характерно для `SERIALIZABLE` у PostgreSQL (SSI) — замість блокування транзакція просто "провалюється" в момент коміту й повинна бути повторена застосунком.

Тому золоте правило на практиці: **обирайте найнижчий рівень ізоляції, який усе ще гарантує коректність вашого конкретного бізнес-сценарію** — а не автоматично `SERIALIZABLE` "про всяк випадок" (детальніше в розділі 9, "Поширені помилки").

## 5. Механізми реалізації ізоляції: блокування vs MVCC

Рівні ізоляції з розділу 4 — це **специфікація поведінки** (що дозволено, а що ні). А ось *як саме* СУБД цю поведінку технічно забезпечує "під капотом" — питання реалізації, і тут існує два принципово різних підходи.

### 5.1 Песимістичне блокування (Pessimistic Locking)

**Ідея:** СУБД виходить із "песимістичного" припущення, що конфлікт **обов'язково станеться**, тому блокування (lock) на рядок/сторінку/таблицю **береться заздалегідь**, до того як хтось інший встигне втрутитись. Інші транзакції, яким потрібен той самий ресурс, змушені **чекати**, доки блокування не звільниться (або отримують помилку, якщо налаштовано `NOWAIT`).

Два основних типи блокувань:

| Тип блокування | Інша назва | Хто може отримати одночасно |
|---|---|---|
| **Shared lock** (S) | Read lock | Багато транзакцій одночасно можуть тримати shared lock на той самий рядок — усі просто **читають** |
| **Exclusive lock** (X) | Write lock | Лише **одна** транзакція може тримати exclusive lock — усі інші (і на читання, і на запис) чекають |

Правило сумісності: `Shared + Shared` — сумісні (можна одночасно). `Shared + Exclusive` та `Exclusive + Exclusive` — **несумісні** (одна транзакція чекає іншу).

```sql
BEGIN TRANSACTION;

-- явно захопити exclusive lock на рядок перед читанням+зміною
SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- будь-яка інша транзакція, що теж хоче SELECT ... FOR UPDATE
-- на цей самий рядок, буде ЗАБЛОКОВАНА (чекатиме) до COMMIT/ROLLBACK

UPDATE products SET stock = stock - 1 WHERE id = 42;

COMMIT; -- lock звільняється
```

**Плюси:** проста ментальна модель, гарантована коректність без ризику "втраченого" запису — конфлікт просто неможливий, бо ресурс фізично заблокований.
**Мінуси:** знижує конкурентність — читачі можуть блокувати письменників (залежно від СУБД), зростає ризик deadlock (розділ 6), погано масштабується під високе навантаження з великою кількістю паралельних транзакцій.

### 5.2 MVCC (Multi-Version Concurrency Control)

**Ідея:** замість того, щоб блокувати рядок при читанні, СУБД зберігає **кілька версій** кожного рядка (кожна версія — це стан рядка на момент певної транзакції/timestamp). Коли транзакція починається, вона отримує узгоджений **знімок (snapshot)** бази даних станом на момент свого старту — і бачить **саме ту версію** кожного рядка, яка була **закомічена до початку** цієї транзакції, повністю ігноруючи зміни, зроблені паралельними транзакціями, що ще не закомітились (або закомітились уже пізніше).

Ключовий наслідок: **читачі ніколи не блокують письменників, і письменники ніколи не блокують читачів.** `SELECT` практично завжди виконується миттєво, незалежно від того, скільки інших транзакцій зараз пишуть у ту саму таблицю.

```
Час  | Версії рядка (id=42, stock)         | T-A (читає)                | T-B (пише)
-----|-------------------------------------|------------------------------------------|
 t1  | v1: stock=10 (закомічено раніше)     |                             |
 t2  |                                      | BEGIN -- знімок: бачить v1  |
 t3  |                                      |                             | BEGIN
 t4  |                                      |                             | UPDATE stock=9
     |                                      |                             | (створює v2, ще не закомічено)
 t5  | v1: stock=10 (все ще "жива" для T-A) |                             |
     | v2: stock=9  (нова, poки не видима   |                             |
     |               для T-A)               |                             |
 t6  |                                      | SELECT stock                |
     |                                      | --> 10 (бачить v1, як і     |
     |                                      |     мало бути за знімком)   |
 t7  |                                      |                             | COMMIT -- v2 стає
     |                                      |                             |   "офіційною" версією
 t8  |                                      | SELECT stock (все ще        |
     |                                      | всередині своєї транзакції) |
     |                                      | --> залежно від рівня       |
     |                                      | ізоляції: REPEATABLE READ   |
     |                                      | -> все ще 10 (свій знімок), |
     |                                      | READ COMMITTED -> нове      |
     |                                      | читання побачить вже 9      |
```

Старі версії рядків (v1 у прикладі вище) не видаляються одразу — вони прибираються пізніше фоновим процесом очищення (у PostgreSQL це називається **VACUUM**), коли жодній активній транзакції вони більше не потрібні.

**СУБД, що активно використовують MVCC:** **PostgreSQL** (класична, "підручникова" реалізація MVCC через мультиверсійні рядки прямо в таблиці), **MySQL/InnoDB** (MVCC через undo-log), **Oracle** (MVCC через undo segments), **SQLite** (WAL-mode).

**Чому MVCC зазвичай кращий вибір для read-heavy навантажень:** оскільки читання ніколи не блокує й не блокується записом, система масштабується значно краще для типового вебзастосунку, де читань на порядки більше, ніж записів (стрічка новин, каталог товарів, дашборди аналітики). Ціна цього — трохи більше споживання диска/пам'яті на зберігання старих версій рядків і накладні витрати на їх періодичне прибирання (VACUUM), а також потенційно застарілі (though consistent) дані в межах довгої транзакції за `REPEATABLE READ`.

### 5.3 Оптимістична конкурентність (Optimistic Concurrency Control)

**Ідея:** на відміну від pessimistic locking, тут узагалі **не береться жодного блокування** на рівні бази даних під час читання. Натомість:

1. Транзакція **читає** дані разом зі спеціальним "версійним" полем (`version`, `row_version`, `updated_at`/timestamp).
2. Транзакція обчислює зміни **в пам'яті застосунку** (можливо, довго — наприклад, поки користувач редагує форму хвилинами).
3. У момент запису (`UPDATE`) — транзакція **перевіряє**, чи версійне поле в базі даних все ще збігається з тим, яке було прочитане на кроці 1:

```sql
UPDATE products
SET stock = 5, version = version + 1
WHERE id = 42 AND version = 3;  -- умова: версія не змінилась з моменту читання

-- якщо СУБД повідомляє "0 рядків оновлено" -> хтось інший встиг
-- змінити цей рядок першим -> конфлікт виявлено, потрібен retry
```

4. Якщо версія **збіглась** — оновлення успішне, версія інкрементується. Якщо версія **не збіглась** (хтось інший устиг оновити раніше) — оновлення **не застосовується**, застосунок отримує сигнал про конфлікт (0 змінених рядків, або спеціальний виняток на рівні ORM — див. приклад у розділі 7.3) і повинен або **повторити спробу (retry)** з новими даними, або показати користувачу повідомлення про конфлікт.

**Оптимістична конкурентність у .NET / EF Core** — це саме те, що реалізує атрибут `[Timestamp]`/властивість `RowVersion`: EF Core автоматично додає `WHERE RowVersion = @original_value` до кожного `UPDATE`/`DELETE`, і якщо жодного рядка не змінено — кидає `DbUpdateConcurrencyException`. Детальний робочий приклад — у розділі 7.3.

**Зв'язок із патерном Memento (з серії про GoF-патерни):** концептуально оптимістична конкурентність спирається на ту саму ідею, що й патерн **Memento** — "зафіксувати знімок стану об'єкта в певний момент часу, щоб пізніше можна було порівняти або відновити його". Версійне поле (`RowVersion`) — це, по суті, компактний "відбиток" (fingerprint) стану рядка на момент читання: замість повного знімку всіх полів об'єкта (як робить класичний Memento), тут зберігається лише один invariant-маркер, але сама ідея — "запам'ятати стан на момент t, щоб пізніше перевірити, чи він не змінився" — концептуально та сама.

**Коли оптимістична конкурентність краща за pessimistic locking:** коли конфлікти **рідкісні** (наприклад, два користувачі рідко редагують той самий запис одночасно) і коли транзакція/операція користувача може тривати **довго** (наприклад, поки людина заповнює форму) — тримати блокування бази даних відкритим стільки часу, скільки людина редагує форму, було б катастрофою для конкурентності (див. розділ 9). Якщо ж конфлікти **часті** (наприклад, лічильник залишку останнього товару, за яким "полюють" сотні одночасних покупців), оптимістичний підхід призводить до **багатьох невдалих retry**, і pessimistic locking (або спеціалізовані структури типу atomic counters) може бути ефективнішим — детально розібрано в реальному сценарії, розділ 8.

## 6. Deadlocks

**Deadlock (взаємне блокування)** — ситуація, коли дві (або більше) транзакції **чекають одна одну нескінченно**, тому що кожна з них тримає ресурс (блокування), який потрібен іншій, і жодна не може продовжити роботу.

### Класичний приклад: циклічне очікування

```
Транзакція A                          Транзакція B
-----------------------------------   -----------------------------------
BEGIN TRANSACTION                     BEGIN TRANSACTION

UPDATE accounts SET balance = ...     UPDATE accounts SET balance = ...
  WHERE id = 1                          WHERE id = 2
-- A захопила EXCLUSIVE lock          -- B захопила EXCLUSIVE lock
   на рядок 1                            на рядок 2

                    (обидві транзакції одночасно намагаються
                     торкнутись і другого рядка теж)

UPDATE accounts SET balance = ...     UPDATE accounts SET balance = ...
  WHERE id = 2                          WHERE id = 1
-- A хоче lock на рядок 2,            -- B хоче lock на рядок 1,
   але його тримає B --> A ЧЕКАЄ        але його тримає A --> B ЧЕКАЄ

              ┌─────────────────────────────────────┐
              │   A чекає на lock, що тримає B       │
              │   B чекає на lock, що тримає A       │
              │   --> ЦИКЛ ОЧІКУВАННЯ (DEADLOCK)      │
              └─────────────────────────────────────┘
```

Схематично цикл очікування (wait-for graph):

```
   тримає row-1, чекає row-2        тримає row-2, чекає row-1
        ┌───────────┐                    ┌───────────┐
        │  T-A      │ ─────чекає────>    │   T-B     │
        │           │ <────чекає──────── │           │
        └───────────┘                    └───────────┘
```

Без втручання ззовні обидві транзакції чекали б одна одну **нескінченно**.

### Як СУБД виявляє й вирішує deadlock

Сучасні СУБД (PostgreSQL, SQL Server, MySQL/InnoDB) постійно відстежують граф очікування транзакцій ("хто на кого чекає") і періодично перевіряють його на наявність **циклів**. Коли цикл знайдено:

1. СУБД обирає одну з транзакцій-учасниць циклу як **"жертву" (victim)** — зазвичай ту, яка виконала менше роботи (найдешевше відкотити), хоча точний критерій вибору відрізняється між СУБД.
2. Транзакція-жертва **примусово відкочується (ROLLBACK)** з боку СУБД, її блокування звільняються.
3. Застосунок, від імені якого виконувалась транзакція-жертва, отримує спеціальну помилку (наприклад, у PostgreSQL — `SQLSTATE 40P01: deadlock detected`; у SQL Server — `Error 1205`).
4. "Транзакція-переможець" (та, яку не обрали жертвою) може безперешкодно продовжити роботу й закомітитись.
5. Застосунок, який отримав помилку deadlock, **повинен сам** перехопити цю помилку й **повторити транзакцію (retry)** — СУБД цього автоматично не робить.

### Практичне запобігання: консистентний порядок доступу

Найважливіше практичне правило, яке повністю усуває клас проблем із циклічним очікуванням:

> **Завжди звертайтесь до ресурсів (рядків, таблиць) в одному й тому ж порядку в усіх транзакціях застосунку.**

Якщо в прикладі вище **обидві** транзакції завжди спочатку блокують рядок із меншим `id`, а потім — з більшим, цикл очікування стає **фізично неможливим**:

```
Транзакція A (правильний порядок)      Транзакція B (правильний порядок)
-----------------------------------    -----------------------------------
UPDATE ... WHERE id = 1  -- спочатку   UPDATE ... WHERE id = 1  -- спочатку
                                        -- B ЧЕКАЄ, бо A вже тримає row-1
UPDATE ... WHERE id = 2  -- потім
COMMIT  -- A звільняє обидва lock

                                        -- тепер B отримує lock на row-1
                                        UPDATE ... WHERE id = 2  -- потім
                                        COMMIT
```

Тепер B просто **чекає**, поки A завершиться повністю (звичайне блокування, а не deadlock) — це може тимчасово знизити throughput, але **ніколи не призведе до нескінченного взаємного очікування**. Це правило варто закладати в застосунку явно: наприклад, завжди сортувати список ID рядків для оновлення за зростанням перед тим, як звертатись до бази (`ORDER BY id`), незалежно від порядку, в якому користувач вибрав елементи в UI.

## 7. Практичні приклади на C#

### 7.1 Приклад 1 — ADO.NET транзакція (переказ коштів)

Класичний приклад атомарності "врукопаш" через `SqlConnection.BeginTransaction()`:

```csharp
using System;
using System.Data;
using Microsoft.Data.SqlClient;

class BankTransferExample
{
    static void TransferMoney(string connectionString, string fromAccountId, string toAccountId, decimal amount)
    {
        using var connection = new SqlConnection(connectionString);
        connection.Open();

        // Починаємо транзакцію явно
        using SqlTransaction transaction = connection.BeginTransaction(IsolationLevel.ReadCommitted);

        try
        {
            // Крок 1: списання коштів з рахунку-джерела
            using (var debitCommand = connection.CreateCommand())
            {
                debitCommand.Transaction = transaction;
                debitCommand.CommandText = @"
                    UPDATE Accounts
                    SET Balance = Balance - @amount
                    WHERE Id = @accountId AND Balance >= @amount"; // не даємо піти в мінус
                debitCommand.Parameters.AddWithValue("@amount", amount);
                debitCommand.Parameters.AddWithValue("@accountId", fromAccountId);

                int rowsAffected = debitCommand.ExecuteNonQuery();
                if (rowsAffected == 0)
                {
                    // Недостатньо коштів або рахунок не знайдено — скасовуємо все
                    throw new InvalidOperationException(
                        $"Недостатньо коштів на рахунку {fromAccountId} або рахунок не існує.");
                }
            }

            // Імітуємо збій рівно між двома операціями (для демонстрації атомарності)
            // if (simulateCrash) throw new Exception("Симуляція падіння застосунку!");

            // Крок 2: зарахування коштів на рахунок-отримувач
            using (var creditCommand = connection.CreateCommand())
            {
                creditCommand.Transaction = transaction;
                creditCommand.CommandText = @"
                    UPDATE Accounts
                    SET Balance = Balance + @amount
                    WHERE Id = @accountId";
                creditCommand.Parameters.AddWithValue("@amount", amount);
                creditCommand.Parameters.AddWithValue("@accountId", toAccountId);
                creditCommand.ExecuteNonQuery();
            }

            // Обидві операції пройшли успішно -> фіксуємо транзакцію
            transaction.Commit();
            Console.WriteLine($"Переказ {amount:C} з {fromAccountId} на {toAccountId} успішний.");
        }
        catch (Exception ex)
        {
            // Будь-яка помилка на будь-якому кроці -> відкочуємо ВСЮ транзакцію
            transaction.Rollback();
            Console.WriteLine($"Переказ скасовано: {ex.Message}. Жодних змін не застосовано.");
        }
    }
}
```

**Консольний вивід у разі успіху:**
```
Переказ 1 000,00 ₴ з A на B успішний.
```

**Консольний вивід у разі, коли на рахунку недостатньо коштів (rowsAffected == 0):**
```
Переказ скасовано: Недостатньо коштів на рахунку A або рахунок не існує. Жодних змін не застосовано.
```

Ключовий момент атомарності тут: якщо виняток стається **після** успішного списання (крок 1), але **до** зарахування (крок 2) — наприклад, через обрив мережі чи будь-який непередбачений виняток — блок `catch` викликає `transaction.Rollback()`, і списання коштів на кроці 1 **теж скасовується**, попри те, що воно "технічно" вже виконалось у межах транзакції. Саме в цьому й полягає гарантія "все або нічого".

### 7.2 Приклад 2 — EF Core транзакції та рівень ізоляції

EF Core за замовчуванням **автоматично** загортає кожен виклик `SaveChanges()` в неявну транзакцію (якщо в межах одного виклику виконується кілька команд `INSERT`/`UPDATE`/`DELETE`). Але часто потрібно об'єднати **кілька викликів** `SaveChanges()` (або й запити до кількох `DbContext`) в одну явну транзакцію — або встановити конкретний рівень ізоляції.

```csharp
using System;
using System.Data;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Storage;

public class OrderProcessingService
{
    private readonly AppDbContext _context;

    public OrderProcessingService(AppDbContext context) => _context = context;

    public async Task PlaceOrderAsync(int customerId, int productId, int quantity)
    {
        // Явно вказуємо рівень ізоляції (провайдер має підтримувати; SQL Server/PostgreSQL підтримують)
        using IDbContextTransaction transaction =
            await _context.Database.BeginTransactionAsync(IsolationLevel.ReadCommitted);

        try
        {
            var product = await _context.Products.FirstAsync(p => p.Id == productId);

            if (product.Stock < quantity)
                throw new InvalidOperationException("Недостатньо товару на складі.");

            product.Stock -= quantity;

            var order = new Order
            {
                CustomerId = customerId,
                ProductId = productId,
                Quantity = quantity,
                CreatedAt = DateTime.UtcNow
            };
            _context.Orders.Add(order);

            // Перший SaveChanges: оновлення товару + створення замовлення
            await _context.SaveChangesAsync();

            var invoice = new Invoice
            {
                OrderId = order.Id,
                Amount = product.Price * quantity
            };
            _context.Invoices.Add(invoice);

            // Другий SaveChanges: створення рахунку-фактури
            // Обидва SaveChanges мають бути закомічені РАЗОМ, тому й потрібна явна транзакція
            await _context.SaveChangesAsync();

            await transaction.CommitAsync();
            Console.WriteLine($"Замовлення №{order.Id} успішно оформлено, рахунок №{invoice.Id} створено.");
        }
        catch (Exception ex)
        {
            await transaction.RollbackAsync();
            Console.WriteLine($"Оформлення замовлення скасовано: {ex.Message}");
            throw;
        }
    }
}
```

**Консольний вивід у разі успіху:**
```
Замовлення №1042 успішно оформлено, рахунок №1042 створено.
```

**Консольний вивід, якщо товару не вистачає:**
```
Оформлення замовлення скасовано: Недостатньо товару на складі.
```

Важливо: без явної `BeginTransactionAsync` тут перший `SaveChangesAsync()` (оновлення товару + замовлення) міг би закомітитись успішно, а другий (створення рахунку) — впасти з помилкою, залишивши замовлення без рахунку-фактури. Явна транзакція гарантує, що **обидва** `SaveChanges` застосуються разом або жоден.

### 7.3 Приклад 3 — Оптимістична конкурентність з RowVersion

Демонстрація того, як `[Timestamp]`-поле (RowVersion) перетворює "тиху" (silent) проблему lost update (розділ 3.4) на **явний, оброблюваний виняток**.

```csharp
using System;
using Microsoft.EntityFrameworkCore;

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int Stock { get; set; }

    [Timestamp] // EF Core автоматично додає WHERE RowVersion = @original до UPDATE/DELETE
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}

public class AppDbContext : DbContext
{
    public DbSet<Product> Products => Set<Product>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Product>()
            .Property(p => p.RowVersion)
            .IsRowVersion(); // для провайдерів без нативного timestamp (напр. PostgreSQL)
    }
}

class OptimisticConcurrencyDemo
{
    static async Task Main()
    {
        var optionsBuilder = new DbContextOptionsBuilder<AppDbContext>()
            .UseSqlServer("Server=.;Database=ShopDb;Trusted_Connection=True;");

        // --- "Користувач 1" завантажує товар ---
        await using var context1 = new AppDbContext(optionsBuilder.Options);
        var productForUser1 = await context1.Products.FirstAsync(p => p.Id == 42);
        Console.WriteLine($"Користувач 1 завантажив товар: Stock = {productForUser1.Stock}");

        // --- "Користувач 2" завантажує ТОЙ САМИЙ товар незалежно ---
        await using var context2 = new AppDbContext(optionsBuilder.Options);
        var productForUser2 = await context2.Products.FirstAsync(p => p.Id == 42);
        Console.WriteLine($"Користувач 2 завантажив той самий товар: Stock = {productForUser2.Stock}");

        // --- Користувач 1 змінює й зберігає першим ---
        productForUser1.Stock -= 1;
        await context1.SaveChangesAsync();
        Console.WriteLine($"Користувач 1 зберіг зміни успішно. Новий Stock = {productForUser1.Stock}");

        // --- Користувач 2 змінює (на основі СВОЄЇ, вже застарілої копії) і намагається зберегти ---
        productForUser2.Stock -= 1;
        try
        {
            await context2.SaveChangesAsync();
            Console.WriteLine("Користувач 2 зберіг зміни успішно.");
        }
        catch (DbUpdateConcurrencyException)
        {
            Console.WriteLine(
                "КОНФЛІКТ! Користувач 2 намагався оновити запис, який хтось інший " +
                "уже змінив з моменту завантаження (RowVersion не збігається). " +
                "SaveChanges для Користувача 2 ВІДХИЛЕНО.");
        }
    }
}
```

**Консольний вивід:**
```
Користувач 1 завантажив товар: Stock = 10
Користувач 2 завантажив той самий товар: Stock = 10
Користувач 1 зберіг зміни успішно. Новий Stock = 9
КОНФЛІКТ! Користувач 2 намагався оновити запис, який хтось інший уже змінив з моменту
завантаження (RowVersion не збігається). SaveChanges для Користувача 2 ВІДХИЛЕНО.
```

Зверніть увагу на ключову різницю з розділом 3.4: **без** `RowVersion` (просто читання й запис `Stock` без версійного поля) обидва `SaveChanges()` пройшли б успішно, і фінальний `Stock` дорівнював би 9 (втрачено одне з двох зменшень — класичний lost update). **З** `RowVersion` другий виклик **явно провалюється** з `DbUpdateConcurrencyException`, і застосунок **знає**, що стався конфлікт, замість того, щоб мовчки втратити дані.

**Типові стратегії обробки `DbUpdateConcurrencyException`:**

1. **Retry (повтор):** перезавантажити рядок зі свіжими даними, повторно застосувати бізнес-логіку (наприклад, ще раз відняти 1 від *нового* значення Stock) і повторити `SaveChanges()`.
2. **Merge (злиття):** показати користувачу обидві версії (свою й актуальну з бази) і дати змогу вручну вирішити конфлікт поле за полем.
3. **Notify user (повідомити користувача):** просто повідомити "Запис було змінено іншим користувачем, оновіть сторінку і спробуйте ще раз" — найпростіший, хоч і найменш "дружній" варіант.

### 7.4 Приклад 4 — Deadlock та його вирішення

Ілюстративний приклад, що відтворює класичний deadlock із розділу 6 за допомогою двох паралельних задач, кожна з яких блокує два рядки в **протилежному** порядку — і виправлення через уніфікацію порядку доступу.

```csharp
using System;
using System.Data;
using System.Threading.Tasks;
using Microsoft.Data.SqlClient;

class DeadlockDemo
{
    // ПРОБЛЕМНА версія: транзакції звертаються до рядків у РІЗНОМУ порядку
    static async Task TransferBadOrderAsync(string connString, int fromId, int toId, decimal amount)
    {
        using var conn = new SqlConnection(connString);
        await conn.OpenAsync();
        using var tx = conn.BeginTransaction(IsolationLevel.ReadCommitted);

        try
        {
            using var cmd1 = conn.CreateCommand();
            cmd1.Transaction = tx;
            cmd1.CommandText = "UPDATE Accounts SET Balance = Balance - @amt WHERE Id = @from";
            cmd1.Parameters.AddWithValue("@amt", amount);
            cmd1.Parameters.AddWithValue("@from", fromId);
            await cmd1.ExecuteNonQueryAsync(); // блокує рядок fromId першим

            await Task.Delay(500); // штучна затримка, щоб гарантовано зіткнутись у прикладі

            using var cmd2 = conn.CreateCommand();
            cmd2.Transaction = tx;
            cmd2.CommandText = "UPDATE Accounts SET Balance = Balance + @amt WHERE Id = @to";
            cmd2.Parameters.AddWithValue("@amt", amount);
            cmd2.Parameters.AddWithValue("@to", toId);
            await cmd2.ExecuteNonQueryAsync(); // блокує рядок toId другим

            tx.Commit();
            Console.WriteLine($"Переказ {fromId} -> {toId} успішний.");
        }
        catch (SqlException ex) when (ex.Number == 1205) // 1205 = deadlock victim у SQL Server
        {
            tx.Rollback();
            Console.WriteLine($"DEADLOCK виявлено під час переказу {fromId} -> {toId}. Транзакцію відкочено.");
        }
    }

    static async Task RunProblematicScenario(string connString)
    {
        // Задача 1: рахунок 1 -> рахунок 2 (спочатку блокує 1, потім 2)
        var task1 = TransferBadOrderAsync(connString, fromId: 1, toId: 2, amount: 100);

        // Задача 2: рахунок 2 -> рахунок 1 (спочатку блокує 2, потім 1) -- ПРОТИЛЕЖНИЙ порядок!
        var task2 = TransferBadOrderAsync(connString, fromId: 2, toId: 1, amount: 50);

        await Task.WhenAll(task1, task2);
        // Результат: одна з двох транзакцій, ймовірно, отримає deadlock (SqlException 1205)
    }

    // ВИПРАВЛЕНА версія: обидві транзакції завжди звертаються до рядків
    // у порядку зростання Id, незалежно від напрямку переказу
    static async Task TransferSafeOrderAsync(string connString, int accountA, int accountB, decimal amountAtoB)
    {
        // Визначаємо консистентний порядок блокування: менший Id -- завжди першим
        int firstId = Math.Min(accountA, accountB);
        int secondId = Math.Max(accountA, accountB);

        using var conn = new SqlConnection(connString);
        await conn.OpenAsync();
        using var tx = conn.BeginTransaction(IsolationLevel.ReadCommitted);

        try
        {
            // Крок 1: спершу "торкаємось" рядка з МЕНШИМ Id (незалежно від того, дебет це чи кредит)
            using (var lockFirst = conn.CreateCommand())
            {
                lockFirst.Transaction = tx;
                lockFirst.CommandText = "SELECT Balance FROM Accounts WITH (UPDLOCK) WHERE Id = @id";
                lockFirst.Parameters.AddWithValue("@id", firstId);
                await lockFirst.ExecuteScalarAsync();
            }

            // Крок 2: потім рядок з БІЛЬШИМ Id
            using (var lockSecond = conn.CreateCommand())
            {
                lockSecond.Transaction = tx;
                lockSecond.CommandText = "SELECT Balance FROM Accounts WITH (UPDLOCK) WHERE Id = @id";
                lockSecond.Parameters.AddWithValue("@id", secondId);
                await lockSecond.ExecuteScalarAsync();
            }

            // Тепер обидва рядки заблоковано в консистентному порядку -- виконуємо реальні зміни
            using var debit = conn.CreateCommand();
            debit.Transaction = tx;
            debit.CommandText = "UPDATE Accounts SET Balance = Balance - @amt WHERE Id = @from";
            debit.Parameters.AddWithValue("@amt", amountAtoB);
            debit.Parameters.AddWithValue("@from", accountA);
            await debit.ExecuteNonQueryAsync();

            using var credit = conn.CreateCommand();
            credit.Transaction = tx;
            credit.CommandText = "UPDATE Accounts SET Balance = Balance + @amt WHERE Id = @to";
            credit.Parameters.AddWithValue("@amt", amountAtoB);
            credit.Parameters.AddWithValue("@to", accountB);
            await credit.ExecuteNonQueryAsync();

            tx.Commit();
            Console.WriteLine($"Переказ {accountA} -> {accountB} успішний (безпечний порядок блокування).");
        }
        catch (Exception ex)
        {
            tx.Rollback();
            Console.WriteLine($"Помилка переказу: {ex.Message}");
        }
    }
}
```

**Консольний вивід проблемного сценарію (типовий, недетермінований результат):**
```
DEADLOCK виявлено під час переказу 2 -> 1. Транзакцію відкочено.
Переказ 1 -> 2 успішний.
```

**Консольний вивід виправленого сценарію (обидві транзакції завжди спочатку блокують менший Id):**
```
Переказ 1 -> 2 успішний (безпечний порядок блокування).
Переказ 2 -> 1 успішний (безпечний порядок блокування).
```

У виправленій версії deadlock **структурно неможливий**: якщо задача 2 (2 → 1) запускається, поки задача 1 (1 → 2) вже тримає lock на рядок `firstId` (тобто рядок 1), задача 2 просто **чекає** на цей самий рядок 1 (бо теж намагається заблокувати його першим, зважаючи на `Math.Min`), а не намагається спершу заблокувати рядок 2 і створити цикл очікування.

## 8. Реальний сценарій: обробка замовлення з паралельним доступом

Розглянемо наскрізний, максимально практичний приклад, що поєднує майже всі концепції цього документа: **два покупці одночасно намагаються купити останню одиницю товару** (`stock = 1`).

### 8.1 Що відбувається без належного контролю конкурентності (баг з overselling)

```
Час  | Покупець 1 (T-A)                    | Покупець 2 (T-B)
-----|--------------------------------------|--------------------------------------
 t1  | BEGIN TRANSACTION                    |
 t2  | SELECT stock FROM products            |
     |   WHERE id = 999                      |
     | --> stock = 1                         |
 t3  |                                       | BEGIN TRANSACTION
 t4  |                                       | SELECT stock FROM products
     |                                       |   WHERE id = 999
     |                                       | --> теж stock = 1 (!)
 t5  | -- застосунок бачить stock=1 >= 1,    |
     |    вирішує: "можна продати"           |
     | UPDATE products SET stock = 0         |
     |   WHERE id = 999                      |
     | INSERT INTO orders (...)              |
 t6  | COMMIT   -- Покупець 1 отримав товар  |
 t7  |                                       | -- застосунок ТЕЖ бачить stock=1 >= 1
     |                                       |    (перевірка робилась на СТАРИХ даних!)
     |                                       |    вирішує: "можна продати"
     |                                       | UPDATE products SET stock = 0 - 1 = -1
     |                                       |   WHERE id = 999
     |                                       | INSERT INTO orders (...)
 t8  |                                       | COMMIT   -- Покупець 2 ТЕЖ отримав товар (!)
-----|---------------------------------------|--------------------------------------
     | Підсумок: продано ДВА замовлення на товар, якого був лише ОДИН екземпляр.
     | stock у базі даних = -1 (фізично неможливе значення).
     | Це класичний OVERSELLING BUG -- і це саме Lost Update (розділ 3.4)
     | в застосуванні до складського обліку.
```

Причина: обидві транзакції прочитали `stock = 1` **до того**, як хтось із них закомітив зміну, і кожна діяла на основі вже застарілої (на момент запису) інформації. Read Committed (типовий default) тут **не рятує** — він лише гарантує, що читання не буде "брудним", але нічого не каже про те, що станеться, якщо два читання відбулися одночасно, а записи — послідовно.

### 8.2 Рішення 1: Pessimistic Locking (SELECT ... FOR UPDATE)

```sql
BEGIN TRANSACTION;

-- Захоплюємо EXCLUSIVE lock на рядок ОДРАЗУ під час читання
SELECT stock FROM products WHERE id = 999 FOR UPDATE;
-- Якщо інша транзакція вже виконує SELECT ... FOR UPDATE на цей самий рядок,
-- ця команда БЛОКУЄТЬСЯ (чекає), доки та транзакція не завершиться (COMMIT/ROLLBACK)

-- ... застосунок перевіряє: stock >= 1 ? ...

UPDATE products SET stock = stock - 1 WHERE id = 999;
INSERT INTO orders (...) VALUES (...);

COMMIT; -- lock звільняється, наступна транзакція в черзі отримує ВЖЕ ОНОВЛЕНИЙ stock
```

Тепер T-B, що намагається виконати `SELECT ... FOR UPDATE` на той самий рядок, **фізично чекає**, доки T-A не закомітить. Коли T-B нарешті отримує lock, вона бачить **вже оновлений** `stock = 0` — і коректно відмовляє покупцю 2 в замовленні ("товар закінчився"), замість того, щоб продати неіснуючу одиницю.

### 8.3 Рішення 2: Optimistic Concurrency Control

```sql
-- Крок 1: читання БЕЗ будь-якого блокування
SELECT stock, version FROM products WHERE id = 999;
-- --> stock = 1, version = 7

-- ... застосунок перевіряє в пам'яті: stock >= 1 -> можна продовжувати ...

-- Крок 2: запис з умовною перевіркою версії
BEGIN TRANSACTION;
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 999 AND version = 7;  -- умова: ніхто інший не встиг змінити рядок

-- якщо affected rows == 0 -> хтось інший устиг оновити першим -> RETRY:
--   перечитати stock/version заново і повторити спробу (або відмовити, якщо stock=0)
COMMIT;
```

Тут обидва покупці читають одночасно без блокування (`stock=1, version=7` для обох). Але лише **один** `UPDATE ... WHERE version = 7` реально спрацює (перший, хто його виконає) — версія в базі одразу стане `8`, і другий `UPDATE ... WHERE version = 7` поверне **0 affected rows**, бо умова `version = 7` більше не виконується. Застосунок покупця 2 бачить "0 rows updated", перечитує актуальний `stock` (тепер уже `0`) і коректно повідомляє: "На жаль, товар щойно розкупили".

### 8.4 Компроміс: коли обирати що для високонавантаженого checkout

| Критерій | Pessimistic Locking (`FOR UPDATE`) | Optimistic Concurrency (`version`) |
|---|---|---|
| Простота реалізації | Проста, зрозуміла ментальна модель | Потребує явної retry-логіки в застосунку |
| Поведінка при конфлікті | Друга транзакція **чекає** (blocking) | Друга транзакція **провалюється миттєво**, потребує retry |
| Масштабованість при **рідкісних** конфліктах | Надлишкові витрати на lock/unlock навіть коли конфліктів немає | Майже нульові накладні витрати, коли конфліктів немає — ідеально |
| Масштабованість при **дуже частих** конфліктах на один рядок (hot row) | Транзакції вишиковуються в чергу — передбачувано, хоч і повільно | Багато марних retry-циклів, можливе "живе тупцювання" (livelock) під дуже високим навантаженням |
| Ризик deadlock | Є (якщо кілька рядків блокуються в різному порядку — розділ 6) | Відсутній (блокувань немає взагалі) |
| Типове застосування | Банківські перекази, бухгалтерія, "hot" лічильники з малою кількістю унікальних рядків | Каталоги товарів, CRM/CMS-редагування записів, коли одночасне редагування того самого запису — рідкість |

**Практична рекомендація для e-commerce checkout із високим навантаженням на "останню одиницю" товару:** якщо очікується **шторм** одночасних запитів саме на один і той самий "гарячий" товар (наприклад, flash sale), **pessimistic locking** з коротким, чітко обмеженим у часі блокуванням (розділ 9) зазвичай передбачуваніший і простіший в експлуатації, ніж каскад retry при optimistic concurrency. Якщо ж конфлікти рідкісні й розподілені по тисячах різних товарів, **optimistic concurrency** масштабується краще, бо не витрачає ресурси на блокування там, де конфлікту, найімовірніше, взагалі не станеться. У продакшн-системах нерідко комбінують обидва підходи: optimistic concurrency як типовий шлях + окремий "запобіжник" на рівні дуже коротких pessimistic locks або atomic-декремент лічильника (`UPDATE ... SET stock = stock - 1 WHERE stock > 0`, без окремого читання взагалі) саме для "гарячих" товарів.

## 9. Поширені помилки

### Помилка 1: занадто довгі транзакції (тримання блокувань під час зовнішніх викликів)

**❌ Погано:**
```csharp
using var tx = connection.BeginTransaction();

var order = LoadOrderForUpdate(connection, tx, orderId); // SELECT ... FOR UPDATE, lock захоплено

await emailService.SendOrderConfirmationAsync(order.CustomerEmail); // виклик ЗОВНІШНЬОГО API!
// -- поки email-сервіс відповідає (може бути 2-3 секунди, або й таймаут 30 секунд),
//    lock на рядок order ПРОДОВЖУЄ ТРИМАТИСЯ, блокуючи всіх інших,
//    хто хоче торкнутись цього самого замовлення

UpdateOrderStatus(connection, tx, orderId, "confirmed");
tx.Commit();
```

Це один із найпоширеніших і найважчих для діагностики реальних performance-багів: транзакція (і, відповідно, усі її блокування) тримається відкритою протягом усього часу очікування відповіді від зовнішнього сервісу — HTTP API, черги повідомлень, навіть просто повільного диска. Якщо зовнішній сервіс "підвисне" на 30 секунд (мережевий таймаут) — усі інші транзакції, яким потрібен цей самий рядок (або гірше — та сама таблиця, якщо блокування ескалувалось), теж чекатимуть ці 30 секунд, ланцюжково блокуючи весь застосунок.

**✅ Добре:**
```csharp
Order order;
using (var tx = connection.BeginTransaction())
{
    order = LoadOrderForUpdate(connection, tx, orderId);
    UpdateOrderStatus(connection, tx, orderId, "confirmed");
    tx.Commit(); // транзакція закрита -- lock звільнено МАКСИМАЛЬНО ШВИДКО
}

// Зовнішній виклик -- ПОЗА межами транзакції бази даних
await emailService.SendOrderConfirmationAsync(order.CustomerEmail);
```

**Правило:** транзакції мають бути **максимально короткими** — лише операції над самою базою даних. Будь-яка мережева взаємодія, виклик зовнішнього API, надсилання email/SMS, важкі обчислення в пам'яті — все це повинно відбуватись **до** `BEGIN` або **після** `COMMIT`, ніколи всередині.

### Помилка 2: використання Serializable "про всяк випадок" скрізь

**❌ Погано:**
```csharp
// "Serializable -- найбезпечніший рівень, поставлю його всюди для надійності"
using var tx = connection.BeginTransaction(IsolationLevel.Serializable);

var product = LoadProduct(connection, tx, productId); // просте читання каталогу товарів
DisplayProductDetails(product);
tx.Commit();
```

Використання `SERIALIZABLE` для звичайного читання картки товару в каталозі — це суттєвий і невиправданий удар по пропускній здатності системи: СУБД змушена або тримати додаткові блокування діапазонів, або (у випадку PostgreSQL SSI) відстежувати додаткові структури для виявлення конфліктів серіалізації — і все це заради сценарію, де взагалі не було жодного ризику аномалії, яку `SERIALIZABLE` покликаний запобігти.

**✅ Добре:**
```csharp
// Read Committed (default) цілком достатньо для простого читання
var product = LoadProduct(connection, productId); // без явної транзакції взагалі, якщо це один SELECT

// А для сценарію "перевірити залишок і продати" -- Read Committed
// + explicit оптимістична конкурентність (розділ 8.3), а НЕ Serializable
using var tx = connection.BeginTransaction(IsolationLevel.ReadCommitted);
var stock = GetStockWithVersion(connection, tx, productId);
// ... UPDATE ... WHERE version = @originalVersion ...
tx.Commit();
```

**Правило:** обирайте **найнижчий** рівень ізоляції, який усе ще гарантує коректність саме вашого сценарію (розділ 4.6). `SERIALIZABLE` варто застосовувати **точково**, лише там, де справді потрібна гарантія відсутності phantom read/write skew (наприклад, складні фінансові звірки, аудит), а не як універсальний "запобіжник за замовчуванням".

### Помилка 3: відсутність retry-логіки для конкурентних помилок

**❌ Погано:**
```csharp
try
{
    await context.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException)
{
    // Просто прокидаємо виняток користувачу як HTTP 500 -- поганий UX
    throw;
}
```

Якщо `DbUpdateConcurrencyException` (розділ 7.3) або deadlock-виняток (розділ 6, розділ 7.4) просто "спливають" до користувача як загальна помилка сервера (HTTP 500 "Щось пішло не так"), користувач бачить незрозумілу помилку там, де насправді достатньо було **тихо повторити операцію** — конфлікт версій чи deadlock часто минущі, і повторна спроба за мілісекунди по тому переважно проходить успішно.

**✅ Добре:**
```csharp
const int maxRetries = 3;
for (int attempt = 1; attempt <= maxRetries; attempt++)
{
    try
    {
        var product = await context.Products.FirstAsync(p => p.Id == productId);
        product.Stock -= quantity;
        await context.SaveChangesAsync();
        break; // успіх -- виходимо з циклу
    }
    catch (DbUpdateConcurrencyException) when (attempt < maxRetries)
    {
        // Конфлікт версій -- перечитуємо АКТУАЛЬНІ дані і пробуємо ще раз
        foreach (var entry in context.ChangeTracker.Entries())
            entry.State = EntityState.Detached; // скидаємо застарілий трекінг
        continue;
    }
    catch (DbUpdateConcurrencyException)
    {
        // Останню спробу теж провалено -- ось тепер справді варто повідомити користувача
        throw new InvalidOperationException(
            "Не вдалося оновити запис через постійні конфлікти. Спробуйте пізніше.");
    }
}
```

**Правило:** конфлікти конкурентності (`DbUpdateConcurrencyException`) та deadlock-помилки (`SqlException` з номером 1205 у SQL Server, `40P01` у PostgreSQL) — це **очікувана, штатна** частина роботи з паралельним доступом, а не виняткова ситуація. Обробляйте їх явним retry з обмеженою кількістю спроб (і бажано — невеликою випадковою затримкою між спробами, exponential backoff), а не даєте їм просто спливати як необроблені помилки.

## 10. Питання для співбесіди за рівнями

### Junior

**1. Розшифруй абревіатуру ACID і коротко поясни кожну літеру.**
> Atomicity (атомарність — все або нічого), Consistency (узгодженість — дані завжди відповідають правилам/constraints), Isolation (ізольованість — паралельні транзакції не заважають одна одній), Durability (довговічність — закомічені дані переживають будь-який збій).

**2. Що таке транзакція простими словами?**
> Група операцій над базою даних, що виконується як єдине ціле: або всі операції застосовуються успішно, або жодна з них (у разі помилки — все відкочується назад, `ROLLBACK`).

**3. Що таке dirty read?**
> Коли одна транзакція читає ще незакомічені (uncommitted) зміни іншої транзакції, і та інша транзакція потім робить rollback — тобто прочитане значення "ніколи насправді не існувало" в базі даних.

**4. Який рівень ізоляції зазвичай є default у більшості СУБД?**
> `READ COMMITTED` — це default у PostgreSQL, SQL Server та Oracle. У MySQL/InnoDB за замовчуванням `REPEATABLE READ`.

**5. Що робить команда COMMIT? А ROLLBACK?**
> `COMMIT` — назавжди фіксує всі зміни транзакції в базі даних (вони стають видимими для інших і переживуть будь-який збій). `ROLLBACK` — скасовує всі зміни транзакції, повертаючи базу даних до стану "до BEGIN".

**6. Навіщо взагалі потрібні транзакції, якщо можна просто виконувати запити по черзі?**
> Без транзакцій немає гарантії атомарності: якщо застосунок впаде між двома пов'язаними `UPDATE`, база даних залишиться в невалідному, "напівзробленому" стані (наприклад, гроші списані з одного рахунку, але не зараховані на інший).

**7. Що таке WAL (Write-Ahead Log) на дуже базовому рівні?**
> Журнал, куди СУБД спочатку записує заплановану зміну, і лише потім (або паралельно) застосовує її до реальних файлів даних — це дозволяє відновити закомічені зміни після збою (durability).

### Middle

**1. Чим Repeatable Read відрізняється від Serializable?**
> `REPEATABLE READ` гарантує, що повторне читання **того самого рядка** в межах транзакції завжди поверне те саме значення, але за класичним визначенням стандарту SQL все ще допускає phantom read (нові рядки можуть з'явитись у повторному діапазонному запиті). `SERIALIZABLE` — найсуворіший рівень, який гарантує, що результат виконання паралельних транзакцій еквівалентний якомусь послідовному порядку їх виконання, і виключає навіть phantom read.

**2. Що таке phantom read і чим він відрізняється від non-repeatable read?**
> Non-repeatable read — про зміну значення **одного вже прочитаного рядка** між двома читаннями в межах транзакції. Phantom read — про зміну **складу набору рядків**, що задовольняють умові діапазонного запиту (`WHERE`): з'являються або зникають цілі рядки, яких не було (або, навпаки, були) при першому виконанні того самого запиту.

**3. Що таке MVCC і навіщо він потрібен?**
> Multi-Version Concurrency Control — механізм, за якого СУБД зберігає кілька версій кожного рядка, і кожна транзакція бачить консистентний "знімок" бази даних станом на момент свого старту. Головна перевага: читачі ніколи не блокують письменників і навпаки, що значно покращує конкурентність для read-heavy навантажень. Використовується в PostgreSQL, MySQL/InnoDB, Oracle.

**4. Чим оптимістична конкурентність відрізняється від песимістичної?**
> Pessimistic locking захоплює блокування **заздалегідь**, до читання/запису — інші транзакції фізично чекають. Optimistic concurrency **не бере жодних блокувань** — читає дані з версійним полем, а в момент запису перевіряє, чи версія не змінилась; якщо змінилась — конфлікт виявляється й потрібен retry. Оптимістичний підхід кращий, коли конфлікти рідкісні; песимістичний — коли конфлікти часті або критично важливо гарантувати відсутність конфлікту одразу.

**5. Що таке Lost Update і чим він небезпечний?**
> Дві транзакції читають те саме значення, обидві обчислюють нове значення на його основі, і остання успішна операція запису мовчки перезаписує результат першої — без жодної помилки чи попередження. Небезпечний тим, що обидва `COMMIT` проходять успішно, тому проблему важко виявити без спеціального контролю конкурентності (версіонування або блокування).

**6. Чому Read Uncommitted майже ніколи не використовується на практиці?**
> Бо він не запобігає жодній з чотирьох класичних аномалій, зокрема dirty read — найгрубішій і найнебезпечнішій, коли транзакція може прийняти рішення на основі даних, яких насправді ніколи не існувало в базі (бо їх було відкочено).

**7. Як EF Core реалізує оптимістичну конкурентність?**
> Через властивість з атрибутом `[Timestamp]` (або `.IsRowVersion()` у Fluent API) — EF Core автоматично додає `WHERE RowVersion = @original_value` до кожного `UPDATE`/`DELETE`. Якщо жодного рядка не змінено (версія не збіглась), EF Core кидає `DbUpdateConcurrencyException`.

### Senior

**1. Опиши сценарій lost update детально і як його запобігти на практиці.**
> Класичний приклад: два процеси читають той самий рядок (наприклад, залишок товару = 10), кожен обчислює нове значення на основі прочитаного (наприклад, "продали 1, новий залишок = 9"), і обидва записують. Останній запис перезаписує перший — фізично продано 2 одиниці, а `stock` зменшився лише на 1. Запобігання: (1) **оптимістична конкурентність** — версійне поле (`version`/`RowVersion`), яке перевіряється в `WHERE`-умові при `UPDATE`; конфлікт виявляється як 0 affected rows або виняток, і застосунок повторює операцію на свіжих даних; (2) **песимістичне блокування** — `SELECT ... FOR UPDATE`, яке гарантує, що ніхто інший не прочитає той самий рядок для запису, поки перша транзакція не завершиться; (3) **атомарні SQL-вирази**, що уникають окремого читання взагалі — наприклад, `UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock >= 1`, де вирахування нового значення відбувається одним атомарним виразом безпосередньо в базі даних, без проміжного читання в застосунку.

**2. Як би ти діагностував і виправив deadlock у продакшені?**
> Діагностика: більшість СУБД логують деталі deadlock у момент його виникнення (у SQL Server — deadlock graph через Extended Events/Profiler; у PostgreSQL — записи в лог з `log_lock_waits`; у MySQL — `SHOW ENGINE INNODB STATUS` показує останній deadlock). З цих логів видно, які саме дві (чи більше) транзакції та в якому порядку блокували які ресурси (рядки/таблиці/індекси), і який SQL-запит кожна виконувала в момент конфлікту. Виправлення: (1) знайти код застосунку, що породжує ці два запити, і привести порядок доступу до ресурсів до **консистентного** (наприклад, завжди сортувати ID рядків перед `UPDATE`); (2) скоротити тривалість транзакцій, щоб зменшити "вікно" для конфлікту; (3) де можливо — знизити рівень блокування (row-level замість table-level) або перейти на оптимістичну конкурентність, якщо специфіка даних дозволяє; (4) переконатись, що застосунок має retry-логіку для перехоплення помилки deadlock (SQLSTATE `40P01`/error 1205) і повторної спроби транзакції.

**3. Коли ти обрав би pessimistic locking замість optimistic concurrency в реальній системі?**
> Коли: (а) конфлікти на той самий рядок **часті** (наприклад, лічильник залишку "гарячого" товару під час flash sale) — оптимістичний підхід призвів би до каскаду невдалих retry; (б) вартість "провалу в останню мить" неприйнятна з точки зору UX або бізнес-логіки (наприклад, у платіжних/бухгалтерських системах простіше й безпечніше одразу заблокувати ресурс, ніж будувати складну логіку компенсації після невдалого коміту); (в) транзакція коротка й швидка — тоді вартість тримання блокування мінімальна, і pessimistic locking не завдає суттєвої шкоди пропускній здатності. Натомість якщо операція користувача може тривати довго (заповнення форми) або конфлікти рідкісні — оптимістична конкурентність майже завжди краща.

**4. Поясни, чому "Consistency" в ACID — це не те саме, що "Consistency" в CAP theorem.**
> В ACID Consistency стосується **однієї бази даних (або одного вузла)** і означає, що транзакція завжди переводить дані з одного валідного стану в інший валідний стан відповідно до визначених constraints/бізнес-правил (foreign keys, check constraints, тригери) — це про **цілісність даних**. У CAP theorem Consistency стосується **розподіленої системи з кількома вузлами/репліками** і означає, що всі вузли повертають **однакові (найсвіжіші) дані** в будь-який момент часу — це про **свіжість і синхронізацію копій даних** між вузлами, а не про бізнес-правила. Система може бути ACID-consistent (усі constraints виконуються на кожному вузлі окремо), але НЕ CAP-consistent (різні репліки тимчасово показують різні, хоч і кожна по собі валідні, значення через затримку реплікації) — і навпаки. Це два незалежних виміри якості системи, які випадково позначені тим самим словом.

**5. Спроєктуй механізм запобігання oversell для високонавантаженого checkout.**
> Багаторівневий підхід: (1) **На рівні бази даних** — атомарний decrement із умовою в одному запиті: `UPDATE products SET stock = stock - 1 WHERE id = @id AND stock > 0`, перевірка `affected rows == 1` як індикатор успіху — це уникає окремого читання й запису, тому Lost Update структурно неможливий навіть без явних блокувань чи версій. (2) **Для екстремально "гарячих" товарів** (flash sale на один SKU з тисячами одночасних запитів) — розглянути винесення лічильника залишку в швидке in-memory сховище (Redis, атомарний `DECR`) як "gatekeeper" перед тим, як узагалі торкатись реляційної БД, з подальшою асинхронною синхронізацією; або чергу запитів (queue), що обробляє покупки послідовно, усуваючи паралелізм там, де він і є джерелом проблеми. (3) **Ідемпотентність замовлень** — унікальний ключ ідемпотентності на запит клієнта, щоб повторні мережеві retry (наприклад, через таймаут на клієнті) не створювали дублікати замовлень. (4) **Моніторинг і алертинг** на кількість невдалих спроб купівлі (`affected rows == 0`) для конкретного товару — сплеск відмов сигналізує про справжній ажіотажний попит і може використовуватись бізнесом (наприклад, для динамічного повідомлення "залишилось мало"). (5) **Компенсаційна логіка** — якщо у виняткових випадках (наприклад, при міграції між системами чи ручному втручанні) все ж стався oversell, має існувати чіткий бізнес-процес компенсації (пропозиція альтернативи, знижка, пріоритетна доставка при поповненні) — технічний механізм зменшує ймовірність до майже нуля, але "майже нуль" — не "нуль" у розподілених системах з реальними мережевими збоями.

**6. Чому Serializable у PostgreSQL реалізовано інакше, ніж просте блокування, і які в цього наслідки?**
> PostgreSQL реалізує `SERIALIZABLE` через **Serializable Snapshot Isolation (SSI)** — оптимістичний механізм, побудований поверх MVCC: транзакції виконуються паралельно на своїх снапшотах без явних блокувань діапазонів, а СУБД відстежує залежності читання/запису між транзакціями і виявляє потенційні цикли серіалізації. Якщо конфлікт виявлено, одна з транзакцій отримує помилку `40001 (serialization_failure)` у момент `COMMIT` (а не блокується заздалегідь). Наслідок для розробника: `SERIALIZABLE`-транзакції в PostgreSQL **обов'язково потребують retry-логіки** в застосунку (на відміну від чистого блокування, де транзакція просто чекає довше, але зрештою виконується) — це свідомий архітектурний trade-off на користь кращої конкурентності під низьким рівнем конфліктів ціною необхідності обробляти відмови на рівні коду.

**7. Наскільки транзакція, що охоплює кілька мікросервісів/баз даних, узгоджується з класичним ACID, і що з цим робити?**
> Класичний ACID гарантується лише в межах **однієї** транзакційної СУБД. Коли операція охоплює кілька незалежних сервісів/баз даних (наприклад, "списати гроші" в одному сервісі й "зарезервувати товар" в іншому), звичайна розподілена ACID-транзакція або недоступна, або вкрай дорога (двофазний коміт, 2PC, зі своїми проблемами доступності при падінні координатора). На практиці застосовують патерни на кшталт **Saga** (послідовність локальних транзакцій з компенсуючими діями на випадок часткового провалу) або **Outbox pattern** (атомарний запис бізнес-зміни та "події для інших сервісів" в межах однієї локальної транзакції, з подальшою гарантованою доставкою події) — це усвідомлена відмова від суворого ACID на користь **eventual consistency** між сервісами, компенсована явною бізнес-логікою для обробки часткових збоїв. Це вже межа з темою розподілених систем і CAP theorem (детально — в окремих документах серії, присвячених NoSQL і розподіленим базам даних).

## 11. Підсумок

### ACID — коротко

| Властивість | Суть |
|---|---|
| **Atomicity** | Все або нічого — жодних "напівзроблених" транзакцій |
| **Consistency** | Дані завжди відповідають constraints/бізнес-правилам (не плутати з Consistency в CAP!) |
| **Isolation** | Паралельні транзакції не заважають одна одній так, ніби виконуються послідовно |
| **Durability** | Закомічені дані переживають будь-який наступний збій (завдяки WAL) |

### Рівні ізоляції × аномалії

| Рівень ізоляції | Dirty Read | Non-Repeatable Read | Phantom Read | Lost Update |
|---|:---:|:---:|:---:|:---:|
| Read Uncommitted | ❌ | ❌ | ❌ | ❌ |
| Read Committed | ✅ | ❌ | ❌ | ❌ |
| Repeatable Read | ✅ | ✅ | ❌* | ❌** |
| Serializable | ✅ | ✅ | ✅ | ✅ |

\* У PostgreSQL фактично запобігає й phantom read завдяки реалізації через MVCC-снапшот, що суворіше за мінімальні вимоги стандарту SQL.
\** Другий конфліктний запис зазвичай провалюється з помилкою серіалізації замість мовчазного перезапису — конкретна поведінка залежить від СУБД.

### Блокування vs MVCC vs Optimistic Concurrency

| | Pessimistic Locking | MVCC | Optimistic Concurrency |
|---|---|---|---|
| Коли береться "захист" | Заздалегідь, до читання/запису | Не потрібен окремий "захист" — версії рядків самі забезпечують снапшот | Лише в момент запису (перевірка версії) |
| Чи блокують читачі письменників | Так (залежно від типу lock) | Ні, ніколи | Ні |
| Ризик deadlock | Так | Немає (для читання), можливий для запису при конфліктуючих UPDATE | Немає (немає блокувань) |
| Поведінка при конфлікті | Очікування (blocking) | Читання завжди консистентне; конфлікт запису — окрема історія | Миттєва відмова + потрібен retry |
| Найкраще підходить для | Часті конфлікти, короткі транзакції, критична коректність "тут і зараз" | Read-heavy навантаження (PostgreSQL, MySQL/InnoDB, Oracle) | Рідкісні конфлікти, довгі "думаючі" транзакції (форми, UI-редагування) |

### Ключові практичні правила з цього документа

1. Тримайте транзакції **максимально короткими** — жодних зовнішніх викликів (HTTP, email, черги) всередині `BEGIN...COMMIT`.
2. Обирайте **найнижчий** рівень ізоляції, достатній для коректності конкретного сценарію — не `SERIALIZABLE` "про всяк випадок" скрізь.
3. Завжди звертайтесь до ресурсів (рядків/таблиць) в **консистентному порядку**, щоб структурно виключити deadlock.
4. Обробляйте `DbUpdateConcurrencyException` і deadlock-винятки через **явний retry**, а не даєте їм спливати як помилки користувачу.
5. Для сценаріїв на кшталт "залишок останньої одиниці товару" — свідомо обирайте між pessimistic locking і optimistic concurrency залежно від частоти конфліктів і критичності негайної коректності, а не навмання.
