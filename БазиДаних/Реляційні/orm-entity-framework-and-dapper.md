## 1. Що таке ORM і навіщо він потрібен?

### 1.1 Проблема "impedance mismatch"

Реляційна база даних і об'єктно-орієнтована програма мислять про дані принципово по-різному, і ця різниця має усталену назву — **object-relational impedance mismatch** ("розбіжність опору" між об'єктною та реляційною моделями, за аналогією з електротехнічним терміном — коли два кола з різним опором погано узгоджуються між собою).

Конкретні точки розбіжності:

| Аспект | Реляційна модель (SQL) | Об'єктна модель (OOP) |
|---|---|---|
| **Ідентичність** | Рядок ідентифікується значенням первинного ключа | Об'єкт має посилальну ідентичність (`ReferenceEquals`), два різні об'єкти можуть мати однакові дані |
| **Зв'язки** | Зовнішні ключі + `JOIN` для відновлення зв'язку | Прямі посилання/колекції (`order.Customer`, `customer.Orders`) |
| **Спадкування** | Таблиці не мають вбудованого спадкування | Класи підтримують спадкування та поліморфізм |
| **Гранулярність** | Стовпці — атомарні скалярні значення | Об'єкти можуть інкапсулювати кілька полів в один value object (наприклад, `Money { Amount, Currency }`) |
| **Робота з даними** | Множинна (set-based): один запит обробляє тисячі рядків одразу | Покрокова (imperative): цикли, методи, окремі виклики |
| **Інкапсуляція** | Дані відкриті будь-якому SQL-запиту | Дані заховані за методами/властивостями класу |

Ці розбіжності — не дрібниця, яку можна ігнорувати. Кожен застосунок, що працює з реляційною БД через об'єктну мову програмування, змушений якось "перекладати" між цими двома світоглядами. Робити це вручну (писати `SqlDataReader`, вручну мапити кожен стовпець у властивість класу, вручну генерувати `INSERT`/`UPDATE` для кожної зміни) — величезний обсяг одноманітного, крихкого коду.

### 1.2 Аналогія: універсальний перекладач

Уявіть двох людей, які говорять принципово різними мовами і навіть мислять по-різному: одна людина мислить **таблицями** ("дай мені всі рядки, де...", "об'єднай ці два набори за ключем"), інша — **об'єктами** ("візьми це замовлення і поклич у нього метод `AddItem`"). ORM (Object-Relational Mapper) — це **універсальний перекладач**, що стоїть між ними: розробник говорить об'єктною мовою (створює екземпляри класів, викликає методи, пише LINQ-вирази), а перекладач на льоту перетворює це на SQL-мову таблиць — і навпаки, перетворює рядки результату запиту назад в об'єкти.

### 1.3 Що саме дає ORM

- ✅ **Менше шаблонного коду** — не потрібно вручну писати мапінг `IDataReader` → властивості класу для кожної сутності.
- ✅ **Типобезпека на етапі компіляції** — помилка в назві стовпця в LINQ-виразі (`o.CustomerNam`) — це помилка компіляції, а не рядковий SQL, що впаде лише під час виконання.
- ✅ **Міграції** — схема бази даних еволюціонує разом із кодом, версіюється, накатується автоматично (розділ 3).
- ✅ **Відстеження змін** — ORM сам визначає, які поля змінились, і генерує мінімально необхідний `UPDATE` (розділ 6).
- ✅ **Портованість** — теоретично можна змінити провайдера БД (SQL Server → PostgreSQL) без переписування всього шару доступу до даних.

### 1.4 Головний ризик: діряве абстрагування

ORM — це **дірява абстракція** (leaky abstraction): вона добре ховає складність у 90% випадків, але в решті 10% розробник, який не розуміє, що відбувається на рівні SQL, отримає застосунок, що падає під навантаженням, генерує катастрофічні запити або витрачає непропорційно багато пам'яті. Один невинний з вигляду LINQ-запит або одна властивість, доступна в циклі, можуть згенерувати сотні реальних SQL-запитів до бази (проблема N+1, розділ 5) або витягнути в пам'ять мільйон рядків замість одного агрегованого значення (розділ 7 та 12).

Саме тому **сіньйор-інженер зобов'язаний вміти "заглянути під капот"** ORM: подивитися на реальний згенерований SQL (`.ToQueryString()`, логування EF Core, SQL Profiler), зрозуміти план виконання запиту, оцінити кількість фактичних звернень до БД. ORM не звільняє від знання SQL і індексів — навпаки, чим глибше розуміння реляційної моделі та того, як індекси й плани виконання впливають на продуктивність (див. відповідний розділ цієї серії, присвячений SQL та індексуванню), тим ефективніше й безпечніше можна користуватися ORM. ORM прибирає рутину, але не прибирає відповідальності за продуктивність.

**Коротке правило:** ORM — інструмент для 90% типового CRUD-коду. Розуміння SQL під капотом — те, що відрізняє middle-розробника, який просто "змушує ORM працювати", від сіньйора, який свідомо контролює, які запити йдуть у базу і чому.

## 2. Entity Framework Core — основи

**Entity Framework Core (EF Core)** — офіційний, повнофункціональний ORM від Microsoft для .NET. Дозволяє описувати доменну модель у вигляді звичайних C#-класів (POCO — Plain Old CLR Objects) і працювати з базою даних через LINQ, без написання SQL вручну (хоча можливість виконати "сирий" SQL теж є).

### 2.1 DbContext і DbSet<T>

- **`DbContext`** — центральний клас EF Core, що представляє **сесію роботи з базою даних**. Він:
  - тримає з'єднання з БД (відкриває його лінькво, за потреби);
  - відстежує стан завантажених сутностей (change tracking, розділ 6);
  - надає `DbSet<T>` для кожної таблиці/сутності;
  - на виклик `SaveChanges()` генерує та виконує весь необхідний SQL (`INSERT`/`UPDATE`/`DELETE`) в межах однієї транзакції.

  У ASP.NET Core `DbContext` зазвичай реєструється в DI-контейнері зі **scoped** життєвим циклом — один екземпляр на один HTTP-запит. Це важливо: `DbContext` **не є потокобезпечним** і не призначений для довготривалого зберігання (наприклад, як singleton) — довге життя контексту накопичує відстежувані сутності в пам'яті й може повертати "застарілі" дані.

- **`DbSet<T>`** — властивість типу `DbSet<TEntity>` на `DbContext`, що представляє **колекцію сутностей одного типу**, доступну для LINQ-запитів (`context.Orders.Where(...)`) та для додавання/видалення (`context.Orders.Add(order)`).

### 2.2 Схема прикладу: інтернет-магазин

Для наскрізних прикладів у цьому документі використовується типова e-commerce-схема: **Customers → Orders → OrderItems → Products → Categories**.

```csharp
public class Customer
{
    public int CustomerId { get; set; }
    public string FullName { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;

    public List<Order> Orders { get; set; } = new();
}

public class Category
{
    public int CategoryId { get; set; }
    public string Name { get; set; } = string.Empty;

    public List<Product> Products { get; set; } = new();
}

public class Product
{
    public int ProductId { get; set; }
    public string Name { get; set; } = string.Empty;
    public decimal Price { get; set; }

    public int CategoryId { get; set; }
    public Category Category { get; set; } = null!;

    public List<Review> Reviews { get; set; } = new();
}

public class Review
{
    public int ReviewId { get; set; }
    public int Rating { get; set; } // 1..5
    public string Comment { get; set; } = string.Empty;

    public int ProductId { get; set; }
    public Product Product { get; set; } = null!;
}

public class Order
{
    public int OrderId { get; set; }
    public DateTime CreatedAt { get; set; }

    public int CustomerId { get; set; }
    public Customer Customer { get; set; } = null!;

    public List<OrderItem> Items { get; set; } = new();
}

public class OrderItem
{
    public int OrderItemId { get; set; }
    public int Quantity { get; set; }
    public decimal UnitPrice { get; set; }

    public int OrderId { get; set; }
    public Order Order { get; set; } = null!;

    public int ProductId { get; set; }
    public Product Product { get; set; } = null!;
}
```

### 2.3 Два способи конфігурації: Data Annotations vs Fluent API

**Data Annotations** — атрибути прямо над властивостями класу:

```csharp
public class Customer
{
    [Key]
    public int CustomerId { get; set; }

    [Required, MaxLength(256)]
    public string Email { get; set; } = string.Empty;
}
```

- ✅ Швидко, наочно, добре для невеликих проєктів і прототипів.
- ❌ "Забруднює" доменну модель посиланнями на `System.ComponentModel.DataAnnotations` — модель перестає бути "чистим" POCO.
- ❌ Не всі можливості EF Core можна виразити атрибутами (складені ключі, фільтровані індекси, конвертери значень, тіньові властивості).

**Fluent API** — конфігурація в `OnModelCreating` (або в окремих класах `IEntityTypeConfiguration<T>`):

```csharp
public class ShopDbContext : DbContext
{
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Product> Products => Set<Product>();
    public DbSet<Review> Reviews => Set<Review>();
    public DbSet<Order> Orders => Set<Order>();
    public DbSet<OrderItem> OrderItems => Set<OrderItem>();

    public ShopDbContext(DbContextOptions<ShopDbContext> options) : base(options) { }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Customer>(e =>
        {
            e.HasKey(c => c.CustomerId);
            e.Property(c => c.Email).IsRequired().HasMaxLength(256);
            e.HasIndex(c => c.Email).IsUnique();
        });

        modelBuilder.Entity<Category>(e =>
        {
            e.HasKey(c => c.CategoryId);
            e.Property(c => c.Name).IsRequired().HasMaxLength(128);
        });

        modelBuilder.Entity<Product>(e =>
        {
            e.HasKey(p => p.ProductId);
            e.Property(p => p.Price).HasColumnType("decimal(18,2)");
            e.HasOne(p => p.Category)
             .WithMany(c => c.Products)
             .HasForeignKey(p => p.CategoryId)
             .OnDelete(DeleteBehavior.Restrict);
        });

        modelBuilder.Entity<Review>(e =>
        {
            e.HasKey(r => r.ReviewId);
            e.HasOne(r => r.Product)
             .WithMany(p => p.Reviews)
             .HasForeignKey(r => r.ProductId);
        });

        modelBuilder.Entity<Order>(e =>
        {
            e.HasKey(o => o.OrderId);
            e.HasOne(o => o.Customer)
             .WithMany(c => c.Orders)
             .HasForeignKey(o => o.CustomerId)
             .OnDelete(DeleteBehavior.Restrict);
        });

        modelBuilder.Entity<OrderItem>(e =>
        {
            e.HasKey(oi => oi.OrderItemId);
            e.Property(oi => oi.UnitPrice).HasColumnType("decimal(18,2)");
            e.HasOne(oi => oi.Order).WithMany(o => o.Items).HasForeignKey(oi => oi.OrderId);
            e.HasOne(oi => oi.Product).WithMany().HasForeignKey(oi => oi.ProductId);
        });
    }
}
```

- ✅ Домен лишається "чистим" POCO без залежності від EF Core.
- ✅ Виразніше й потужніше: складені ключі, конвертери типів, тіньові властивості, точний контроль над кожним нюансом мапінгу.
- ✅ Легко винести конфігурацію кожної сутності в окремий клас (`IEntityTypeConfiguration<Order>`), що масштабується на десятки сутностей без роздування `OnModelCreating`.
- 🧩 **Практична порада (senior-level):** у великих проєктах Fluent API + окремі класи конфігурації на кожну сутність — де-факто стандарт. Data Annotations лишають для дрібних допоміжних DTO чи прототипів.

## 3. Міграції (Migrations)

**Міграція** — це версійований, інкрементальний C#-клас, що описує **одну зміну схеми бази даних**: створення таблиці, додавання стовпця, зміну типу, додавання індексу тощо. Кожна міграція має метод `Up()` (застосувати зміну) і `Down()` (відкотити зміну). EF Core зберігає список уже застосованих міграцій у службовій таблиці бази даних `__EFMigrationsHistory`.

### 3.1 Типовий робочий процес

```bash
# Створити нову міграцію на основі поточних відмінностей моделі й останнього знімка
dotnet ef migrations add AddCustomerEmailIndex

# (те саме в Package Manager Console у Visual Studio)
Add-Migration AddCustomerEmailIndex

# Застосувати всі неприйняті міграції до бази даних
dotnet ef database update

# (те саме в PMC)
Update-Database
```

Приклад згенерованого файлу міграції:

```csharp
public partial class AddCustomerEmailIndex : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.CreateIndex(
            name: "IX_Customers_Email",
            table: "Customers",
            column: "Email",
            unique: true);
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropIndex(
            name: "IX_Customers_Email",
            table: "Customers");
    }
}
```

### 3.2 Сіньйорські нюанси роботи з міграціями в команді/продакшені

- ⚠️ **Ніколи не довіряйте `dotnet ef database update` наосліп проти продакшн-бази.** Замість прямого застосування генеруйте **ідемпотентний SQL-скрипт** для рев'ю (DBA, code review, CI/CD pipeline):
  ```bash
  dotnet ef migrations script --idempotent -o migration.sql
  ```
  Цей скрипт можна прочитати, перевірити на предмет блокувань довгих таблиць, небезпечних `ALTER TABLE`, відсутніх індексів — і застосувати керовано (через пайплайн деплою), а не через `dotnet ef` напряму з локальної машини розробника.

- ⚠️ **Конфлікти міграцій із паралельних гілок.** Якщо два розробники одночасно створюють міграції від однієї й тієї ж "останньої" точки в різних гілках, після мержу виникає **нелінійна історія**: два файли міграцій, кожен вважає себе "наступним" після спільного предка, а знімок моделі (`ModelSnapshot`) конфліктує. Типове вирішення:
  1. Один з розробників перебазовує свою гілку на актуальний `main` **після** того, як міграція іншого вже змержена.
  2. Видаляє свою локальну (ще не застосовану ніде) міграцію (`dotnet ef migrations remove`).
  3. Перегенеровує її заново поверх оновленої моделі — тепер вона коректно "йде після" міграції колеги.
  
  Якщо обидві міграції вже застосовані в різних середовищах (наприклад, у різних розробників локально) — потрібно акуратно звести `__EFMigrationsHistory` вручну або застосувати обидві послідовно там, де це можливо.

- 🚫 **Небезпека редагування вже застосованої міграції.** Якщо міграція вже накочена хоч на одному спільному середовищі (staging, продакшн, гілка колеги), **редагувати її файл заднім числом — заборонено**. EF Core визначає застосовані міграції за іменем/поряднком у таблиці історії, а не перевіряє контрольну суму коду — тобто якщо ви зміните вже застосовану міграцію, середовища, де вона вже виконана, **ніколи не отримають виправлення**, а нові середовища виконають вже змінену версію. Результат — розбіжність (drift) між тим, що записано в історії міграцій, і фактичною структурою різних баз даних, яку потім вкрай важко діагностувати. Правильний підхід — **завжди створювати нову міграцію** для виправлення помилки, навіть якщо вона просто скасовує щойно зроблене.

- 🧩 **Безпечна еволюція схеми без простою (zero-downtime).** Наприклад, додавання `NOT NULL`-стовпця в таблицю, що вже використовується продакшн-застосунком старої версії коду під час деплою, зазвичай робиться в кілька кроків:
  1. Міграція 1: додати стовпець як **nullable**.
  2. Backfill-скрипт: заповнити значення для існуючих рядків.
  3. Міграція 2 (пізніше, коли весь код уже оновлено): зробити стовпець `NOT NULL` з дефолтним значенням.
  
  Це дозволяє старій і новій версії застосунку одночасно працювати з однією базою під час поетапного розкатування (rolling deployment).

## 4. Завантаження пов'язаних даних: Eager, Lazy, Explicit Loading

Коли сутність має навігаційні властивості (`Order.Customer`, `Customer.Orders`), постає питання: **коли саме** EF Core має завантажити ці пов'язані дані з бази? Є три стратегії.

### 4.1 Eager Loading — `.Include()` / `.ThenInclude()`

Пов'язані дані завантажуються **одразу, у той самий момент**, коли виконується основний запит — явно вказано в LINQ-виразі:

```csharp
var orders = await context.Orders
    .Include(o => o.Customer)
    .Include(o => o.Items)
        .ThenInclude(i => i.Product)
    .ToListAsync();
```

EF Core згенерує один SQL-запит із `JOIN` (або кілька окремих запитів у режимі `AsSplitQuery()`, якщо `Include`-ланцюжків із колекціями кілька — щоб уникнути декартового добутку рядків).

- ✅ Передбачувано: наперед видно, скільки й яких даних буде завантажено.
- ✅ Один (або невелика фіксована кількість) SQL-запит замість багатьох.
- ❌ Легко "перезавантажити" зайве, якщо `.Include()` тягне дані, які насправді не потрібні на цьому екрані (over-fetching).

### 4.2 Lazy Loading — навігаційні властивості, що довантажуються самі

Пов'язані дані завантажуються **автоматично, в момент першого звернення** до навігаційної властивості — без жодного явного виклику в коді. Потребує:
- `virtual` навігаційних властивостей;
- пакета `Microsoft.EntityFrameworkCore.Proxies`;
- `optionsBuilder.UseLazyLoadingProxies()` при конфігурації контексту.

```csharp
var order = await context.Orders.FirstAsync(o => o.OrderId == 1);

// SQL-запит для завантаження Customer виконується САМЕ ТУТ, непомітно для читача коду:
Console.WriteLine(order.Customer.FullName);
```

- ✅ Код виглядає простим і "природним" — ніби `order.Customer` завжди вже там.
- ❌ **Найнебезпечніша стратегія за замовчуванням.** Приховує момент виконання SQL-запиту від розробника, що читає код. У циклі — це пряма дорога до проблеми N+1 (розділ 5).
- ❌ Якщо `DbContext` уже звільнено (наприклад, сутність повернули з методу й контекст вийшов зі scope), звернення до lazy-навігації кине виняток (`ObjectDisposedException` або подібний).

### 4.3 Explicit Loading — ручне завантаження за запитом

Розробник **явно** вирішує, коли довантажити пов'язані дані, викликаючи `.Load()` на записі відстеження:

```csharp
var customer = await context.Customers.FirstAsync(c => c.CustomerId == 1);

// Явно довантажуємо колекцію замовлень саме зараз, саме в цьому місці коду:
await context.Entry(customer)
    .Collection(c => c.Orders)
    .LoadAsync();

// Явно довантажуємо одну навігаційну властивість:
await context.Entry(order)
    .Reference(o => o.Customer)
    .LoadAsync();
```

- ✅ Повний контроль: видно точно, де і коли виконується додатковий запит.
- ✅ Немає магії — читаючи код, одразу розумієш, скільки запитів піде в базу.
- ❌ Більш багатослівно — потрібен явний виклик у кожному місці, де це потрібно.

### 4.4 Порівняльна таблиця

| Стратегія | Коли завантажується | Продуктивність | Головна небезпека | Коли використовувати |
|---|---|---|---|---|
| **Eager (`Include`)** | Одразу, разом з основним запитом | ✅ Передбачувана, 1 (або кілька) запит | Over-fetching, якщо `Include` тягне зайве | Заздалегідь відомо, які пов'язані дані знадобляться (типовий сценарій — сторінка деталей/списку) |
| **Lazy (proxies)** | Автоматично, при першому зверненні до властивості | ❌ Непередбачувана, легко отримати N+1 | Прихована генерація запитів "по одному", ризик винятку після Dispose контексту | Рідко виправдано для продакшн-коду; іноді зручно у прототипах/скриптах |
| **Explicit (`.Load()`)** | Вручну, коли розробник це прописав | ✅ Передбачувана, точна | Легко забути викликати там, де дані таки потрібні | Умовне довантаження ("довантаж лише якщо певна умова виконалась") |

**Практичне правило сіньйора:** за замовчуванням lazy loading варто **вимикати глобально** (не підключати `UseLazyLoadingProxies()`) і свідомо використовувати `Include()` там, де дані потрібні наперед відомо, або `Explicit Loading` там, де довантаження умовне. Це робить кількість запитів до бази передбачуваною й видимою прямо в коді, а не прихованою за "магією" навігаційної властивості.

## 5. Проблема N+1 — детальний розбір

Це, ймовірно, **найважливіша практична пастка** EF Core (і ORM загалом) — і одна з найпопулярніших тем на технічних співбесідах.

### 5.1 Як саме це відбувається

1. Виконується **один** запит, що повертає список із **N** батьківських сутностей (наприклад, `N` замовлень).
2. Для **кожного** з цих `N` замовлень окремо виконується **ще один** запит, щоб довантажити пов'язану сутність (наприклад, `Customer` цього замовлення) — через lazy loading або через ручний виклик усередині циклу.
3. Разом: **1 (батьківський запит) + N (по одному на кожен елемент) = N+1 запитів** до бази даних замість 1–2.

При `N = 1000` замовлень це означає **1001 окремий SQL-запит** там, де достатньо було б одного `JOIN`-запиту. Кожен запит — це окремий network round-trip до сервера БД, парсинг, побудова плану виконання (або взяття з кешу планів) — накладні витрати, які лінійно ростуть із розміром даних і здатні перетворити відповідь за 20 мс на відповідь за кілька секунд.

### 5.2 Приклад "поганого" коду (класичне "знайди баг" на співбесіді)

```csharp
// ❌ ПОГАНО: lazy loading увімкнено, навігаційна властивість Customer — virtual
public class Order
{
    public int OrderId { get; set; }
    public int CustomerId { get; set; }
    public virtual Customer Customer { get; set; } = null!;
    // ...
}

// ...

var orders = await context.Orders.ToListAsync(); // Запит №1: SELECT * FROM Orders

foreach (var order in orders)
{
    // На КОЖНІЙ ітерації, при першому зверненні до order.Customer,
    // EF Core непомітно виконує ОКРЕМИЙ запит:
    // SELECT * FROM Customers WHERE CustomerId = @p0
    Console.WriteLine($"Замовлення #{order.OrderId} належить {order.Customer.FullName}");
}
```

Якщо `orders.Count == 500`, у консолі логів EF Core (`.LogTo(...)`) буде видно:

```
SELECT [o].[OrderId], [o].[CustomerId], ... FROM [Orders] AS [o]              -- 1 запит
SELECT [c].[CustomerId], [c].[FullName], ... FROM [Customers] AS [c]
      WHERE [c].[CustomerId] = @__p_0                                         -- запит для order #1
SELECT [c].[CustomerId], [c].[FullName], ... FROM [Customers] AS [c]
      WHERE [c].[CustomerId] = @__p_0                                         -- запит для order #2
... (ще 498 подібних запитів)
```

**Разом: 1 + 500 = 501 запит.** Це і є "N+1" — назва не випадкова.

### 5.3 Виправлення: Eager Loading

```csharp
// ✅ ДОБРЕ: явно кажемо EF Core завантажити Customer одразу, одним запитом (JOIN)
var orders = await context.Orders
    .Include(o => o.Customer)
    .AsNoTracking() // якщо дані лише для читання (розділ 6)
    .ToListAsync();

foreach (var order in orders)
{
    // Дані вже в пам'яті — жодного додаткового звернення до бази тут немає
    Console.WriteLine($"Замовлення #{order.OrderId} належить {order.Customer.FullName}");
}
```

Тепер у логах — **один** запит (концептуально):

```sql
SELECT o.OrderId, o.CreatedAt, c.CustomerId, c.FullName, c.Email
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.CustomerId
```

**Разом: 1 запит замість 501.** Саме така зміна — додавання одного `.Include(...)` — типово перетворює сторінку зі "секунди на завантаження" на "20 мс на завантаження" в реальних продакшн-інцидентах.

### 5.4 Як виявити N+1 на практиці

- **Увімкнути логування SQL EF Core** й подивитися, скільки реальних запитів виконується на один HTTP-запит:
  ```csharp
  optionsBuilder.UseSqlServer(connectionString)
      .LogTo(Console.WriteLine, LogLevel.Information)
      .EnableSensitiveDataLogging(); // лише для dev/debug!
  ```
- **Профайлери**: SQL Server Profiler / Extended Events, MiniProfiler (вбудована інтеграція з EF Core, показує список усіх запитів прямо на сторінці в браузері під час розробки), Application Insights / OpenTelemetry-трейси в продакшені (кожен SQL-виклик — окремий span; N+1 видно як "гребінець" з однакових коротких запитів підряд).
- **Правило "одне на список":** якщо код виглядає як `foreach` по колекції, а всередині циклу звертається до навігаційної властивості (або викликає метод, що робить запит) — це **сигнал перевірити**, чи не потрібен тут `Include()`.
- У code review — окремо зважати на будь-який `virtual` навігаційний член, доступ до якого відбувається всередині циклу.

## 6. Відстеження змін: Change Tracking, AsNoTracking

### 6.1 Як EF Core відстежує зміни

Коли `DbContext` виконує запит **без** `AsNoTracking()`, для кожної повернутої сутності він:

1. Створює екземпляр класу й заповнює його даними з рядка результату.
2. Робить **знімок (snapshot)** початкових значень усіх властивостей.
3. Реєструє сутність у внутрішньому **change tracker** зі станом `Unchanged`.
4. При будь-якій зміні властивості порівнює поточне значення зі знімком (або одразу позначає стан як `Modified` — залежно від стратегії відстеження) — і при виклику `SaveChanges()` генерує `UPDATE`, що зачіпає (за замовчуванням) стовпці, що реально позначені як модифіковані.

Це те, що дозволяє писати:

```csharp
var customer = await context.Customers.FindAsync(1);
customer.Email = "new@example.com"; // просто присвоєння властивості
await context.SaveChangesAsync();   // EF Core сам згенерує UPDATE Customers SET Email = ... WHERE CustomerId = 1
```

— без жодного ручного `UPDATE`-запиту.

### 6.2 Ціна відстеження

Відстеження **не безкоштовне**:
- **Пам'ять**: для кожної відстежуваної сутності зберігається знімок значень (фактично — подвоєння даних сутності в пам'яті на час життя контексту).
- **CPU**: виявлення змін (`DetectChanges`) проходиться по всіх відстежуваних сутностях і порівнює значення властивість-за-властивістю.
- Це масштабується лінійно з кількістю завантажених сутностей — для запиту, що повертає кілька рядків, різниця непомітна; для запиту, що повертає 50 000 рядків для звіту, накладні витрати стають суттєвими.

### 6.3 `AsNoTracking()` — критична оптимізація для читання

Якщо результати запиту **ніколи не будуть змінені й збережені назад** (типовий випадок — сторінка списку, звіт, API-ендпоінт "лише для читання"), відстеження не потрібне взагалі:

```csharp
// ✅ ДОБРЕ: сторінка списку товарів — дані показуються, але не редагуються тут
var products = await context.Products
    .AsNoTracking()
    .Where(p => p.CategoryId == categoryId)
    .ToListAsync();
```

Переваги:
- ✅ Не створюється знімок значень — менше пам'яті.
- ✅ Не виконується `DetectChanges` для цих сутностей — менше CPU.
- ✅ Швидше виконання запиту загалом (EF Core також може застосувати деякі внутрішні оптимізації для no-tracking запитів).

**Правило:** будь-який LINQ-запит, що обслуговує суто читання (listing-сторінки, звіти, API `GET`-ендпоінти, що повертають DTO), має за замовчуванням мати `.AsNoTracking()`. Відстеження вмикати свідомо лише там, де сутність справді буде змінена й збережена в межах того самого `DbContext`.

Для ще більшого контролю можна встановити поведінку за замовчуванням на рівні контексту:

```csharp
optionsBuilder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
```

— і вмикати відстеження явно (`.AsTracking()`) лише там, де воно справді потрібне (протилежність до типової поведінки за замовчуванням, зручно для застосунків із переважно read-heavy навантаженням, наприклад — публічні каталоги, дашборди).

## 7. LINQ-переклад у SQL та підводні камені

### 7.1 Як працює переклад

Коли ви пишете LINQ-запит проти `DbSet<T>` (`IQueryable<T>`), EF Core **не виконує його одразу**. Замість цього він будує **дерево виразів** (expression tree), аналізує його та **транслює у SQL**, який фактично виконується лише в момент матеріалізації (`.ToList()`, `.First()`, `foreach`, тощо — так званий "відкладений виконання", deferred execution).

Проблема в тому, що **не кожен C#-вираз можна перекласти в SQL**. SQL — це мова з обмеженим набором операцій (порівняння, арифметика, вбудовані функції певного діалекту), тоді як C# дозволяє викликати будь-який метод, включно з довільною логікою.

### 7.2 Явна помилка (fail-fast) — сучасний EF Core

```csharp
bool IsRecent(DateTime date) => date > DateTime.UtcNow.AddDays(-7);

// ❌ IsRecent — звичайний C#-метод, EF Core не знає, як перекласти його в SQL
var recent = await context.Orders
    .Where(o => IsRecent(o.CreatedAt))
    .ToListAsync();
```

У EF Core 3.0+ це, як правило, одразу кидає `InvalidOperationException` із чітким повідомленням, що вираз не може бути перекладений — і це **добре**: помилка видима одразу, а не проявляється як тиха деградація продуктивності.

### 7.3 Значно небезпечніший випадок — тиха клієнтська оцінка

Набагато підступніша ситуація — коли код **компілюється, виконується без винятків і навіть повертає правильний результат**, але робить це вкрай неефективно:

```csharp
// ❌ НЕБЕЗПЕЧНО: AsEnumerable() перемикає виконання з IQueryable (SQL) на IEnumerable (LINQ-to-Objects)
// ще ДО фільтрації — увесь Where() виконується вже в пам'яті, над УСІМА рядками таблиці
var expensiveOrders = context.Orders
    .AsEnumerable()                      // <-- ось тут відбувається SELECT * FROM Orders (усі рядки!)
    .Where(o => o.TotalAmount > 100)     // фільтрація вже в C#, а не в SQL
    .ToList();
```

На тестовій базі з сотнею рядків це працює миттєво й непомітно. У продакшені, коли таблиця `Orders` виросте до мільйонів рядків, цей самий код почне тягнути в пам'ять **всю таблицю цілком** щоразу, коли викликається — типовий приклад проблеми, що "непомітно росте" разом із даними й вибухає в найгірший момент.

Ще один типовий різновид тієї самої пастки — виклик властивості або методу, що має складну логіку, всередині `Where()`, яку EF Core формально вміє перекласти лише частково, тому виконує частину фільтрації на сервері БД, а частину — довантаживши проміжні дані в пам'ять клієнта (часткова клієнтська оцінка підвиразу). Це складніше помітити, ніж явний `AsEnumerable()`, і саме тому важливо перевіряти реальний SQL, а не покладатись на "код скомпілювався і працює".

### 7.4 Як виявити проблему

- **`.ToQueryString()`** — метод на будь-якому `IQueryable<T>`, що повертає **точний SQL-текст**, який буде згенеровано, без фактичного виконання запиту:
  ```csharp
  var query = context.Orders.Where(o => o.TotalAmount > 100);
  Console.WriteLine(query.ToQueryString());
  // Виведе реальний SQL - або кине виняток, якщо переклад неможливий
  ```
- **Логування EF Core** (`LogTo` з категорією `Microsoft.EntityFrameworkCore.Database.Command`) — показує кожен реально виконаний запит під час роботи застосунку; якщо перед очікуваним `SELECT ... WHERE ...` замість фільтра в SQL стоїть `SELECT * FROM Orders` без `WHERE` — це і є сигнал клієнтської оцінки.
- **Ручний рев'ю коду** на предмет `.AsEnumerable()`/`.ToList()`/`.AsQueryable()`-переходів у середині LINQ-ланцюжка **до** фільтрації/сортування/пагінації — золоте правило: `Where`, `OrderBy`, `Select`, `Skip`/`Take` мають виконуватись **до** будь-якого переходу в `IEnumerable`, а не після.

## 8. Dapper — мікро-ORM для контролю та швидкості

### 8.1 Філософія Dapper

**Dapper** — це не повноцінний ORM, а **мікро-ORM**: він не генерує SQL, не має LINQ-провайдера, не відстежує зміни, не керує міграціями. Його єдина відповідальність — **ефективно змапити рядки результату SQL-запиту, який ви написали самі, на C#-об'єкти** (через набір розширювальних методів над `IDbConnection`).

Філософська різниця з EF Core:

| | EF Core | Dapper |
|---|---|---|
| **Хто пише SQL** | EF Core генерує SQL із LINQ-виразу | Розробник пише SQL вручну |
| **Що робить бібліотека** | Переклад LINQ → SQL, change tracking, ідентичність, міграції | Лише мапінг результату запиту → об'єкти (через кешовану IL-компільовану функцію мапера) |

### 8.2 Приклад використання

```csharp
using var connection = new SqlConnection(connectionString);

const string sql = @"
    SELECT o.OrderId, o.CreatedAt, o.CustomerId
    FROM Orders o
    WHERE o.CustomerId = @CustomerId";

var orders = await connection.QueryAsync<Order>(sql, new { CustomerId = customerId });
```

Параметри передаються через анонімний об'єкт — Dapper сам перетворює їх на параметризований запит (`@CustomerId`), тому це **захищено від SQL-ін'єкцій** так само, як параметризовані запити в ADO.NET чи EF Core.

### 8.3 Порівняльна таблиця EF Core vs Dapper

| Критерій | EF Core | Dapper |
|---|---|---|
| **Контроль над згенерованим SQL** | Опосередкований (через LINQ, можна щось не передбачити) | Повний — SQL пишете самі, до символу |
| **Продуктивність / накладні витрати** | Вищі накладні витрати (change tracking, побудова дерева виразів, трансляція) | Мінімальні — тонкий шар над `IDbCommand`/`IDataReader` |
| **Швидкість розробки типового CRUD** | Дуже висока — `Add`/`SaveChanges`, LINQ-фільтри без жодного SQL | Нижча — кожен запит (включно з `INSERT`/`UPDATE`) пишете вручну |
| **Складні звіти / нетривіальні агрегації** | Складно виразити ефективно через LINQ, легко отримати неоптимальний SQL | Природно — просто пишете SQL, який реально хочете виконати |
| **Крива навчання** | Вища — LINQ, change tracking, стратегії завантаження, конфігурація моделі | Нижча — потрібне лише знання SQL і базових атрибутів мапінгу |
| **Міграції схеми** | Вбудовані (розділ 3) | Відсутні — потрібен окремий інструмент (наприклад, DbUp, FluentMigrator) |
| **Найкращий сценарій використання** | Типовий CRUD-застосунок, де продуктивність LINQ-запитів прийнятна, а швидкість розробки важливіша | Продуктивність-критичні ділянки, складні звіти/дашборди, де потрібен точний контроль над планом виконання |

### 8.4 Практичний висновок

Це не питання "що краще", а питання **вибору правильного інструменту під конкретну задачу**. Типова продакшн-архітектура нерідко використовує **обидва** підходи одночасно: EF Core — для основного CRUD-шару застосунку (створення замовлень, оновлення профілю користувача, звичайні списки), і Dapper — для окремих, ретельно оптимізованих запитів (складні звіти, дашборди з агрегаціями, ендпоінти під високим навантаженням, де кожна мілісекунда важлива).

## 9. Repository та Unit of Work поверх ORM

### 9.1 Класичний підхід

**Repository** — патерн, що абстрагує доступ до даних за інтерфейсом, приховуючи деталі конкретного сховища (EF Core, Dapper, файл, зовнішній API):

```csharp
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(int orderId);
    Task<List<Order>> GetByCustomerAsync(int customerId);
    Task AddAsync(Order order);
    void Remove(Order order);
}
```

**Unit of Work** — патерн, що координує кілька операцій над кількома репозиторіями в межах **однієї транзакції/одного збереження**:

```csharp
public interface IUnitOfWork
{
    IOrderRepository Orders { get; }
    ICustomerRepository Customers { get; }
    Task<int> SaveChangesAsync();
}
```

Обидва патерни детально розглядаються із загальних позицій у розділі GoF-патернів цієї серії (Repository — структурний варіант обгортки над джерелом даних, Unit of Work — координаційний патерн, близький за духом до Command/Transaction Script).

### 9.2 Чесний сіньйорський нюанс: чи потрібен цей шар над EF Core?

Тут варто визнати незручну правду: **`DbContext` уже, по суті, є Unit of Work** (усі зміни в межах контексту фіксуються атомарно одним викликом `SaveChanges()`, у межах однієї транзакції), а **`DbSet<T>` уже, по суті, є Repository** (типізована, фільтрована через LINQ, доповнювана й видаляєма колекція сутностей одного типу). Тобто написання власного `IOrderRepository`, що всередині просто робить `context.Orders.Where(...)`, у багатьох випадках додає **ще один шар обгортки над вже готовою абстракцією**, а не реальну нову цінність.

Це — реальна, активно обговорювана дискусія в спільноті .NET, і чесна відповідь — "залежить", а не однозначне "так" чи "ні".

**Аргументи "за" Repository поверх EF Core:**
- Простіше повністю замінити технологію збереження даних (EF Core → Dapper → щось інше) в майбутньому, якщо інтерфейс справді моделює доменні операції, а не 1-в-1 обгортає `DbSet`.
- Юніт-тести бізнес-логіки без реальної БД — досить замокати `IOrderRepository`, не думаючи про специфіку EF Core.
- Гарне місце, щоб інкапсулювати складні, повторно використовувані запити з доменною семантикою (`GetOverdueOrdersAsync()`, `GetTopCustomersByRevenueAsync()`) замість розкиданого по всьому застосунку LINQ.

**Аргументи "проти" (зайва абстракція):**
- Генеричний `IRepository<T>` із `Add`/`Get`/`Update`/`Delete`, що просто прокидує виклики в `DbSet<T>`, не додає жодної цінності — це "абстракція заради абстракції".
- Часто такий репозиторій зрештою змушений або **повертати `IQueryable<T>`** назовні (щоб дозволити гнучку фільтрацію/сортування зверху) — а тоді абстракція зведена нанівець, бо викликач усе одно бачить деталі ORM; або **обростає десятками спеціалізованих методів** (`GetByEmailAndActive`, `GetByEmailAndActiveIncludingOrders`...) — що теж погано масштабується.
- EF Core вже добре тестується без реальної БД через провайдер SQLite in-memory чи InMemory-провайдер — тож аргумент "тестованості" частково втрачає силу, якщо мова про модульні тести, що обслуговує в основному сам механізм запитів.
- `Include()`, `AsNoTracking()`, `ExecuteUpdate`/`ExecuteDelete` (bulk-операції) — потужні можливості EF Core, які generic-репозиторій або приховує, або змушений явно пробросити кожну окремо, роздуваючи інтерфейс.

**Практичний висновок:** якщо репозиторій моделює **реальні доменні операції** (а не є тонкою переобгорткою `DbSet<T>` 1-в-1) — це виправдана, корисна абстракція, особливо в DDD-орієнтованих архітектурах з чіткими агрегатами. Якщо ж це просто generic CRUD-обгортка "про всяк випадок" без реальної потреби колись замінити ORM — це часто зайва індирекція, що додає шар коду, який потрібно підтримувати, не даючи натомість реальної гнучкості. Рішення варто приймати свідомо, під конкретний проєкт, а не за замовчуванням "бо так завжди роблять".

### Приклад 1 — Повний цикл EF Core: читання (Include + AsNoTracking) і запис (change tracking + транзакція)

```csharp
using Microsoft.EntityFrameworkCore;

// --- Читання: тільки для показу даних, зміни зберігати не будемо ---
using (var context = new ShopDbContext(options))
{
    var orders = await context.Orders
        .Include(o => o.Customer)
        .Include(o => o.Items)
            .ThenInclude(i => i.Product)
        .Where(o => o.CreatedAt >= DateTime.UtcNow.AddDays(-30))
        .AsNoTracking()
        .ToListAsync();

    foreach (var order in orders)
    {
        Console.WriteLine($"Замовлення #{order.OrderId} від {order.Customer.FullName}:");
        foreach (var item in order.Items)
            Console.WriteLine($"  - {item.Product.Name} x{item.Quantity} = {item.UnitPrice * item.Quantity:C}");
    }
}

// --- Запис: реальна зміна даних, потребує відстеження й транзакції ---
using (var context = new ShopDbContext(options))
{
    await using var transaction = await context.Database.BeginTransactionAsync();
    try
    {
        var order = await context.Orders
            .Include(o => o.Items)
            .FirstAsync(o => o.OrderId == 42); // БЕЗ AsNoTracking - будемо змінювати

        order.Items.Add(new OrderItem { ProductId = 7, Quantity = 2, UnitPrice = 19.99m });

        var customer = await context.Customers.FindAsync(order.CustomerId);
        customer!.Email = "updated@example.com";

        await context.SaveChangesAsync(); // один UPDATE + один INSERT, в межах транзакції
        await transaction.CommitAsync();

        Console.WriteLine("Замовлення оновлено, транзакцію зафіксовано.");
    }
    catch
    {
        await transaction.RollbackAsync();
        throw;
    }
}
```


### Приклад 2 — Проблема N+1: відтворення й виправлення

```csharp
// Налаштування контексту з увімкненим логуванням SQL для демонстрації
var options = new DbContextOptionsBuilder<ShopDbContext>()
    .UseSqlServer(connectionString)
    .UseLazyLoadingProxies()               // явно вмикаємо lazy loading для демонстрації проблеми
    .LogTo(sql => queryCount++, LogLevel.Information, DbContextLoggerOptions.None)
    .Options;

// ❌ ПОГАНО: N+1
int queryCount = 0;
using (var context = new ShopDbContext(options))
{
    var orders = await context.Orders.Take(100).ToListAsync(); // запит №1

    foreach (var order in orders)
    {
        var name = order.Customer.FullName; // lazy loading -> окремий запит НА КОЖНУ ітерацію
    }
}
Console.WriteLine($"[Погано] Виконано SQL-запитів: {queryCount}");
// [Погано] Виконано SQL-запитів: 101   (1 + 100)

// ✅ ДОБРЕ: Eager loading
queryCount = 0;
using (var context = new ShopDbContext(options))
{
    var orders = await context.Orders
        .Include(o => o.Customer)
        .AsNoTracking()
        .Take(100)
        .ToListAsync(); // один запит з JOIN

    foreach (var order in orders)
    {
        var name = order.Customer.FullName; // дані вже завантажені, жодного нового запиту
    }
}
Console.WriteLine($"[Добре] Виконано SQL-запитів: {queryCount}");
// [Добре] Виконано SQL-запитів: 1
```

**Консольний вивід:**
```
[Погано] Виконано SQL-запитів: 101
[Добре] Виконано SQL-запитів: 1
```

Різниця в 101 раз для лише 100 замовлень наочно показує, чому N+1 — не теоретична, а дуже реальна проблема продуктивності.

### Приклад 3 — Той самий сценарій читання через Dapper

```csharp
using Dapper;
using Microsoft.Data.SqlClient;

// Порівняно з Прикладом 1 (EF Core LINQ), тут ми пишемо SQL самі:
const string sql = @"
    SELECT o.OrderId, o.CreatedAt, o.CustomerId,
           c.CustomerId, c.FullName, c.Email
    FROM Orders o
    INNER JOIN Customers c ON o.CustomerId = c.CustomerId
    WHERE o.CreatedAt >= @Since";

using var connection = new SqlConnection(connectionString);

var orders = await connection.QueryAsync<Order, Customer, Order>(
    sql,
    (order, customer) =>
    {
        order.Customer = customer;
        return order;
    },
    new { Since = DateTime.UtcNow.AddDays(-30) },
    splitOn: "CustomerId");

foreach (var order in orders)
    Console.WriteLine($"Замовлення #{order.OrderId} від {order.Customer.FullName}");
```

**Порівняння підходу:**

| | EF Core (Приклад 1) | Dapper (Приклад 3) |
|---|---|---|
| Хто пише JOIN | EF Core (з `.Include()`) | Розробник (у тексті SQL) |
| Мапінг результату в об'єкти | Автоматичний, вбудований | Явний делегат-мапер (`(order, customer) => ...`) або автомапінг за назвами стовпців |
| Контроль над точним SQL | Опосередкований | Повний |
| Рядків коду для цього запиту | Менше | Трохи більше, але прозоріше щодо реального SQL |

### Приклад 4 — Repository над EF Core (з відсиланням до дискусії з розділу 9)

```csharp
public interface IOrderRepository
{
    Task<Order?> GetWithDetailsAsync(int orderId);
    Task<List<Order>> GetRecentByCustomerAsync(int customerId, int days);
    Task AddAsync(Order order);
}

public class EfOrderRepository : IOrderRepository
{
    private readonly ShopDbContext _context;

    public EfOrderRepository(ShopDbContext context) => _context = context;

    public Task<Order?> GetWithDetailsAsync(int orderId) =>
        _context.Orders
            .Include(o => o.Customer)
            .Include(o => o.Items).ThenInclude(i => i.Product)
            .AsNoTracking()
            .FirstOrDefaultAsync(o => o.OrderId == orderId);

    public Task<List<Order>> GetRecentByCustomerAsync(int customerId, int days) =>
        _context.Orders
            .Where(o => o.CustomerId == customerId && o.CreatedAt >= DateTime.UtcNow.AddDays(-days))
            .AsNoTracking()
            .ToListAsync();

    public Task AddAsync(Order order)
    {
        _context.Orders.Add(order);
        return _context.SaveChangesAsync();
    }
}

// Примітка (див. розділ 9): цей репозиторій виправданий, бо методи моделюють
// РЕАЛЬНІ доменні сценарії (GetWithDetails, GetRecentByCustomer), а не є
// сліпою 1-в-1 обгорткою над DbSet<Order>. Якби єдиними методами були
// generic Add/Get/Update/Delete без жодної доменної семантики -
// варто було б поставити собі питання, чи цей шар взагалі щось додає
// понад те, що вже дає сам DbContext/DbSet.
```

## 11. Реальний сценарій: оптимізація повільної сторінки списку товарів в адмінці

**Ситуація.** Адміністративна панель інтернет-магазину показує список товарів: назву, ціну, **назву категорії**, **кількість відгуків** і **середній рейтинг**. Сторінка з 50 товарами на сторінку раптом стала завантажуватись 4–6 секунд — набагато довше, ніж очікується для такого невеликого списку.

**Крок 1 — діагностика.** Вмикаємо логування SQL EF Core (`LogTo`) і одразу бачимо характерну картину: один запит `SELECT ... FROM Products ...` (швидкий), а одразу за ним — **сотні** дрібних запитів виду `SELECT ... FROM Categories WHERE CategoryId = @p0` і `SELECT ... FROM Reviews WHERE ProductId = @p0`. Це класична проблема N+1 з розділу 5: код виглядав приблизно так:

```csharp
// ❌ Причина проблеми
var products = await context.Products.ToListAsync(); // 1 запит

var result = products.Select(p => new ProductListItemDto
{
    Name = p.Name,
    Price = p.Price,
    CategoryName = p.Category.Name,               // lazy loading -> запит на КОЖЕН товар
    ReviewCount = p.Reviews.Count,                 // lazy loading -> ЩЕ ОДИН запит на КОЖЕН товар
    AverageRating = p.Reviews.Any()
        ? p.Reviews.Average(r => r.Rating)         // і ще один запит/довантаження ПОВНИХ Review-сутностей
        : 0
}).ToList();
```

Для 50 товарів це означає щонайменше `1 + 50 (Category) + 50 (Reviews)` = **101 запит** — а якщо доступ до `p.Reviews` відбувається двічі (для `Count` і для `Average`), і lazy loading не кешує колекцію між зверненнями в одному й тому ж циклі коректно, кількість може бути ще вищою.

**Крок 2 — перше виправлення: Eager Loading + AsNoTracking.** Сторінка суто для читання (адмін лише переглядає список), тому:

```csharp
var products = await context.Products
    .Include(p => p.Category)
    .Include(p => p.Reviews)
    .AsNoTracking()
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync();
```

Це вже прибирає N+1 — кількість запитів падає до 1–2 (EF Core, найімовірніше, розіб'є це на окремий запит для колекції `Reviews`, щоб уникнути декартового добутку через одночасний `Include` кількох колекцій — `AsSplitQuery()` за потреби). Величезний виграш — але не оптимальний, тому що...

**Крок 3 — глибше: навіщо взагалі тягнути повні сутності `Review` в пам'ять?** Мета сторінки — показати лише **кількість** відгуків і **середній рейтинг**, а не самі тексти відгуків. Завантажувати повні об'єкти `Review` (з текстом коментаря, датами тощо) лише щоб потім у C# порахувати `.Count()` і `.Average()` — це витрата мережевого трафіку, пам'яті й CPU на дані, які взагалі не потрібні на цьому екрані. Правильний підхід — **перекласти агрегацію на СУБД**, яка робить `COUNT`/`AVG` набагато ефективніше за допомогою індексів і виконання на рівні сервера, а не передавати всі рядки клієнту:

```csharp
// ✅ Найкраще: агрегація виконується в SQL, у пам'ять клієнта потрапляють лише готові числа
var result = await context.Products
    .Where(p => /* фільтр категорії, якщо є */ true)
    .Select(p => new ProductListItemDto
    {
        Name = p.Name,
        Price = p.Price,
        CategoryName = p.Category.Name,
        ReviewCount = p.Reviews.Count(),
        AverageRating = p.Reviews.Any() ? p.Reviews.Average(r => r.Rating) : 0
    })
    .AsNoTracking()
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync();
```

Тут `.Select()` з проєкцією в DTO дозволяє EF Core перекласти `Count()`/`Average()` прямо в SQL (підзапити або `LEFT JOIN` + `GROUP BY` — залежно від того, як EF Core оптимізує конкретний вираз), а не завантажувати сутності `Review` в пам'ять і рахувати в C#. Замість передачі, скажімо, 500 рядків відгуків по мережі — передається лише 50 готових чисел.

**Підсумок сценарію:** типовий шлях оптимізації такої сторінки — (1) виявити N+1 через логування SQL, (2) прибрати lazy loading через `.Include()`, (3) додати `.AsNoTracking()`, оскільки дані лише читаються, (4) переглянути, чи справді потрібно завантажувати повні пов'язані сутності, чи достатньо агрегованої проєкції — перенісши обчислення (`COUNT`, `AVG`, `SUM`) якомога ближче до бази даних, де для цього є ефективні алгоритми та індекси (див. розділ цієї серії про SQL та індексування щодо того, як індекси прискорюють саме такі агрегації та `JOIN`).

## 12. Поширені помилки

### ❌ Помилка 1 — Lazy loading увімкнено глобально без дисципліни

```csharp
// ❌ ПОГАНО
optionsBuilder.UseLazyLoadingProxies(); // увімкнено "про всяк випадок" для всього застосунку

foreach (var order in await context.Orders.ToListAsync())
    Console.WriteLine(order.Customer.FullName); // непомітний N+1 у КОЖНОМУ подібному місці коду
```

Проблема ховається в тому, що код виглядає абсолютно нормально й проходить рев'ю — адже ніде явно не видно, що `order.Customer` викликає SQL-запит. У великому застосунку з десятками таких місць проблема N+1 виникає систематично й непомітно, поки продуктивність не почне деградувати під реальним навантаженням.

```csharp
// ✅ ДОБРЕ: lazy loading вимкнено, залежність від пов'язаних даних видно прямо в запиті
var orders = await context.Orders
    .Include(o => o.Customer)
    .AsNoTracking()
    .ToListAsync();

foreach (var order in orders)
    Console.WriteLine(order.Customer.FullName); // дані вже тут, жодних прихованих запитів
```

### ❌ Помилка 2 — Забутий `AsNoTracking()` на великих read-only вибірках

```csharp
// ❌ ПОГАНО: звіт на 20 000 рядків, дані ніколи не змінюються й не зберігаються
var report = await context.Orders
    .Where(o => o.CreatedAt.Year == 2025)
    .ToListAsync(); // за замовчуванням ВСІ 20 000 сутностей потрапляють у change tracker
```

Це витрачає пам'ять на знімки значень і CPU на потенційний `DetectChanges` для даних, які ніхто ніколи не збереже назад у базу.

```csharp
// ✅ ДОБРЕ
var report = await context.Orders
    .Where(o => o.CreatedAt.Year == 2025)
    .AsNoTracking()
    .ToListAsync();
```

### ❌ Помилка 3 — Завантаження повних сутностей у пам'ять заради обчислення агрегату

```csharp
// ❌ ПОГАНО: усі рядки Products (з усіма стовпцями!) тягнуться в пам'ять клієнта
decimal totalCatalogValue = context.Products
    .ToList()                      // <-- SELECT * FROM Products, ВСІ рядки в пам'ять
    .Sum(p => p.Price);             // підсумок рахується вже в C#
```

Якщо в таблиці мільйон товарів — це мільйон повних об'єктів `Product` у пам'яті лише заради одного підсумкового числа.

```csharp
// ✅ ДОБРЕ: SUM() виконується безпосередньо в СУБД, у пам'ять клієнта потрапляє лише одне число
decimal totalCatalogValue = await context.Products
    .SumAsync(p => p.Price);       // перекладається в SQL: SELECT SUM(Price) FROM Products
```

## 13. Питання для співбесіди за рівнями

### Junior

1. **Що таке ORM і навіщо він потрібен?**
   ORM (Object-Relational Mapper) — бібліотека, що автоматично перекладає між об'єктною моделлю програми (класи, об'єкти) і реляційною моделлю бази даних (таблиці, рядки), генеруючи SQL із коду й мапуючи результати запитів назад в об'єкти. Потрібен, щоб позбавитись рутинного ручного мапінгу `IDataReader` → властивості та ручного написання `INSERT`/`UPDATE`/`DELETE` для кожної зміни.

2. **Що таке `DbContext` у EF Core?**
   Клас, що представляє сесію роботи з базою даних: тримає з'єднання, надає `DbSet<T>` для кожної сутності, відстежує зміни завантажених об'єктів і на `SaveChanges()` генерує весь потрібний SQL у межах однієї транзакції.

3. **Чим eager loading відрізняється від lazy loading?**
   Eager loading (`.Include()`) завантажує пов'язані дані одразу, в тому ж запиті/явному наборі запитів. Lazy loading завантажує пов'язані дані автоматично й непомітно в момент першого звернення до навігаційної властивості — і це небезпечно в циклах (проблема N+1).

4. **Що таке міграція в EF Core?**
   Версійований C#-клас з методами `Up()`/`Down()`, що описує одну зміну схеми бази даних (створення таблиці, додавання стовпця тощо). Створюється командою `dotnet ef migrations add`, застосовується — `dotnet ef database update`.

5. **Навіщо потрібен `DbSet<T>`?**
   Це властивість на `DbContext`, що представляє колекцію сутностей певного типу — через неї виконуються LINQ-запити (`context.Products.Where(...)`) і додавання/видалення сутностей (`context.Products.Add(...)`).

6. **Чим Data Annotations відрізняються від Fluent API?**
   Data Annotations — атрибути прямо над властивостями класу (`[Key]`, `[Required]`), швидко, але обмежено. Fluent API — конфігурація в `OnModelCreating`, більш потужна й гнучка, не забруднює доменну модель залежностями EF Core.

### Middle

1. **Поясни проблему N+1 і як її вирішити.**
   Один запит повертає N батьківських сутностей, а потім для кожної окремо виконується запит на пов'язані дані (зазвичай через lazy loading в циклі) — разом N+1 запитів замість 1–2. Вирішується через eager loading (`.Include()`), що завантажує пов'язані дані одним запитом (JOIN) або невеликою фіксованою кількістю запитів (`AsSplitQuery()`), або через явне пакетне завантаження.

2. **Навіщо потрібен `AsNoTracking()` і коли його використовувати?**
   Вимикає відстеження змін для результатів запиту — не створюється знімок значень, не витрачається CPU на `DetectChanges`. Використовувати для будь-якого read-only сценарію: сторінки списків, звіти, GET-ендпоінти API, де результат ніколи не буде змінено й збережено назад через той самий контекст.

3. **Чим Dapper відрізняється від EF Core і коли обрати кожен?**
   Dapper — мікро-ORM: розробник сам пише SQL, бібліотека лише мапує результат у об'єкти; немає change tracking, LINQ-провайдера, міграцій. EF Core генерує SQL із LINQ і керує повним життєвим циклом сутностей. EF Core обирають для типового CRUD, де швидкість розробки важливіша; Dapper — для продуктивність-критичних або складних звітних запитів, де потрібен точний контроль над SQL.

4. **Що таке client-side evaluation і чому воно небезпечне?**
   Ситуація, коли частина (або весь) LINQ-запиту не може бути перекладена в SQL і замість цього виконується в пам'яті (`IEnumerable`) вже після завантаження даних із бази. Небезпечно тим, що код компілюється й працює правильно на малих обсягах даних, але масштабується катастрофічно погано — типовий приклад: випадковий виклик `.AsEnumerable()` перед фільтром замість після нього.

5. **Що робить `.Include()` і `.ThenInclude()` під капотом?**
   `.Include()` вказує EF Core завантажити вказану навігаційну властивість разом з основним запитом — через `JOIN` або через окремий, але одразу виконуваний, запит (`AsSplitQuery()`). `.ThenInclude()` дозволяє продовжити ланцюжок на наступний рівень вкладеності (наприклад, `Order → Items → Product`).

6. **Чому не варто тримати `DbContext` як singleton?**
   `DbContext` не потокобезпечний і не призначений для довгого життя: тривале накопичення відстежуваних сутностей споживає дедалі більше пам'яті, а довге з'єднання суперечить типовому патерну "unit of work на один логічний запит". У ASP.NET Core стандартний scoped lifetime (одна сесія на HTTP-запит) відповідає цьому патерну природно.

### Senior

1. **Опиши, як би ти діагностував і виправив N+1 у продакшн-коді, якого ти не писав.**
   Спершу — увімкнути логування SQL EF Core (`LogTo`) або скористатись існуючими трейсами APM (Application Insights, OpenTelemetry) для конкретного повільного ендпоінта й порахувати кількість реальних SQL-запитів на один HTTP-запит. Характерна ознака N+1 — "гребінець" однакових коротких запитів, що повторюються N разів підряд. Далі — знайти відповідне місце в коді (зазвичай `foreach`/`Select` над колекцією з доступом до навігаційної властивості), перевірити, чи ввімкнено lazy loading проксі, і додати `.Include()`/`.ThenInclude()` для потрібних навігацій, а також `.AsNoTracking()`, якщо сценарій суто читальний. Важливо після виправлення перевірити план виконання отриманого SQL і переконатись, що новий `JOIN`-запит сам по собі ефективний (є потрібні індекси на стовпцях зв'язку) — інакше можна отримати "1 повільний запит" замість "N+1 швидких", що не завжди краще при дуже великих обсягах пов'язаних даних (у такому разі варто розглянути `AsSplitQuery()` або явну пагінацію пов'язаної колекції).

2. **Чи потрібен Repository pattern поверх EF Core — обґрунтуй свою позицію.**
   Чесна відповідь — "залежить, і в обидва боки є вагомі аргументи" (детально в розділі 9). `DbContext` уже функціонально є Unit of Work, а `DbSet<T>` — Repository, тому generic `IRepository<T>`, що прямо прокидує виклики в `DbSet`, часто додає шар коду без реальної цінності (особливо якщо застосунок ніколи не планує міняти ORM). Водночас репозиторій, що моделює реальні доменні операції (а не CRUD 1-в-1), корисний для інкапсуляції складних, повторно використовуваних запитів і для чистішого юніт-тестування бізнес-логіки без залежності від деталей EF Core. Рішення варто приймати виходячи з реальних потреб конкретного проєкту (розмір команди, ймовірність зміни технології збереження, складність доменної логіки), а не за замовчуванням "бо так прийнято".

3. **Поясни, як LINQ перекладається в SQL і що може піти не так (client-side evaluation).**
   LINQ-вираз проти `IQueryable<T>` будує дерево виразів, яке EF Core аналізує й транслює в SQL конкретного діалекту бази даних лише в момент матеріалізації запиту (відкладене виконання). Не всі C#-конструкції мають еквівалент у SQL — довільні методи, складна умовна логіка, деякі виклики .NET API можуть бути неперекладними. Сучасний EF Core (3.0+) здебільшого явно кидає виняток при неможливості перекладу верхньорівневого виразу — це добре (fail-fast). Найнебезпечніший випадок — коли частина запиту виконується в пам'яті непомітно (наприклад, ранній перехід через `.AsEnumerable()`/`.ToList()` посеред ланцюжка LINQ до фільтрації) — код працює коректно, але завантажує в пам'ять значно більше даних, ніж потрібно, і масштабується катастрофічно погано з ростом таблиці. Виявляється через `.ToQueryString()` (побачити реальний SQL без виконання) і через логування виконаних запитів під час роботи застосунку.

4. **Коли ти обрав би Dapper замість EF Core для конкретної частини системи, і чому?**
   Типові кандидати: (1) складні звітні/аналітичні запити з багатьма агрегаціями та `JOIN`, які важко або неефективно виразити через LINQ і де потрібен точний контроль над планом виконання; (2) ділянки під дуже високим навантаженням, де накладні витрати EF Core (побудова дерева виразів, трансляція, change tracking) стають вимірюваним вузьким місцем; (3) робота з існуючими збереженими процедурами чи вже написаним, ретельно оптимізованим SQL, де немає сенсу "перевинаходити" його через LINQ. Водночас для основного CRUD-шару застосунку (створення/оновлення сутностей, типові списки з фільтрами) EF Core, як правило, залишається кращим вибором через швидкість розробки, типобезпеку й вбудовані міграції — тому в реальних системах обидва підходи часто співіснують у різних шарах.

5. **Спроєктуй стратегію оптимізації повільної сторінки з великою кількістю пов'язаних даних.**
   Покроково: (1) виміряти — скільки реальних SQL-запитів і скільки часу займає кожен, через логування/APM, а не здогадки; (2) перевірити на N+1 — характерний "гребінець" однакових запитів; (3) для read-only сценаріїв одразу додати `.AsNoTracking()`; (4) замінити lazy/множинне завантаження на `.Include()`/`.ThenInclude()` там, де потрібні повні пов'язані сутності, і на `AsSplitQuery()`, якщо одночасних `Include`-колекцій кілька й виникає декартів добуток рядків; (5) переглянути, чи справді потрібні повні пов'язані сутності, чи достатньо агрегованої проєкції (`.Select()` з `Count()`/`Average()`/`Sum()`, що транслюється в SQL, замість завантаження сирих рядків для підрахунку в C#); (6) перевірити, чи є потрібні індекси на стовпцях, що беруть участь у `JOIN`/`WHERE`/`ORDER BY` отриманого запиту (план виконання, а не здогадки); (7) для дійсно важких сценаріїв — розглянути винесення конкретного запиту в Dapper із ретельно написаним і провіреним SQL; (8) додати пагінацію (`Skip`/`Take`) там, де показується довгий список, замість завантаження всього набору одразу; (9) за потреби — кешування результату на короткий час для даних, що рідко змінюються.

## 14. Підсумок

### Стратегії завантаження — шпаргалка

| Стратегія | Коли завантажується | Ризик | Типовий сценарій |
|---|---|---|---|
| **Eager (`Include`)** | Разом з основним запитом | Over-fetching при зайвих `Include` | Наперед відомий набір потрібних пов'язаних даних |
| **Lazy (proxies)** | Автоматично, при зверненні | N+1, приховані запити | Уникати в продакшн-коді за замовчуванням |
| **Explicit (`.Load()`)** | Вручну, за умовою | Забути викликати там, де треба | Умовне довантаження |

### EF Core vs Dapper — коли що обрати

| Критерій | EF Core | Dapper |
|---|---|---|
| Контроль над SQL | Опосередкований | Повний |
| Швидкість CRUD-розробки | Висока | Нижча |
| Продуктивність "з коробки" | Помірна (накладні витрати ORM) | Максимальна (тонкий шар) |
| Складні звіти/агрегації | Складно оптимізувати через LINQ | Природно — пишете точний SQL |
| Міграції схеми | Вбудовані | Відсутні, потрібен окремий інструмент |
| Найкраще для | Основний CRUD-шар застосунку | Продуктивність-критичні/звітні запити |

### Чек-лист виявлення й запобігання N+1

- [ ] Lazy loading вимкнено глобально (`UseLazyLoadingProxies()` не підключено) — за замовчуванням.
- [ ] Кожен запит, що повертає список сутностей із пов'язаними даними, використовує явний `.Include()`/`.ThenInclude()` для того, що справді потрібно на екрані.
- [ ] Логування SQL (`LogTo`) або APM-трейси підключені хоча б для dev/staging середовища — щоб бачити реальну кількість запитів.
- [ ] Будь-який доступ до навігаційної властивості всередині `foreach`/`Select` над колекцією проходить рев'ю на предмет прихованого довантаження.
- [ ] Read-only запити (списки, звіти, GET-ендпоінти) мають `.AsNoTracking()`.
- [ ] Агрегати (`Count`, `Sum`, `Average`) обчислюються через LINQ-проєкцію, що транслюється в SQL, а не через завантаження повних сутностей і підрахунок у C#.
- [ ] Для запитів з кількома одночасними `.Include()` колекцій розглянуто `AsSplitQuery()` там, де це доречно.
- [ ] Міграції рев'юяться (`dotnet ef migrations script`) перед застосуванням до продакшену; жодна вже застосована міграція не редагується заднім числом.
