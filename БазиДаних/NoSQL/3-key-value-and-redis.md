## 1. Що таке ключ-значення БД?

Ключ-значення (key-value) сховище — це найпростіша можлива модель даних у світі баз даних. Уся база даних концептуально — це одна величезна хеш-таблиця (`Dictionary<TKey, TValue>`, якщо думати в термінах C#):

```
"user:1001"        -> "Іван Петренко"
"product:55:price" -> "1299.00"
"session:abc123"   -> { дані сесії }
```

Це все. Немає таблиць, немає стовпців, немає схеми, немає JOIN, немає `WHERE price > 100`. Базі даних, по суті, **байдуже, що знаходиться всередині значення** — з її погляду значення найчастіше є непрозорим (opaque) блобом байтів. Вона вміє робити рівно дві речі добре: покласти значення за ключем (`SET`/`PUT`) і дістати значення за ключем (`GET`).

### Аналогія з реального життя

Уявіть гардероб у театрі. Ви віддаєте своє пальто гардеробнику, він вішає його на вішак і дає вам **номерок** — це ваш ключ. Гардеробник не знає і не цікавиться, що лежить у кишенях пальта, якого воно кольору, з якої тканини — для нього це просто "об'єкт номер 47". Коли ви пізніше приходите з номерком, він миттєво знаходить вішак під тим самим номером і віддає вам **точно те саме пальто, яке ви здали** — не схоже пальто, не пальто "приблизно такого ж кольору", а те саме, за ідентичним ключем.

Це ідеально передає суть key-value моделі:

- **Ключ → повернення точного значення** — швидко, напряму, без пошуку "по вмісту".
- **Неможливо запитати** "дай мені всі пальта синього кольору" (це запит *по значенню*) — гардеробник фізично не індексує пальта за кольором, лише за номерком.
- Якщо ви загубили номерок — вважайте, пальто недоступне, навіть якщо воно фізично висить за два метри від вас.

### Компроміс: швидкість в обмін на виразність запитів

Ключ-значення сховища свідомо жертвують гнучкістю запитів заради екстремальної швидкості:

**Що ви отримуєте:**
- Пошук за ключем — операція **O(1)** (в середньому) завдяки хеш-таблиці. Немає B-Tree обходу, немає планувальника запитів, немає обчислення JOIN.
- Мінімальні накладні витрати — не потрібно парсити SQL, будувати план виконання, перевіряти обмеження зовнішніх ключів.
- Дуже передбачувана latency — операція `GET` коштує приблизно однаково незалежно від того, скільки мільйонів ключів у сховищі.

**Що ви втрачаєте:**
- **Не можна запитувати за значенням.** Не існує еквівалента `SELECT * FROM users WHERE age > 30` — якщо тільки сховище (як Redis) не надає для цього спеціальних додаткових структур та індексів.
- **Не можна запитувати за частиною структури значення** без додаткових механізмів. Якщо значення — це серіалізований JSON з полем `email`, "чисте" key-value сховище не вміє знайти запис за цим email — воно бачить лише непрозорий рядок байтів.
- **Ви зобов'язані знати ключ заздалegiu.** Це фундаментальне обмеження: доступ можливий лише "з ключа", ніколи "з умови".

Це не недолік дизайну — це свідомий інженерний вибір. Коли ваш патерн доступу справді "дай мені запис за ідентифікатором" (кеш, сесія, лічильник, конфігурація), key-value сховище буде на порядки швидшим за реляційну БД саме тому, що воно не намагається підтримувати універсальні запити. Це та сама тема trade-off "простота моделі vs виразність запитів", яка вже піднімалася в документі про NoSQL та CAP-теорему цієї серії — key-value є найбільш "крайньою" точкою цього спектра: максимальна простота моделі, мінімальна виразність запитів.

Найвідоміший представник цієї категорії — **Redis** (REmote DIctionary Server), і саме йому присвячена решта цього документа.

## 2. Redis — не просто key-value, а структура даних у пам'яті

Тут важливо одразу розвіяти поширене спрощення. Redis офіційно позиціонує себе не просто як "key-value store", а як **"in-memory data structure store"** — сховище структур даних у пам'яті. Це ключова відмінність від "чистого" key-value сховища (як, наприклад, простий DynamoDB-запис або Memcached).

У "чистому" key-value сховищі значення — це непрозорий блоб: рядок байтів, який ви серіалізуєте і десеріалізуєте самі. Хочете оновити одне поле об'єкта — доведеться дістати весь блоб, десеріалізувати на клієнті, змінити поле, серіалізувати назад, записати весь блоб знову.

**Redis натомість надає значенням структуру, яку сам сервер розуміє і вміє атомарно оперувати нею**, не витягуючи все значення на клієнта. Це і є головна суперсила Redis. Розглянемо основні типи даних — кожен із конкретним e-commerce прикладом.

### 2.1. String — найпростіший тип

`String` у Redis — це послідовність байтів (текст, число, навіть бінарні дані на кшталt серіалізованого об'єкта чи картинки) розміром до 512 МБ. Це базовий "блоб"-тип, аналогічний класичному key-value.

Особливо цінна властивість: Redis вміє **атомарно інкрементувати/декрементувати** число, що зберігається як рядок, командами `INCR`/`DECR`/`INCRBY`, без гонки даних (race condition), навіть коли тисячі клієнтів роблять це одночасно.

**Приклад:** лічильник переглядів сторінки товару або rate limiter.

```
SET page:views:product:55 0
INCR page:views:product:55   -> 1
INCR page:views:product:55   -> 2
INCRBY page:views:product:55 10   -> 12
```

Це набагато швидше й простіше, ніж робити `SELECT`, `+1` на клієнті і `UPDATE` в реляційній БД під транзакцією/блокуванням — Redis гарантує атомарність інкременту на рівні однієї команди сервера.

### 2.2. Hash — міні-об'єкт із полями

`Hash` — це, по суті, `Dictionary<string, string>` всередині одного ключа Redis. Замість того, щоб серіалізувати весь об'єкт у JSON-рядок і зберігати його як `String`, ви зберігаєте об'єкт як набір іменованих полів — і можете читати/оновлювати **одне конкретне поле**, не чіпаючи інші.

**Приклад:** сесія користувача або кешовані атрибути товару.

```
HSET session:abc123 userId 1001 cartId 77 loginAt 1732450000
HGET session:abc123 userId          -> "1001"
HSET session:abc123 loginAt 1732451111   -- оновили тільки одне поле
HGETALL session:abc123               -> увесь об'єкт одразу
```

Порівняйте з альтернативою — зберігати сесію як один JSON-рядок у `String`: щоб оновити лише `loginAt`, довелося б прочитати весь JSON, розпарсити, змінити поле, серіалізувати й перезаписати весь рядок цілком. `Hash` дозволяє оновити одне поле однією командою — менше трафіку, менше CPU, і що важливо — без ризику "загубити" паралельне оновлення іншого поля тим самим клієнтом.

### 2.3. List — впорядкована послідовність

`List` — це зв'язний список рядків із гарантованим порядком, оптимізований для швидкого додавання/вилучення **з обох кінців** (`LPUSH`/`RPUSH`/`LPOP`/`RPOP` — усі це O(1)).

**Приклад 1 — проста черга завдань:**

```
LPUSH queue:emails "order:1001:confirmation"
LPUSH queue:emails "order:1002:confirmation"
RPOP queue:emails   -> "order:1001:confirmation"  (FIFO: перший прийшов — перший вийшов)
```

**Приклад 2 — "нещодавно переглянуті товари":**

```
LPUSH user:1001:recently_viewed "product:55"
LPUSH user:1001:recently_viewed "product:12"
LTRIM user:1001:recently_viewed 0 9   -- лишити тільки 10 останніх
LRANGE user:1001:recently_viewed 0 -1 -> ["product:12", "product:55", ...]
```

`LTRIM` тут ключовий трюк: список автоматично обрізається до фіксованого розміру, тож "нещодавно переглянуті" ніколи не розростається безмежно.

### 2.4. Set — унікальні неупорядковані елементи

`Set` зберігає унікальні члени без порядку, з O(1) перевіркою належності (`SISMEMBER`) і потужними операціями над множинами: перетин (`SINTER`), об'єднання (`SUNION`), різниця (`SDIFF`).

**Приклад 1 — унікальні відвідувачі:**

```
SADD visitors:2026-08-24 "user:1001"
SADD visitors:2026-08-24 "user:1002"
SADD visitors:2026-08-24 "user:1001"   -- дублікат ігнорується
SCARD visitors:2026-08-24              -> 2   (кількість унікальних)
```

**Приклад 2 — товари, які переглянули і Клієнт A, і Клієнт B (класичний приклад для співбесід):**

```
SADD viewed:customerA "product:1" "product:5" "product:9"
SADD viewed:customerB "product:5" "product:9" "product:20"

SINTER viewed:customerA viewed:customerB   -> {"product:5", "product:9"}
```

Одна команда `SINTER` дає перетин множин — ідеально для функцій на кшталт "покупці, схожі на вас, також дивились" без жодного JOIN чи циклу на клієнті.

### 2.5. Sorted Set (ZSet) — найпотужніша й найвідоміша структура Redis

`Sorted Set` (ZSet) — це `Set`, де кожен елемент (member) має асоційований **числовий score**, і Redis підтримує елементи **завжди відсортованими за цим score** внутрішньо (структура даних під капотом — skip list + hash table). Це, ймовірно, найвиразніша й найбільш "нестандартна для типового key-value" структура Redis, і саме тому вона — улюблена тема технічних співбесід.

Ключові операції:
- `ZADD key score member` — додати елемент зі score (або оновити score, якщо вже існує).
- `ZINCRBY key delta member` — атомарно **збільшити** score елемента на `delta` (не перезаписуючи його — саме тому це ідеально для "живих" лічильників).
- `ZRANGE` / `ZREVRANGE` — отримати діапазон за рангом (позицією в сортуванні).
- `ZRANGEBYSCORE` — отримати елементи в діапазоні score.
- `ZRANK` / `ZREVRANK` — дізнатись поточну позицію (ранг) конкретного елемента.
- Усі ці операції виконуються за **O(log N)** — логарифмічно від кількості елементів, навіть коли елементів мільйони.

**Приклад 1 — лідерборд (leaderboard) гри чи програми лояльності:**

```
ZADD leaderboard 1500 "player:Andrii"
ZADD leaderboard 2200 "player:Olena"
ZADD leaderboard 980  "player:Ivan"

ZREVRANGE leaderboard 0 2 WITHSCORES
-> 1) "player:Olena"  2200
   2) "player:Andrii" 1500
   3) "player:Ivan"    980

ZREVRANK leaderboard "player:Andrii"   -> 1   (другe місце, 0-індексація)
```

**Приклад 2 — топ-10 товарів, що продаються найкраще, оновлюється в реальному часі при кожному продажу:**

```
-- при кожному продажу товару просто інкрементуємо його score
ZINCRBY bestsellers 1 "product:55"
ZINCRBY bestsellers 1 "product:12"
ZINCRBY bestsellers 3 "product:55"   -- продали 3 одиниці одночасно

ZREVRANGE bestsellers 0 9 WITHSCORES   -- топ-10 в реальному часі, без пере обчислення
```

Це надзвичайно важливо зрозуміти: **немає окремого кроку "перерахувати рейтинг"**. Кожен `ZINCRBY` одразу і атомарно оновлює позицію елемента у відсортованій структурі. Отримати "топ-10 зараз" — це операція `O(log N + 10)`, а не повне сортування мільйонів записів при кожному запиті, як довелося б робити в реляційній БД без спеціального індексу (`ORDER BY sales_count DESC LIMIT 10` на великій таблиці — потенційно дорога операція, особливо при частих оновленнях).

Чому це "вбивчий" приклад на співбесіді: він одночасно демонструє (а) розуміння того, що Redis — не просто кеш рядків, (б) розуміння складності алгоритмів (O(log N) для skip list), і (в) практичний, реальний use case, який складно ефективно реалізувати "на голому" SQL без денормалізованого/матеріалізованого лічильника.

## 3. Персистентність: RDB та AOF

Redis — це, насамперед, **сховище в оперативній пам'яті** (in-memory). Це і є джерело його швидкості: немає дискового I/O на кожну операцію читання/запису. Але оперативна пам'ять зникає при перезапуску процесу чи збоє сервера — тож Redis пропонує механізми персистентності (durability) для тих сценаріїв, де втрата даних неприйнятна.

### 3.1. RDB (Redis Database) — снапшоти

RDB — це періодичний point-in-time знімок (snapshot) усього набору даних, збережений у компактному бінарному файлі (`dump.rdb`).

- Налаштовується правилами на кшталт "зберегти снапшот, якщо змінилось ≥ 100 ключів за останні 60 секунд" (`SAVE 60 100`).
- **Плюси:** компактний файл, дуже швидке відновлення при рестарті (просто завантажити файл у пам'ять), мінімальний вплив на продуктивність під час роботи (фонова fork-копія процесу).
- **Мінуси:** якщо сервер впаде між двома снапшотами — **всі зміни з моменту останнього снапшоту втрачаються назавжди**. Якщо снапшот раз на 5 хвилин, а сервер впав на 4-й хвилині — ви втратили майже 4 хвилини записів.

### 3.2. AOF (Append-Only File) — журнал операцій

AOF логує **кожну операцію запису** послідовно у файл, у міру її виконання — концептуально це той самий принцип, що й **Write-Ahead Log (WAL)**, розглянутий у документі про внутрішній устрій зберігання реляційних БД цієї серії: спочатку журналюємо намір/факт зміни, і при відновленні після збою можна відтворити стан, повторно застосувавши журнал.

AOF надає кращу довговічність даних, ніж RDB, ціною дещо нижчої продуктивності запису і більшого розміру файлу (Redis періодично "переписує" — compaction, AOF rewrite — щоб файл не розростався безмежно).

Ключове налаштування — **політика fsync** (коли дані фізично скидаються на диск, а не просто лежать у буфері ОС):

| Політика `appendfsync` | Поведінка | Компроміс |
|---|---|---|
| `always` | fsync після **кожної** команди запису | Максимальна довговічність, помітно нижча пропускна здатність |
| `everysec` (за замовчуванням) | fsync раз на секунду | Хороший баланс — у гіршому випадку втрата ≤ 1 секунди записів |
| `no` | fsync віддається на відкуп операційній системі | Найшвидше, але найменш передбачувано щодо втрати даних при збої |

Це той самий класичний "рубильник" durability-vs-performance, який зустрічається у багатьох базах даних (наприклад, `synchronous_commit` у PostgreSQL) — чим більше гарантій довговічності, тим вища latency на запис.

### 3.3. Комбінація RDB + AOF, або взагалі без персистентності

Redis дозволяє увімкнути **обидва механізми одночасно**: RDB — для швидкого й компактного повного бекапу/відновлення, AOF — для мінімізації втрати даних між снапшотами. Це типова конфігурація для Redis-інстансів, що зберігають дані, які реально важливо не втратити (наприклад, кошики покупок, лічильники, чергу завдань).

**Але для дуже поширеного випадку — Redis як "чистий" кеш** — персистентність часто **свідомо вимикають повністю**. Логіка проста: якщо дані в Redis — це лише копія/похідна від даних у реальному джерелі істини (наприклад, PostgreSQL), і Redis можна в будь-який момент "розігріти" знову простим переповторенням запитів до основної БД при cache miss — то немає сенсу платити за I/O персистентності. Якщо кеш-сервер перезапуститься і втратить усі ключі — це просто масовий cache miss на кілька хвилин, поки кеш знову наповниться; жодні дані фактично не втрачені, бо вони ніколи не були "єдиним джерелом істини" для цих даних.

**Головне правило-орієнтир:** персистентність важлива рівно тою мірою, якою Redis є єдиним місцем, де існують ці дані. Якщо дані відновлювані з іншого джерела — персистентність опційна оптимізація. Якщо ні — персистентність (і правильно налаштована) обов'язкова.

## 4. TTL (Time To Live) та Eviction Policies

### 4.1. TTL — автоматичне видалення ключів

Будь-якому ключу в Redis можна призначити час життя командою `EXPIRE key seconds` (або встановити одразу при записі: `SET key value EX seconds`). Коли цей час спливає, Redis **автоматично видаляє ключ** — без жодної додаткової дії з боку клієнта.

```
SET session:abc123 "..." EX 1800   -- сесія живе 30 хвилин
TTL session:abc123                  -> 1800 (секунд лишилось)
-- через 30 хвилин ключ зникає сам, GET поверне nil
```

TTL — це серцевина найпоширенішого use case Redis: **кешування**. Кеш-запис за визначенням має бути тимчасовим — він повинен або оновитися, або зникнути, коли перестає бути актуальним відображенням даних із джерела істини.

### 4.2. Eviction Policies — що робити, коли пам'яті бракує

TTL вирішує проблему "застарілих" даних, але не проблему **обмеженого обсягу пам'яті**. Redis зазвичай налаштовують із жорстким лімітом (`maxmemory`), і коли цей ліміт досягнуто, а потрібно записати новий ключ — Redis має вирішити, які старі ключі "викинути" (evict), керуючись налаштованою **eviction policy**.

| Policy | Поведінка | Коли підходить |
|---|---|---|
| `noeviction` | Нічого не видаляти; нові записи повертають помилку `OOM` | Коли втрата будь-яких даних неприйнятна — краще відмовити запису, ніж мовчки видалити щось важливе |
| `allkeys-lru` | Видаляти найменш нещодавно використовувані (Least Recently Used) ключі **серед усіх** ключів | Класичний "чистий кеш" — усі ключі однаково відновлювані, найкращий кандидат за замовчуванням для кеш-інстансу |
| `volatile-lru` | LRU-видалення, але тільки серед ключів, що **мають TTL** | Мішаний інстанс: частина ключів — кеш (мають TTL), частина — постійні дані (без TTL, ніколи не видаляються примусово) |
| `allkeys-lfu` | Видаляти найменш **часто** використовувані (Least Frequently Used) ключі серед усіх | Коли "популярність" важливіша за "нещодавність" — рідкісний, але завжди затребуваний ключ не повинен видалятись через тимчасове затишшя |
| `volatile-lfu` | LFU, тільки серед ключів з TTL | Те саме, але для мішаного інстансу |
| `volatile-ttl` | Видаляти ключі, **найближчі до спливання TTL**, незалежно від частоти використання | Коли логічно "жертвувати" тим, що й так скоро мало зникнути, а не тим, що активно використовується |
| `allkeys-random` / `volatile-random` | Видаляти випадковий ключ | Рідко використовується; іноді простіше й дешевше обчислювально за LRU/LFU-трекінг |

**Практична порада senior-рівня:** якщо Redis-інстанс використовується **виключно** як кеш (усі ключі відновлювані з іншого джерела) — `allkeys-lru` зазвичай найбезпечніший і найпростіший вибір за замовчуванням. Якщо той самий інстанс містить **і** кеш-ключі (з TTL), **і** дані, які повинні жити вічно й ніколи не видалятися примусово (наприклад, чергу завдань чи лічильники без TTL) — тоді потрібен `volatile-*` варіант, щоб eviction торкався лише "викидних" ключів, а постійні дані натомість захищені `noeviction`-подібною поведінкою (Redis просто ніколи не чіпатиме ключі без TTL при `volatile-*` policy). Змішування типів даних в одному інстансі без ретельного вибору policy — поширена операційна помилка, яка призводить до несподіваної втрати "важливих" даних під тиском пам'яті.

## 5. Типові патерни використання Redis

### 5.1. Кешування (Cache-Aside pattern)

Це найпоширеніший сценарій використання Redis. Логіка "Cache-Aside" (також відома як "lazy loading"):

1. Застосунок хоче прочитати дані — спочатку перевіряє кеш (Redis).
2. **Cache hit:** дані знайдено в кеші → повернути одразу, без звернення до основної БД.
3. **Cache miss:** дані відсутні в кеші → зробити запит до реальної БД (джерела істини) → покласти результат у кеш (з TTL) → повернути результат.

Це просто й ефективно, але інвалідація кешу — за відомим жартом Філа Карлтона, одна з "двох найважчих речей в computer science" (поряд із називанням змінних і помилками на межі "на одиницю") — на практиці містить кілька класичних пасток:

- **Застарілий кеш після оновлення (stale cache).** Якщо дані в основній БД змінились (наприклад, товар оновив ціну), а відповідний кеш-запис ще не спливив за TTL — користувачі бачитимуть застарілу ціну доти, доки TTL не спливе або хтось явно не інвалідує (видалить) кеш-ключ при оновленні джерела. Правильна практика — інвалідовувати (або оновлювати) відповідний кеш-ключ **у той самий момент**, коли пишете в основну БД, а не покладатися виключно на TTL.
- **Thundering herd (cache stampede).** Якщо дуже популярний ключ (наприклад, головна сторінка каталогу) спливає за TTL, і в цю саму мілісекунду прилітають тисячі одночасних запитів — усі вони одночасно бачать cache miss і одночасно кидаються запитувати основну БД, різко навантажуючи її, іноді до відмови. Детальніше розглянемо мітигацію в розділі "Поширені помилки".

### 5.2. Сесії користувачів

Класичний веб-застосунок зі стейтфул сесіями "в пам'яті" процесу (`in-process session`) не масштабується горизонтально: якщо балансувальник навантаження направить наступний запит користувача на інший сервер, той сервер не матиме доступу до сесії, створеної на першому.

Зберігання сесій у Redis (замість пам'яті конкретного веб-сервера) вирішує це: будь-який інстанс застосунку може прочитати сесію користувача з централізованого Redis за ключем `session:<sessionId>`, незалежно від того, який сервер обслуговував попередній запит цього користувача. Це прямо реалізує принцип **stateless-застосунку**, необхідний для горизонтального масштабування — тему, детально розглянуту в реляційній частині цієї серії стосовно масштабування застосунків.

### 5.3. Rate Limiting

Класична задача: обмежити кількість запитів від одного користувача/IP за проміжок часу (наприклад, "не більше 100 запитів за хвилину"). Найпростіша реалізація на Redis — **fixed window counter**:

```
INCR rate:user:1001:2026-08-24T15:30   -- інкремент лічильника для поточного вікна
EXPIRE rate:user:1001:2026-08-24T15:30 60   -- вікно живе 60 секунд (тільки при першому створенні!)

-- якщо результат INCR > ліміт (наприклад, 100) -> відхилити запит (HTTP 429)
```

Це фундаментальне поєднання `INCR` + `EXPIRE` — практично найчастіше цитоване практичне питання-завдання на технічних співбесідах ("спроєктуй rate limiter на Redis"). Детальніше розберемо реалізацію та її нюанси (зокрема, проблему "сплеску на межі вікна" fixed-window підходу і чому sliding-window точніший) у розділі з практичним кодом і в питаннях для senior-рівня.

### 5.4. Черги завдань (Pub/Sub та List-based черги)

Redis надає два простих механізми "повідомлень":

**Pub/Sub (`PUBLISH`/`SUBSCRIBE`)** — видавець публікує повідомлення в канал, усі підписники, що зараз слухають цей канал, отримують його миттєво.

```
SUBSCRIBE notifications:order-updates
PUBLISH notifications:order-updates "order:1001 shipped"
```

**Чесне попередження:** Redis Pub/Sub — це **fire-and-forget**. Якщо підписник не був підключений у момент публікації повідомлення — він **ніколи його не отримає**; повідомлення ніде не зберігається, немає механізму redelivery чи підтвердження доставки (ack). Це принципово відрізняється від повноцінного брокера повідомлень (RabbitMQ, Kafka, Azure Service Bus), який гарантує збереження й доставку повідомлень навіть підписникам, що тимчасово офлайн. Для некритичних сповіщень у реальному часі (наприклад, live-оновлення UI) Redis Pub/Sub чудово підходить; для критичних робочих потоків (обробка платежу, надсилання замовлення на склад) — потрібен справжній брокер повідомлень із гарантіями доставки.

**List-based черга** (простіше та надійніше за Pub/Sub для задач "обробити один раз"): продюсер робить `LPUSH`, воркер робить `BRPOP` (блокуючий pop — чекає, поки з'явиться елемент). На відміну від Pub/Sub, елемент фізично лежить у списку, доки якийсь воркер його не забере — навіть якщо жоден воркер не був онлайн у момент `LPUSH`.

### 5.5. Розподілена блокування (Distributed Locking / Redlock)

Коли кілька інстансів застосунку (наприклад, кілька подів у Kubernetes) повинні гарантувати, що лише **один** з них виконує певну дію одночасно (наприклад, обробляє конкретне замовлення чи виконує заплановане завдання), потрібен розподілений м'ютекс (mutex), і Redis часто використовують для цього як центральну координаційну точку.

Базова примітива — атомарна команда:

```
SET lock:order:1001 "instance-A" NX EX 30
```

- `NX` ("set if Not eXists") — команда встигає успішно виконатись лише якщо ключ ще не існує → саме це і є "захоплення блокування".
- `EX 30` — блокування автоматично звільниться через 30 секунд, навіть якщо інстанс, що його тримав, впав і не звільнив блокування явно (захист від "мертвого" утримувача).
- Звільнення блокування — видалення ключа, причому **тільки якщо значення все ще належить саме тому інстансу**, який його встановив (щоб уникнути випадкового звільнення чужого блокування, наприклад, якщо TTL вже сплив і хтось інший встиг захопити блокування першим).

Для більш надійного варіанту через кілька незалежних Redis-вузлів існує алгоритм **Redlock**, запропонований творцем Redis — він вимагає успішного захоплення блокування на більшості (кворумі) з N незалежних Redis-інстансів.

**Чесна примітка senior-рівня:** розподілене блокування через Redis — тема, яка активно дебатується в спільноті. Найвідоміша дискусія — обмін аргументами між Мартіном Клеппманном (автором "Designing Data-Intensive Applications") і Сальваторе Санфіліппо (автором Redis) щодо теоретичних гарантій Redlock за наявності затримок мережі, пауз GC чи розсинхронізації годинників на вузлах. Висновок для практики: Redis-блокування чудово підходить як **оптимізаційний** механізм (наприклад, "не робити одну й ту саму дорогу роботу двічі одночасно" — best-effort де рідкісний "подвійний запуск" не катастрофічний), але якщо вам потрібна **математично строга** гарантія взаємовиключення (наприклад, критично важлива фінансова операція, де подвійне виконання неприпустиме за жодних обставин) — варто розглянути спеціалізовані системи консенсусу (ZooKeeper, etcd із їхніми гарантіями лідерства) або принаймні додатковий рівень захисту на рівні бізнес-логіки (ідемпотентність операцій, унікальні constraint'и в реляційній БД).

### Приклад 1 — Підключення та операції зі String

```csharp
using StackExchange.Redis;

// ConnectionMultiplexer — важкий, потокобезпечний об'єкт з'єднання.
// Створюється ОДИН РАЗ на весь час життя застосунку (наприклад, як singleton у DI),
// а не на кожен запит — повторне створення дорого коштує і не потрібне.

string? productName = db.StringGet("product:55:name");
Console.WriteLine($"Товар: {productName}");
// Товар: Бездротові навушники XZ-200

// --- Лічильник переглядів сторінки (атомарний INCR) ---
string viewsKey = "page:views:product:55";
long views1 = db.StringIncrement(viewsKey);
long views2 = db.StringIncrement(viewsKey);

Console.WriteLine($"Перегляди після 1-го інкременту: {views1}");
Console.WriteLine($"Перегляди після 2-го інкременту: {views2}");
Console.WriteLine($"Перегляди після +10: {views3}");
// Перегляди після 1-го інкременту: 1
// Перегляди після 2-го інкременту: 2
// Перегляди після +10: 12
```

### Приклад 2 — Sorted Set: живий лідерборд бестселерів

```csharp
using StackExchange.Redis;

using var redis = ConnectionMultiplexer.Connect("localhost:6379");
IDatabase db = redis.GetDatabase();

const string leaderboardKey = "bestsellers:2026-08";

// Симулюємо продажі товарів протягом дня —
// кожен продаж просто збільшує score товару в ZSet
db.SortedSetIncrement(leaderboardKey, "product:55 — Навушники XZ-200", 3);
db.SortedSetIncrement(leaderboardKey, "product:12 — Клавіатура MK-7", 1);
db.SortedSetIncrement(leaderboardKey, "product:99 — Веб-камера HD", 7);
db.SortedSetIncrement(leaderboardKey, "product:55 — Навушники XZ-200", 5); // ще 5 продажів того ж товару
db.SortedSetIncrement(leaderboardKey, "product:12 — Клавіатура MK-7", 2);

// Отримуємо топ-3 за спаданням score (найбільш продавані першими)
SortedSetEntry[] top3 = db.SortedSetRangeByRankWithScores(
    leaderboardKey, start: 0, stop: 2, order: Order.Descending);

Console.WriteLine("=== Топ-3 бестселери за серпень 2026 ===");
int rank = 1;
foreach (var entry in top3)
{
    Console.WriteLine($"{rank}. {entry.Element} — продано: {(int)entry.Score} шт.");
    rank++;
}
// === Топ-3 бестселери за серпень 2026 ===
// 1. product:99 — Веб-камера HD — продано: 7 шт.
// 2. product:55 — Навушники XZ-200 — продано: 8 шт.
// 3. product:12 — Клавіатура MK-7 — продано: 3 шт.
```

> Зверніть увагу: `SortedSetIncrement` — атомарна операція. Навіть якщо тисячі продажів фіксуються одночасно з різних серверів застосунку, кожен виклик коректно додається до існуючого score без втрати даних (на відміну від "прочитати число, додати на клієнті, записати назад", де можлива гонка даних).

### Приклад 3 — Cache-Aside pattern

```csharp
using StackExchange.Redis;
using System.Text.Json;

public class ProductCacheService
{
    private readonly IDatabase _redis;
    private static readonly TimeSpan CacheTtl = TimeSpan.FromMinutes(10);

    public ProductCacheService(IDatabase redis) => _redis = redis;

    // Симуляція "реальної" повільної бази даних (наприклад, PostgreSQL)
    private ProductDto QuerySlowDatabase(int productId)
    {
        Console.WriteLine($"  [БД] Виконую повільний запит до основної бази для товару {productId}...");
        Thread.Sleep(200); // імітація latency реальної БД
        return new ProductDto(productId, "Навушники XZ-200", 1299.00m);
    }

    public ProductDto GetProduct(int productId)
    {
        string cacheKey = $"product:{productId}:cache";

        // 1. Спочатку перевіряємо кеш
        RedisValue cached = _redis.StringGet(cacheKey);
        if (cached.HasValue)
        {
            Console.WriteLine($"  [КЕШ] Cache HIT для товару {productId}");
            return JsonSerializer.Deserialize<ProductDto>(cached!)!;
        }

        // 2. Cache miss -> йдемо в реальну БД
        Console.WriteLine($"  [КЕШ] Cache MISS для товару {productId}");
        ProductDto product = QuerySlowDatabase(productId);

        // 3. Наповнюємо кеш з TTL, щоб дані не жили вічно
        string json = JsonSerializer.Serialize(product);
        _redis.StringSet(cacheKey, json, CacheTtl);

        return product;
    }
}

public record ProductDto(int Id, string Name, decimal Price);

// --- Використання ---
using var redis = ConnectionMultiplexer.Connect("localhost:6379");
var cacheService = new ProductCacheService(redis.GetDatabase());

Console.WriteLine("Перший виклик:");
var p1 = cacheService.GetProduct(55);
Console.WriteLine($"Отримано: {p1.Name}, {p1.Price} грн\n");

Console.WriteLine("Другий виклик (одразу після першого):");
var p2 = cacheService.GetProduct(55);
Console.WriteLine($"Отримано: {p2.Name}, {p2.Price} грн");

// Перший виклик:
//   [КЕШ] Cache MISS для товару 55
//   [БД] Виконую повільний запит до основної бази для товару 55...
// Отримано: Навушники XZ-200, 1299.00 грн
//
// Другий виклик (одразу після першого):
//   [КЕШ] Cache HIT для товару 55
// Отримано: Навушники XZ-200, 1299.00 грн
```

### Приклад 4 — Rate Limiter (fixed window)

```csharp
using StackExchange.Redis;

public class FixedWindowRateLimiter
{
    private readonly IDatabase _redis;
    private readonly int _limit;
    private readonly TimeSpan _window;

    public FixedWindowRateLimiter(IDatabase redis, int limit, TimeSpan window)
    {
        _redis = redis;
        _limit = limit;
        _window = window;
    }

    public bool TryAcquire(string clientId)
    {
        // Ключ прив'язаний до поточного "вікна" часу (наприклад, поточна хвилина)
        string windowBucket = DateTime.UtcNow.ToString("yyyyMMddHHmm");
        string key = $"rate:{clientId}:{windowBucket}";

        long count = _redis.StringIncrement(key);

        if (count == 1)
        {
            // Перший запит у цьому вікні -> ставимо TTL, щоб лічильник зник
            // разом із закінченням вікна
            _redis.KeyExpire(key, _window);
        }

        return count <= _limit;
    }
}

// --- Демонстрація: ліміт 5 запитів на хвилину ---
using var redis = ConnectionMultiplexer.Connect("localhost:6379");
var limiter = new FixedWindowRateLimiter(redis.GetDatabase(), limit: 5, window: TimeSpan.FromMinutes(1));

for (int i = 1; i <= 8; i++)
{
    bool allowed = limiter.TryAcquire("user:1001");
    Console.WriteLine($"Запит #{i}: {(allowed ? "ДОЗВОЛЕНО ✅" : "ЗАБЛОКОВАНО 🔴 (429 Too Many Requests)")}");
}

// Запит #1: ДОЗВОЛЕНО ✅
// Запит #2: ДОЗВОЛЕНО ✅
// Запит #3: ДОЗВОЛЕНО ✅
// Запит #4: ДОЗВОЛЕНО ✅
// Запит #5: ДОЗВОЛЕНО ✅
// Запит #6: ЗАБЛОКОВАНО 🔴 (429 Too Many Requests)
// Запит #7: ЗАБЛОКОВАНО 🔴 (429 Too Many Requests)
// Запит #8: ЗАБЛОКОВАНО 🔴 (429 Too Many Requests)
```

> **Обмеження fixed-window підходу:** якщо вікно — календарна хвилина, клієнт теоретично може зробити 5 запитів наприкінці однієї хвилини і ще 5 одразу на початку наступної — тобто 10 запитів за коротший проміжок, ніж заявлена 1 хвилина ("сплеск на межі вікна"). Для точнішого контролю використовують sliding-window log (зберігання таймстампів у Sorted Set) або sliding-window counter (зважене поєднання двох сусідніх вікон) — детальніше в питаннях senior-рівня нижче.

### Приклад 5 — Розподілене блокування

```csharp
using StackExchange.Redis;

public class SimpleDistributedLock
{
    private readonly IDatabase _redis;

    public SimpleDistributedLock(IDatabase redis) => _redis = redis;

    // Повертає унікальний токен володіння, якщо блокування захоплено, інакше null
    public string? TryAcquireLock(string resource, TimeSpan expiry, string instanceId)
    {
        string lockKey = $"lock:{resource}";

        // SET key value NX EX ttl — атомарно "встановити, тільки якщо ключа ще немає"
        bool acquired = _redis.StringSet(lockKey, instanceId, expiry, When.NotExists);

        return acquired ? instanceId : null;
    }

    // Звільняємо блокування, ТІЛЬКИ якщо воно досі належить нашому інстансу
    // (захист від випадкового звільнення чужого блокування після спливу TTL)
    public bool ReleaseLock(string resource, string instanceId)
    {
        string lockKey = $"lock:{resource}";
        RedisValue currentOwner = _redis.StringGet(lockKey);

        if (currentOwner == instanceId)
        {
            return _redis.KeyDelete(lockKey);
        }
        return false; // блокування вже не наше (або спливло, або перехоплене іншим)
    }
}

// --- Демонстрація: два "інстанси" застосунку змагаються за одне й те саме блокування ---
using var redis = ConnectionMultiplexer.Connect("localhost:6379");
var db = redis.GetDatabase();
var lockManager = new SimpleDistributedLock(db);

string resource = "order:1001:processing";

// Instance A захоплює блокування першим
string? tokenA = lockManager.TryAcquireLock(resource, TimeSpan.FromSeconds(30), "instance-A");
Console.WriteLine(tokenA != null
    ? "Instance A: блокування ЗАХОПЛЕНО ✅"
    : "Instance A: не вдалося захопити блокування 🔴");

// Instance B намагається захопити те саме блокування, поки воно ще утримується
string? tokenB = lockManager.TryAcquireLock(resource, TimeSpan.FromSeconds(30), "instance-B");
Console.WriteLine(tokenB != null
    ? "Instance B: блокування захоплено ✅"
    : "Instance B: НЕ вдалося захопити блокування — вже утримується іншим інстансом 🔴");

// Instance A завершує роботу і звільняє блокування
bool released = lockManager.ReleaseLock(resource, "instance-A");
Console.WriteLine(released ? "Instance A: блокування звільнено ✅" : "Instance A: не вдалося звільнити");

// Тепер Instance B може успішно захопити блокування
string? tokenB2 = lockManager.TryAcquireLock(resource, TimeSpan.FromSeconds(30), "instance-B");
Console.WriteLine(tokenB2 != null
    ? "Instance B (повторна спроба): блокування ЗАХОПЛЕНО ✅"
    : "Instance B (повторна спроба): все ще заблоковано 🔴");

// Instance A: блокування ЗАХОПЛЕНО ✅
// Instance B: НЕ вдалося захопити блокування — вже утримується іншим інстансом 🔴
// Instance A: блокування звільнено ✅
// Instance B (повторна спроба): блокування ЗАХОПЛЕНО ✅
```

## 7. Реальний сценарій: кошик покупок і кешування каталогу для великого магазину

Продовжуючи наскрізну e-commerce архітектуру, розглянуту в інших документах цієї серії/репозиторію (див. загальний гайд з архітектури інтернет-магазину), розберемо, де саме Redis — правильний вибір, а де — категорично неправильний.

### 7.1. Кошик покупок (Shopping Cart) — ідеальний кандидат для Redis

Кошик покупок має характеристики, які майже ідеально збігаються з сильними сторонами Redis:

- **Дуже високе навантаження читання/запису.** Кожне додавання товару, зміна кількості, перегляд кошика — це окрема операція, що відбувається значно частіше, ніж, скажімо, оформлення замовлення.
- **Природна ефемерність.** Більшість кошиків ніколи не перетворюються на замовлення (покинуті кошики — статистично типова, очікувана поведінка користувачів). Немає сенсу тримати ці дані вічно в дорогій, суворо durable реляційній БД.
- **Не потребує "суворих" гарантій**, які обов'язкові для Замовлень (Orders): якщо, у вкрай рідкісному випадку збою, кошик частково втрачено — це прикра, але не катастрофічна подія (користувач просто додасть товари ще раз). Це кардинально відрізняється від втрати даних про вже підтверджене й оплачене замовлення.

**Реалізація:** кошик природно моделюється як **Hash** — один ключ на клієнта, поля — ідентифікатори товарів, значення — кількість:

```
HSET cart:customer:1001 product:55 2
HSET cart:customer:1001 product:12 1
HINCRBY cart:customer:1001 product:55 1   -- додали ще одну одиницю товару 55
HGETALL cart:customer:1001                 -- увесь кошик одним запитом

EXPIRE cart:customer:1001 259200   -- TTL ~ 3 доби: покинуті кошики самі "розчиняються"
```

TTL на кошику вирішує проблему покинутих кошиків елегантно і без окремого фонового job'а для очищення: якщо клієнт не повертається протягом розумного часу (наприклад, 3 доби), кошик просто зникає сам, звільняючи пам'ять — точно та поведінка, яку й очікуємо від "ефемерних" даних.

### 7.2. Кешування каталогу товарів — Cache-Aside перед основною БД

Сторінки каталогу (список товарів категорії, картка товару, результати пошуку) — це класичний **read-heavy** трафік: одні й ті самі дані запитуються тисячами користувачів одночасно, змінюються відносно рідко (ціна, опис, наявність оновлюються значно рідше, ніж читаються).

Розміщення Redis як шару Cache-Aside перед основною реляційною (чи документо-орієнтованою) БД товарів різко знижує навантаження на основну БД: замість того, щоб кожен перегляд сторінки категорії бив по основній БД складним запитом із JOIN'ами, фільтрами й сортуванням, переважна більшість запитів обслуговується прямо з Redis за долі мілісекунди, і основна БД бачить лише "холодні" запити (перше звернення після закінчення TTL кешу).

### 7.3. Де Redis НЕ повинен бути єдиним джерелом істини

**Ніколи не зберігайте авторитетні дані Замовлень (Orders) чи Платежів (Payments) виключно в Redis.** Причина пряма і фундаментальна: навіть із увімкненими RDB і AOF, гарантії довговічності Redis слабші й менш "перевірені боєм" для суворо транзакційних, юридично та фінансово значущих даних, ніж у правильно налаштованої реляційної БД з увімкненим WAL/commit-логом і повними ACID-гарантіями транзакцій (детально розглянутими в документі про ACID та транзакційність у реляційній частині цієї серії).

Замовлення й платежі повинні жити в реляційній БД як джерело істини — з усіма гарантіями атомарності, узгодженості та довговічності, які надає правильно спроєктована транзакційна система. Redis у цьому контексті може виступати **допоміжним** шаром (наприклад, кеш статусу замовлення для швидкого відображення на фронтенді, або чергу подій "замовлення створено" для асинхронної обробки), але ніколи — єдиним і остаточним записом про те, що клієнт заплатив гроші й отримає товар.

## 8. Поширені помилки

### Помилка 1 — Redis як єдине сховище критичних даних без розуміння trade-off персистентності

**Погано:**
```csharp
// Зберігаємо результат оплати ЛИШЕ в Redis, без запису в реляційну БД
db.StringSet($"payment:{orderId}:status", "PAID");
// Якщо Redis перезапуститься до наступного RDB-снапшоту (або взагалі
// без увімкненої персистентності) — інформація про оплату зникає безслідно.
```

**Добре:**
```csharp
// Джерело істини — реляційна БД в транзакції; Redis - лише прискорювач читання
using var transaction = dbConnection.BeginTransaction();
UpdatePaymentStatusInSql(orderId, "PAID", transaction);
transaction.Commit();

// Тепер можна безпечно оновити/інвалідувати кеш - це вже НЕ джерело істини
db.KeyDelete($"order:{orderId}:cache");
```

Правило з розділу 3: якщо дані відновлювані з іншого джерела — Redis без персистентності прийнятний. Якщо ні — або вмикайте AOF з `appendfsync always`/`everysec` і розумійте залишковий ризик, або (значно надійніше для дійсно критичних даних) зберігайте авторитетну копію в реляційній БД.

### Помилка 2 — забутий TTL на кеш-записах

**Погано:**
```csharp
// Немає TTL взагалі -> ключ живе вічно, поки хтось явно його не видалить
db.StringSet($"product:{id}:cache", json);
```

Наслідок: пам'ять Redis поступово, невблаганно росте з кожним новим унікальним товаром/користувачем/сесією, що коли-небудь потрапляли в кеш, аж поки не спрацює eviction (якщо policy це дозволяє) або сервер не впаде через `OOM` (якщо `noeviction`). Це особливо підступна помилка, бо в тестовому середовищі з малою кількістю даних усе працює ідеально — проблема проявляється лише в продакшені, через тижні чи місяці роботи.

**Добре:**
```csharp
// Явний TTL - кеш сам "прибирає за собою"
db.StringSet($"product:{id}:cache", json, TimeSpan.FromMinutes(15));
```

### Помилка 3 — thundering herd / cache stampede при спливанні популярного ключа

**Погано:**
```csharp
public ProductDto GetProduct(int id)
{
    var cached = _redis.StringGet($"product:{id}:cache");
    if (cached.HasValue) return Deserialize(cached);

    // Якщо ключ дуже популярний і щойно спливив -
    // тисячі одночасних запитів ОДНОЧАСНО потрапляють сюди
    var product = QuerySlowDatabase(id); // усі тисячі одночасно б'ють по основній БД!
    _redis.StringSet($"product:{id}:cache", Serialize(product), TimeSpan.FromMinutes(10));
    return product;
}
```

**Добре (два поширені підходи для пом'якшення):**

1. **Розмита (jittered) TTL** — замість фіксованих 10 хвилин для всіх ключів, додається невеликий випадковий розкид, щоб масові ключі не спливали в один момент:
```csharp
var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 60));
_redis.StringSet(cacheKey, json, TimeSpan.FromMinutes(10) + jitter);
```

2. **Блокування перерахунку (lock-based repopulation)** — тільки один запит фактично йде в БД і перезаповнює кеш, решта чекають або отримують трохи застаріле значення:
```csharp
public ProductDto GetProduct(int id)
{
    var cached = _redis.StringGet($"product:{id}:cache");
    if (cached.HasValue) return Deserialize(cached);

    string lockKey = $"lock:product:{id}:repopulate";
    bool gotLock = _redis.StringSet(lockKey, "1", TimeSpan.FromSeconds(5), When.NotExists);

    if (gotLock)
    {
        var product = QuerySlowDatabase(id);
        _redis.StringSet($"product:{id}:cache", Serialize(product), TimeSpan.FromMinutes(10));
        _redis.KeyDelete(lockKey);
        return product;
    }

    // Хтось інший вже перераховує - трохи почекати й повторно спробувати кеш
    Thread.Sleep(50);
    return GetProduct(id);
}
```

## 9. Питання для співбесіди за рівнями

### Junior

1. **Що таке ключ-значення база даних?**
   Модель даних, де кожне значення адресується унікальним ключем, і доступ можливий лише за точним ключем (не за вмістом значення). Забезпечує дуже швидкий (O(1)) пошук ціною відсутності запитів "за значенням".

2. **Назвіть основні типи даних Redis.**
   String, Hash, List, Set, Sorted Set (ZSet). Також існують більш спеціалізовані (Bitmap, HyperLogLog, Stream, геопросторові індекси), але п'ять перелічених — основні й найчастіше застосовувані.

3. **Що таке TTL у Redis?**
   Time To Live — час життя ключа, після спливання якого Redis автоматично видаляє ключ. Встановлюється командою `EXPIRE` або одразу при записі (`SET key value EX seconds`).

4. **Навіщо потрібне кешування?**
   Щоб уникнути повторного виконання дорогих операцій (запитів до БД, обчислень) для тих самих даних, зберігаючи вже обчислений результат у швидкому сховищі (найчастіше — в оперативній пам'яті) на певний час.

5. **Redis зберігає дані на диску чи в оперативній пам'яті?**
   Насамперед в оперативній пам'яті (in-memory) — це джерело його швидкості. Опційно може персистувати дані на диск через RDB (снапшоти) та/або AOF (журнал операцій) для довговічності при перезапуску.

6. **Чим Hash відрізняється від простого String, що містить серіалізований JSON?**
   Hash дозволяє читати/оновлювати окремі поля об'єкта атомарно й без передачі всього об'єкта, тоді як String із JSON вимагає завжди читати/писати весь блоб цілком, навіть щоб змінити одне поле.

### Middle

1. **Чим RDB відрізняється від AOF?**
   RDB — періодичний повний бінарний снапшот усього набору даних (швидке відновлення, можлива втрата даних з моменту останнього снапшоту). AOF — журнал кожної операції запису (кращі гарантії довговічності, більший файл, дещо повільніше). Часто використовуються разом.

2. **Поясніть патерн Cache-Aside.**
   Застосунок спочатку перевіряє кеш; при cache hit повертає дані звідти; при cache miss звертається до основної БД, отримує результат, кладе його в кеш (з TTL) і повертає користувачу. Основний виклик — коректна й вчасна інвалідація кешу при оновленні джерела істини.

3. **Що таке eviction policy і які основні варіанти є?**
   Правило, за яким Redis вирішує, які ключі видаляти, коли досягнуто ліміту пам'яті (`maxmemory`). Основні: `noeviction` (відмова запису), `allkeys-lru`/`volatile-lru` (видалення найменш нещодавно використовуваних), `allkeys-lfu`/`volatile-lfu` (найменш часто використовувані), `volatile-ttl` (першими видаляються ключі, найближчі до спливання TTL).

4. **Як реалізувати найпростіший rate limiter на Redis?**
   `INCR` лічильника, прив'язаного до ключа з ідентифікатором клієнта та поточним часовим "вікном" (наприклад, поточна хвилина); при першому інкременті в новому вікні встановити `EXPIRE`, що дорівнює довжині вікна; якщо результат `INCR` перевищує ліміт — відхилити запит.

5. **Чому Redis Pub/Sub не підходить для критичних, гарантовано доставлюваних повідомлень?**
   Це fire-and-forget механізм: якщо підписник не був підключений у момент публікації, повідомлення втрачається назавжди — немає збереження, немає підтвердження доставки, немає redelivery. Для гарантованої доставки потрібен повноцінний брокер повідомлень (RabbitMQ, Kafka тощо) або, як мінімум, List-based черга з `BRPOP`, де елемент фізично зберігається до забору воркером.

6. **Що робить операцію `INCR` безпечною при паралельному доступі з багатьох клієнтів?**
   Redis однопотоковий у виконанні команд (single-threaded event loop для обробки команд), тому кожна окрема команда, включно з `INCR`, виконується атомарно "від початку до кінця" без можливості перемежування з іншою командою — це усуває класичну гонку даних "read-modify-write", яка виникла б, якби інкремент реалізовувався на клієнті трьома окремими кроками.

### Senior

1. **Спроєктуй розподілену систему rate limiting для API з високим навантаженням.**
   Ключові рішення: (а) алгоритм — fixed window простий, але має сплеск на межі вікон; sliding window log (timestamp-и запитів у Sorted Set, `ZREMRANGEBYSCORE` для видалення застарілих + `ZCARD` для підрахунку) точний, але дорожчий по пам'яті; sliding window counter — компроміс (зважене поєднання поточного й попереднього фіксованих вікон); token bucket — дозволяє контрольовані сплески (burst) понад базову ставку. (б) Атомарність — операції "перевірити і оновити" рахунок повинні виконуватись атомарно; для складнішої логіки, ніж один `INCR`, використовують Lua-скрипти (`EVAL`), які Redis виконує атомарно як єдину команду, уникаючи гонки між кількома окремими викликами клієнта. (в) Розподіленість — якщо кілька інстансів застосунку обробляють запити одного й того ж клієнта, лічильник має бути централізованим (у Redis, а не локальним у пам'яті кожного інстансу), інакше ліміт фактично множиться на кількість інстансів. (г) Продуктивність — для екстремального навантаження варто розглянути локальне наближене обмеження (наприклад, "приблизний" локальний token bucket з періодичною синхронізацією) замість звернення до Redis на кожен запит, жертвуючи точністю ліміту заради latency.

2. **Поясни проблему thundering herd/cache stampede і способи її пом'якшення.**
   Виникає, коли дуже популярний кеш-ключ спливає (за TTL), і величезна кількість одночасних запитів одночасно фіксує cache miss і одночасно звертається до основної БД/дорогого обчислення, різко навантажуючи джерело істини — іноді до відмови (каскадний збій). Мітигації: (1) jittered/staggered TTL — випадковий розкид часу життя, щоб масові ключі не спливали синхронно; (2) блокування перерахунку — лише один запит (той, що першим отримав розподілене блокування) фактично перераховує й перезаповнює кеш, решта або чекають на нього коротко, або отримують дещо застаріле значення (stale-while-revalidate); (3) "вічний" кеш із фоновим проактивним оновленням (background refresh) до фактичного спливання, щоб користувацькі запити ніколи не бачили справжній cache miss; (4) request coalescing на рівні застосунку — якщо кілька запитів на той самий ключ прилітають одночасно в межах одного процесу, об'єднати їх в один фактичний запит до БД.

3. **Коли Redis НЕ підходить як єдине сховище даних, і чому?**
   Коли дані є єдиним і остаточним джерелом істини для критично важливих, юридично/фінансово значущих операцій (замовлення, платежі, баланси рахунків), де неприйнятна навіть невелика ймовірність втрати даних при збої процесу/вузла. Навіть з увімкненим AOF (`appendfsync always`) Redis не проходив настільки тривалу й широку "перевірку боєм" щодо строгих ACID-гарантій транзакцій багатокрокових операцій, як зрілі реляційні БД. Правильний підхід — реляційна БД як джерело істини з повними транзакційними гарантіями, а Redis — як допоміжний шар прискорення читання чи координації, дані в якому завжди можна відновити або звірити з основного джерела.

4. **Опиши, як би ти реалізував розподілене блокування на Redis, і які в нього обмеження (Redlock)?**
   Базова примітива — атомарний `SET key uniqueToken NX EX ttl` для захоплення, і звільнення лише після перевірки, що поточний власник ключа — саме той, хто намагається звільнити (найкраще — атомарно через Lua-скрипт, що об'єднує `GET`+`DEL` в одну нероздільну операцію, уникаючи гонки між перевіркою і видаленням). Redlock розширює це на кілька (зазвичай 5) незалежних Redis-вузлів: блокування вважається успішно захопленим, тільки якщо його вдалося встановити на більшості вузлів у межах обмеженого часу. Обмеження, підняті в дискусії Клеппманн-vs-Санфіліппо: алгоритм покладається на приблизну синхронність годинників і обмежені затримки мережі/паузи GC — довга пауза процесу (наприклад, GC stop-the-world) між перевіркою й фактичною дією під захистом блокування може призвести до того, що TTL блокування спливе, інший клієнт захопить його, а перший клієнт "прокинеться" і продовжить діяти, гадаючи, що досі володіє блокуванням (класичний "split-brain" сценарій). Для дійсно критичних інваріантів рекомендується додатковий "fencing token" — монотонно зростаючий номер, що видається разом із блокуванням, і який захищений ресурс перевіряє й відхиляє застарілі (менші за вже прийняті) токени.

5. **Порівняй Sorted Set для лідерборду з альтернативними підходами.**
   Sorted Set дає O(log N) вставку/оновлення score і O(log N + k) вибірку топ-k, тримаючи дані завжди відсортованими "живцем", без окремого кроку перерахунку — ідеально для лідербордів, що оновлюються дуже часто (кожен ігровий результат, кожен продаж). Альтернатива на реляційній БД — таблиця з індексом за стовпцем score і `ORDER BY score DESC LIMIT k`: працює, але кожен `INSERT`/`UPDATE` частоти score потенційно вимагає перебудови B-Tree індексу, і під дуже частими оновленнями (тисячі за секунду) це помітно дорожче, ніж skip-list операції Redis в пам'яті. Альтернатива на матеріалізованому/денормалізованому кеш-стовпці (наприклад, `Product.SalesCount`, що оновлюється тригером чи фоновою задачею) дешевша для читання, але вносить затримку узгодженості (eventual consistency) і додаткову складність підтримки коректності лічильника. Загальний висновок: Sorted Set — найкращий вибір, коли потрібні і часті оновлення score, і швидкий доступ до впорядкованого топ-N чи рангу конкретного елемента одночасно; для рідко змінюваних, але складно фільтрованих рейтингів (наприклад, "топ товарів за рейтингом серед категорії X із ціною < Y") реляційний підхід з індексами може бути гнучкішим за рахунок можливості комбінувати умови.

6. **Як би ти спроєктував мультирегіональне (multi-region) кешування на Redis для глобального інтернет-магазину?**
   Ключові рішення: локальний Redis-кластер у кожному регіоні (мінімізація latency для read-шляху, який домінує в трафіку), а не єдиний глобальний інстанс. Дані каталогу (переважно read-only з погляду кінцевого користувача) реплікуються/кешуються незалежно в кожному регіоні з прийнятною eventual consistency; дані, що вимагають строгої консистентності одразу після запису в усіх регіонах (наприклад, залишок товару на складі при обмеженому стоку), потребують або централізованого джерела істини з коротким TTL кешу, або явної інвалідації міжрегіональними подіями (наприклад, через Kafka/pub-sub шар подій, що сповіщає всі регіони про інвалідацію конкретного ключа одразу після запису в джерело істини). Важливо явно визначити, які дані толерантні до "трохи застарілих" читань (майже все відображення каталогу), а які — ні (доступність товару в момент оформлення замовлення повинна перевірятись безпосередньо в джерелі істини, а не з регіонального кешу, щоб уникнути продажу того, чого фактично вже немає в наявності).

## 10. Підсумок

### 🗂️ Типи даних Redis — шпаргалка

| Тип | Що це | Типовий e-commerce приклад | Ключові команди |
|---|---|---|---|
| String | Простий рядок/число/блоб | Лічильник переглядів, кешований HTML-фрагмент | `SET`, `GET`, `INCR`, `EXPIRE` |
| Hash | Об'єкт із іменованими полями | Кошик покупок, сесія користувача | `HSET`, `HGET`, `HGETALL`, `HINCRBY` |
| List | Впорядкована послідовність | Черга завдань, "нещодавно переглянуті" | `LPUSH`, `RPOP`, `LRANGE`, `LTRIM` |
| Set | Унікальні неупорядковані елементи | Унікальні відвідувачі, перетин інтересів клієнтів | `SADD`, `SISMEMBER`, `SINTER`, `SUNION` |
| Sorted Set (ZSet) | Set із числовим score, завжди відсортований | Лідерборд, топ бестселерів у реальному часі | `ZADD`, `ZINCRBY`, `ZREVRANGE`, `ZRANK` |

### ⚡ Eviction Policies — шпаргалка

| Policy | Що видаляє | Коли обирати |
|---|---|---|
| `noeviction` | Нічого (відмова запису при OOM) | Дані критичні, втрата неприйнятна |
| `allkeys-lru` | Найдавніше використовувані серед усіх | Інстанс — чистий кеш, за замовчуванням |
| `volatile-lru` | Найдавніше використовувані серед тих, що мають TTL | Мішаний інстанс: кеш + постійні дані |
| `allkeys-lfu` | Найрідше використовувані серед усіх | Популярність важливіша за нещодавність |
| `volatile-lfu` | Найрідше використовувані серед тих, що мають TTL | Те саме, для мішаного інстансу |
| `volatile-ttl` | Найближчі до спливання TTL | Логічно жертвувати тим, що й так скоро зникне |

### ✅ Патерни використання — шпаргалка

| Патерн | Задача | Головна пастка |
|---|---|---|
| Cache-Aside | Пришвидшити читання, знизити навантаження на основну БД | Інвалідація застарілих даних, thundering herd |
| Сесії користувача | Дозволити горизонтальне масштабування stateless-серверів | Забутий TTL → безмежний ріст пам'яті |
| Rate Limiting | Обмежити частоту запитів на клієнта/IP | Сплеск на межі fixed-window вікна |
| Черги (List/Pub-Sub) | Асинхронна обробка, сповіщення в реальному часі | Pub/Sub не гарантує доставку (fire-and-forget) |
| Розподілене блокування | Взаємовиключення між інстансами застосунку | Не строга гарантія при паузах GC/розсинхронізації годинників — потрібен fencing token для критичних інваріантів |
