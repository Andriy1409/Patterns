## 1. Що таке графова база даних?

Уявіть, що ви малюєте на аркуші паперу карту дружніх зв'язків у своїй компанії друзів. Ви малюєте кружечок для кожної людини, підписуєте ім'я, а потім з'єднуєте кружечки стрілочками там, де є зв'язок: "Олена → дружить з → Максим", "Максим → підписаний на → Ірина", "Ірина → працює з → Олена". У результаті на аркуші з'являється павутина з кружечків і підписаних стрілочок між ними.

Це і є, буквально, **графова база даних** — тільки замість аркуша паперу дані зберігаються в структурі, оптимізованій саме для такого "павутинного" вигляду інформації.

### 1.1 Два фундаментальні будівельні блоки

**Вузол (Node)** — це сутність, приблизно як рядок у реляційній таблиці або об'єкт у коді: людина, товар, банківський рахунок, місто. Вузол:

- може мати одну або кілька **міток (Labels)** — грубий аналог "таблиці" або "класу" (`:Person`, `:Product`, `:Account`);
- може мати **властивості (Properties)** — пари ключ-значення, що описують сутність (`name: "Олена"`, `age: 29`, `email: "olena@example.com"`).

**Зв'язок (Relationship)** — це напрямлене, типізоване з'єднання між двома вузлами. І ось тут — головна концептуальна відмінність графової БД від реляційної:

> **У графовій базі даних зв'язок — це рівноправний, повноцінний елемент моделі даних (first-class citizen), а не "довідкова інформація заднім числом" на кшталт зовнішнього ключа.**

У реляційній моделі зв'язок між `Orders` і `Customers` — це просто стовпець `CustomerId`, який СУБД повинна щоразу **реконструювати** через `JOIN`, зіставляючи значення в двох таблицях. Сам факт зв'язку ніде фізично не зберігається як окрема сутність — це побічний ефект збігу значень у двох стовпцях.

У графовій моделі зв'язок — це:

- **типізований** (`:KNOWS`, `:PURCHASED`, `:FOLLOWS`, `:WORKS_AT` — тип зв'язку так само важливий, як мітка вузла);
- **напрямлений** (має чіткий початок і кінець — хоча Cypher дозволяє запитувати в обох напрямках);
- може мати **власні властивості** (наприклад, зв'язок `:PURCHASED` може мати властивість `date: "2026-03-14"` або `amount: 1250`);
- **фізично зберігається як окремий запис** із прямим вказівником на обидва вузли — до нього не треба нічого "реконструювати" під час запиту.

```
        (:Person {name: "Олена"})
                    │
             [:KNOWS {since: 2019}]
                    │
                    ▼
        (:Person {name: "Максим"})
                    │
            [:FOLLOWS {since: 2021}]
                    │
                    ▼
        (:Person {name: "Ірина"})
                    │
           [:WORKS_WITH {team: "Backend"}]
                    │
                    ▼
        (:Person {name: "Олена"})   ← цикл! граф не обов'язково ациклічний
```

### 1.2 Аналогія: карта на папері vs таблиці з ID

Продовжимо аналогію з паперовою картою дружніх зв'язків. Якщо ви спробуєте записати ту саму інформацію у вигляді електронної таблиці (`PersonId`, `Name`) плюс окремої таблиці зв'язків (`FriendshipId`, `PersonId1`, `PersonId2`, `Since`) — інформація технічно збережеться вся, **але "павутинність" зникає з поля зору**. Дивлячись на два рядки таблиці `Friendship`, ви не бачите форму мережі — чи є там щільні кластери, чи є "містки" між групами, хто найбільш "центральний" вузол. Щоб побачити цю форму, вам доведеться писати запит, який реконструює граф із рядків — і саме ця реконструкція є тим, за що реляційна модель платить продуктивністю на глибоких запитах (див. розділ 2).

Графова база даних, навпаки, зберігає дані **у тій формі, у якій ви їх і так подумки уявляєте** — як павутину сутностей і зв'язків. Це не просто "інша нотація" — це інша фізична структура зберігання, оптимізована під **обхід (traversal)** зв'язків, а не під зіставлення значень стовпців.

| | Реляційна модель | Графова модель |
|---|---|---|
| Сутність | Рядок таблиці | Вузол (Node) |
| Зв'язок | Зовнішній ключ + `JOIN` під час запиту | Зв'язок (Relationship) — фізично збережений, типізований, напрямлений |
| Природний запит | "Дай мені рядки, де X = Y" (фільтрація множин) | "Пройди від цього вузла по зв'язках такого типу" (обхід графа) |
| Що добре виходить | Агрегації, транзакційні операції над "плоскими" сутностями | Багатокрокові зв'язки, пошук шляхів, виявлення кластерів/шаблонів у мережі |

**Ключовий висновок:** графова БД — це не "ще один формат зберігання JSON" і не конкурент документній БД. Це модель даних, у якій **сам зв'язок між сутностями є настільки ж важливим об'єктом першого класу, як і самі сутності**, і яка фізично зберігається так, щоб обхід цих зв'язків був максимально дешевим.

## 2. Чому реляційні JOIN-и погано масштабуються для глибоких зв'язків

Це — центральна мотивація для існування графових баз даних. Якщо ви зрозумієте тільки один розділ цього документа, нехай це буде цей.

### 2.1 Задача "друзі друзів друзів"

Уявіть соціальну мережу і задачу: **"Знайти всіх людей, які є друзями друзів друзів Олени"** (3-крокова навігація, "friends of friends of friends", 3-hop traversal). Це типова задача для рекомендації нових знайомих.

#### Реляційний підхід

У реляційній моделі дружба зберігається як таблиця `Friendships (PersonId1, PersonId2)`. Щоб знайти друзів-на-відстані-3, потрібно **триразово з'єднати таблицю саму з собою**:

```sql
SELECT DISTINCT p3.Name
FROM People p0
JOIN Friendships f1 ON f1.PersonId1 = p0.Id
JOIN People p1 ON p1.Id = f1.PersonId2          -- 1-й крок: друзі Олени
JOIN Friendships f2 ON f2.PersonId1 = p1.Id
JOIN People p2 ON p2.Id = f2.PersonId2          -- 2-й крок: друзі друзів
JOIN Friendships f3 ON f3.PersonId1 = p2.Id
JOIN People p3 ON p3.Id = f3.PersonId2          -- 3-й крок: друзі друзів друзів
WHERE p0.Name = 'Олена'
  AND p3.Id NOT IN (
      SELECT PersonId2 FROM Friendships WHERE PersonId1 = p0.Id
  );
```

Проблема не в тому, що цей SQL складно написати (хоча він уже доволі громіздкий на 3 кроки — уявіть 5 чи 6). Проблема — **у тому, як цей запит виконується всередині СУБД**.

Кожен `JOIN` — це операція, яка (залежно від наявних індексів і статистики оптимізатора) зазвичай передбачає побудову або сканування проміжного набору результатів. Навіть за наявності ідеальних індексів на `PersonId1`/`PersonId2`:

- крок 1 повертає, скажімо, 150 друзів Олени;
- крок 2 для КОЖНОГО з цих 150 людей шукає їхніх друзів — набір може розрости до 15 000 рядків;
- крок 3 для КОЖНОГО з 15 000 знову шукає друзів — набір може вибухнути до мільйонів проміжних рядків, перш ніж застосується `DISTINCT` і фільтрація.

Це називають **"вибухом проміжних результатів" (combinatorial/intermediate result explosion)**: кожен додатковий `JOIN`-крок множить (а не додає) обсяг роботи оптимізатора. І що важливіше — **вартість кожного `JOIN` залежить від розміру задіяних таблиць**: `JOIN` для соцмережі на 10 000 людей — це один порядок вартості, а `JOIN` для соцмережі на 500 мільйонів людей (як у реального Facebook/Instagram) — зовсім інший порядок, навіть якщо конкретна людина, з якої ми стартуємо, має ті самі 150 друзів. Оптимізатору доводиться приймати рішення про порядок з'єднання таблиць, будувати хеш-таблиці для `HASH JOIN`, або йти по індексу для `NESTED LOOP JOIN` — і на кожному з цих шляхів вартість зростає разом із загальним розміром датасету, навіть якщо результат, який нас насправді цікавить, невеликий.

### 2.2 Графовий підхід: index-free adjacency

Ось тут графові бази даних (принаймні **"нативні" (native)** графові БД, до яких належить Neo4j) роблять дещо принципово інше. Ключова властивість називається **index-free adjacency** ("суміжність без індексу", буквально — "суміжність, вільна від індексу").

**Що це означає технічно:** кожен вузол у графовій БД фізично зберігає **прямі вказівники (пойнтери)** на свої зв'язки, а кожен зв'язок зберігає прямі вказівники на два вузли, які він з'єднує (і, як правило, на "наступний" і "попередній" зв'язок того самого вузла — так формується зв'язаний список суміжних ребер). Це нагадує структуру даних "зв'язаний список" або "вказівники на сусідні вузли" у класичному уявленні графа в інформатиці (adjacency list на рівні дискового представлення, а не побудована "на льоту" через індекс).

```
Реляційна модель (щоб перейти від Person(5) до його друзів):
  1. SELECT * FROM Friendships WHERE PersonId1 = 5   ← ПОШУК через індекс, O(log n)
  2. Отримати список PersonId2                        ← побудова проміжного набору
  3. Ще один пошук/JOIN, щоб дістати самі People-рядки

Графова модель (index-free adjacency), щоб перейти від (:Person {id:5}):
  1. У вузла ВЖЕ Є фізичний вказівник на перший зв'язок типу :KNOWS
  2. Перейти по вказівнику — O(1), незалежно від розміру всієї бази
  3. Якщо зв'язків кілька — пройти по зв'язаному списку зв'язків цього вузла
```

**Головна відмінність:** у реляційній моделі кожен крок навігації — це **пошук** (index lookup), вартість якого залежить від розміру таблиці (нехай і логарифмічно). У нативній графовій БД, коли ви **вже стоїте на вузлі**, перехід до сусіднього вузла через конкретний зв'язок — це **пряме розіменування вказівника**, вартість якого **не залежить від того, скільки всього вузлів у базі** — 10 тисяч чи 10 мільярдів. Це і називають "O(1)-подібним" переходом, і на цьому побудована вся продуктивність графових БД на глибоких обходах.

> **Точне формулювання для співбесіди:** Index-free adjacency — це властивість архітектури зберігання даних, за якою кожен вузол безпосередньо (фізичними вказівниками) знає про свої суміжні зв'язки та вузли, тому обхід (`traversal`) від вузла до вузла не потребує глобального пошуку через індекс на кожному кроці — вартість переходу залежить лише від кількості зв'язків у ЦЬОГО КОНКРЕТНОГО вузла (його "ступеня", degree), а не від загального розміру графа.

### 2.3 Порівняння на масштабі

```
Розмір датасету →           10 тис. вузлів     1 млн вузлів      1 млрд вузлів
─────────────────────────────────────────────────────────────────────────────
SQL: 3× self-JOIN            швидко             помітно повільніше   дуже повільно /
   "друзі друзів друзів"                        (проміжні набори     може не завершитись
                                                  ростуть)             у розумний час
─────────────────────────────────────────────────────────────────────────────
Cypher: 3-hop traversal       швидко             швидко                швидко
  (:Person)-[:KNOWS*3]->()                       (залежить від         (залежить від
                                                   ступеня ВУЗЛА,        ступеня ВУЗЛА,
                                                   не всієї бази)        не всієї бази)
```

Це не означає, що графова БД "швидша за реляційну в усьому" — для точкових вибірок, агрегацій по всій таблиці чи транзакційних операцій над плоскими сутностями реляційна модель залишається чудовим і часто кращим вибором (детальніше — секція 8 "Поширені помилки"). Перевага графової БД строго локалізована: **вона проявляється саме на багатокрокових (multi-hop) обходах зв'язків**, і що глибші ці обходи (2, 3, 5+ кроків) і що більший загальний датасет — то драматичніша різниця.

### 2.4 Коротко про масштабування й узгодженість (без повторення CAP з нуля)

Оскільки в цій серії документів теорема CAP і компроміси узгодженості вже детально розібрані в оглядовому документі NoSQL, тут — лише те, що специфічно для графових БД. Index-free adjacency дає величезну перевагу на глибоких обходах, **але має і зворотний бік**: обхід графа (особливо `shortestPath` чи глибокий `*1..N` traversal) значно важче "розрізати" на незалежні шматки й розподілити по кількох машинах, ніж, скажімо, просте партиціювання документів за ключем у документній БД. Тому:

- Neo4j традиційно масштабується **вертикально** для самого графового рушія (один потужний сервер, весь граф у пам'яті/на швидкому диску) — це прямий наслідок того, що ефективний traversal хоче мати прямий доступ до вказівників без мережевих переходів між шардами;
- **горизонтальне** масштабування в Neo4j реалізується через кластер із однією "провідною" копією для запису (causal cluster: 1 leader + кілька read replica), що дає **читання, що масштабується горизонтально**, і **консистентність за моделлю "causal consistency"** (кожен клієнт гарантовано бачить свої власні попередні записи) — компроміс, що ближче до AP/eventual-consistency сторони спектра CAP для читань з реплік, і ближче до CP для запису через єдиного лідера;
- це прямо контрастує з деякими документними чи колонковими БД (обговорюваними раніше в серії), спроєктованими з нуля під горизонтальне шардування великих обсягів слабко зв'язаних записів.

**Практичний висновок:** якщо ваш граф справді сягає мільярдів вузлів/зв'язків і потребує горизонтального масштабування запису на десятки вузлів — це вже інша вагова категорія (розподілені графові рушії, спеціалізовані рішення), а не типовий кейс "додати граф як допоміжне сховище" з розділу 7. Для переважної більшості практичних застосувань (рекомендації, антифрод, дозволи) одного добре ресурсованого кластера Neo4j цілком достатньо.

## 3. Cypher — мова запитів графів

**Cypher** — декларативна мова запитів, створена спеціально для Neo4j (пізніше частково стандартизована через ISO GQL — Graph Query Language). Її головна дизайнерська ідея — **справді елегантна і варта того, щоб її явно оцінити**: синтаксис запиту **виглядає як ASCII-малюнок того графового шаблону, який ви шукаєте**.

```
(вузол1)-[:ТИП_ЗВ'ЯЗКУ]->(вузол2)
```

Круглі дужки `()` малюють вузол (як кружечок на паперовій карті), квадратні дужки `[]` малюють зв'язок (як підпис на стрілочці), а `->` буквально показує напрямок стрілочки. **Ви пишете запит, малюючи те, що шукаєте** — це не метафора заради краси, а буквальний, наскрізний принцип синтаксису Cypher.

### 3.1 Пошук вузла за властивістю

```cypher
MATCH (p:Person {name: "Олена"})
RETURN p;
```

Прочитайте це вголос: "знайди вузол з міткою `Person`, у якого властивість `name` дорівнює `"Олена"`, і поверни його". Синтаксис `{name: "Олена"}` усередині дужок вузла — це фільтр за властивостями прямо в патерні.

Еквівалент через `WHERE` (те саме, інша форма запису — корисно для складніших умов):

```cypher
MATCH (p:Person)
WHERE p.name = "Олена"
RETURN p;
```

### 3.2 Пошук прямих зв'язків

"Знайти всіх, кого Олена знає напряму":

```cypher
MATCH (olena:Person {name: "Олена"})-[:KNOWS]->(friend:Person)
RETURN friend.name;
```

Знову — прочитайте буквально: "(Олена) -[ЗНАЄ]-> (друг)". Запит візуально відображає граф-патерн, що шукається:

```
(olena:Person {name:"Олена"}) ──[:KNOWS]──▶ (friend:Person)
```

Можна фільтрувати ще й за типом та властивостями зв'язку:

```cypher
MATCH (olena:Person {name: "Олена"})-[r:KNOWS]->(friend:Person)
WHERE r.since < 2020
RETURN friend.name, r.since;
```

### 3.3 Багатокрокові (variable-length) шляхи

Ось де Cypher показує свою справжню силу — і де показано вже обговорену в розділі 2 перевагу index-free adjacency на практиці. Синтаксис `*1..3` після типу зв'язку означає "від 1 до 3 переходів цього типу зв'язку підряд":

```cypher
MATCH (olena:Person {name: "Олена"})-[:KNOWS*1..3]->(someone:Person)
WHERE someone <> olena
RETURN DISTINCT someone.name;
```

Це і є те саме "друзі друзів друзів" із розділу 2 — але замість трьох `JOIN`-ів на 3 таблиці, це **один патерн** `[:KNOWS*1..3]`, що читається як "від 1 до 3 стрибків по зв'язку KNOWS". Варіанти запису довжини шляху:

| Синтаксис | Значення |
|---|---|
| `[:KNOWS]` | рівно 1 крок (прямий зв'язок) |
| `[:KNOWS*2]` | рівно 2 кроки |
| `[:KNOWS*1..3]` | від 1 до 3 кроків |
| `[:KNOWS*..5]` | до 5 кроків (мінімум не заданий → 1) |
| `[:KNOWS*]` | необмежена кількість кроків (обережно — потенційно дорого на щільних графах!) |

### 3.4 Фільтрація та повернення конкретних властивостей

Повноцінний приклад — знайти імена та вік друзів Олени старших за 25, відсортованих за віком:

```cypher
MATCH (olena:Person {name: "Олена"})-[:KNOWS]->(friend:Person)
WHERE friend.age > 25
RETURN friend.name AS ім'я, friend.age AS вік
ORDER BY friend.age DESC
LIMIT 10;
```

Структура запиту практично завжди така: `MATCH` (описати шаблон, що шукаємо) → `WHERE` (додаткові фільтри, які незручно чи неможливо виразити прямо в патерні) → `RETURN` (що повернути, з аліасами через `AS`) → опційно `ORDER BY`, `LIMIT`, `SKIP`.

### 3.5 Ще кілька важливих конструкцій

Кілька додаткових елементів Cypher, які постійно зустрічаються в реальних запитах і варто знати для впевненого middle/senior рівня.

**`OPTIONAL MATCH`** — аналог `LEFT JOIN`: повертає рядок навіть якщо патерн не знайдено (з `null` замість відсутніх значень), на відміну від звичайного `MATCH`, який просто відкидає рядки без збігу:

```cypher
MATCH (c:Customer {id: 1})
OPTIONAL MATCH (c)-[:PURCHASED]->(p:Product)
RETURN c.name, COLLECT(p.name) AS purchases;
-- Якщо клієнт ще нічого не купував — поверне рядок з порожнім списком,
-- а не "зникне" з результату, як сталося б зі звичайним MATCH
```

**Найкоротший шлях (`shortestPath`)** — вбудована функція для класичної задачі "як найкоротше пов'язані ці два вузли":

```cypher
MATCH path = shortestPath(
  (olena:Person {name: "Олена"})-[:KNOWS*..10]-(ihor:Person {name: "Ігор"})
)
RETURN path, LENGTH(path) AS кроків;
```

Це прямий аналог задачі пошуку найкоротшого шляху в графі (BFS) — тієї самої, що згадується в мережевому розділі цієї серії стосовно маршрутизації пакетів між вузлами мережі. `shortestPath` під капотом виконує BFS від обох кінців одночасно (bidirectional search), що на графі з мільйонами вузлів суттєво дешевше за наївний повний обхід.

**Агрегатні функції** (`COUNT`, `COLLECT`, `SUM`, `AVG`, `MAX`/`MIN`) працюють подібно до SQL, але типово застосовуються після `MATCH`-патерна, що знайшов групу зв'язаних вузлів:

```cypher
MATCH (c:Customer)-[:PURCHASED]->(p:Product)
RETURN c.name, COUNT(p) AS кількістьПокупок, COLLECT(p.name) AS товари
ORDER BY кількістьПокупок DESC;
```

**`MERGE`** — "знайти або створити" (upsert): шукає патерн, і якщо його не існує — створює. Критично важливо для ідемпотентних скриптів завантаження даних (наприклад, ETL-процес, який може повторно обробити ту саму подію):

```cypher
MERGE (c:Customer {id: 42})
ON CREATE SET c.name = "Новий клієнт", c.createdAt = datetime()
ON MATCH SET c.lastSeenAt = datetime();
```

Без `MERGE` (тобто з `CREATE`) повторний запуск того самого скрипту створив би дублікати вузлів — поширена помилка при побудові ETL-пайплайнів у граф (див. також розділ 8).

**Ключовий висновок:** Cypher навмисно "малюється", а не пишеться в стилі SQL-таблиць. Це не просто синтаксичний цукор — це прямий наслідок того, що дані фізично зберігаються як граф, тому і мова запитів природно моделюється як опис графового шаблону.

## 4. Класичні застосування графових БД

### 4.1 Соціальні мережі — рекомендація друзів

Класична задача: **"друзі друзів, які ще не є моїми друзями"** — типовий алгоритм "People You May Know".

```cypher
MATCH (me:Person {name: "Олена"})-[:KNOWS]->(:Person)-[:KNOWS]->(candidate:Person)
WHERE NOT (me)-[:KNOWS]->(candidate) AND candidate <> me
RETURN candidate.name, COUNT(*) AS mutualFriends
ORDER BY mutualFriends DESC
LIMIT 10;
```

Патерн `NOT (me)-[:KNOWS]->(candidate)` — ще один приклад "малювання" запиту: буквально "НЕ існує стрілочки KNOWS від мене до кандидата". `COUNT(*)` тут рахує кількість шляхів довжиною 2, тобто кількість спільних друзів — природний сигнал для ранжування рекомендацій.

### 4.2 Рекомендаційні системи

"Клієнти, які купили X, також купили Y" — обхід графа покупок:

```cypher
MATCH (:Product {sku: "X"})<-[:PURCHASED]-(:Customer)-[:PURCHASED]->(other:Product)
WHERE other.sku <> "X"
RETURN other.name, COUNT(*) AS timesCoBought
ORDER BY timesCoBought DESC
LIMIT 5;
```

Більш витончений варіант — багатокроковий обхід "люди, схожі на вас, яким сподобалося Z" (колаборативна фільтрація глибиною 2-3 переходи: клієнт → товари, які купував → інші клієнти, що купували ті самі товари → товари, які купували ВОНИ). Це саме той тип задачі, де реляційні багатоJOIN-запити починають деградувати на масштабі, а графовий обхід залишається швидким (розділ 2). Це — **пряме продовження теми з `ecommerce-architecture-guide.md`** цієї серії документів: там рекомендаційний рушій для великого магазину згадується як підсистема, яку варто виносити в окремий спеціалізований сервіс — і графова БД є природним технологічним вибором саме для рушія типу "разом із цим товаром також купують" на великому каталозі й великій історії покупок (докладніше — розділ 7).

### 4.3 Виявлення шахрайства (Fraud Detection)

Це один із найсильніших "хрестоматійних" кейсів для графових БД, і варто розібрати його трохи глибше. Класична задача антифрод-систем — не знайти ОДИН підозрілий рахунок (це часто просто), а знайти **кластер (кільце) із кількох формально не пов'язаних акаунтів**, які насправді пов'язані через спільні приховані атрибути:

```
(:Account A) ──[:USED_CARD]──▶ (:Card #1234) ◀──[:USED_CARD]── (:Account B)
      │                                                              │
      │                                                              │
[:USED_DEVICE]                                                [:USED_DEVICE]
      │                                                              │
      ▼                                                              ▼
(:Device "fp-9981") ◀─────────────[:USED_DEVICE]───────────── (:Account C)
```

Тут акаунти A, B і C формально належать різним людям з різними іменами й адресами — у жодній парі рядків таблиці `Accounts` немає прямого поля, яке б їх пов'язувало. Але якщо промалювати граф "рахунок → картка/пристрій/IP/адреса, якими він користувався", раптом виявляється **кластер спільних атрибутів**, що є класичним сигналом мережі шахрайства (наприклад, ферма фейкових акаунтів, що використовують один і той самий пристрій чи одну вкрадену картку).

```cypher
MATCH (a1:Account)-[:USED_CARD]->(c:Card)<-[:USED_CARD]-(a2:Account)
WHERE a1 <> a2
WITH c, COLLECT(DISTINCT a1) + COLLECT(DISTINCT a2) AS accounts
UNWIND accounts AS acc
WITH c, COLLECT(DISTINCT acc) AS distinctAccounts
WHERE SIZE(distinctAccounts) > 3
RETURN c.fingerprint AS підозріла_картка, SIZE(distinctAccounts) AS кількість_акаунтів;
```

Чому реляційна модель тут "болюча": еквівалентний SQL-запит потребував би самоз'єднання таблиці `AccountCardUsage` сама з собою, групування за карткою, підрахунку `DISTINCT AccountId`, і це лише для **одного рівня** спільного атрибута (спільна картка). Якщо потрібно знайти кластери через **комбінацію** атрибутів (спільна картка АБО спільний пристрій АБО спільна IP-адреса, транзитивно — рахунок A пов'язаний з B через картку, а B пов'язаний з C через пристрій), у SQL це виливається в дедалі складніші рекурсивні CTE з непередбачуваною глибиною рекурсії. У Cypher це — природне розширення того самого патерна `*1..N` для будь-якого типу спільного зв'язку, і саме тому банки, платіжні системи (PayPal — один із класичних публічних кейсів) та страхові компанії використовують графові БД саме для антифрод-аналітики.

### 4.4 Керування доступом / дозволами (Permission Graphs)

Складні ієрархії ролей і груп ("користувач → належить до групи → група успадковує роль → роль дає дозвіл") природно моделюються як граф:

```
(:User {name:"Іван"})-[:MEMBER_OF]->(:Group {name:"Розробники"})
                                            │
                                     [:HAS_ROLE]
                                            ▼
                                   (:Role {name:"Editor"})
                                            │
                                    [:GRANTS]
                                            ▼
                              (:Permission {name:"EDIT_ARTICLE"})
```

Питання "чи має Іван дозвіл `EDIT_ARTICLE`?" перетворюється на обхід шляху будь-якої довжини між вузлом користувача і вузлом дозволу:

```cypher
MATCH (u:User {name: "Іван"})-[:MEMBER_OF|HAS_ROLE|GRANTS*1..5]->(p:Permission {name: "EDIT_ARTICLE"})
RETURN COUNT(*) > 0 AS маєДозвіл;
```

У реляційній моделі складні вкладені ієрархії ролей (роль успадковує іншу роль, група вкладена в групу довільної глибини) традиційно моделюються через рекурсивні CTE (`WITH RECURSIVE`) — робоче, але значно менш природне рішення, ніж прямий graph traversal.

### 4.5 Мережева/інфраструктурна топологія

Роутери, комутатори та їхні фізичні й логічні з'єднання — це, буквально, граф: вузли — це пристрої, зв'язки — це кабелі/логічні лінки з властивостями (пропускна здатність, затримка, статус лінку). Це прямо перегукується з темами топології мереж, VLAN-сегментації та маршрутизації з мережевого розділу цієї серії документів (`Мережі/switching-and-vlans.md`, `Мережі/routing-fundamentals.md`) — задачі на кшталт "знайти найкоротший шлях між двома вузлами мережі" чи "які пристрої постраждають, якщо цей комутатор впаде" — це класичні задачі обходу графа (BFS/найкоротший шлях), для яких графова БД є природним інструментом моделювання та аналізу топології великих мереж.

## 5. Індексація в графових БД

Важливий і водночас часто неправильно зрозумілий момент: **графові бази даних теж використовують індекси**, і "index-free adjacency" **не означає, що індекси взагалі не потрібні**.

### 5.1 Точний розподіл ролей

Потрібно чітко розділяти два різні етапи будь-якого графового запиту:

1. **Знайти стартовий вузол (entry point)** — наприклад, "знайти вузол `Person`, у якого `email = "olena@example.com"`". Це **точковий пошук за властивістю**, і для нього Neo4j (та інші графові БД) використовують індекси, концептуально дуже схожі на B-Tree індекси з реляційного світу (див. `Реляційні/3-indexes-and-query-optimization.md` цієї серії — там детально розібрано, як влаштовано B-Tree). Без такого індексу пошук стартового вузла за властивістю означав би повне сканування всіх вузлів бази (full node scan) — так само повільно, як сканування таблиці без індексу в SQL.

2. **Обійти зв'язки від уже знайденого вузла** — от тут і застосовується index-free adjacency: коли ви **вже стоїте** на конкретному вузлі (знайденому на кроці 1), перехід до сусідніх вузлів через його зв'язки не потребує ЖОДНОГО додаткового індексного пошуку — це пряме розіменування фізичного вказівника.

```
Запит: MATCH (p:Person {email: "olena@example.com"})-[:KNOWS*1..3]->(x) RETURN x

Крок 1: p:Person {email: "..."}   ← ІНДЕКС по email, знаходимо СТАРТОВИЙ вузол
        (без індексу — full scan усіх вузлів :Person, повільно на мільйонах)
                    │
                    ▼
Крок 2: -[:KNOWS*1..3]->            ← INDEX-FREE ADJACENCY, прямі вказівники,
        (від знайденого вузла         не потребує індексу на кожному кроці
         далі по зв'язках)
```

> **Точне формулювання, яке часто плутають на співбесіді:** Index-free adjacency прискорює **обхід** графа від вузла до вузла, коли ви вже на ньому стоїте. Вона **нічого не говорить** про те, як швидко ви знайдете сам початковий вузол за довільним критерієм — для цього, як і в реляційній БД, потрібен звичайний індекс. Плутанина цих двох речей — одна з найпоширеніших помилок розуміння графових БД (див. також розділ 8).

### 5.2 Практика в Neo4j

```cypher
-- Створити індекс на властивості email вузлів з міткою Person
CREATE INDEX person_email_index IF NOT EXISTS
FOR (p:Person) ON (p.email);

-- Створити обмеження унікальності (автоматично створює й індекс)
CREATE CONSTRAINT person_email_unique IF NOT EXISTS
FOR (p:Person) REQUIRE p.email IS UNIQUE;
```

Без такого індексу запит `MATCH (p:Person {email: "..."}) ...` на базі з 50 мільйонами вузлів `Person` означав би прочитати всі 50 мільйонів вузлів, перш ніж почати сам граф-обхід — саме та проблема, яку індекси вирішують у реляційному світі, повністю переноситься сюди без змін по суті.

## 6. Практичні приклади на Cypher та C#

### Приклад 1 — Побудова графа e-commerce і колаборативна фільтрація

```cypher
// Створення клієнтів
CREATE (c1:Customer {id: 1, name: "Олена"}),
       (c2:Customer {id: 2, name: "Максим"}),
       (c3:Customer {id: 3, name: "Ірина"});

// Створення товарів
CREATE (p1:Product {sku: "LAPTOP-15", name: "Ноутбук 15\""}),
       (p2:Product {sku: "MOUSE-WL", name: "Бездротова миша"}),
       (p3:Product {sku: "BAG-LAP",  name: "Сумка для ноутбука"}),
       (p4:Product {sku: "STAND-LAP", name: "Підставка для ноутбука"});

// Зв'язки покупок
MATCH (c1:Customer {id: 1}), (c2:Customer {id: 2}), (c3:Customer {id: 3}),
      (p1:Product {sku: "LAPTOP-15"}), (p2:Product {sku: "MOUSE-WL"}),
      (p3:Product {sku: "BAG-LAP"}), (p4:Product {sku: "STAND-LAP"})
CREATE (c1)-[:PURCHASED {date: date("2026-01-10")}]->(p1),
       (c1)-[:PURCHASED {date: date("2026-01-10")}]->(p2),
       (c2)-[:PURCHASED {date: date("2026-02-03")}]->(p1),
       (c2)-[:PURCHASED {date: date("2026-02-03")}]->(p3),
       (c3)-[:PURCHASED {date: date("2026-02-20")}]->(p1),
       (c3)-[:PURCHASED {date: date("2026-02-20")}]->(p4);

// Зв'язки схожості товарів (можна виводити окремим ETL-процесом)
MATCH (p2:Product {sku: "MOUSE-WL"}), (p3:Product {sku: "BAG-LAP"}), (p4:Product {sku: "STAND-LAP"})
CREATE (p2)-[:SIMILAR_TO]->(p3),
       (p3)-[:SIMILAR_TO]->(p4);
```

Тепер запит "товари, які купували клієнти, що також купували LAPTOP-15" (базова колаборативна фільтрація):

```cypher
MATCH (:Product {sku: "LAPTOP-15"})<-[:PURCHASED]-(c:Customer)-[:PURCHASED]->(rec:Product)
WHERE rec.sku <> "LAPTOP-15"
RETURN rec.name AS рекомендація, COUNT(DISTINCT c) AS кількістьКлієнтів
ORDER BY кількістьКлієнтів DESC;
```

Результат: `MOUSE-WL` (1 клієнт), `BAG-LAP` (1 клієнт), `STAND-LAP` (1 клієнт) — на реальних даних із тисячами клієнтів це природно виявляє найпопулярніші супутні товари.

### Приклад 2 — "Друзі друзів" на Cypher vs SQL

```cypher
MATCH (me:Person {name: "Олена"})-[:KNOWS*2..3]->(fof:Person)
WHERE NOT (me)-[:KNOWS]->(fof) AND fof <> me
RETURN DISTINCT fof.name;
```

Один рядок `MATCH` виражає весь 2-3-кроковий обхід. Порівняйте це з еквівалентним SQL, де кожен додатковий "крок" — це ще один `JOIN` і ще одна проміжна таблиця в плані виконання:

```sql
-- SQL-еквівалент "друзів на відстані 2-3" через self-JOIN
SELECT DISTINCT p_end.Name
FROM People p0
JOIN Friendships f1 ON f1.PersonId1 = p0.Id
JOIN People p1        ON p1.Id = f1.PersonId2
JOIN Friendships f2 ON f2.PersonId1 = p1.Id
JOIN People p2        ON p2.Id = f2.PersonId2
LEFT JOIN Friendships f3 ON f3.PersonId1 = p2.Id
LEFT JOIN People p_end   ON p_end.Id = COALESCE(f3.PersonId2, p2.Id)
WHERE p0.Name = 'Олена'
  AND p_end.Id NOT IN (SELECT PersonId2 FROM Friendships WHERE PersonId1 = p0.Id)
  AND p_end.Id <> p0.Id;
```

Помітьте: SQL-версія навіть для "від 2 до 3 кроків" (а не фіксовано 3) стає суттєво складнішою (потрібен `LEFT JOIN` + `COALESCE`, щоб обробити обидві довжини шляху), тоді як у Cypher це просто зміна діапазону `*2..3`. І, як розібрано в розділі 2, продуктивність SQL-версії деградує зі зростанням таблиць `People`/`Friendships`, тоді як продуктивність Cypher-версії залежить головно від ступеня (кількості зв'язків) конкретних вузлів на шляху, а не від загального розміру бази.

### Приклад 3 — Виявлення шахрайства: спільний платіжний відбиток

Задача: знайти платіжні картки (за унікальним "відбитком" — fingerprint, а не самим номером картки, з міркувань безпеки), якими користувалися **більше 3** формально не пов'язаних клієнтських акаунтів — класична ознака кільця шахрайства (fraud ring):

```cypher
MATCH (card:PaymentFingerprint)<-[:USED_CARD]-(acc:Account)
WITH card, COLLECT(DISTINCT acc) AS accounts
WHERE SIZE(accounts) > 3
RETURN card.fingerprint AS підозріла_картка,
       SIZE(accounts) AS кількістьАкаунтів,
       [a IN accounts | a.email] AS повʼязаніАкаунти
ORDER BY кількістьАкаунтів DESC;
```

Розширений варіант — врахувати ще й спільний пристрій (транзитивний зв'язок через два різні типи атрибутів одночасно):

```cypher
MATCH (a1:Account)-[:USED_CARD|USED_DEVICE*1..2]-(a2:Account)
WHERE a1 <> a2 AND a1.registeredCountry <> a2.registeredCountry
WITH a1, COLLECT(DISTINCT a2) AS suspiciousLinks
WHERE SIZE(suspiciousLinks) >= 3
RETURN a1.email AS акаунт, SIZE(suspiciousLinks) AS підозрілихЗв'язків;
```

Тут `[:USED_CARD|USED_DEVICE*1..2]` шукає зв'язок ОБОХ типів (картка АБО пристрій), до 2 кроків, а фільтр `registeredCountry` додає бізнес-логіку "акаунти з різних країн, які раптом ділять платіжні атрибути, — підозріліше, ніж просто члени однієї родини з одного будинку".

### Приклад 4 — C# з Neo4j.Driver

```csharp
using Neo4j.Driver;

// Підключення до Neo4j (типово: bolt://localhost:7687)
await using var driver = GraphDatabase.Driver(
    "bolt://localhost:7687",
    AuthTokens.Basic("neo4j", "your_password"));

// Перевірка з'єднання (гарна практика при старті застосунку)
await driver.VerifyConnectivityAsync();

await using var session = driver.AsyncSession(o => o.WithDatabase("neo4j"));

// Параметризований Cypher-запит — рекомендація товарів
var recommendations = await session.ExecuteReadAsync(async tx =>
{
    var cursor = await tx.RunAsync(
        """
        MATCH (:Product {sku: $sku})<-[:PURCHASED]-(c:Customer)-[:PURCHASED]->(rec:Product)
        WHERE rec.sku <> $sku
        RETURN rec.name AS name, rec.sku AS sku, COUNT(DISTINCT c) AS score
        ORDER BY score DESC
        LIMIT 5
        """,
        new { sku = "LAPTOP-15" });

    return await cursor.ToListAsync(record => new
    {
        Name = record["name"].As<string>(),
        Sku = record["sku"].As<string>(),
        Score = record["score"].As<long>()
    });
});

Console.WriteLine("Рекомендовані товари для LAPTOP-15:");
foreach (var rec in recommendations)
{
    Console.WriteLine($"  {rec.Sku,-12} {rec.Name,-30} (куплено разом: {rec.Score})");
}

// Приклад запису (транзакція запису)
await session.ExecuteWriteAsync(async tx =>
{
    await tx.RunAsync(
        """
        MATCH (c:Customer {id: $customerId}), (p:Product {sku: $sku})
        CREATE (c)-[:PURCHASED {date: datetime()}]->(p)
        """,
        new { customerId = 4, sku = "MOUSE-WL" });
});
```

Очікуваний консольний вивід:

```
Рекомендовані товари для LAPTOP-15:
  MOUSE-WL     Бездротова миша                (куплено разом: 142)
  BAG-LAP      Сумка для ноутбука             (куплено разом: 98)
  STAND-LAP    Підставка для ноутбука         (куплено разом: 51)
```

**Важливі практичні деталі роботи з драйвером:**

- `session.ExecuteReadAsync` / `ExecuteWriteAsync` — рекомендований спосіб виконання запитів: драйвер автоматично повторює транзакцію при тимчасових помилках (наприклад, при перевиборі лідера в кластері).
- Завжди використовуйте **параметризовані запити** (`$sku`, а не конкатенацію рядків) — так само, як параметризовані SQL-запити захищають від SQL-ін'єкцій, параметризований Cypher захищає від Cypher-ін'єкцій і дозволяє Neo4j кешувати план виконання запиту.
- `await using` на `IDriver` і `IAsyncSession` гарантує коректне звільнення мережевих ресурсів (пул з'єднань) навіть при винятках.

### Приклад 5 — Найкоротший шлях та обробка помилок у C#

П'ятий приклад показує використання `shortestPath` (розділ 3.5) з C#, а також типову обробку помилок при роботі з драйвером — важливо для production-коду, а не лише навчального прикладу.

```csharp
using Neo4j.Driver;

public class GraphRecommendationService : IAsyncDisposable
{
    private readonly IDriver _driver;

    public GraphRecommendationService(string uri, string user, string password)
    {
        _driver = GraphDatabase.Driver(uri, AuthTokens.Basic(user, password));
    }

    // Знаходимо, наскільки "близько" пов'язані два клієнти в мережі рекомендацій
    // (наприклад, для соціального фіда "друзі ваших друзів купили це")
    public async Task<int?> GetConnectionDistanceAsync(long fromCustomerId, long toCustomerId)
    {
        await using var session = _driver.AsyncSession();

        try
        {
            return await session.ExecuteReadAsync(async tx =>
            {
                var cursor = await tx.RunAsync(
                    """
                    MATCH path = shortestPath(
                        (a:Customer {id: $fromId})-[:KNOWS*..6]-(b:Customer {id: $toId})
                    )
                    RETURN LENGTH(path) AS distance
                    """,
                    new { fromId = fromCustomerId, toId = toCustomerId });

                var record = await cursor.SingleAsync();
                return record["distance"].As<int>();
            });
        }
        catch (Neo4jException ex)
        {
            // ClientError -> проблема в запиті/даних, TransientError -> варто повторити,
            // Neo4j.Driver сам повторює транзакції для типових transient-збоїв усередині
            // ExecuteReadAsync/ExecuteWriteAsync, тому тут ми переважно ловимо логічні помилки
            Console.Error.WriteLine($"Помилка виконання Cypher-запиту: {ex.Message}");
            return null; // шлях не знайдено або сталася помилка — деградуємо, не падаємо
        }
    }

    public async ValueTask DisposeAsync() => await _driver.DisposeAsync();
}

// Використання:
await using var service = new GraphRecommendationService(
    "bolt://localhost:7687", "neo4j", "your_password");

var distance = await service.GetConnectionDistanceAsync(fromCustomerId: 1, toCustomerId: 42);

Console.WriteLine(distance is null
    ? "Клієнти не пов'язані в межах 6 кроків (або сталася помилка)."
    : $"Клієнти пов'язані через {distance} крок(и/ів) у мережі.");
```

Зверніть увагу на паттерн: **графовий запит завжди має fallback-поведінку** (`return null` замість необробленого винятку) — це узгоджується з ідеєю graceful degradation із розділу 7: якщо графова БД тимчасово недоступна чи запит не знаходить шляху, основний функціонал застосунку (наприклад, показ товару чи оформлення замовлення) не повинен падати через це.

## 7. Реальний сценарій: коли додати графову БД до великого інтернет-магазину поруч з іншими БД

Головна теза цього розділу, яку варто чітко зафіксувати: **графова база даних майже ніколи не є основним сховищем правди (system of record) для e-commerce платформи**. Замовлення, товари, клієнти, платежі — усе це продовжує жити в реляційній БД і/або документних сховищах, які вже розглядалися раніше в цій серії документів. Графова БД додається як **додаткове, спеціалізоване сховище**, що живиться тими самими даними через окремий потік подій чи ETL-процес — це конкретна ілюстрація **поліглотної персистентності (polyglot persistence)**, про яку йшлося в оглядовому документі NoSQL цієї серії: різні задачі — різні бази даних, а не "одна база на всі випадки життя".

### 7.1 Типова архітектура

```
                     ┌──────────────────────┐
                     │  Реляційна БД (SQL)   │  ← Джерело правди:
                     │  Orders, Customers,   │    замовлення, каталог,
                     │  Products, Payments   │    транзакційна цілісність
                     └──────────┬────────────┘
                                │
                     подія / CDC / ETL
                     (напр. Kafka, Debezium,
                      або нічний batch-job)
                                │
                                ▼
        ┌───────────────────────────────────────────┐
        │              Graph DB (Neo4j)               │
        │  Customer ──PURCHASED──▶ Product             │
        │  Product ──SIMILAR_TO──▶ Product              │
        │  Account ──USED_CARD──▶ PaymentFingerprint     │
        └───────────────────────────────────────────┘
                    │                        │
                    ▼                        ▼
       "Разом із цим також купують"    Антифрод-модуль
       (рекомендаційний віджет            (перевірка нових
        на сторінці товару)                акаунтів/транзакцій)
```

### 7.2 Чому саме так, а не "замінити реляційну БД графовою"

- **Транзакційна цілісність замовлень** (оплата, списання зі складу, нарахування бонусів) вимагає ACID-гарантій і добре відпрацьованих реляційних патернів (детально розглянутих у `Реляційні/1-relational-model-and-normalization.md`) — графові БД теж можуть підтримувати транзакції, але це не їхня сильна сторона й не причина, з якої їх обирають.
- **90%+ запитів адмінки та каталогу** — це прості точкові вибірки й фільтрація ("покажи товар за SKU", "покажи замовлення клієнта за останній місяць") — саме те, у чому реляційна БД з правильними індексами не поступається, а часто й перевершує графову БД за зручністю (SQL-агрегації, звітність, `GROUP BY` тощо).
- **Тільки конкретні "фічі" вигідно виносити в граф**: рекомендаційний віджет "з цим товаром також купують" і антифрод-скоринг — обидва вимагають саме багатокрокових обходів зв'язків на великому масштабі, де реляційні multi-JOIN запити (розділ 2) починають деградувати.

### 7.3 Практичний план впровадження

1. Основна система (checkout, каталог, платежі) продовжує писати в реляційну/документну БД як і раніше — **без жодних змін** до критичного шляху замовлення.
2. Подієвий потік (наприклад, подія `OrderCompleted` у Kafka чи через Change Data Capture) асинхронно проєктує факти покупок у графову БД у вигляді вузлів `Customer`/`Product` та зв'язків `PURCHASED`.
3. Рекомендаційний сервіс (окремий мікросервіс) читає **виключно** з графової БД, будуючи `MATCH`-запити на кшталт прикладу 1 із розділу 6.
4. Якщо графова БД тимчасово недоступна — рекомендаційний віджет деградує (graceful degradation) до простого fallback (наприклад, "популярні товари цієї категорії" з реляційної БД), а не валить весь checkout — ключова перевага того, що граф є **додатковим**, а не єдиним сховищем.

**Ключовий висновок:** рішення "чи потрібна нам графова БД" звучить не як "чи великий у нас магазин", а конкретніше — "чи є в нас функція, що вимагає багатокрокового обходу зв'язків на великому масштабі (рекомендації, антифрод, аналіз впливу в мережі), і чи виправдовує цінність цієї функції операційну вартість підтримки ще однієї бази даних у продакшні".

## 8. Поширені помилки

### Помилка 1 — Графова БД "про запас" для даних без реальних багатокрокових зв'язків

❌ **Погано:** команда вирішує зберігати простий каталог товарів (`Product: name, price, sku, description`) у Neo4j "бо це модно і гнучко", хоча немає жодних цікавих багатокрокових запитів — усе, що потрібно, це `SELECT * FROM Products WHERE Category = X`.

```cypher
// Навіщо?! Тут немає жодного цінного graph traversal
MATCH (p:Product {category: "Electronics"}) RETURN p;
```

✅ **Добре:** простий каталог без складних мережевих зв'язків лишається у реляційній чи документній БД — там для нього є готові індекси, звітність, транзакції і величезна екосистема інструментів. Графова БД додається **окремо** й **тільки** під конкретну функцію з реальними багатокроковими обходами (рекомендації, антифрод) — див. розділ 7.

**Чому це помилка:** графова БД додає операційну складність (ще один кластер, ще один драйвер, ще одна модель узгодженості даних, ще один член команди, який має розуміти Cypher) без жодної реальної вигоди, якщо у вас немає задач, для яких властива саме "павутинна" природа даних і глибокі обходи.

### Помилка 2 — Забути проіндексувати стартові властивості обходу

❌ **Погано:**

```cypher
// Немає індексу на Person.email — цей запит виконує ПОВНЕ СКАНУВАННЯ
// всіх вузлів :Person, перш ніж почати обхід!
MATCH (p:Person {email: "olena@example.com"})-[:KNOWS*1..3]->(x)
RETURN x;
```

На базі з мільйонами вузлів `Person` цей запит буде повільним не через сам graph traversal (який справді швидкий завдяки index-free adjacency), а через **лінійний пошук самого стартового вузла**.

✅ **Добре:**

```cypher
CREATE INDEX person_email_index IF NOT EXISTS
FOR (p:Person) ON (p.email);

MATCH (p:Person {email: "olena@example.com"})-[:KNOWS*1..3]->(x)
RETURN x;
```

**Чому це помилка:** це та сама плутанина, яку явно розібрано в розділі 5 — index-free adjacency прискорює обхід зв'язків **від уже знайденого вузла**, але аж ніяк не сам пошук вузла за довільною властивістю. Забутий індекс на властивості, яку ви використовуєте як "вхідну точку" запиту, зводить нанівець усю перевагу графової моделі на цьому конкретному запиті.

### Помилка 3 — Моделювання зв'язку як рядкової властивості замість вузла+зв'язку

❌ **Погано:**

```cypher
CREATE (p:Product {name: "Ноутбук", category: "Electronics"})
```

Категорія тут — просто рядок у властивості. Здається зручно й швидко, але це **втрачає всю графову природу цих даних**: неможливо ефективно знайти "усі товари в тій самій категорії, що й цей", неможливо побудувати ієрархію категорій ("Electronics" → підкатегорія "Laptops"), неможливо приєднати до категорії власні властивості (опис, банер, SEO-метадані) без дублювання рядка в кожному товарі.

✅ **Добре:**

```cypher
CREATE (p:Product {name: "Ноутбук"})-[:IN_CATEGORY]->(c:Category {name: "Electronics"})
```

Тепер можна:

```cypher
// Усі товари тієї ж категорії, що й цей товар (природний graph traversal)
MATCH (:Product {sku: "LAPTOP-15"})-[:IN_CATEGORY]->(cat:Category)<-[:IN_CATEGORY]-(other:Product)
RETURN other.name;

// Ієрархія категорій — теж просто зв'язок
CREATE (:Category {name: "Laptops"})-[:SUBCATEGORY_OF]->(:Category {name: "Electronics"})
```

**Чому це помилка:** правило-орієнтир — якщо значення описує **власну сутність, яку хочеться в майбутньому запитувати, розширювати властивостями чи зв'язувати з іншими сутностями** (категорія, бренд, тег, локація) — це кандидат на окремий вузол зі зв'язком. Якщо значення — це просто "плоский" описовий атрибут без власної незалежної ідентичності (наприклад, `weight: 2.5`, `color: "чорний"` як разова характеристика) — властивість цілком доречна. Перетворення кожної властивості на вузол теж є антипатерном (надмірна нормалізація графа, що ускладнює прості запити без реальної вигоди) — як і в реляційному світі, тут є компроміс, а не універсальне правило "завжди роби вузлом".

### Помилка 4 — Необмежений `*` замість розумної верхньої межі глибини обходу

❌ **Погано:**

```cypher
// Необмежена глибина обходу на потенційно щільному графі!
MATCH (a:Person {name: "Олена"})-[:KNOWS*]->(b:Person)
RETURN b.name;
```

Index-free adjacency робить **кожен окремий крок** обходу дешевим, але це не означає, що **необмежений** обхід (`*` без верхньої межі) безпечний на щільному графі. Якщо у графі є цикли (Олена знає Максима, Максим знає Ірину, Ірина знає Олену — цілком реальна ситуація в соцмережі), кількість можливих шляхів зростає комбінаторно з кожним додатковим кроком, і запит без обмеження глибини може почати обходити практично весь зв'язний компонент графа, споживаючи величезну кількість пам'яті та часу CPU ще до того, як спрацює будь-який `LIMIT` у кінці запиту.

✅ **Добре:**

```cypher
// Явна, обґрунтована бізнесом верхня межа глибини
MATCH (a:Person {name: "Олена"})-[:KNOWS*1..4]->(b:Person)
RETURN DISTINCT b.name
LIMIT 50;
```

**Чому це помилка:** "index-free adjacency = кожен крок дешевий" — правда лише локально; вона нічого не говорить про те, скільки ВСЬОГО шляхів існує при необмеженій глибині на графі з циклами. Завжди явно обмежуйте верхню межу `*min..max` числом, обґрунтованим бізнес-задачею (наприклад, "не більше 4 рукостискань" для рекомендацій, "не більше 6 переходів" для permission-графів), і за потреби додавайте `LIMIT` до фінального `RETURN`.

## 9. Питання для співбесіди за рівнями

### Middle

**1. Що таке вузол (Node) і зв'язок (Relationship) у графовій базі даних?**

Вузол — сутність (аналог рядка/об'єкта), що має мітки (labels) і властивості (properties). Зв'язок — напрямлене, типізоване з'єднання між двома вузлами, яке також може мати власні властивості. Ключова відмінність від реляційної моделі — зв'язок є повноцінним об'єктом першого класу, фізично збереженим із прямими вказівниками на обидва вузли, а не побічним результатом зіставлення зовнішнього ключа під час `JOIN`.

**2. Чому реляційні JOIN-и погано масштабуються для глибоких (multi-hop) зв'язків?**

Кожен `JOIN` у реляційному запиті будує проміжний набір результатів, розмір якого залежить від розміру задіяних таблиць; при кількох послідовних `JOIN`-ах (наприклад, "друзі друзів друзів") проміжні набори можуть комбінаторно розростатися, і вартість кожного кроку зростає разом із загальним розміром датасету. Графова БД, натомість, обходить зв'язки через прямі вказівники від уже знайденого вузла — вартість переходу залежить від ступеня конкретного вузла, а не від розміру всієї бази.

**3. Наведи приклад класичного застосування графової БД.**

Рекомендаційні системи ("клієнти, які купили X, також купили Y"), рекомендація друзів у соцмережах ("друзі друзів"), виявлення шахрайства (пошук кластерів акаунтів зі спільними прихованими атрибутами), керування дозволами (граф ролей/груп/прав), моделювання мережевої топології.

**4. Що таке Cypher?**

Декларативна мова запитів Neo4j, синтаксис якої нагадує "ASCII-малюнок" самого графового шаблону, що шукається: `(вузол1)-[:ТИП_ЗВ'ЯЗКУ]->(вузол2)`. Основні ключові слова — `MATCH` (описати патерн), `WHERE` (фільтр), `RETURN` (що повернути).

**5. Чим властивість (property) вузла відрізняється від окремого пов'язаного вузла?**

Властивість — це "плоский" атрибут без власної ідентичності (число, рядок, дата). Якщо значення варто в майбутньому запитувати окремо, зв'язувати з іншими сутностями чи розширювати власними властивостями (категорія, бренд, тег) — це кандидат на окремий вузол зі зв'язком, а не на властивість.

**6. Що таке мітка (Label) у Neo4j?**

Мітка — це грубий аналог "таблиці" чи "класу" для вузла: вона класифікує вузол за типом сутності (`:Person`, `:Product`) і дозволяє індексувати та фільтрувати вузли за типом. Один вузол може мати кілька міток одночасно.

**7. Як виглядає запит "усі прямі друзі людини на ім'я Олена" на Cypher?**

```cypher
MATCH (:Person {name: "Олена"})-[:KNOWS]->(friend:Person)
RETURN friend.name;
```

### Senior

**1. Поясни, що таке index-free adjacency і чому це дає перевагу в продуктивності.**

Index-free adjacency — властивість архітектури зберігання даних нативної графової БД, за якою кожен вузол фізично зберігає прямі вказівники на свої зв'язки (і кожен зв'язок — прямі вказівники на два вузли, які він з'єднує), формуючи зв'язаний список суміжних ребер прямо на диску. Це означає, що коли обхід уже знаходиться на конкретному вузлі, перехід до сусіднього вузла через певний зв'язок є прямим розіменуванням вказівника — операцією, вартість якої залежить від ступеня (кількості зв'язків) саме ЦЬОГО вузла, а не від загальної кількості вузлів у базі. Це фундаментально відрізняється від реляційної моделі, де кожен крок навігації (кожен `JOIN`) — це індексний пошук, вартість якого (нехай логарифмічно) все ж залежить від розміру задіяних таблиць. Важливо додати уточнення (типова "пастка" запитання): index-free adjacency стосується виключно обходу від уже знайденого вузла — початковий пошук вузла за довільною властивістю все одно потребує звичайного індексу (розділ 5).

**2. Спроєктуй систему виявлення шахрайства на основі графової БД.**

Модель даних: вузли `Account`, `PaymentFingerprint` (хешований відбиток картки, а не сам номер), `Device` (fingerprint пристрою), `IPAddress`, `Address`; зв'язки `USED_CARD`, `USED_DEVICE`, `LOGGED_IN_FROM`, `SHIPPED_TO` — усі з властивістю часу для аналізу свіжості. Пайплайн: подієвий потік із транзакційної системи (Kafka/CDC) асинхронно оновлює граф при кожній новій транзакції/логіні — граф ніколи не є системою запису для самих транзакцій, лише додатковим шаром аналізу зв'язків. Основний запит-патерн: групування спільних вузлів-атрибутів (`WITH card, COLLECT(DISTINCT acc) AS accounts WHERE SIZE(accounts) > N`) для виявлення кластерів акаунтів, що ділять один платіжний засіб/пристрій/IP понад пороговою кількістю. Для складніших кілець — багатокроковий обхід через кілька типів спільних атрибутів одночасно (`[:USED_CARD|USED_DEVICE*1..2]`) з додатковими бізнес-фільтрами (різні країни реєстрації, короткий проміжок часу між реєстраціями — типова ознака "ферми" акаунтів). Результат — скоринг ризику чи прапорець "на ручний розгляд", а не автоматичне блокування (щоб уникнути хибнопозитивних для родин/офісів зі спільним Wi-Fi). Важливо: графовий аналіз тут — доповнення до, а не заміна, класичних правил і ML-моделей скорингу.

**3. Коли б ти додав графову БД поруч із реляційною системою, а не замінював би нею основну БД?**

Коли з'являється конкретна функція, що вимагає багатокрокового (2+ переходи) обходу зв'язків на великому й зростаючому масштабі — і при цьому та сама функція, реалізована через реляційні multi-JOIN запити, вже демонструє (або передбачувано продемонструє) деградацію продуктивності зі зростанням таблиць (розділ 2). Типові кандидати — рекомендаційний рушій, антифрод, аналіз впливу в мережі/графі дозволів. Основна система запису (замовлення, платежі, каталог) залишається в реляційній/документній БД, а графова БД живиться від неї асинхронно через подієвий потік чи ETL і обслуговує виключно ці спеціалізовані читання — класичний приклад поліглотної персистентності. Якщо такої функції немає — додавання графової БД суто "про запас" є невиправданою операційною складністю (розділ 8).

**4. Порівняй запит "друзі друзів" на SQL (через self-JOIN) і на Cypher за складністю та продуктивністю на масштабі.**

За складністю запису: SQL-версія для N кроків вимагає N явних self-JOIN-ів (плюс `LEFT JOIN`+`COALESCE`, якщо потрібен діапазон довжин шляху, а не фіксована кількість), тоді як Cypher виражає це одним патерном `[:KNOWS*1..N]`, де зміна діапазону — це зміна двох чисел, а не структури запиту. За продуктивністю: вартість SQL-версії залежить від розміру задіяних таблиць на кожному кроці `JOIN` — оптимізатору доводиться будувати/скановувати проміжні набори результатів, які можуть комбінаторно розростатися при кожному додатковому кроці, і ця вартість зростає разом із загальним розміром датасету. Вартість Cypher-версії залежить головно від ступеня (кількості зв'язків) конкретних вузлів на шляху обходу — завдяки index-free adjacency, перехід від вузла до вузла не потребує повторного індексного пошуку на кожному кроці, тож 3-кроковий обхід на графі з мільярдом вузлів залишається практично так само швидким, як на графі з мільйоном, якщо конкретні залучені вузли мають подібний ступінь.

**5. Опиши компроміс між зберіганням даних як властивості вузла проти окремого вузла+зв'язку.**

Властивість вузла — дешевше й простіше зберігати та читати разом з основним вузлом (не потрібен додатковий "стрибок" по зв'язку), але дані стають "непрозорими" для графового двигуна: неможливо ефективно знайти всі вузли з однаковим значенням властивості без сканування чи окремого індексу, неможливо приєднати до значення власні метадані, неможливо побудувати ієрархію значень (підкатегорії). Окремий вузол+зв'язок робить значення повноцінно "запитуваним" через graph traversal (усі товари тієї ж категорії — природний обхід), дозволяє розширювати сутність власними властивостями та зв'язками, але додає рівень непрямої адресації (indirection) і трохи більше вузлів/зв'язків для підтримки. Практичний орієнтир: якщо значення описує сутність із власною ідентичністю, яку хочеться запитувати, розширювати чи зв'язувати з іншими речами — виносьте в окремий вузол; якщо це разовий "плоский" атрибут без такої потреби — властивість цілком доречна. Як і в реляційній нормалізації, тут немає універсально правильної відповіді — тільки свідомий компроміс під конкретні патерни запитів.

**6. Що таке нативна графова БД (native graph database) і чим вона відрізняється від "графового шару" поверх іншого сховища?**

Нативна графова БД (як Neo4j) реалізує index-free adjacency на рівні фізичного зберігання: вузли й зв'язки — це першокласні структури зі взаємними вказівниками прямо на диску/в пам'яті. "Графовий шар" поверх реляційної чи документної БД (наприклад, емуляція графа таблицями `nodes`/`edges` у Postgres) дає графову МОДЕЛЬ даних і, можливо, графову мову запитів, але під капотом усе одно виконує індексні пошуки/JOIN-и для кожного переходу — тобто не отримує головної продуктивнісної переваги нативного підходу на глибоких multi-hop обходах, хоча може бути цілком прийнятним рішенням для неглибоких (1-2 переходи) запитів чи коли команда не хоче додавати ще одну технологію в стек.

**7. Наведи ситуацію, коли графова БД буде ГІРШИМ вибором, ніж реляційна, навіть для даних зі зв'язками.**

Аналітичні агрегації по всій таблиці (наприклад, "сума виручки за категоріями за квартал", складна звітність із `GROUP BY`/`HAVING`/віконними функціями) — реляційні БД (та колонкові аналітичні сховища) суттєво краще оптимізовані для сканування й агрегації великих обсягів "плоских" даних, ніж графові БД, чия сильна сторона — саме прицільний обхід зв'язків від конкретних вузлів, а не масове сканування всього датасету. Так само транзакційні операції з жорсткими вимогами ACID і складною бізнес-логікою (списання коштів, резервування складу) залишаються природнішими й перевіренішими в реляційній моделі.

## 10. Підсумок

### Термінологія

| Термін | Значення |
|---|---|
| **Вузол (Node)** | Сутність графа (аналог рядка/об'єкта); має мітки та властивості |
| **Зв'язок (Relationship)** | Напрямлене, типізоване з'єднання між двома вузлами; першокласний об'єкт, може мати властивості |
| **Мітка (Label)** | Класифікація вузла за типом (аналог "таблиці"/"класу") |
| **Властивість (Property)** | Пара ключ-значення на вузлі або зв'язку |
| **Index-free adjacency** | Вузли фізично зберігають прямі вказівники на свої зв'язки — обхід від вузла до вузла не потребує індексного пошуку на кожному кроці |
| **Traversal (обхід)** | Навігація по графу від вузла до вузла через зв'язки |
| **Cypher** | Декларативна мова запитів Neo4j з "ASCII-малюнковим" синтаксисом |

### Класичні застосування

| Застосування | Патерн запиту |
|---|---|
| Соціальні мережі | "друзі друзів, які ще не мої друзі" — 2-hop traversal + `NOT EXISTS` |
| Рекомендаційні системи | "клієнти, що купили X, також купили Y" — спільний сусід через `PURCHASED` |
| Виявлення шахрайства | Кластери акаунтів зі спільним прихованим атрибутом (картка/пристрій/IP) |
| Керування дозволами | Обхід ієрархії ролей/груп змінної глибини до вузла `Permission` |
| Мережева топологія | Найкоротший шлях/аналіз впливу у графі пристроїв і з'єднань |

### Cypher — швидкий довідник синтаксису

```cypher
// Пошук вузла за міткою й властивістю
MATCH (p:Person {name: "Олена"}) RETURN p;

// Прямий зв'язок
MATCH (a)-[:KNOWS]->(b) RETURN b;

// Багатокроковий (variable-length) шлях
MATCH (a)-[:KNOWS*1..3]->(b) RETURN b;

// Фільтр, сортування, ліміт
MATCH (a)-[:KNOWS]->(b)
WHERE b.age > 25
RETURN b.name ORDER BY b.age DESC LIMIT 10;

// Створення вузлів і зв'язків
CREATE (a:Person {name: "X"})-[:KNOWS {since: 2024}]->(b:Person {name: "Y"});

// Індекс на властивості (потрібен для швидкого старту traversal!)
CREATE INDEX person_email_index IF NOT EXISTS FOR (p:Person) ON (p.email);
```

**Головне, що варто винести з цього документа:** графова БД не замінює реляційну чи документну модель — вона доповнює їх там, де природа задачі є справді "павутинною" (багатокрокові зв'язки на великому масштабі), і де ключова перевага — index-free adjacency — реально проявляється: обхід зв'язків від уже знайденого вузла, а не початковий пошук цього вузла (для якого, як і завжди, потрібен індекс).
